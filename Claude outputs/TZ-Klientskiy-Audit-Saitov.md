## 0. Суть и, прежде всего, красная линия

Продукт — отдельная ТМА в экосистеме viral4creators: клиент вводит **ссылку
на свой сайт** и получает автоматический аудит и (после подтверждения
права) тестирование безопасности, чтобы не держать штатного QA/безопасника.
Это и есть «owner can buy automated testing without QA», но owner здесь —
**владелец проверяемого сайта**, наш платящий клиент, а не мы.

Ровно потому, что цель — чужой сайт, всё ТЗ стоит на одной границе:

> **Активное тестирование безопасности чужого сайта запускается только
> после доказанного права на этот сайт.** «Клиент дал ссылку» — не
> доказательство. Без подтверждения владения (или письменного разрешения
> владельца) активный/security-скан не стартует — ни в UI, ни в API, ни в
> обход. Несанкционированное сканирование чужих систем — правонарушение
> (в Украине — ст. 361 КК; в ЕС/США — аналоги: Computer Misuse Act, CFAA),
> и продукт спроектирован так, чтобы его нельзя было для этого применить.

Отсюда — **две модели входа**, жёстко разделённые (обе выбраны владельцем):

- **Модель A. Публичный неинтрузивный аудит — по любому URL.** Анализ
  только того, что сайт **сам отдаёт обычному браузеру**: скорость/Core
  Web Vitals, SEO, доступность, тех-стек, битые ссылки, публичные
  security-заголовки, гигиена TLS/сертификата, mixed-content, robots/
  sitemap, мета/OG. Никаких проб, атак, фаззинга, перебора. Это эквивалент
  захода на страницу и потому легально без разрешения владельца — так
  работают Lighthouse/PageSpeed, SSL Labs, Mozilla Observatory,
  securityheaders.com. Это **воронка** и лид-магнит.
- **Модель B. Авторизованное тестирование безопасности — только по
  подтверждённому сайту.** Полноценный DAST (OWASP ZAP, Nuclei) с
  проверкой владения и юридическими воротами. Это **платная услуга**.

Модель A ведёт в модель B: клиент видит бесплатный публичный отчёт →
подтверждает владение → покупает глубокий скан и мониторинг.

## 1. Чего этот продукт НЕ делает (чтобы не спроектировать оружие)

- Не сканирует произвольный чужой URL «на уязвимости» без подтверждения
  права. Активные пробы по неподтверждённой цели невозможны by design.
- Не разрабатывает эксплойты, не подбирает пароли к чужим системам, не
  обходит защиту третьих лиц, не делает латеральное движение. Модель B —
  это оркестрация **известных** сканеров и сопоставление с OWASP, а не
  автономный атакующий агент (XBOW/NodeZero/Pentera — вне продукта, см. §3).
- Не позволяет использовать публичный аудит как инструмент разведки/DoS в
  масштабе: строгие лимиты, кэш, SSRF-защита, анти-абьюз (§6).
- Не заменяет ручной пентест человеком для критичных систем — публичный
  аудит и авто-DAST это дополняют, а не заменяют (честно сообщаем клиенту).

## 2. Модель монетизации

«Купить автотест» реализуется как воронка «бесплатно → платно»:

| Тариф | Что входит | Ворота |
| --- | --- | --- |
| Публичный аудит | Модель A: скорость/SEO/доступность/тех-стек/публичные заголовки/TLS/битые ссылки + **пассивный аудит форм и флоу** (без сабмитов) + **черновик tutorial** (экраны/шаги). Один прогон, водяной знак, ограничение частоты | нет (любой URL) |
| Flow-QA (владельца) | Интерактивное прокликивание форм с проверкой «всё прошло» + полная генерация tutorial с реальными действиями. Может быть бесплатным для подтверждённого владельца — воронка сохраняется | verified ownership (или staging/тест-данные владельца) |
| Basic Security | + ZAP baseline (passive) + Nuclei (безопасные шаблоны); полный отчёт без watermark | verified ownership |
| Pro Security | + активный DAST (неразрушающий, staging-приоритет), скан зоны за логином по кредам клиента, скан API по OpenAPI | ownership + доп. подтверждение + ToS-гарантия |
| Monitoring | повторяющийся скан по расписанию, тренды, алерты о новых находках/регрессе | подписка |

- Списание/потолки — через существующие `credit-ledger`, `spend-limits`,
  `plan`, `billing` (Stars + WayForPay, как этап 62).
- Публичный аудит бесплатен и служит лид-магнитом; ценность подписки —
  **мониторинг** (повторяемость), а не разовый скан.

## 3. Глубокий обзор ниши (это другой рынок, чем в v1)

Рынок делится на два сегмента, ровно под наши две модели.

### 3.1. Публичный неинтрузивный аудит (лид-ген, любой URL)

- **Производительность:** Google **Lighthouse** / PageSpeed Insights /
  web.dev, **WebPageTest**, **GTmetrix** — Core Web Vitals, метрики
  загрузки.
- **SEO/структура:** **Sitebulb**, **Screaming Frog** — краул, мета,
  каноникалы, sitemap; для одиночной страницы — Lighthouse SEO-раздел.
- **Доступность:** **axe-core** (Deque), **Pa11y**, **WAVE** — WCAG.
- **Публичная гигиена безопасности (без проб!):** **Mozilla Observatory**
  (security-заголовки), **securityheaders.com**, **Qualys SSL Labs** /
  **testssl.sh** (TLS/сертификат) — всё это читает то, что сервер сам
  отдаёт в заголовках/handshake, не атакуя.
- **Тех-стек:** **Wappalyzer**-подобное определение по публичным маркерам.

**Что берём:** ядро публичного аудита — **Lighthouse (headless Chrome) +
axe-core + testssl.sh + чтение security-заголовков + лёгкий краул битых
ссылок/sitemap + определение стека**. Всё OSS, всё сам-хостится в воркере.
Ценность нашего продукта не в самих движках (они общедоступны), а в
**упаковке**: единый русскоязычный отчёт в Telegram, воронка в платный
скан, объяснение «почему это важно и как чинить».

**Что НЕ берём:** внешние платные API (PageSpeed API лимитирован; GTmetrix
платный) — гоняем Lighthouse сами.

### 3.2. Авторизованное тестирование безопасности (платный DAST-сервис)

Рынок 2026 (по обзорам Astra, Aikido, Escape, AppSecSanta): **Detectify**,
**Intruder.io**, **Probely**, **Pentest-Tools.com**, **StackHawk** (DAST в
CI, API-центричный), **Acunetix**, **Invicti/Netsparker**, **Qualys WAS**,
**Rapid7 InsightAppSec**, облако **ProjectDiscovery** (Nuclei). Общее у
всех легальных: **обязательная верификация владения доменом перед активным
сканом** — это индустриальный стандарт, а не наша перестраховка.

**Что берём:** движки — **OWASP ZAP** (глубина, passive+active) +
**Nuclei** (широта шаблонов CVE/мисконфигов). Это доказанный self-hosted
минимум (сравнения 2026: AppSecSanta, codenote, Pi Stack). Наш слой —
**ворота владения + юр-контур + оркестрация + отчёт + мониторинг + доставка
в Telegram**. По сути мы собираем «Detectify для Telegram-аудитории на
русском», не переизобретая сканеры.

**Что НЕ берём:** коммерческие движки (Acunetix/Invicti/Qualys) — цена и
lock-in; облачные SaaS как бэкенд — им пришлось бы отдавать клиентские цели
и результаты. **Autonomous-pentest** (XBOW, Horizon3 NodeZero, Pentera,
RidgeBot) — вне продукта: реальная эксплуатация и латеральное движение по
чужому сайту недопустимы даже с разрешения без отдельного тяжёлого
юр-контура; нам достаточно DAST+пассива с верификацией находок.

### 3.3. Где наш угол

Ни один из крупных DAST-сервисов не живёт в Telegram и не говорит с
СНГ/украинской аудиторией на русском в формате «вставь ссылку — получи
понятный отчёт». Публичный аудит как бесплатная воронка + платный
авторизованный скан + мониторинг в мессенджере — это ниша, где мы не
конкурируем с Detectify по глубине, а берём аудиторию и удобство.

## 4. Методологическая рамка

- **Разделение по интрузивности — главная ось.** Каждая проверка помечена:
  `passive-public` (модель A, любой URL), `passive-verified`,
  `active-verified` (модель B). Класс проверки определяет ворота, а не
  «на глаз».
- **OWASP как каркас безопасности:** **Top-10** (что искать), **WSTG**
  (как и к чему привязывать находку), **ASVS** (уровни зрелости L1/L2),
  **CVSS** (severity). Публичная гигиена — по **Mozilla Observatory** и
  **OWASP Secure Headers**.
- **Веб-качество:** **Core Web Vitals** (Google) для скорости, **WCAG 2.2**
  для доступности, базовые SEO-эвристики.
- **Нормализация** выхода всех движков в единый формат (ориентир —
  **SARIF** для security, свой формат для качества), дедуп, тренды.
- **Честный пропуск** (как в `doc/CI.md`): недоступный инструмент/цель =
  явный пропуск с причиной, не «зелёно».
- **Объяснимость:** каждая находка отвечает «почему важно» и «как чинить» —
  иначе клиент без QA её не применит (это и есть смысл продукта).

## 5. Архитектура

### 5.1. Схема

```
[ТМА «Аудит сайта»] ─initData→ [NestJS: site-audit API]
[Admin panel]       ─admin-auth→        │
                                         ├─ target + (для B) ownership verify
                                         ├─ authorization record + ToS gate
                                         ├─ create AuditRun (queued)
                                         ▼
                               [Postgres: Target/Ownership/Run/Finding…]
                                         ▼
                    [Runner-воркер на Hetzner/Dokploy, Docker]
             (lighthouse, axe, testssl, header-check, crawler | zap, nuclei)
                                         │  через SSRF-guard + rate-limit
                                         ▼
                       [Blob] + normalize → Finding → отчёт
                                         ▼
                         [notify: клиенту + служебный канал]
```

### 5.2. Раннер — не на Vercel

Как и в v1: Lighthouse (headless Chrome), ZAP, Nuclei не живут в serverless.
API — в основном NestJS-бэкенде; раннер — отдельный долгоживущий воркер в
Swarm с жёсткими resource-limits. **Публичный и security-раннеры лучше
физически разнести**: публичный (модель A) держит поток мелких быстрых
задач по любым URL; security (модель B) — тяжёлые редкие прогоны по
подтверждённым целям. Разные лимиты, разные очереди, разный анти-абьюз.

### 5.3. Multi-tenant с первого этапа

Это клиентский продукт с множеством владельцев — изоляция данных между
клиентами (`ownerRef` на всех сущностях) закладывается **сразу**, а не
как фаза B (в v1 это было открытым вопросом — здесь закрыт: да,
multi-tenant с Э0). Клиент видит только свои цели, прогоны, отчёты.

### 5.4. Модули NestJS

- `site-audit` — публичный аудит (модель A).
- `site-target` — цели + **верификация владения** (для B).
- `site-security` — авторизованный скан (модель B), юр-ворота.
- `site-flow-qa` — интерактивное прокликивание форм + генерация tutorial
  (§7.1-бис); реюз `client-site-tutorial`/`ui-snapshot`/`tutorial-runner`.
- `site-runner` — контракт «задание → воркер → результат» (2 очереди).
- `site-finding` — нормализация в единую находку.
- `site-billing-glue` — тарифы/списание/потолки.
Переиспуются: `notify`, `telegram-auth`, `admin-auth`, `storage`, `plan`,
`credit-ledger`, `ai-usage`, `cron`, `legal`, `export`, `health`.

## 6. Безопасность и легальность самого сервиса (критический раздел)

Сервис, который по ссылке ходит на чужие сайты, опасен двумя способами:
им можно **атаковать чужих** и через него можно **достать нашу
инфраструктуру** (SSRF). Оба закрываются здесь.

### 6.1. Ворота владения (для любой модели B)

Активный/security-скан не стартует, пока владение целью не подтверждено:
- **DNS-запись** (TXT с токеном) — основной;
- **файл-маркер** `/.well-known/<токен>`;
- **мета-тег** на главной.
Перепроверка перед каждым прогоном (домен мог сменить владельца). Токен
привязан к аккаунту клиента.

### 6.2. Юридические ворота (ToS + запись авторизации)

- При регистрации и перед каждым security-прогоном клиент **подтверждает
  гарантию**: «я владею целью или уполномочен её тестировать; беру
  ответственность и освобождаю сервис от претензий». Чекбокс + ввод домена
  вручную (осознанность, как smart-delete этапа 89).
- Создаётся **неизменяемая запись авторизации** (кто, какая цель, scope,
  профиль, окно, подтверждение) — доказательство правомерности и основа
  разбора инцидентов/претензий.
- Юр-тексты (ToS, оговорка об авторизации, политика допустимого
  использования) — через `legal`/`sync-legal`, **с обязательным ревью
  юриста** (в проекте legal-документы уже помечены как требующие юриста).
  Учесть юрисдикции: клиент/цель могут быть в ЕС/США (go-to-market проекта
  — UA→EU/US), значит GDPR и местные computer-misuse законы.

### 6.3. SSRF-защита и allowlist адресов (для ОБЕИХ моделей)

Даже публичный аудит ходит на внешний адрес — это вектор SSRF внутрь нашей
инфры и вектор атаки на приватные сети:
- Резолвим домен и **проверяем итоговый IP**: запрет RFC1918/loopback/
  link-local, cloud-metadata (169.254.169.254), внутренних доменов,
  нестандартных портов; защита от DNS-rebinding (проверка после резолва,
  повторная проверка перед запросом).
- Раннер — в сети без доступа к нашим внутренним портам (3000/8088/2377 и
  так off-internet — `DEPLOYMENT.md`).

### 6.4. Анти-абьюз (чтобы сервис не стал инструментом атаки)

- **Rate-limit и лимит конкуренции на цель и глобально:** публичный аудит
  — не более N прогонов на домен в час; security — по расписанию/бюджету.
- **Уважение robots.txt** краулером публичного аудита; краул мелкий и
  вежливый (не DoS).
- **Кэш публичного отчёта** на домен на короткое окно — один и тот же URL
  не гоняется бесконечно.
- **Детект злоупотребления:** один аккаунт гоняет много несвязанных чужих
  доменов → флаг/бан (типичный признак разведки).
- **Kill-switch** и **авто-стоп по деградации** цели: если цель начала
  отвечать 5xx/медленно — стоп (не добиваем чужой сайт).
- **Бан-лист и приём жалоб/такедаунов.**

### 6.5. Неразрушающесть

- Модель A — только чтение отдаваемого; никаких проб.
- Модель B по умолчанию — passive; **active** только по подтверждённой
  цели, с доп.подтверждением, приоритет staging клиента, глобальный
  фиче-флаг; никаких заведомо разрушающих проверок и стресс-нагрузки.

### 6.6. Аудит-лог

Каждый прогон, ворота владения, запись авторизации, kill-switch, доступ к
отчёту, срабатывание анти-абьюза — в неизменяемый лог.

## 7. Функциональные блоки

### 7.1. Публичный аудит (модель A)

Вход: любой валидный http(s)-URL (после SSRF-проверки §6.3). Проверки
(`passive-public`):
- **Скорость:** Lighthouse (Core Web Vitals, вес, блокирующие ресурсы).
- **SEO:** мета/title/description, каноникал, robots/sitemap, OG/Twitter,
  заголовки h1, alt.
- **Доступность:** axe-core (WCAG-нарушения на странице).
- **Публичная безопасность (без проб):** security-заголовки (CSP, HSTS,
  X-Frame-Options и т.д. по OWASP Secure Headers), TLS/сертификат
  (testssl.sh: протоколы, срок, слабые шифры), mixed-content, cookie-флаги.
- **Тех-стек:** определение CMS/фреймворка/аналитики по публичным маркерам.
- **Битые ссылки:** мелкий вежливый краул (robots-aware).
- **Пассивный аудит форм и флоу (без сабмитов):** находим формы и
  многошаговые сценарии чтением DOM; проверяем — HTTPS у `action`,
  наличие валидации (required/pattern/type), лейблы и `aria` (доступность),
  `autocomplete`, наличие защиты (капча/токен), число шагов, очевидные
  UX-проблемы (нет обратной связи об ошибке, ловушки фокуса). **Ничего не
  отправляем** — это разведка структуры, а не тест прохождения.
- **Черновик tutorial (без действий):** снимаем экраны и шаги публичной
  навигации и складываем **черновик** для последующей генерации обучалки —
  через уже существующие механизмы проекта (`client-site-tutorial`,
  `ui-snapshot`, `tutorial-runner`, `tutorial-scenario`). Это черновик-заготовка,
  не готовый tutorial: реальное прокликивание — в §7.1-бис.
Выход: единый отчёт с оценками, «почему важно», «как чинить», и два оффера —
«подтвердите владение → интерактивная Flow-QA форм + tutorial» и
«→ глубокий скан безопасности».

### 7.1-бис. Интерактивная Flow-QA форм + полная генерация tutorial (ворота владения)

Отдельно от §7.1, потому что **отправка форм интрузивна**: сабмит создаёт
записи, шлёт письма, дёргает бэкенд чужого сайта, и «проверить, что форма
проходит успешно» без отправки нельзя. Поэтому это НЕ в бесплатном слое
«любой URL», а за воротами владения (§6.1) — но может быть бесплатным для
**подтверждённого владельца**, чтобы воронка сохранилась.

- **Прокликивание форм и сценариев** (Playwright в воркере): проход по
  ключевым флоу сайта, заполнение тестовыми данными, сабмит, **проверка
  успеха** (ожидаемый экран/редирект/сообщение, коды ответов, отсутствие
  ошибок в консоли/сети) — это функциональный QA, который проект уже умеет
  гонять Playwright'ом.
- **Данные для форм:** только тестовые/безопасные; для форм с побочными
  эффектами (оплата, реальная отправка) — режим «до сабмита» или staging/
  тест-данные, которые дал владелец; настоящую оплату/необратимое —
  никогда без явного согласия и тестовой среды.
- **Само-лечение селекторов** — как находка «селектор изменился», не молчаливо
  (риск маскировки регрессии).
- **Полная генерация tutorial** из реального прохода: реюз
  `client-site-tutorial`/`ui-snapshot`/`tutorial-runner`/`tutorial-video-admin` —
  черновик из §7.1 превращается в готовую обучалку (кадры/озвучка/шаги).
- **Анти-абьюз усилен:** интерактив уважает лимиты на цель, авто-стоп по
  деградации, kill-switch, запись авторизации на прогон (§6). Прокликивание
  чужого сайта в объёме — это нагрузка и действия, поэтому только по
  подтверждённой цели и в согласованном окне.
- **Выход:** отчёт «флоу прошёл/упал где» с трейсом + готовый/черновой
  tutorial.

### 7.2. Авторизованный security-скан (модель B)

После ворот §6.1–6.2:
- **Basic:** ZAP baseline (passive по прокрауленному сайту) + Nuclei
  (безопасные шаблоны: известные CVE, мисконфиги, exposed-панели).
- **Pro:** ZAP active (неразрушающие инъекционные пробы) по подтверждённой
  цели с приоритетом staging; скан зоны за логином по кредам, которые
  клиент **сам** предоставил для своего сайта; скан API по загруженному
  OpenAPI.
- Приоритет проверок risk-based: формы, авторизация, платежи, загрузки.
- Все находки — с CVSS и привязкой к WSTG.

### 7.3. Мониторинг (подписка)

Повтор скана по расписанию (cron), сравнение с прошлым прогоном, алерт о
**новых** находках и регрессе (истёк сертификат, пропал заголовок, новый
CVE в определённом стеке). Это главная повторяющаяся ценность.

### 7.4. Отчёты и находки

- **Единая находка:** id, ownerRef, targetId, класс (perf/seo/a11y/
  security), интрузивность, severity (CVSS для security), привязка
  (WSTG/ASVS/CWV/WCAG), «как чинить», артефакты, статус, дедуп-ключ,
  `false-positive`/`accepted-risk`.
- **Отчёт:** сводка «проверено/найдено/пропущено с причиной», тренд,
  экспорт PDF/MD (через `export`), шаринг-ссылка (для платных — без
  watermark).

### 7.5. Интеллектуальная отладка / объяснение (AI)

LLM (Gemini/Grok, уже подключены) **объясняет** находки простым языком и
предлагает исправление; помечается как рекомендация, не приговор. Строгий
потолок токенов на прогон, вызов после дедупа (один раз на группу).
LLM **не** решает, что сканировать, и **не** трогает ворота.

## 11. Нефункциональные требования

- **Изоляция/права:** раннер минимальных прав, секреты точечно, SSRF-сеть
  (§6.3).
- **Приватность:** отчёты и артефакты клиента изолированы (multi-tenant);
  креды клиента для скана за логином — шифрование, короткий TTL, никогда в
  логах; артефакты ZAP редактируются (маскирование) перед хранением; PII
  на скриншотах — как ПД (GDPR для EU-целей).
- **Ретенция:** отчёты/артефакты с TTL (env), уборка в daily cron (как
  purge этапа 89).
- **Детерминизм/честный пропуск** (§4).
- **Стоимость/производительность:** тяжёлые прогоны по расписанию; LLM с
  потолком и кэшем.
- **Законность:** §6.2; отдельная политика допустимого использования.

## 12. Открытые вопросы владельцу

- **§12.1** Целевая аудитория security-модели: только владельцы своих
  сайтов, или ты берёшь и агентства (тестируют сайты своих клиентов)? Во
  втором случае нужна цепочка авторизации (агентство подтверждает
  разрешение конечного владельца) — это отдельный юр-слой.
- **§12.2** Юрисдикция ToS и где ты готов принимать клиентов/цели (UA/EU/
  US) — от этого зависит объём юр-контура и GDPR.
- **§12.3** Очередь: Postgres `SKIP LOCKED` или Redis/BullMQ (две очереди —
  public/security).
- **§12.4** Хост раннеров: тот же Swarm с лимитами или отдельный узел (риск
  конкуренции с продом на Hetzner без панели).
- **§12.5** LLM для объяснений: Gemini или Grok, с каким потолком токенов.
- **§12.6** Глубина модели A: одна страница или мелкий краул сайта (влияет
  на нагрузку и анти-абьюз).
- **§12.7** Активный DAST (Pro) — включаем сразу или после наработки
  доверия/юр-контура.

## 13. Критерии приёмки (эскиз)

- [ ] Security-скан невозможен без verified ownership — API и UI отказывают.
- [ ] Активный скан невозможен по цели `env: prod` без доп.подтверждения и
      при выключенном глобальном флаге.
- [ ] SSRF-guard блокирует приватные IP/metadata/DNS-rebinding в ОБЕИХ
      моделях (проверка на тест-цели).
- [ ] Публичный аудит уважает robots, limit на домен/час, кэширует.
- [ ] Анти-абьюз ловит массовый скан несвязанных доменов одним аккаунтом.
- [ ] Запись авторизации и ToS-версия сохраняются неизменяемо.
- [ ] Данные клиентов изолированы (tenant не видит чужие цели/отчёты).
- [ ] Креды клиента для скана за логином не попадают в логи/артефакты.
- [ ] Недоступная цель = честный пропуск с причиной, kill-switch и
      авто-стоп по деградации цели работают.
- [ ] Мета-тест: заведомо-уязвимая тест-цель обязана дать известную находку.
- [ ] Публичный аудит форм **не отправляет** ни одной формы (проверка по
      сетевому логу прогона: нет POST/PUT к цели в модели A).
- [ ] Интерактивная Flow-QA (сабмиты) недоступна без verified ownership.
- [ ] Черновик tutorial из модели A пишется без действий; полная генерация —
      только после ворот владения.
