# Деплой на Vercel — четыре проекта из одного репозитория

Покрывает пункты 5 и 7 из `VERCEL-READINESS-AUDIT.md`. Все четыре
критичных находки аудита уже исправлены в коде (см. пометки ✅ там же) —
этот документ описывает саму настройку деплоя на стороне Vercel, которую
нельзя сделать из кода, только руками в дашборде.

**Backend-проект требует план Vercel Pro** (этап 61, ТЗ §14.5/§14.6) —
единственное отступление от Hobby во всём документе. Причина —
`backend/vercel.json`: крон-маршрут выгрузки в YouTube/TikTok
(`/api/cron/publish`) заведён на расписание `*/2 * * * *` (каждые 2
минуты), а Vercel Hobby не запускает крон-задачи чаще раза в сутки —
Vercel либо откажет в деплое такого `vercel.json`, либо молча выполнит
расписание раз в день, и одобренные заявки будут висеть в очереди почти
сутки. С этапа 65 (ТЗ §44) на том же расписании `*/2 * * * *` работает и
`/api/cron/catalog-batch-run`, с этапа 66 (TODO §III.6) — `/api/cron/ab-test-run`,
а с этапа 68 (TODO §Уровень 2 п.8) — и `/api/cron/feed-import-run`
тоже; ни для одного из них Pro не отдельное требование, все просто
попадают под уже действующее из-за `/cron/publish`. Десятый крон-слот
подряд в `vercel.json` (было семь до этапа 65, восемь после, девять
после этапа 66) — лимит числа крон-задач на плане Vercel Pro в этой
песочнице не проверялся, не блокирует работу (тот же прецедент, что у
добавления крона на этапах 57/61/62/63/65/66, см. §44/§45/§47 SPEC).
`frontend`/`admin`/`landing` в апгрейде не нуждаются — Pro нужен только
там, где живёт `vercel.json` с этим расписанием.

**Почему несколько проектов, а не один `vercel.json` с rewrites**:
`backend` (NestJS), `frontend` (Vite SPA / TMA), `admin` и `landing`
(Next.js 14) — разные типы сборки. Практичнее завести отдельные
Vercel-проекты на один и тот же git-репозиторий, у каждого свой Root
Directory, чем городить монорепо-роутинг в одном `vercel.json`. Ни то,
ни другое пока не настроено — ниже пошагово. `admin`/`landing`
появились позже основных двух — см. `doc/TELEGRAM-ADMIN.md` про
Telegram-логин, который их и породил.

## 1. Backend-проект

1. Vercel Dashboard → **Add New** → **Project** → выбрать этот
   репозиторий.
2. **Root Directory**: `backend`.
3. Framework Preset: Vercel обычно определяет как "Other" — это ок,
   реальный запуск идёт через `backend/server.js` (см. пункт 1 в
   аудите), а не через framework-пресет.
4. **Build Command**: оставить дефолтный из `backend/package.json`
   (`npm run build` → `prisma generate && nest build`).
5. **Environment Variables** — перенести из `backend/.env.example` (не
   коммитить реальные значения!):
   - `DATABASE_URL`, `DIRECT_URL` — из Supabase (см. `PRISMA-SUPABASE.md`).
   - `BLOB_READ_WRITE_TOKEN`, `BLOB_STORE_ID` — единственное хранилище
     файлов в приложении (референсное видео, картинка товара,
     сгенерированное видео — см. `VERCEL-READINESS-AUDIT.md`, ответ на
     вопрос "зачем нам S3"). Если подключить Vercel Blob Store через
     дашборд этого же проекта, эти две переменные Vercel подставит через
     OIDC автоматически, вручную указывать не нужно.
   - `GEMINI_API_KEY` (синоним `GOOGLE_GEMINI_API_KEY` — код принимает
     любое из двух имён; достаточно одного).
   - `GEMINI_MODEL` — **влияет на стоимость всех пяти вызовов Gemini**
     (разбор видео, релевантность, аудит ролика, категория по фото,
     голос→текст). По умолчанию `gemini-2.5-flash`; модель вне прайса
     (`common/ai-pricing.ts`) пишется в расход как `unpriced`, и вкладка
     «Расходы» покажет это отдельно. До этапа 53 переменная не была
     описана здесь вовсе (В-6.6) — тот, кто настраивал прод по этому
     документу, не знал, что модель вообще выбирается.
   - `GEMINI_IMAGE_MODEL` — отдельная от `GEMINI_MODEL` модель:
     статичное превью персонажа из текста (двойной клик по описанию в
     `CharacterCasting.tsx`, `common/gemini-image-model.ts`) — генерация
     картинки, а не текста, не взаимозаменяема с `GEMINI_MODEL`. По
     умолчанию `gemini-3.1-flash-image` (с 17.09.2026: прежняя
     `gemini-2.5-flash-image` отключается 02.10.2026 — см. фазу −1
     `doc/AI-SKETCH-SPEC.md`). Лимиты превью на пользователя —
     `AI_SKETCH_DAY_LITE/STANDARD/PREMIUM` (по умолчанию 3/15/50 в сутки)
     и `AI_SKETCH_MONTH_LITE/STANDARD/PREMIUM` (20/150/600 в месяц),
     `common/image-generation-quota.ts`.
   - `LAOZHANG_API_KEY`, `LAOZHANG_API_BASE_URL` — прокси к OpenAI для
     сборки промпта. Альтернатива без прокси: `OPENAI_API_KEY` и
     `OPENAI_API_BASE_URL` (код берёт первое заданное). `OPENAI_GPT_MODEL`
     — модель сборки промпта, по умолчанию `gpt-5`.
   - `FFMPEG_API_BASE_URL` — адрес хостед-ffmpeg (по умолчанию из
     `configuration.ts`); менять только при своём инстансе.
   - `PORT` — Vercel задаёт сам; локально `3000`.
   - `TELEGRAM_BOT_TOKEN` — обязателен, как только Telegram-логин
     используется хоть где-то (см. `doc/TELEGRAM-ADMIN.md`). Получить у
     @BotFather. Этот же бот валидирует и TMA-`initData`, и Login Widget
     кнопки «Войти через Telegram» на `frontend/` (`doc/TELEGRAM-ADMIN.md`,
     §2.4) — для последней у него должен быть настроен
     `/setdomain` → домен `frontend`-проекта (шаг 4 раздела 2 ниже; сама
     TMA в домене не нуждается, только Login Widget).
   - `ADMIN_LOGIN_BOT_TOKEN` — опционален, только если под Telegram
     Login Widget админки заводится отдельный бот (у Login Widget домен
     привязывается к боту через `/setdomain`, один домен на бота — раз
     `TELEGRAM_BOT_TOKEN`'s бот уже привязан к домену `frontend`, для
     `admin`-проекта, живущего на СВОЁМ домене, одним ботом не
     обойтись).
   - `ALLOW_DEV_AUTH` — **не задавать здесь вообще**. Это переменная
     локального докер-стенда (`docker-compose.dev.yml`); двойной
     предохранитель (`NODE_ENV!==production`, см.
     `backend/src/modules/admin-auth/dev-login.ts`) и так закрывает
     dev-вход на Vercel, но лучше, чтобы переменная там даже не
     существовала. С этапа 43 второй предохранитель стоит и на
     dev-обходе личности в TMA (`telegram-identity.middleware.ts`) — до
     этого там было одно условие, и утёкшая переменная означала
     подделку личности одним заголовком, о чём этот документ, наоборот,
     успокаивал.
   - `CORS_ORIGIN` — **обязательна в проде** и с **разным значением для
     Production и Preview** (Vercel Dashboard позволяет задать
     переменную отдельно на каждое окружение). Включает точный домен
     `admin`-проекта: без него не только браузерный CORS, но и
     CSRF-проверка (`backend/src/common/csrf.ts`) отклонит все не-GET
     запросы из админки. С этапа 82 сюда же нужен домен `landing`-проекта
     — до этого лендинг ходил в backend только сервер-сервер (блог, без
     CORS), а виджет ИИ-консультанта (`AssistantWidget.tsx`) впервые
     зовёт `/assistant/*` прямо из браузера посетителя; эти маршруты без
     cookie, но `PublicOriginGuard` сверяет `Origin` той же функцией
     (`matchesAllowedOrigin`), что и `app.enableCors()` ниже — один и тот
     же список доменов, без домена лендинга запрос отклонят оба слоя.

     С этапа 41 незаданная переменная в проде **закрывает** запись по
     cookie, а не открывает её: раньше пустой список молча выключал
     CSRF-проверку целиком, и внешне всё работало — CORS при этом
     выглядел настроенным, потому что у него есть умолчание
     `http://localhost:5173`. Теперь при `NODE_ENV=production` и пустом
     списке любой не-GET запрос с `Origin` получит 403; вне прода
     поведение прежнее. Симптом неверной настройки —
     «Cross-origin request rejected (CSRF protection)» в ответах и в
     логах.

     Та же проверка теперь стоит и на пользовательской cookie
     (`user_session`), а не только на админской, — иначе форма с чужого
     сайта могла бы от имени вошедшего человека принять оферту, завести
     проект или потратить деньги владельца на пробу голоса.
     - Production: `https://<домен-frontend>.vercel.app,https://<домен-admin>.vercel.app,https://<домен-landing>.vercel.app`
       (домен лендинга — с этапа 82, см. выше)
     - Preview: то же самое плюс `*.vercel.app`
       (добавляем wildcard, потому что у каждого preview-деплоя
       фронтенда — свой случайный `*.vercel.app` адрес; сам backend
       разбирает список через запятую и wildcard-суффиксы — см.
       `main.ts`/`configuration.ts`). `admin`-проект у Vercel Hobby
       обычно не имеет preview-трафика с CSRF-риском (внутренний
       инструмент), но если он всё же появится — добавить его домен
       так же явно, wildcard `*.vercel.app` для CSRF-проверки
       намеренно не используется (см. `isOriginAllowed` — точное
       совпадение, не суффикс).
   - `TELEGRAM_ALERTS_CHAT_ID` и `TELEGRAM_STATS_CHAT_ID` (§28, этап 45)
     — два служебных канала: ошибки и статистика. Задавать стоит: без
     них о сбое узнают от пользователя, а суточный отчёт уходит в
     никуда. Это идентификаторы ЧАТОВ, а не список операторов —
     добавить человека значит добавить его в чат, деплой не нужен.
     Отправляет тот же бот, что и `TELEGRAM_BOT_TOKEN`; у групп id
     отрицательный, узнаётся через `getUpdates`.
   - `SESSION_TTL_HOURS`.
   - `LIBRARY_UNUSED_TTL_DAYS` (этап 51) — через сколько дней разбор из
     библиотеки с нулём использований удаляется суточной уборкой вместе с
     кадрами; по умолчанию 180, `0` выключает. Библиотека — вторая по
     скорости роста таблица (~0,9 ГБ в год без чистки).
   - **Известное ограничение (пятый аудит, Д-4.4).** Суточная уборка
     (`runCleanupSessions`) чистит `Session`/`AdminSession`/`UserSession`,
     `alert_states`, `rate_limits` и невостребованную `analysis_library` —
     и только их. Три группы таблиц этапов 65–68 —
     `CatalogBatchRun`/`CatalogBatchItem` (партии по каталогу),
     `AbTestRun`/`AbTestVariant` (A/B-варианты, включая полный текст
     промпта и озвучки на каждый вариант, `@db.Text`) и
     `ProductFeedImportRun`/`ProductFeedImportItem` (импорт товарного
     фида) — растут без ограничения и без чистки джобом ни одним. При
     текущем масштабе (доступно только Premium) цена умеренная —
     сознательно принятый риск, а не забытая правка; если объём вырастет,
     нужен отдельный джоб очистки (или ручной SQL по возрасту
     `createdAt`), которого сегодня нет.
   - `PLANS_BILLING_ENABLED` (§23, §41) — не задавать или `false`, пока
     все режимы бесплатны; `true` переключает `PATCH /api/me/plan` на
     режим оплаты: понижение до LITE становится запросом отмены
     подписки (доступ остаётся до конца оплаченного периода), а прямой
     переход на STANDARD/PREMIUM отклоняется с указанием на
     `POST /api/billing/checkout/subscription` — самостоятельно
     повысить режим больше нельзя, только через покупку.
   - `DAILY_SPEND_LIMIT_USD_*` (§26.4) — суточные потолки расхода по
     режимам и общий для анонимных. Не заданы — работают умолчания из
     кода; на проде их стоит выставить осознанно, это единственное, что
     ограничивает счёт за Veo.
   - `AI_PRICE_*` (§26) — переопределение ставок прайса, если цены
     провайдеров разошлись с таблицей в коде.
   - `FFMPEG_API_KEY` (§15.4/§16.1) — постобработка ролика: обрезка кадра
     до форматов, которые Veo не рендерит нативно, и наложение своей
     звуковой дорожки. Не задан — ролики остаются в 16:9/9:16 со звуком
     Veo, интерфейс об этом честно пишет.
   - `VOICE_API_KEY` (§15) — синтез речи (ElevenLabs); опционально
     `VOICE_ID` и `VOICE_MODEL`. Не задан — озвучивает сам Veo, ровно
     как до этапа 35; это мягкий фоллбек, а не ошибка.
   - `TTS_PROVIDER` (doc/TTS-PROVIDER-ALTERNATIVES-SPEC.md) — второй
     провайдер синтеза, Resemble AI, рядом с ElevenLabs, не вместо
     него: значение `elevenlabs` (умолчание, если переменная не
     задана или задана неизвестным значением) или `resemble`. При
     `resemble` — опционально `RESEMBLE_API_KEY` и
     `RESEMBLE_VOICE_ID`, тот же мягкий фоллбек, что у ElevenLabs: без
     ключа синтез Resemble пропускается, ролик всё равно получится. У
     Resemble нет универсального голоса каталога, поэтому без
     `RESEMBLE_VOICE_ID` и без выбора голоса в манифесте бренда синтез
     тоже пропускается — это ожидаемо, не поломка. **Значение продукта
     (решение владельца, 26.09.2026): `RESEMBLE_VOICE_ID=8561c50d`** —
     женский голос по умолчанию для брендов, не выбравших свой. Это
     идентификатор голоса, не секрет; меняется в переменных проекта на
     Vercel и вступает в силу только после передеплоя (в админке
     таблица env — диагностика, запись оттуда не предусмотрена).
     Важно: переменная влияет на БУДУЩИЕ синтезы. Уже отрендеренный
     ролик хранит свой `voiceStatus`/`postError`, и надпись «голос не
     выбран» на его экране останется, пока ролик не переозвучат или не
     пересоберут. Голос, выбранный
     под одним провайдером, помечается в `BrandManifest.ttsProvider` и
     не подставляется под другой при переключении `TTS_PROVIDER`
     (§4.2 того же документа) — при смене провайдера на проде бренды
     увидят предупреждение и должны выбрать голос заново.
   - `RESEMBLE_WEBHOOK_SECRET` (этап 73, TODO п.32) — клонирование
     голоса пользователями через Resemble AI (`PlanFeature.voiceCloning`,
     Standard и выше). Секрет вебхука `POST
     /api/voices/webhook/resemble?secret=...`, которым Resemble
     сообщает о готовности обучения — сверяется constant-time, как
     `TELEGRAM_WEBHOOK_SECRET`, но передаётся в QUERY-параметре, не в
     заголовке (у Resemble нет отдельного поля под секрет заголовка,
     см. `resemble-webhook-secret.ts`). Не задан — вебхук отвечает 503,
     но клонирование всё равно работает: готовность подтягивается
     poll-фоллбеком при каждом открытии списка голосов (медленнее, но
     рабочий путь). Значение генерируется так же, как `CRON_SECRET`
     (`openssl rand -hex 16`); URL для регистрации у Resemble собирается
     кодом из `API_PUBLIC_URL` + этого секрета, регистрировать вручную
     не нужно — `callback_uri` передаётся в каждом вызове
     `POST /voices` (Resemble не требует отдельного `setWebhook`-шага).
   - `HEDRA_API_KEY` (doc/AVATAR-LIPSYNC-PIPELINE-SPEC.md, этап 72) —
     пилот говорящего AI-аватара (Hedra Character-3). Не задан — ручной
     запуск оператором (`POST /admin/actors/:sessionId/generate`)
     отвечает понятной ошибкой, остальной продукт не затронут. Голос
     для пилота — Resemble явно (`RESEMBLE_API_KEY` выше), независимо
     от `TTS_PROVIDER`. Маршрут admin-only (`AdminSessionGuard` +
     оператор), пользователям продукта не показывается.
   - **`CRON_SECRET` — задать обязательно.** Это единственное, что
     открывает `/api/cron/*`: с этапа 54 (Б-3.3) без переменной ни один
     из маршрутов `cron.controller.ts` не работает, все отвечают 503 —
     число выросло с пяти на момент этапа 54 (суточный отчёт, уборка
     сессий, метла, блог, выгрузка в каналы) до одиннадцати сейчас
     (добавились продление подписок, маркетинговая рассылка, партии
     каталога, A/B-варианты, импорт товарного фида, синхронизация
     автоэкспорта) — актуальный список маршрутов всегда виден в самом
     `cron.controller.ts`, не переписывайте число здесь при добавлении
     нового крона (до этапа 54 они без секрета были публичными, а
     `sweep-orphans` необратимо удаляет файлы). Значение генерируется,
     например, `openssl rand -hex 16`; Vercel сам шлёт его заголовком
     `Authorization: Bearer` при вызове крона, контроллер сверяет
     constant-time. Проверить после деплоя:
     `curl -i https://<backend>/api/cron/cleanup-sessions` должен вернуть
     401 (секрет задан, заголовка нет), а не 503 (секрет не задан) и не
     200. На dev-стенде (`ALLOW_DEV_AUTH=true` вне production) крон открыт
     без секрета — те же два предохранителя, что у dev-входа.
   - `FIXTURE_USER_TOKEN` и `FIXTURE_TELEGRAM_ID` (§3.3 ТЗ
     doc/TMA-UI-SNAPSHOT-AND-TUTORIAL-VIDEO-SPEC.md, этап 97,
     `backend/src/common/fixture-token.ts`) — служебный вход
     автоматического исполнителя сценариев обучающих видео (крон
     `/api/cron/tutorial-scenario-run`): headless-браузер шлёт заголовок
     `X-Fixture-Token`, middleware сверяет constant-time и выдаёт
     identity пользователя с `telegramId=FIXTURE_TELEGRAM_ID`. Не
     ALLOW_DEV_AUTH — тот обход недоступен на проде, а этот исполнитель
     обязан работать именно там. Не заданы — крон-джоб не падает, просто
     логирует предупреждение и пропускает прогон (см.
     `TutorialScenarioRunnerService`). `FIXTURE_USER_TOKEN` генерируется
     так же, как `CRON_SECRET`; фикстурного пользователя и его данные
     (проект/товар/манифест/сессия с роликом) заводит отдельный
     ops-скрипт `backend/scripts/seed-fixture-user.ts`, запускается
     вручную один раз, не частью деплоя.
   - `SITE_TUTORIAL_TOKEN_KEY`, `SITE_TUTORIAL_ROUNDS_PER_DAY`,

       конфигурационный путь.
   - **ИИ-консультант на лендинге (doc/LANDING-TUTORIAL-AI-CONSULTANT-SPEC.md,
     этап 82)** — выключен по умолчанию (`assistant_enabled` в
     `PlatformSetting`, включается в админке, `/settings`), поэтому все
     переменные ниже необязательны для деплоя как такового:
     - `ASSISTANT_IP_HASH_SECRET` — соль для `sha256(ip:суточная соль:секрет)`
       в `AssistantExchange.ipHash` (§8 ТЗ — сам IP не хранится). Не
       задана — используется `CRON_SECRET`, а если и его нет —
       встроенное значение для разработки (`dev-only-assistant-ip-salt`,
       годится только для dev-стенда, НЕ для прод). Генерируется так же,
       что и остальные секреты: `openssl rand -hex 16`.
   - **Первый случай браузерного похода лендинга в backend напрямую**
     (`NEXT_PUBLIC_API_BASE_URL` у `landing`-проекта, раздел 4 ниже) —
     `CORS_ORIGIN` этого backend-проекта ДОЛЖЕН включать origin
     лендинга, иначе виджет консультанта получает CORS-ошибку на каждый
     запрос из браузера посетителя; до этого этапа `CORS_ORIGIN`
     обслуживал только `admin`/`frontend` (лендинг ходил в backend
     только с сервера при SSR — тому CORS не нужен, см. `API_BASE_URL`
     ниже).
6. Deploy. Полученный URL (например
   `https://viral4creators-backend.vercel.app`) — это то, что пойдёт во
   `VITE_API_BASE_URL` фронтенда и `NEXT_PUBLIC_API_BASE_URL`
   admin/landing (шаги ниже), а с `/api` на конце — в `API_PUBLIC_URL`
   этого же проекта (шаг 5 выше; переменную можно дозаполнить и
   передеплоить уже после первого деплоя — до этого домен неизвестен).
7. **Если подключаете каналы YouTube/TikTok (§14, этап 61)** — заведите
   OAuth-приложения на сторонах Google и TikTok и укажите там redirect
   URI на именно этот, уже задеплоенный домен:
   - Google Cloud Console → APIs & Services → Credentials → OAuth client
     ID (Web application) → Authorized redirect URIs →
     `<API_PUBLIC_URL>/channels/oauth/YOUTUBE/callback`.
   - TikTok for Developers → приложение → Login Kit → Redirect URI →
     `<API_PUBLIC_URL>/channels/oauth/TIKTOK/callback`.
   - До прохождения проверки (аудита) обеих платформ выгрузка на
     YouTube ограничена приватным/по ссылке показом, а на TikTok —
     принудительно видимостью «только я» (`SELF_ONLY`) — платформенные
     ограничения для неаудированных приложений, не настройка деплоя (см.
     открытый вопрос 14.1 в `PRODUCT-PROJECT-SPEC.md` §14).
8. **Если включаете оплату (§41, этап 62)** — после того, как
   `TELEGRAM_WEBHOOK_SECRET` задан и проект задеплоен, зарегистрируйте
   вебхук у Telegram ОДНИМ ручным вызовом (код приложения `setWebhook`
   не вызывает сам — это не повторяющийся шаг деплоя, а разовая
   настройка бота):
   ```
   curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
     -d "url=<API_PUBLIC_URL>/billing/webhook/telegram" \
     -d "secret_token=<TELEGRAM_WEBHOOK_SECRET>"
   ```
   Проверить: `getWebhookInfo` должен показать тот же `url` и
   `pending_update_count: 0` после первого тестового платежа. На
   локальном докер-стенде входящий вебхук всё равно недостижим извне
   (`localhost`) — там `setWebhook` не регистрируется, Stars-оплата
   локально не проверяется end-to-end (см. `doc/ACCEPTANCE-CHECKLIST.md`
   §6u).
   Мерчант-аккаунт WayForPay должен быть включён на **regular
   payments** ДО того, как заработает автопродление подписки картой —
   это делается в личном кабинете WayForPay (организационный шаг,
   не настройка Vercel); без этого доступна только разовая оплата,
   `recToken` для продления просто не приходит, и подписки через
   WayForPay остаются одноразовыми до конца оплаченного периода без
   автоматического продления (Stars-подписки от этого не зависят — у
   них автопродление на стороне Telegram, см. `PRODUCT-PROJECT-SPEC.md`
   §41).

### 1.x. Версия сборки (этап 154)

Ничего настраивать не нужно — но знать, откуда она берётся, стоит:
именно её спрашивают у баг-репорта первым, и по ней решают, чинить
находку или закрывать как уже исправленную.

| Переменная | Кто задаёт | Что делает |
| --- | --- | --- |
| `VERCEL_GIT_COMMIT_SHA` | Vercel, сам | Хеш коммита сборки. Бэкенд берёт из него первые 7 символов и сообщает их как версию; фронтенд подставляет в свой штамп на этапе сборки |
| `BUILD_ID` | вручную, необязательно | Перебивает автоматическую версию. Нужен, когда сборка нестандартная и её надо пометить по-человечески (`hotfix-2026-09-25`) |
| `TELEGRAM_BOT_USERNAME` | вручную | Имя бота без `@`. Из него собирается ссылка приглашения тестировщика (`t.me/<bot>?start=t_<токен>`, этап 155). Не задано — в админке вместо ссылки видна заметная заглушка, потому что молча собранный `https://t.me/undefined?start=…` выглядел бы рабочим |

Ни та, ни другая не заданы — версия читается как `dev`. На стенде это
норма; на проде значит, что по тикету нельзя понять, на какой сборке он
снят, и вкладка «Настройки» в админке об этом предупреждает.

**Наружу версия не отдаётся.** В `/health` её нет намеренно: там
записано «ни версий, ни имён хостов», и коммит на анонимном маршруте
сказал бы постороннему, какой именно код сейчас работает. Оператор
видит версию в админке, пользователь — в подвале мини-аппа, тикет
получает её сам.

## 2. Frontend-проект

1. Vercel Dashboard → **Add New** → **Project** → тот же репозиторий.
2. **Root Directory**: `frontend`.
3. Framework Preset: Vite — определится автоматически.
4. **Environment Variables**:
   - `VITE_API_BASE_URL` = `https://<backend-домен>.vercel.app/api` —
     **одно и то же значение для Production и Preview** (у backend'а
     нет preview-деплоев для каждого фронтенд-PR, он один стабильный —
     см. `frontend/.env.example`). В Vercel это можно поставить галочкой
     "All Environments" вместо раздельных Production/Preview значений.
   - `VITE_ALLOW_DEV_AUTH` — **не задавать в проде** (или явно `false`).
     `VITE_DEV_USER_ID` — идентификатор dev-пользователя для того же
     обхода; без него dev-вход подставляет `123`. Тоже только стенд.
     Это только для локального докер-стенда, см.
     `doc/TELEGRAM-ADMIN.md`.
   - `VITE_TELEGRAM_BOT_USERNAME` — username (без `@`) бота
     `TELEGRAM_BOT_TOKEN`, для кнопки «Войти через Telegram» (см.
     `doc/TELEGRAM-ADMIN.md`, §2.4). Без него кнопка просто не
     рендерится — не обязательная переменная, но без неё нет и
     постоянного логина вне Telegram.
   - `VITE_LANDING_URL` = URL landing-проекта (шаг 4 ниже) — этап 60,
     ТЗ §40: `ShareVideoPanel.tsx` строит по нему ссылку «Открыть
     страницу»/«Поделиться» на опубликованную публичную страницу ролика
     (`<landing>/video/:id`). Без неё падает на дефолт
     `http://localhost:3003`, который в проде никуда не ведёт.
   - `VITE_CLAUDE_REFERRAL_URL` — доп. запрос владельца продукта:
     реферальная ссылка Claude в футере TMA и на экране принятия условий
     (`App.tsx`/`TermsGate.tsx`). Не обязательна — без неё используется
     зашитый дефолт (тот же адрес, что дал владелец продукта); задавать
     в env нужно, только если реферальный код сменится.
5. У бота `TELEGRAM_BOT_TOKEN` настроить
   `@BotFather /setdomain` → этот frontend-домен (нужно только для
   Login Widget-кнопки; TMA-часть работает без этого шага).
6. Deploy.

2. **Root Directory**: `admin`.
3. Framework Preset: Next.js — определится автоматически.
4. **Environment Variables**:

     (С `/api` — та же логика, что у `VITE_API_BASE_URL` фронтенда:
     бэкенд навешивает глобальный префикс `/api` на все роуты, включая

     Telegram Login Widget. У бота должен быть настроен домен этого

   через Telegram Login Widget один раз, затем вручную
   `UPDATE users SET "isOperator" = true WHERE "telegramId" = '<ваш telegram id>'`
   в Supabase SQL editor — см. `doc/TELEGRAM-ADMIN.md`, §2.5. Это

## 4. Landing-проект

1. Vercel Dashboard → **Add New** → **Project** → тот же репозиторий.
2. **Root Directory**: `landing`.
3. Framework Preset: Next.js — определится автоматически.
4. **Environment Variables**:
   - `NEXT_PUBLIC_TMA_URL` = URL frontend-проекта (шаг 2 выше) — лендинг
     ссылается на него как на сам продукт, работающий и как обычный
     сайт вне Telegram.
   - `API_BASE_URL` = `https://<backend-домен>.vercel.app/api` (этап 58,
     блог: `GET /blog`, `GET /blog/:slug`). БЕЗ префикса `NEXT_PUBLIC_` —
     это сознательно: страницы блога, `sitemap.xml`, `sitemap-news.xml`
     и RSS-ленты читают его на сервере (сборка + ISR-ревалидация, см.
     `landing/src/lib/blog-api.ts`), а не в браузере посетителя, и в
     клиентский бандл ему попадать незачем.
   - `SITE_URL` = `https://<домен-этого-проекта>.vercel.app` (или
     кастомный домен) — абсолютный адрес самого лендинга, нужен
     `sitemap.xml`/`sitemap-news.xml`/RSS (там `<loc>`/`<link>` обязаны
     быть абсолютными) и JSON-LD-разметке (`NewsArticle`/
     `BreadcrumbList`) на страницах блога.
   - `NEXT_PUBLIC_API_BASE_URL` = тот же `https://<backend-домен>.vercel.app/api`,
     что и `API_BASE_URL` выше, но ОБЯЗАТЕЛЬНО с префиксом
     `NEXT_PUBLIC_` (doc/LANDING-TUTORIAL-AI-CONSULTANT-SPEC.md, этап
     82) — виджет ИИ-консультанта (`AssistantWidget.tsx`) ходит в
     backend прямо из браузера посетителя (SSE-стрим чата, конфиг,
     телеметрия), это первый такой случай у лендинга, поэтому нужна
     отдельная от серверной `API_BASE_URL` переменная — без
     `NEXT_PUBLIC_` Next.js не включит значение в клиентский бандл.
   - `NEXT_PUBLIC_CLAUDE_REFERRAL_URL` — тот же приём, что у TMA
     (`VITE_CLAUDE_REFERRAL_URL` выше): реферальная ссылка Claude в
     футере лендинга (`page.tsx`, `lib/content.ts`). Не обязательна —
     без неё тот же зашитый дефолт.
   - `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` — username бота БЕЗ `@` (этап
     134). По нему страница приглашения `/r/<код>` строит кнопку
     «Открыть в Telegram» (`t.me/<бот>/app?startapp=r_<код>`). Дефолта в
     коде НЕТ намеренно: неверный `NEXT_PUBLIC_TMA_URL` ведёт на
     мёртвый localhost, а выдуманное имя бота увело бы приглашённых к
     ЧУЖОМУ боту. Не задана — кнопки нет, вторая дорога («Продолжить
     здесь», `NEXT_PUBLIC_TMA_URL?ref=<код>`) работает.
5. Deploy. Про CORS: для блога `CORS_ORIGIN` backend-проекта дополнять
   НЕ нужно — тот запрос идёт сервер-сервер (сборка/ревалидация на
   Vercel, см. `API_BASE_URL` выше). Но с этапа 82 это уже не вся
   картина: виджет консультанта (`NEXT_PUBLIC_API_BASE_URL` выше) ходит
   в backend ИЗ БРАУЗЕРА посетителя лендинга — `CORS_ORIGIN`
   backend-проекта ДОЛЖЕН включать origin этого landing-проекта, иначе
   `GET /assistant/config`/`POST /assistant/chat`/`POST /assistant/event`
   отвечают браузеру CORS-ошибкой (тот же принцип, что у admin/frontend,
   раздел 1, шаг 5). Остальной лендинг — статический контент, как и
   раньше.

## 5. Проверка после деплоя

- Открыть frontend-URL, пройти воркфлоу до шага загрузки видео — если
  `CORS_ORIGIN` настроен верно, запросы к backend не должны падать с CORS
  ошибкой в консоли браузера.
- Открыть preview-деплой фронтенда (например, после пуша в отдельную
  ветку) — тот же тест: preview получает случайный `*.vercel.app` адрес,
  wildcard в `CORS_ORIGIN` backend'а должен его пропустить.
- `GET https://<backend-домен>.vercel.app/api/health` — должен отвечать
  200 (health-check уже есть, см. `main.ts`).
- Открыть admin-URL `/login`, войти через Telegram Login Widget —
  редирект на `/sessions` без ошибок в консоли (если Widget не
  показывается, проверить `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` и
  `@BotFather /setdomain` для этого домена).
- Открыть frontend-URL вне Telegram — в шапке видна кнопка «Войти через
  Telegram» (если не показывается, проверить `VITE_TELEGRAM_BOT_USERNAME`
  и `@BotFather /setdomain` для ЭТОГО домена — см. п.5 раздела 2), войти
  — виджет должен исчезнуть и смениться на «Вошли как ...».
- Открыть landing-URL — кнопка ведёт на frontend-URL.
- **Советник в мастере приезжает выключенным** и включается руками —
  порядок и то, за чем смотреть первые сутки, в
  `doc/WIZARD-GUIDE-RUNBOOK.md`. Это единственная фича, которую деплой
  сознательно не включает: она платит за каждый показ.
- Открыть `<landing-URL>/ru/blog` (этап 58) — список записей (или
  честное пустое состояние, если модератор ещё ничего не опубликовал);
  `<landing-URL>/sitemap.xml`, `/sitemap-news.xml`, `/robots.txt`,
  `/feed.xml` — отдают XML/текст без ошибки 500 (пустой список из-за
  недоступного `API_BASE_URL` — это баг конфигурации, а не сети:
  проверить, что переменная задана и указывает на `/api`).
