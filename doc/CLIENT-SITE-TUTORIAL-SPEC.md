# Обучающее видео по ссылке на сайт заказчика — self-service «вид проекта»

## 0. Статус и происхождение документа

Это ТЗ пересобирает и **заменяет** черновик из §11
`doc/TMA-UI-SNAPSHOT-AND-TUTORIAL-VIDEO-SPEC.md` («Возможное расширение:
обучающие видео по сайту заказчика») после явного уточнения владельца
продукта. §11 остаётся в исходном документе как есть (архивная запись
хода мысли), но помечается коротким указателем сюда — см. §12 этого
документа.

Прямая цитата запроса, с которого начат этот документ:

> Давай допроектируем создание обучалки по пользовательской ссылке
> (новый вид проекта). Первым шагом задаётся ссылка, и кнопка
> исследовать. Делаем запрос и получаем скрин страницы по ссылке.
> Селекторы инпутов на странице (если открылась) — тогда создаём форму
> для ввода данных и варианты на какую кнопку нажать если их больше
> одной. Есть ли редирект на логин форму — в этом случае просим либо
> кредентиалы к тестовому пользователю либо зайти через iframe например
> и сохраняем куки в Кеше. Все это сохраняем по той же схеме что штатную
> обучалку и отправляем в пост продакшн. Нужно максимально достоверное
> ТЗ со всеми вариантами воркфлоу.

На уточняющий вопрос «кто пользуется инструментом — оператор (админка)
или сам клиент продукта (ТМА, self-service)?» получен явный ответ,
который меняет модель владения из §11 и является отправной точкой этого
документа:

> Я думаю это просто вид проекта, на той же вкладке где создаём проект,
> только выбираем на первом шаге не мастер по товару а мастер по
> клиентскому сайту.

Из этого следует главный архитектурный пивот относительно §11:

| | §11 (старый черновик) | Этот документ |
|---|---|---|
| Кто заводит запись | Оператор вручную, `TutorialClientSite` — не самообслуживание | **Сам пользователь**, третий вариант в мастере создания проекта |
| Кто владеет данными | Ничей — общий справочник заказчиков | **`Project`** конкретного пользователя (`Project.userId`) |
| Кто пишет сценарий | ИИ по тексту промпта, по аналогии с §4.10 | **Сам пользователь**, кликая по реально показанной странице — сценарий не угадывается ИИ, а буквально записывается за живым действием |
| Согласие | Отдельная модерация заведения `baseUrl` оператором | Пользователь сам вводит ссылку на **свой собственный** сайт/кабинет — согласие подразумевается тем же способом, что и остальной self-service продукта (сам ввёл товар, сам ввёл ссылку) |
| Одобрение перед показом | `costly`/`approved`, п.4 §11.2 | Сохраняется как отдельный гейт — см. §8 — именно потому что self-service снимает один барьер (оператор больше не заводит запись), но не снимает нужды проверить итоговое видео перед публикацией |

Второй момент, который пересматривается по итогам исследования (не по
прямому вопросу пользователю, а как техническое решение, требующее
последующего подтверждения, впоследствии закрытого, см. §13): §11 п.2
предполагал, что ИИ пишет шаги сценария по снятой DOM-структуре. Ниже
(§4–§6) показано, что при self-service с «формой для ввода данных и
вариантами на какую кнопку нажать» сценарий фактически **не пишется
ИИ вообще** — он собирается интерактивно, экран за экраном, из реальных
действий самого пользователя. Это не отход от запроса, а его буквальная
реализация: пользователь сам вводит данные и сам выбирает кнопку —
значит сценарий — прямая запись этого выбора, а не предсказание модели.
Это также снимает самый тяжёлый пункт §11 («упрощённое дерево элементов
→ модель пишет шаги, которые могут не совпасть с реальной страницей») —
здесь скриншот и есть источник правды, а шаг сохраняется только когда
пользователь его буквально выполнил.

## 1. Идея в одном абзаце

На экране создания проекта (`ProjectCreateScreen.tsx`) появляется
третий вариант типа проекта — «по сайту» — рядом с «Одиночный» и
«Линейка». Выбор этого варианта уводит пользователя не в форму
название/страна/бренд-манифест, а в отдельный визард: ссылка + кнопка
«Исследовать» → скриншот целевой страницы и распознанные на ней поля
ввода/кнопки → пользователь заполняет поля своими значениями и жмёт ту
кнопку, которая ему нужна (если кандидатов несколько — выбирает из
списка) → бэкенд реально выполняет это действие headless-браузером на
целевом сайте и возвращает скриншот СЛЕДУЮЩЕГО экрана → цикл повторяется
экран за экраном, пока пользователь не нажмёт «Готово». Если по пути
встречается форма логина — предлагается ввести тестовые
логин/пароль (шифруются и хранятся, чтобы повторно ввестись при сборке
финального ролика). По «Готово» пользователь попадает не сразу на
отправку, а на предпросмотр — ленту уже отрисованных по пути кадров
целиком (§6.3, §11 экран 3), и только после этого называет черновик
и отправляет на проверку. Накопленная последовательность действий
сохраняется в том же словаре шагов (`goto`/`fill`/`click`/`waitFor`),
что и штатная обучалка (§4.10 TMA-спеки), и уходит в тот же
пост-продакшн конвейер (кадры → внешний ffmpeg-api → сборка →
`TutorialVideoAsset`), после чего проходит ту же ручную модерацию
(§4.6/§4.11) и может быть опубликована уже существующим (этап 101,
этот же чат) `PublicationService.publishTutorialVideo()` без единой
правки.

## 4. Экран создания проекта

### 4.1 `ProjectType`

```prisma
enum ProjectType {
  SINGLE
  LINE
  CLIENT_SITE   // НОВОЕ — этот документ
}
```

Миграция: `ALTER TYPE "ProjectType" ADD VALUE 'CLIENT_SITE';` (Postgres
не позволяет удалить/переименовать значение enum в той же транзакции,
что и его добавление — стандартное ограничение, отдельная миграция,
как и остальные добавления значений в проекте).

`Project` для типа `CLIENT_SITE` использует уже существующие поля
(`title`, `countryCode`/`currency`, `brandManifestId`) без изменений —
это по-прежнему проект, просто без `ProductItem`. Поля, специфичные для
этого типа (ссылка, накопленные шаги, куки, креды), не размазываются по
`Project` — уходят в отдельную таблицу (§6.1), тем же принципом, что
`ProductItem`/`BrandManifest` не хранятся прямо в `Project`.

**Решение по `countryCode`/`currency` для `CLIENT_SITE` (закрывает
§13 п.2).** Колонки остаются `NOT NULL` как есть — миграция на
nullable НЕ делается: это лишний схемный риск и лишние null-проверки
во всех местах, которые уже читают `Project.countryCode`/`currency`
(отчёты, экспорт, будущие фичи), ради поля, которое для этого типа
проекта всё равно ничего не считает (нет `ProductItem`/цены). Вместо
этого — нулевая по стоимости мера против оттока на первом шаге:
`POST /projects` для `type: 'CLIENT_SITE'` (то же тело, что и сегодня)
принимает `countryCode` НЕОБЯЗАТЕЛЬНЫМ полем и при его отсутствии
подставляет `countryCode` последнего проекта того же пользователя
(`Project.findFirst({ where: { userId }, orderBy: { createdAt: 'desc'
} })` — уже есть похожий запрос-паттерн в `ProjectService`), а если
это первый проект пользователя вообще — платформенный дефолт (константа
`DEFAULT_COUNTRY_CODE`, по умолчанию `'UA'` — домашний рынок продукта).
`currency` считается тем же способом, что и сегодня (вывод из
`countryCode`, без нового кода). Экран 1 визарда (§4.2/§11) не
показывает выбор страны вообще — пользователь просто вводит ссылку,
ничего не выбирает. Максимальный профит: ноль трения на входе в
платную self-service-фичу (каждый лишний обязательный шаг на входе —
это часть аудитории, которая не дойдёт до создания проекта), ноль
миграций, ноль новых null-проверок ниже по коду.

### 4.2 `ProjectCreateScreen.tsx`

`frontend/src/features/projects/ProjectCreateScreen.tsx` сейчас (строки
79-104) рендерит `Pills` с двумя вариантами (`SINGLE`/`LINE`), и вся
форма ниже (название, страна, бренд-манифест) — общая для обоих. Для
`CLIENT_SITE` эта форма **не подходит**: нет «названия товара» до того,
как исследована страница, и не нужен явный шаг «страна» на этом экране
(валюта проекта для сайта заказчика не имеет смысла — решение см. §4.1:
поле заполняется сервером автоматически, шаг просто не показывается).

Решение: третья `Pill` («По сайту заказчика», иконка `Globe` из
`lucide-react`, уже используемого в файле) переключает форму целиком —
не просто третий вариант в той же форме, а условный рендер:

```tsx
{type === 'CLIENT_SITE' ? (
  <ClientSiteWizard onCreated={(project) => navigate(routes.project(project.id), true)} />
) : (
  /* существующая форма название/страна/бренд-манифест, без изменений */
)}
```

`ClientSiteWizard` — новый компонент (§11), который:
1. на первом шаге просит только ссылку (без страны/валюты — они не
   нужны для сути этого вида проекта; отдельный маленький шаг «название
   проекта» может быть либо частью этого экрана, либо задаваться позже,
   на шаге «Готово», см. §5.4 — рекомендация ниже: спросить в конце,
   когда уже понятно, что это за сайт, а не заранее «как назвать
   проект, которого ты ещё не видел»);
2. сам создаёт `Project{type:'CLIENT_SITE'}` через тот же

## 5. Бэкенд: пошаговое исследование страницы

### 5.1 Ограничения serverless-архитектуры — почему это НЕ живая браузерная сессия

`doc/DEPLOYMENT.md`/`doc/DOCKER.md`/`docker-compose.yml` фиксируют:
прод — Vercel Functions, без постоянного диска и без гарантии, что два
последовательных HTTP-запроса попадут в один и тот же тёплый инстанс
(а тем более — что между ними доживёт открытый процесс Chromium в
памяти). `headless-chromium.ts` уже спроектирован под это: один резолвер
плана на инстанс, страница открывается и закрывается в границах ОДНОГО
вызова (`og-image-fetcher.ts` — единственный текущий вызывающий,
открывает/закрывает браузер за один HTTP-запрос).

Пошаговый визард по определению требует нескольких раундов «клиент
отправил выбор → сервер применил его на реальной странице → вернул
следующий скриншот» — то есть **много HTTP-запросов подряд к одной и
той же логической браузерной сессии**. Держать процесс Chromium живым
между ними на serverless-функции невозможно в принципе (не «сложно», а
архитектурно исключено — функция может быть убита после каждого
ответа). Значит нужна модель, где браузер **честно закрывается после
каждого запроса**, а состояние (куда мы уже дошли и что там за
куки) — персистентное, в БД, и **восстанавливается** заново перед
каждым следующим шагом. Это ключевое архитектурное решение раздела:

**Каждый шаговый запрос = свежий `launchHeadlessBrowser()` → `page.
setCookie(...)` (восстановление куки из предыдущего шага) → `page.
goto(lastUrl)` → выполнить РОВНО один новый шаг (`fill`+`click`,
`fill`-only, или просто `goto` на первом шаге) → снять скриншот +
извлечь элементы новой страницы → сохранить обновлённые `lastUrl`/
`cookiesEnc`/`steps` → закрыть браузер → ответить клиенту.**

**Примитив переноса куки между запусками браузера уже реализован**
(этап 110): `backend/src/common/cookie-jar.ts` —
`parseCookieJar()`/`restoreCookieJar()`/`encryptCookieJar()`/
`decryptCookieJar()`, с тестами. Он появился до остальной обучалки
потому, что аудит этапа 109 обнаружил: `page.setCookie` не встречался в
`backend/` НИ РАЗУ, то есть самая нагруженная часть этого абзаца не
имела реализации вообще. В нём же закрыты две тонкости CDP, каждая из
которых молча ломает ровно сессионные куки логина (CDP отвечает
успехом, кука просто не появляется): `expires: -1` нельзя отправлять
обратно — это «истекла в 1969», сессионная кука передаётся ОТСУТСТВИЕМ
поля; и `SameSite=None` без `Secure` Chromium отклоняет целиком, так
что атрибут в этом сочетании снимается, чтобы кука хотя бы легла.
Восстанавливать jar нужно ДО `goto` и на чистой странице — иначе
puppeteer подставит текущий URL как `url` куки, и домен из jar'а
перестанет быть единственным источником правды (`cdp/Page.js:506-517`).

Это не эмуляция «живой» сессии, а её честная сериализация: каждый шаг
самодостаточен, ничего не остаётся висеть в памяти инстанса между
запросами. Плата — фиксированные ~3 секунды холодного старта Chromium
на каждый шаг (цифра из комментария `headless-chromium.ts`) — приемлемо
для процесса, где пользователь и так читает страницу и вводит данные
между кликами, неприемлемо было бы для чего-то, что должно отвечать
мгновенно.

### 5.2 Эндпоинты (новый модуль `client-site-tutorial`)

(`backend/src/modules/project/project.service.ts:587`) — только
владелец `Project.userId` может исследовать/продолжать свой черновик.

**Конкурентная защита (найдено аудитом §14 п.1): оптимистичная
блокировка по `version`.** Каждый мутирующий вызов (`/explore` после
создания, `/step`, `/login`, `/undo`) принимает `expectedVersion?:

646`) — тот паттерн защищает от гонки на СОЗДАНИЕ, а здесь гонка на

### 5.3 `ClientSiteRouteResolver`

Аналог `route-templates.ts`, но без словаря маршрутов — принимает
буквальный URL/относительный путь и проверяет его происхождение против
уже зафиксированного `draft.baseUrl` (§8.1):

```ts
export function makeClientSiteRouteResolver(
  baseUrl: string,
): ScenarioRouteResolver {
  return (routeName) => {
    let resolved: URL;
    try {
      resolved = new URL(routeName, baseUrl);
    } catch {
      return { ok: false, reason: 'некорректный URL шага' };
    }
    if (resolved.origin !== new URL(baseUrl).origin) {
      return {
        ok: false,
        reason: `переход за пределы ${baseUrl} запрещён`,
      };
    }
    return { ok: true, url: resolved.toString() };
  };
}
```

`routeName` в `ScenarioStepGoto.route` для этой фичи хранит буквальный
URL (не имя маршрута ТМА, как в §4.10) — то же поле, другая семантика,
задокументированная прямо в `scenario-steps.types.ts` доккомментарием
при реализации (шаг `goto` изначально был спроектирован маршрутно-
нейтральным именно ради такого переиспользования — §11.2 п.1 старого
черновика уже это предвидел).

### 5.4 Извлечение интерактивных элементов — `PageExploration`

Новая логика (нет прямого прецедента в проекте — `og-image-fetcher.ts`
вытаскивает только мета-тег `og:image`, не общее дерево элементов).
Выполняется через `page.evaluate()` сразу после `goto`/каждого шага:

```ts
export interface PageElement {
  selector: string;       // стабильный CSS-селектор (см. ниже приоритет)
  tag: 'input' | 'select' | 'textarea' | 'button' | 'a';
  type?: string;           // input[type] — 'text'|'email'|'password'|'checkbox'|...
  label?: string;          // текст <label for=...>, aria-label, placeholder — в этом порядке
  visibleText?: string;    // innerText для button/a — для показа «на какую кнопку нажать»
  name?: string;
}

export interface PageExploration {
  currentUrl: string;
  screenshotDataUrl: string;   // data:image/jpeg;base64,... — см. §6.3, почему не Blob
  elements: PageElement[];
  looksLikeLogin: boolean;
}
```

Приоритет построения `selector` (тот же принцип, которым обычно
пользуются инструменты автотестирования — устойчивость к вёрстке важнее
краткости): `#id` → `[data-testid]`/`[data-test]` → `[name]` →
`[aria-label]` → CSS-путь по тегам с `:nth-of-type()` как последний,
самый хрупкий вариант (если сайт использует нестабильные сгенерированные
классы — единственная альтернатива). Это чистая функция без сети/Nest,
тестируемая тем же приёмом, что `scenario-runner.spec.ts` — мок DOM,
без реального Chromium.

**Реализовано на этапе 112** (`client-site-tutorial/page-exploration.ts`)
с тремя уточнениями, найденными при написании:

1. **Каждый кандидат в селекторы проверяется на единственность**
   (`querySelectorAll(...).length === 1`) и только потом отдаётся.
   Без этого `input[name="email"]` на странице, где рядом стоят форма
   входа и форма регистрации, указывал бы на ЧУЖОЕ поле — и обучалка
   молча записала бы не тот сценарий. Неуникальный кандидат
   отбрасывается, берётся следующий по приоритету.
2. **Критерий видимости шире, чем `offsetParent !== null`.** У элемента
   внутри `position: fixed` контейнера `offsetParent` равен `null` — а
   модальное окно входа ровно такое, и это ровно тот случай, ради
   которого визард существует. Поэтому второй критерий: непустой
   `getClientRects()`.
3. **Сама функция уезжает в страницу строкой** (`toString()` +
   `page.evaluate`), потому что аргументом DOM не передать. Отсюда
   жёсткое правило: никаких импортов и обращений наружу в её теле —
   иначе в браузере `ReferenceError`, а в Node все тесты зелёные.
   Правило сторожится отдельным тестом, разбирающим исходник функции.

`looksLikeLogin` — эвристика: хотя бы один `input[type=password]`
видим на странице. Простое и достаточно надёжное правило (то же самое,
что фактически использует любой автозаполнитель паролей в браузере) —
не нужен отдельный классификатор.

ВАЖНО: этот флаг переключает только выбор между формой учётных данных
(`/login`) и списком шагов (`/step`). Кнопка ЖИВОГО входа от него НЕ
зависит — см. §11.2. Первая версия визарда прятала её внутрь ветки
`looksLikeLogin`, и это был дефект: живой вход существует ради
логинов, где поля пароля на странице нет вовсе — первый экран Google
SSO это кнопка «Continue with Google», Telegram Login Widget живёт в
кроссдоменном iframe и в DOM верхнего фрейма не виден, вход по magic
link пароля не имеет никогда. То есть кнопка не появлялась ровно в тех
случаях, ради которых фича и сделана.

Расширять сам `looksLikeLogin` эвристиками («на странице есть кнопка
Войти», «URL вида /login») для этого НЕЛЬЗЯ: он переключает ветку, а
на SSO-странице заполняемых полей нет — ветка показала бы пустую форму
входа с предупреждением «кнопка входа не распозналась» вместо рабочего
списка шагов. Поэтому изменён не флаг, а место блока живого входа:
отдельная карточка на экране страницы, зависящая только от того,
настроено ли реле (`liveLoginAvailable`) и редактируем ли черновик.
Предикат вынесен в `liveLoginVisible()` (`client-site-elements.ts`),
инвариант «не зависит от `looksLikeLogin`» сторожится тестом
`scripts/client-site-wizard.test.ts`, включая проверку по исходнику
разметки — перенести блок обратно внутрь ветки можно правкой JSX, не
трогая предикат.

Цена лишнего показа — одна живая сессия из суточного лимита
(`reserveLiveSession`, §15.7), и только если человек специально нажмёт
кнопку. Цена пропуска — неработающая фича.

Отбор кандидатов «на какую кнопку нажать» — просто все `elements` с
`tag: 'button'` или `tag: 'a'` с непустым `visibleText`, видимые
(`offsetParent !== null` в `page.evaluate`) на момент снятия. Фронтенд
показывает их как список опций (§11.2) — количество кандидатов не
ограничивается искусственно; если на странице десятки ссылок в
навигации — это уже вопрос качества сайта заказчика, не наш фильтр (хотя
разумно НЕ включать ссылки, ведущие на другой origin, — они всё равно
будут отвергнуты резолвером §5.3 при попытке пройти по ним, лучше не
предлагать их вовсе, чем предложить и тут же отказать).

### 6.2 Связь с `TutorialVideoAsset`

`TutorialVideoAsset` (`backend/prisma/schema.prisma:2232`) сейчас
ключуется `subjectKey`/`locale` — свободные строки для ШАГА НАШЕЙ
обучалки. Для этой фичи `subjectKey` не подходит по смыслу (это не шаг
воркфлоу продукта), но менять существующее поле не нужно — по тому же
журнальному (мягкая ссылка) принципу, что `scenarioId`, добавляется:

```prisma
model TutorialVideoAsset {

  /// Мягкая ссылка (НЕ Prisma-связь, тот же принцип, что scenarioId выше)
  /// на ClientSiteTutorialDraft, из которого собран этот ролик — NULL для

```

Индекс добавлен сразу (найдено аудитом §14 п.9) — тот же принцип, что

же предполагает фильтр `WHERE clientSiteDraftId IS NOT NULL`, заводить

NULL — поле в схеме уже `String`, не nullable, менять его тип не нужно;
использовать существующее поле для нового смысла — тот же приём, что
`generatedBy: 'ai' | 'manual'`, свободная строка вместо нового enum),

смысла втихую» — комментарий у поля дополняется при реализации явным
указанием на оба варианта использования.

page.tsx`, `VideoContentTab`) видит эти ролики в ОБЩЕМ списке рядом со
штатными — можно отфильтровать по `clientSiteDraftId IS NOT NULL`, если
понадобится отдельная вкладка, но для MVP не обязательно: правки
компонента не требуются, весь путь до модерации/публикации (этап 101)
уже готов и проверен.

### 6.3 Почему скриншот не льётся в Blob на каждом шаге

Скриншот на КАЖДОМ шаге визарда — это, по сути, черновой, потенциально
многократно отменяемый (`/undo`) кадр, который живёт секунды-минуты,
пока пользователь работает, и в процессе может смениться десяток раз.
Заливать его в постоянный Blob на каждый раунд — лишняя запись/лишний
мусор при `/undo`/брошенных черновиках (§10). Вместо этого — `data:`
URL прямо в ответ API (`page.screenshot({ encoding: 'base64' })` —
puppeteer-core отдаёт это без доп. кода), JPEG с невысоким качеством
(тот же уровень, что уже используется для кадров пост-продакшна,
`tutorial-video-frames/...jpg` — см. `tutorial-scenario-runner.service.
spec.ts:267`).

**Это НЕ значит «нигде не персистится, кроме памяти фронтенда» — второй
аудит (§15 п.1) исправил именно это.** Каждый кадр раунда пишется в
`draft.roundScreenshots` (§6.1) — ту же строку Postgres, что и так уже
переписывается на каждой мутации (`steps`/`cookiesEnc`/`version`), а не
в Blob: это принципиально другая по стоимости операция — дописать
элемент в JSON-колонку уже сохраняемой строки почти бесплатно
относительно ЗАВЕДЕНИЯ НОВОГО объекта в Blob (собственный round-trip к
хранилищу, собственный путь, собственная судьба при `/undo`/удалении
черновика). Довод «не копить лишние Blob-объекты на каждый черновой
кадр» остаётся в силе для Blob конкретно; он не был доводом против
персистентности вообще — то, что раньше жило ТОЛЬКО в оперативной
памяти вкладки фронтенда, тихо терялось при перезагрузке страницы
посреди визарда, и предпросмотр (экран 3, §11) после такой перезагрузки
не мог показать полную ленту. Фронтенд по-прежнему МОЖЕТ кэшировать
кадры у себя ради мгновенного, без лишнего запроса, рендера экрана 3
сразу после «Готово» — но это больше не единственная копия: `GET
/site-tutorial` (§5.2) в любой момент отдаёт `roundScreenshots`
целиком.

Граница, где скриншоты попадают в Blob (а не только в Postgres), —
РОВНО ОДИН момент, `/finish` (§5.2), и ровно ПО ОДНОЙ причине:
предпросмотр серии скриншотов до начала генерации (по прямому
предложению владельца продукта) — и пользователю (экран 3), и позже
оператору (админка, §5.2) нужна одна и та же, устойчивая, доступная по
прямой Blob-ссылке серия кадров, а не JSON-колонка черновика, которая
удаляется вместе с ним. `/finish` теперь берёт `screenshots` НЕ из тела
запроса (клиент их больше не присылает — второй аудит, §15 п.1: сервер
уже сам знает эти кадры доподлинно, доверять присланному клиентом
списку — лишний и небесплатный риск рассинхрона), а из уже накопленного
`draft.roundScreenshots`, и заливает их в Blob как есть. Это НЕ то же
самое, что «/finish запускает пост-продакшн» — залить уже готовые кадры
в Blob дёшево (просто переложить существующий JPEG), запустить
настоящую сборку через внешний ffmpeg-api дорого (§4.3 TMA-спеки, §9) —
эти два шага разведены по времени намеренно (найдено аудитом §14 п.2,
закреплено здесь): `/finish` только копит и замораживает, сборку
по-прежнему запускает исключительно `PATCH .../approve` (§5.2).

## 7. Обработка логина

### 7.1 Два варианта, предложенных владельцем продукта — и их цена

Пользователь предложил (буквально) два способа: (а) тестовые
логин/пароль, (б) вход «например через iframe» с последующим
кешированием куки. Оба разбираются здесь честно, с одной важной
технической оговоркой по варианту (б) — уже проговорена и закрыта
владельцем продукта, см. §7.4 и итоговый реестр §13.

**(а) Тестовые логин/пароль.** Прямая реализация: два `fill`-шага
(логин, пароль) + один `click` (кнопка входа), в точности как любой
другой экран визарда (§5.2, эндпоинт `/login` вместо общего `/step` —
единственная разница в том, что введённые значения дополнительно
шифруются и сохраняются в `draft.credentialsEnc`, а не проигрываются
один раз и забываются). Это НОВАЯ поверхность хранения чужого секрета
в проекте (в §11 старого черновика это уже отмечалось как «не
маленькая задача») — здесь она сведена к ровно тому же паттерну,
что уже есть для OAuth-токенов каналов выгрузки (`token-crypto.ts`,
`CHANNEL_TOKEN_KEY`, AES-256-GCM), просто новый столбец вместо новой
криптосхемы.

**(б) «Через iframe».** Буквальная реализация — `<iframe src="https://
сайт-заказчика.com/login">` внутри ТМА — работает НЕ на всех сайтах:
подавляющее большинство современных страниц входа отдают заголовок
`X-Frame-Options: DENY/SAMEORIGIN` или CSP `frame-ancestors 'self'`
именно для защиты от clickjacking — браузер тогда отказывается
отрисовать iframe вообще (пустой белый прямоугольник, не ошибка,
которую можно поймать программно заранее — только после факта, что
пользователь увидел пустой iframe). Это ограничение браузера, а не
нашего кода — обойти его на уровне iframe нельзя в принципе (весь смысл
заголовка — не дать встроить страницу в чужой домен).

Технически эквивалентная ПО РЕЗУЛЬТАТУ идея, которая ДЕЙСТВИТЕЛЬНО
работает независимо от `X-Frame-Options` сайта заказчика: не встраивать
чужую страницу как iframe, а **транслировать наш собственный headless-
Chromium** как последовательность скриншотов (тот же `PageExploration.
screenshotDataUrl`, что уже используется для остального визарда) и
пересылать клики/ввод пользователя обратно в реальную страницу через
Puppeteer (`page.mouse.click(x,y)`/`page.keyboard.type(...)`) — с точки
зрения пользователя ощущается как «форма входа прямо здесь», а
технически это тот же браузер, что уже открыт для всего остального
визарда, просто вместо структурированных `fill`/`click`-по-селектору
шагов — прямые координатные клики по картинке. Это не запрещено ничем
техническим, но требует того самого «живого» браузера между запросами,
от которого сознательно отказались в §5.1 ради serverless-совместимости
— то есть либо (i) отдельная инфраструктура с постоянным процессом
(не Vercel Function — противоречит текущей архитектуре прода,
`doc/DEPLOYMENT.md`), либо (ii) более дешёвый суррогат — держать сессию
живой ТОЛЬКО на время самого логина через короткий поллинг с
привязкой к инстансу (не гарантированно на serverless, ненадёжно) —
оба варианта существенно дороже по инфраструктуре, чем всё остальное
это ТЗ.

**Решение:** оба варианта строятся вместе, одной поставкой (владелец
продукта подтвердил — «Фаза 2 сразу», без ожидания подтверждённого
спроса на MVP). Вариант (а) — тестовые логин/пароль — базовый путь для
обычной формы «логин + пароль + кнопка». Вариант (б) — «интерактивная
удалённая сессия браузера» — полностью спроектирован ниже, в §7.4:
конкретная, реализуемая архитектура, требующая одного нового
постоянного сервиса (не Vercel Function, площадка уже выбрана — Dokploy,
§7.4.9). Он строится НЕ как замена кредам, а как отдельный путь для
случаев, где обычная форма логина в принципе не проходит без живого
человека: капча, 2FA/одноразовый код, вход через чужой SSO (Google/
Facebook кнопка), биометрия/passkey — см. §7.4.0, почему это сужает (и
одновременно оправдывает) объём работы. Оба пути нужны с первой
поставки: без live-сессии часть сайтов заказчиков (любой с капчой/2FA/
SSO) была бы просто не поддержана.

Кеширование куки (то, что пользователь просил «сохраняем в Кеше») —
побочный эффект `/step` и `/login` — `draft.cookiesEnc` (§6.1) — просто
не отдельная фича входа, а внутренняя оптимизация каждого раунда. §7.4
переиспользует то же поле для результата live-сессии.

### 7.2 Куки как ускоритель раунда, не как замена кредов

`draft.cookiesEnc` восстанавливается перед КАЖДЫМ шагом (§5.1) —
избавляет от необходимости заново идти по всей цепочке `goto`+клики с
начала черновика при каждом следующем действии (переигровка с нуля
работала бы тоже правильно, но дороже: N шагов туда-обратно на каждый
следующий шаг вместо одного восстановления куки + один `goto` на
`lastUrl`). Это чисто перформансная роль — источник правды по-прежнему
`draft.steps`.

### 7.3 Финальная сборка — креды проигрываются буквально, не куки

При постановке в пост-продакшн (`/finish` → одобрение оператора → сборка,
§8.3) используется НЕ `cookiesEnc` (куки истекают, могут быть привязаны к
IP/User-Agent сессии восстановления — ненадёжны для отложенной пересборки),
а буквальное повторное исполнение шагов логина из `draft.steps` со
значениями из `draft.credentialsEnc` — то есть тот же самый честный вход,
просто выполненный ещё раз, свежей сессией. Это устраняет целый класс
багов «протухшие куки» и делает финальную сборку идемпотентной —
пересобрать ролик (например, после правки оператором) можно сколько
угодно раз тем же способом.

### 7.4 Live-интерактивная сессия входа — полный дизайн

Проработано по прямому запросу владельца продукта («проработать
live-login любым удобным и высокорезультативным способом») — ниже не
набросок, а конкретная архитектура. Владелец продукта подтвердил:
«Фаза 2 сразу» — реализуется вместе с MVP §7.1 варианта а, а не после
него, одной первой поставкой (§13 закрывает этот вопрос).

#### 7.4.0 Зачем это на самом деле нужно — уточнение объёма

Обычная форма «логин + пароль + кнопка войти» полностью закрывается
вариантом (а) — двумя `fill`-шагами и одним `click`, без всякого
«живого» браузера. Настоящая причина, по которой этого недостаточно
для ЛЮБОГО сайта заказчика — три класса форм входа, где между вводом
пароля и попаданием за экран логина стоит шаг, который принципиально
нельзя описать заранее детерминированным `fill`/`click`, потому что его
содержимое узнаётся только в моменте и требует живого человека:

- **капча** (reCAPTCHA/hCaptcha/Cloudflare Turnstile и т.п.) —
  результат каждый раз новый, автоматическое решение — либо покупной
  сервис обхода капчи (отдельный НЕ рассматриваемый здесь вопрос —
  скорее всего прямо запрещённый условиями использования капчи и
  самого сайта заказчика), либо живой человек;
- **2FA/одноразовый код** (SMS/приложение-аутентификатор/email-код) —
  код существует секунды-минуты и физически недоступен нашему серверу;
- **вход через чужой SSO** (кнопка «Войти через Google/Facebook») —
  уводит на страницу входа ДРУГОГО домена, где нужен реальный, уже
  залогиненный аккаунт живого человека, а не автоматизация.

Значит live-сессия — не более дорогая версия обычного логина, а
единственный способ вообще пройти ИМЕННО эти три случая. Это сужает
(и одновременно оправдывает) объём: не «стримить весь визард», а
«дать человеку разово вмешаться в конкретной точке, которую автомат в
принципе пройти не может» — короткая, ограниченная по времени сессия,
не постоянная инфраструктура на весь визард.

**Четвёртый класс — уже не про логин вообще (найдено аудитом §14 п.4,
принято как документированное ограничение, не задача на реализацию).**
Список выше — капча/2FA/SSO — не исчерпывает всё, что может
заблокировать автоматизацию: сайты за коммерческим bot-management
(Cloudflare Bot Management, DataDome, Akamai, PerimeterX и т.п.) умеют
фингерпринтить именно headless Chromium/Puppeteer (по `navigator.
webdriver`, паттернам таймингов, отсутствию реальных сигналов курсора и
т.д.) и блокировать ДО любого явного шага логина — не только на форме
входа, а на любой странице сайта. Ни MVP (креды), ни live-сессия
(§7.4.2 — тот же headless Chromium, просто под управлением живого
человека, а не скрипта) это не решают: подмена отпечатка браузера
(stealth-плагины и т.п.) — гонка вооружений против конкретных
провайдеров защиты, хрупкая и, для части таких провайдеров, прямо
нарушающая их условия использования — сознательно НЕ входит в объём
этого документа. Решение — честно документированное ограничение, а не
тихая недоработка: если сайт заказчика блокирует автоматизированный
доступ на уровне защиты от ботов, `/explore`/`/step` возвращают понятную
ошибку («этот сайт блокирует автоматизированный доступ — инструмент
здесь бессилен») вместо неопределённого зависания/непонятного таймаута.

#### 7.4.1 Почему это не укладывается в модель §5.1

§5.1 сознательно отказался от «живого» браузера между запросами ради
serverless-совместимости, заменив его переигровкой шагов с нуля на
каждый раунд. Для ввода логина/пароля это работало (сам текст полей
пользователь набирает в ОБЫЧНОМ HTML-поле нашего интерфейса — ввод
идёт не в реальную страницу заказчика, а к нам, и улетает на целевой
сайт одним `fill`+`click` уже готовым значением). Для капчи/2FA/SSO
такой трюк невозможен по конструкции: пользователь должен видеть и
взаимодействовать с РЕАЛЬНОЙ отрисованной страницой заказчика
(картинки капчи, экран согласия чужого SSO) в реальном времени, а
не с промежуточной формой, которую мы сами нарисовали. «Переигровка с
нуля на раунд» не масштабируется до раунда «на каждое движение мыши» —
холодный старт Chromium (~3с, `headless-chromium.ts`) на КАЖДОЕ
нажатие клавиши при вводе капчи/кода — неюзабельно. Единственный
честный выход — держать один экземпляр браузера открытым НА ВРЕМЯ ВСЕЙ
live-сессии (минуты, не миллисекунды), а значит — вне модели Vercel
Function с её невозможностью гарантировать, что следующий запрос
попадёт в тот же прогретый инстанс.

#### 7.4.2 Архитектура: отдельный постоянный сервис-реле

Новый пятый деплоймый пакет монорепо (рядом с `backend`/`frontend`/
`admin`/`landing`) — условно `live-login-relay/`: маленький Node-процесс
(не NestJS, не Prisma — намеренно минимальная поверхность), который
живёт ПОСТОЯННО (не serverless), на любой площадке с постоянными
контейнерами (та же модель, что уже есть в проекте для локальной
разработки — `docker-compose.dev.yml` — просто теперь и в проде, а не
только локально; конкретная площадка выбрана и подтверждена владельцем
продукта — **Dokploy**, обоснование в §7.4.9, реестр решений §13).

**Браузер реле — не `@sparticuz/chromium-min`.** Тот пакет
специально заточен под холодный старт с распаковкой в `/tmp` на каждый
serverless-инстанс (§2/§5.1) — для постоянного контейнера это лишний
шаг. Удачно, что `resolveHeadlessBrowserLaunchPlan()`
(`backend/src/common/headless-chromium.ts:143-156`) уже содержит ГОТОВУЮ,
но сейчас мёртвую ветку именно под этот случай — системный Chromium по
`PUPPETEER_EXECUTABLE_PATH`, с комментарием в самом файле «флаги для
системного Chromium в Docker-образе (если он когда-либо понадобится
локально — на Vercel этой ветки не будет)». Она понадобилась — просто
не локально, а в этом новом сервисе: та же идея (системный Chromium по
`PUPPETEER_EXECUTABLE_PATH`) переносится в `live-login-relay`.

**Уточнение (детализация `doc/LIVE-LOGIN-RELAY-SPEC.md` §6): НЕ
буквальным импортом `common/`.** Первая версия этого абзаца говорила
«переиспользует эту же функцию как есть, импортируя `common/`» — на
практике невыполнимо: `live-login-relay/` собирается отдельным Docker
build context (ниже в этом же разделе — «у сервиса нет ни Prisma, ни
остальных сервисов монорепо», §7.4.9), а `COPY` в Dockerfile не может
взять файл за пределами своего build context, не расширив его на весь
монорепо целиком — что как раз стирает то самое разделение, ради
которого каталог заводится отдельным. Вместо импорта — своя маленькая
копия РОВНО той части (`DOCKER_CHROMIUM_ARGS`, дословно те же 9 флагов)
и своя минимальная функция запуска, без кэширующего резолвера
(`launchPlanPromise`) — та мемоизация существует специально под
serverless-повторное использование тёплого инстанса, а у постоянного
контейнера `PUPPETEER_EXECUTABLE_PATH` статичен с момента старта, кэш
ей ничего не даёт. Полная детализация — `doc/LIVE-LOGIN-RELAY-SPEC.md`
§6, включая точный код. Запускается в Docker-образе с предустановленным
Chromium (`doc/LIVE-LOGIN-RELAY-SPEC.md` §11 — Debian slim + `apt-get
install chromium`, а не сторонний базовый образ) и переменной
`PUPPETEER_EXECUTABLE_PATH`, выставленной в самом Dockerfile.

#### 7.4.3 Протокол: CDP screencast + dispatch, не HTTP-поллинг скриншотов

`puppeteer-core` даёт доступ к низкоуровневому CDP через
`page.target().createCDPSession()` — независимо от прикладного API
Puppeteer, это тот же протокол, которым сам Chrome DevTools рисует
удалённый инспектор. Реле использует:
- `Page.startScreencast` — Chromium сам присылает новый JPEG-кадр по
  CDP при перерисовке экрана (событие `Page.screencastFrame`), а не
  мы дёргаем `page.screenshot()` по таймеру — ниже задержка, не нужно
  гадать с частотой опроса;
- `Input.dispatchMouseEvent`/`Input.dispatchKeyEvent` — события от
  пользователя (движение мыши, клик, нажатие клавиши), присланные с
  фронтенда, ретранслируются в РЕАЛЬНУЮ страницу через CDP, а не через
  `page.mouse.click(x,y)` высокого уровня (то же самое по сути, но CDP
  напрямую — меньше слоёв между вводом и результатом).

Оба конца соединены через WebSocket МЕЖДУ БРАУЗЕРОМ ПОЛЬЗОВАТЕЛЯ И
РЕЛЕ НАПРЯМУЮ (не проксируется через наш NestJS/Vercel — постоянный
видеопоток через serverless-функцию не имеет смысла ни по архитектуре,
ни по биллингу Vercel, который считает время исполнения функции).
Фронтенд рисует полученные кадры на `<canvas>`, переводит клики/
нажатия внутри `<canvas>` в координаты страницы и шлёт их туда же по
WS — с точки зрения пользователя это неотличимо от честного iframe
(которого технически не может быть, §7.1), а на деле — управление
нашим собственным браузером, просто без задержки на HTTP round-trip к
serverless-функции на каждое движение.

**Практический риск, который стоит явно отметить, а не замалчивать:**
перевод координат клика на `<canvas>` в координаты страницы внутри
Chromium требует учитывать масштаб (реальный размер вьюпорта страницы
может не совпадать с размером `<canvas>` на экране пользователя,
особенно на мобильных устройствах — ТМА работает внутри Telegram,
разные экраны) и `devicePixelRatio`. Известный класс багов у любого
инструмента такого рода (remote-debugging просмотрщики, noVNC-подобные
инструменты) — не блокер, но нужно тестировать на реальных телефонах,
не только на десктопной отладке.

#### 7.4.4 Жизненный цикл сессии и безопасность

1. Фронтенд просит НАШ backend (не реле напрямую) начать live-сессию:
   `POST /projects/:projectId/site-tutorial/live-login/start` (под
   `TelegramIdentityGuard`, проверка владения проектом — как и все
   остальные эндпоинты §5.2).
2. Backend вызывает реле с общим секретом (тот же приём, что
   `CRON_SECRET`/`cron-secret.ts` — заголовок вида `X-Relay-Secret`,
   не публичный вызов): `POST {LIVE_LOGIN_RELAY_URL}/sessions` с телом
   `{ startUrl: draft.lastUrl, allowedOrigin: draft.baseUrl }`. Реле
   поднимает `launchHeadlessBrowser()` (§7.4.2), переходит на
   `startUrl`, открывает CDP-сессию, возвращает `{ sessionId,
   streamToken }` — `streamToken` одноразовый, короткоживущий (аналог
   `fixture-token.ts` — не про личность пользователя вообще, только
   «есть право говорить с этой конкретной сессией реле в ближайшие N
   минут»).
3. Backend отдаёт фронтенду `{ sessionId, streamToken, relayWsUrl }`.
   Фронтенд соединяется с реле НАПРЯМУЮ по WS с этим токеном — реле
   ничего не знает про Telegram-личность/Prisma, только проверяет
   токен своей собственной короткоживущей памятью (никакой БД в реле
   вообще не требуется — минимальная поверхность намеренно).
4. **Доменный замок здесь — прозрачность, не блокировка (поправка,
   внесённая детализацией `doc/LIVE-LOGIN-RELAY-SPEC.md` §9).** Первая
   версия этого пункта была внутренне противоречива: утверждала, что
   «реле отклоняет любую навигацию за пределы `allowedOrigin`», и тут
   же — оговоркой про SSO ниже — что «не блокирует переход целиком».
   При детализации выяснилось, что активно ПРЕПЯТСТВОВАТЬ навигации
   через CDP либо требует поддерживаемого списка легитимных сторонних
   доменов (SSO-провайдеры, платёжные 3-D Secure шлюзы — заведомо
   неполный список), либо сводится к запоздалому детекту-и-откату
   постфактум, который не даёт защиты сверх и так уже нужной финальной
   проверки. **Решение:** реле НЕ блокирует и не откатывает навигацию
   во время live-сессии вообще — единственная точка контроля остаётся
   ровно там, где и была изначально верно специфицирована, в §7.4.5
   ниже: `finalUrl` (где пользователь нажал «Готово, я вошёл»)
   проверяется на принадлежность `draft.baseUrl` НА СТОРОНЕ BACKEND при
   завершении сессии — ушёл не туда, откуда должен был выйти, — явная
   ошибка «похоже, вход не завершён», а не тихий успех. Возможность
   зайти куда угодно ВО ВРЕМЯ сессии — не дыра, а прямое следствие
   того, что за рулём живой, зрячий человек (§7.4.0 — весь смысл
   live-сессии в том, чтобы дать человеку вмешаться там, где автомат не
   может); роль реле — чисто транспортная прозрачность
   (`{type:"navigated", url}` на каждую навигацию, чтобы фронтенд мог
   показать текущий домен и человек сам заметил неладное), не
   программное принуждение.

   Отдельная, специально оговорённая оговорка (остаётся в силе, теперь
   без противоречия с абзацем выше): SSO-вход (Google/Facebook, §7.4.0)
   ПО СМЫСЛУ уводит на чужой домен (accounts.google.com и т.п.) — сам
   факт временного визита стороннего домена ВНУТРИ live-сессии не
   нарушает инвариант §8.1, потому что тот инвариант проверяется только
   на выходе из сессии: успешной она считается, только если сессия
   заканчивается возвратом на `allowedOrigin` (иначе логин не
   засчитывается, п.7.4.5 ниже) — и только этот момент когда-либо
   фиксируется как `draft.baseUrl`/используется дальнейшими `goto`-
   шагами сценария, а не сам факт временного визита.
5. Жёсткий потолок по времени: например 3 минуты стены + автозакрытие
   после 60с без единого события ввода (тот же принцип «сфейлиться
   громко, ограничить стоимость по конструкции», что уже применён в
   `MAX_SCENARIO_STEPS`/`LAUNCH_FAILURE_COOLDOWN_MS` в этом же проекте).

#### 7.4.5 Завершение сессии и передача результата обратно в черновик

Пользователь жмёт «Готово, я вошёл» во фронтенде, когда видит, что
попал за экран логина. Фронтенд вызывает НАШ backend (не реле):
`POST /projects/:projectId/site-tutorial/live-login/complete
{ sessionId }`. Backend запрашивает у реле результат — `GET
{LIVE_LOGIN_RELAY_URL}/sessions/:id/result` → `{ cookies, finalUrl }`
— и закрывает сессию на реле. Реле собирает `cookies` НЕ через
`page.cookies()` без аргументов — тот CDP-вызов по умолчанию отдаёт
куки только текущего URL страницы, а для SSO-варианта (п.4 выше)
именно куки СТОРОННЕГО домена (accounts.google.com и т.п.), с которого
только что ушли, могут быть нужны для последующего тихого обновления
сессии на `allowedOrigin` (найдено аудитом §14 п.5: буквальное чтение
§7.4.4 п.4 «SSO временно разрешён» само подразумевает, что куки с того
домена тоже могут понадобиться, а исходная формулировка это не
учитывала) — реле собирает куки со ВСЕХ доменов, с которыми сессия
взаимодействовала (весь cookie jar браузерного контекста, не только
текущей страницы), и шифрует все. Дальше:
- `finalUrl` проверяется на принадлежность `draft.baseUrl` (см. оговорку
  п.4 выше про SSO — если пользователь закрыл сессию, всё ещё находясь
  на чужом домене логина, это ошибка, а не успех — фронтенд должен явно
  сообщить «похоже, вход не завершён», а не молча принять чужие куки);
- `cookies` шифруются (`token-crypto.ts`, тем же способом, что и
  `credentialsEnc`) в `draft.cookiesEnc` (переиспользуется то же поле,
  что уже используется как перформансная оптимизация раунда, §7.2 —
  здесь оно временно становится источником правды, см. §7.4.7 про
  честную границу этого решения);
- `draft.lastUrl = finalUrl`;
- в `draft.steps` дописывается не буквальная последовательность
  fill/click (бессмысленно для интерактивно пройденной капчи/2FA/SSO —
  её нельзя детерминированно воспроизвести), а маркерный шаг вида
  `{ kind: 'assertVisible', selector: '<элемент, доказывающий, что мы
  за экраном входа>' }` плюс явный флаг на самом черновике,
  `requiresLiveLoginReplay: true` (новое поле `ClientSiteTutorialDraft`,
  §6.1) — честно фиксирует «этот сценарий нельзя пересобрать полностью
  автоматически, см. §7.4.7».

**Дописав это, backend НЕ отвечает сразу `{sessionId}`-квитанцией — он
тут же выполняет ОБЫЧНЫЙ раунд по модели §5.1** (найдено вторым аудитом,
§15 п.2: без этого шага ответ `/live-login/complete` не содержал вообще
никакого `PageExploration`, а визарду нечем было бы продолжить — экран 2
(§11) не может отрисовать форму/кандидатов на следующей странице без
свежих `elements`, и у неё не было бы кадра для `roundScreenshots`/
предпросмотра): свежий `launchHeadlessBrowser()` → восстановить только
что сохранённые `cookiesEnc` → `page.goto(finalUrl)` → снять
`PageExploration` (скриншот+элементы уже АВТОРИЗОВАННОЙ страницы) →
закрыть браузер. Именно ЭТОТ раунд, а не сама live-сессия, пополняет
`stepsPerRound` (числом `1` — ровно один маркерный `assertVisible`-шаг)
и `draft.roundScreenshots` (§6.1) — так live-вход становится
полноценным раундом визарда наравне с `/explore`/`/step`/`/login`, а не
исключением, выпадающим из общей модели раунд↔кадр (§15 п.3). Ответ
`/live-login/complete` — тот же по форме `PageExploration`, что и у
`/step`, только сам маркер шага — `assertVisible`, а не `fill`/`click`.

#### 7.4.6 Что попадёт в итоговый ролик — рекомендация: ничего из самой сессии

Технически можно было бы записать саму live-сессию (кадры CDP-
скринкаста) и вклеить как часть финального обучающего видео. Осознанно
**не рекомендуется** для MVP этой фичи:
- кадры капчи/2FA неизбежно содержат то, что не должно попадать в
  публикуемый (§4.6/§4.11 TMA-спеки) ролик — настоящий одноразовый
  код, реальный email/номер телефона в подсказке 2FA, экран согласия
  чужого SSO-аккаунта;
- это отдельный, немаленький риск-ревью на модерации (§8.3), которого
  проще избежать архитектурно, чем полагаться на то, что оператор
  всегда его заметит.

Итоговое видео просто монтируется как раньше: последний кадр «до»
(страница логина) → первый кадр «после» (уже с восстановленными
куками) — без склейки самого процесса входа. Живой человек тратит
минуту на капчу/2FA один раз при записи черновика, и это не отражается
в самом видео вообще — ролик показывает только то, что ЗА входом, что
и было целью обучалки.

#### 7.4.7 Честная граница: финальная сборка live-логина не идемпотентна

§7.3 объясняет, почему креды (вариант а) проигрываются заново при
КАЖДОЙ сборке видео, а не полагаются на кешированные куки — так
надёжнее и не имеет проблемы протухания. Для live-сессии (капча/2FA/
SSO) это **невозможно** — нет детерминированного способа заново пройти
капчу без человека. Значит при `requiresLiveLoginReplay: true`
финальная сборка (§8.3, после одобрения) обязана использовать
СОХРАНЁННЫЕ куки `draft.cookiesEnc` напрямую (`page.setCookie(...)`
перед `runScenario()`), **принимая риск**, что чужая сессия к моменту
сборки уже истекла. Если истекла — сборка обязана явно упасть с понятной
причиной («сессия входа устарела, нужно повторить live-вход»), а не
тихо собрать ролик с шагов ПОСЛЕ логина на неавторизованной странице.
Практическое следствие для UX: `/finish` (§5.2) для черновика с
`requiresLiveLoginReplay: true` должен предупреждать пользователя, что
пересборка (например, после правки оператором) может потребовать
повторить live-вход — честно, а не как будто это тот же уровень
надёжности, что у кредов.

#### 7.4.8 Тарификация и защита от злоупотреблений

Постоянный контейнер с Chromium дороже по устройству биллинга, чем
Vercel Function (плата за контейнер-секунды владения, не только за
исполнение) — live-сессия гейтится строже, чем обычный шаг визарда:
тот же `PlanFeature siteTutorial` (§9), плюс отдельный дневной лимит
именно на live-сессии на пользователя (реле — общий ограниченный
ресурс на всех пользователей продукта одновременно, не изолированный
по инстансам, как serverless-функции — нужен и общий потолок
одновременных сессий на реле, отдельно от лимита на пользователя).

#### 7.4.9 Новые сущности инфраструктуры (для `doc/DEPLOYMENT.md` при реализации)

- Новый пакет `live-login-relay/` — свой `package.json`/Dockerfile, вне
  `backend`/`frontend`/`admin`/`landing`.
- Переменные окружения backend: `LIVE_LOGIN_RELAY_URL`,
  `LIVE_LOGIN_RELAY_SECRET` (по аналогии с `CRON_SECRET`/
  `FFMPEG_API_BASE_URL` — опциональная интеграция, отсутствие которой не
  валит старт приложения, просто делает live-сессию недоступной, кнопка
  «показать страницу входа как есть» во фронтенде скрывается/
  дизейблится, если backend сообщает, что реле не настроено — тот же
  принцип мягкой деградации, что уже описан для `CHANNEL_TOKEN_KEY` в
  `token-crypto.ts`).
- Переменная окружения реле: `PUPPETEER_EXECUTABLE_PATH` (уже
  поддержана существующим кодом, §7.4.2).
- **Хостинг реле — выбран.** По прямому требованию владельца продукта
  («площадка та, что поддерживает деплой docker compose нативно») —
  проверено предметно (см. §13, п.1), не по памяти:
  - **Railway — НЕ подходит**, несмотря на репутацию «удобного деплоя
    из Docker»: официальная документация прямо говорит, что Railway
    **не запускает `docker-compose.yml` напрямую** — каждый сервис из
    Compose-файла нужно вручную пересобрать как отдельный Railway-сервис
    (`docs.railway.com/guides/docker-compose`). Это ровно тот случай
    «выглядит нативно, а на деле рерайт конфигурации», которого просил
    избежать владелец продукта.
  - **Подходят реально** (загрузил `docker-compose.yml` как есть, без
    переписывания под свой формат) — self-hosted PaaS поверх обычного
    VPS: **Coolify** и **Dokploy** (открытый исходный код, бесплатны,
    платите только за сервер), а также **Portainer**/**Easypanel**/
    **CapRover** тем же классом решения.
  - **Решение владельца продукта: Dokploy.** Подтверждено явно
    («Dokploy — идеальный вариант»), Coolify упомянут выше только как
    отклонённая альтернатива того же класса — не как запасной план.
    Для одного небольшого сервиса (реле — один процесс, не сложный
    многосервисный стек) у Dokploy Compose — «первоклассный примитив»
    (нативнее, чем у Coolify, где поддержка Compose ощущается вторичной
    поверх остальной модели), и заметно легче по накладным расходам на
    скромном VPS.
  - Практическое следствие: `live-login-relay/docker-compose.yml`
    (отдельный, свой — не тот же файл, что `docker-compose.yml`/
    `docker-compose.dev.yml` проекта, у сервиса нет ни Prisma, ни
    остальных сервисов монорепо) деплоится на Dokploy как есть, без
    адаптации под формат платформы — то, ради чего этот класс
    инструмента и выбран. Dokploy — «вы сами администрируете
    Linux-хост»: патчи ОС/бэкапы/инциденты остаются на владельце
    продукта, тем же способом, что уже верно для текущего Docker Compose
    локальной разработки этого проекта. Практический план: небольшой
    VPS (провайдер — на усмотрение владельца продукта, этот документ его
    не выбирает — единственное требование Dokploy к хосту — поддержка
    Docker) → установка Dokploy одной shell-командой (его стандартный
    способ установки) → импорт `live-login-relay/docker-compose.yml`
    как есть через UI Dokploy → `PUPPETEER_EXECUTABLE_PATH` и
    `LIVE_LOGIN_RELAY_SECRET` (общий с backend, §7.4.4) задаются в
    переменных окружения сервиса там же.

#### 7.4.10 Более дешёвый вариант без нового сервиса — и почему это не рекомендация

Рассмотрен и осознанно отклонён: попросить пользователя войти на
сайте заказчика в СВОЁМ обычном браузере (вне нашего приложения) и
вручную скопировать куки (через DevTools) обратно к нам. Отклонено —
это хуже по всем осям сразу: просить рядового пользователя продукта
копипастить сырые сессионные куки — заметно худший UX, чем всё
остальное в этом документе, и больший риск случайной утечки/ошибки
(вставил не то, вставил в чужой черновик), чем любая часть дизайна
выше. Оговорка сохранена как честная запасная позиция на случай сбоя
реализации (Фаза 2 уже решена — «сразу», §13), а не как альтернативный
план: если постоянный сервис-реле (§7.4.2) на практике окажется
неприемлемым по стоимости/срокам, более здоровый откат НЕ в сторону
копипаста кук, а в сторону временного сужения охвата — остаться на
варианте (а) и явно сообщать «капча/2FA/вход через Google на этом сайте
пока не поддерживаются», тот же принцип, что уже применён во всём
остальном этом документе (§7.1 — явное решение не делать буквальный
iframe, §9 — явные лимиты), а не более слабая версия live-сессии с
худшим UX.

## 8. Безопасность и согласие

### 8.1 Доменный замок

`draft.baseUrl` фиксируется на первом `/explore` и проверяется резолвером
(§5.3) на КАЖДОМ последующем `goto` — переход за пределы исходного origin
запрещён на уровне валидации, не только на словах в промпте (тот же
принцип, что уже сформулирован в §11.2 п.6 старого черновика, просто
роль «кто согласился на этот домен» переходит от оператора,
заводящего запись вручную, к самому пользователю, вводящему ссылку —
согласие остаётся явным действием, просто другого человека).

**Уточнение объёма замка — совпадение origin, а не registrable domain
(найдено аудитом §14 п.7).** `§5.3`'s `resolved.origin !== new
URL(baseUrl).origin` — точное совпадение схемы+хоста+порта. У обычного
интернет-магазина/SaaS реальный клиентский путь часто пересекает
поддомены ОДНОГО и того же бизнеса (`shop.example.com` →
`checkout.example.com`/`accounts.example.com`) — при строгом
origin-замке такой переход технически «выход за пределы `baseUrl`» и
будет отклонён резолвером посреди обычной (не live) записи, даже
если весь трафик остаётся внутри домена, на автоматизацию которого
пользователь и давал согласие. Решение: замок остаётся строгим
СЕГОДНЯ (MVP) — расширение до «тот же registrable domain» (eTLD+1,
через библиотеку вида `tldts`/`psl`, НЕ наивное сравнение хвоста
строки — `evil-example.com` не должен проходить как «тот же домен»,
что и `example.com`) явно вынесено как первое расширение объёма ПОСЛЕ
MVP, не блокер запуска: строгий origin — самый безопасный default,
цена — пользователь с многодоменным сайтом упрётся в отказ резолвера
раньше, чем ожидал, и увидит понятную причину (`ok:false, reason`,
уже предусмотрено §5.3), а не тихий провал.

**СДЕЛАНО** (находка Т-4 `docs-tz/AUDIT-Client-Site-Tutorial-Landing.md`).
Замок сравнивает регистрируемый домен — `assertSameSite`
(`client-site-tutorial/draft-rounds.ts`), список публичных суффиксов из
`tldts`, с `allowPrivateDomains: true`. Приватная часть списка здесь
принципиальна: без неё `alice.github.io` и `bob.github.io` имеют один
регистрируемый домен `github.io`, и запись с сайта одного человека
уезжала бы на сайт другого; то же для `*.myshopify.com`,
`*.vercel.app` и прочих платформ, где сайт заказчика — это поддомен.
Схема и порт по-прежнему обязаны совпадать. Хост без регистрируемого
домена (IP, `localhost`) сравнивается точно, как раньше.

Вместе с расширением добавлена вторая половина проверки, без которой
оно было бы дырой. Пока сравнение было точным, любой редирект на
другой хост отклонялся, и адрес, на который он вёл, до §8.2 не
доходил. Теперь редирект на соседний поддомен разрешён — значит
владелец домена мог бы завести `internal.example.com` → 10.0.0.5 и
получить раунд против нашей внутренней сети. Поэтому при СМЕНЕ ХОСТА
после перехода адрес проверяется `assertPubliclyRoutableUrl` заново,
как если бы его ввели руками (`assertStillInside`).

### 8.2 SSRF

`assertPubliclyRoutableUrl()` (§2) — обязательный вызов перед КАЖДЫМ
`goto`, не только первым: since self-service means the target is
whatever URL a paying customer types, this becomes essential defensive
infrastructure rather than opt-in (§2). Редиректы внутри целевого домена
на сторонний non-public адрес (маловероятно на практике, но дёшево
проверить) — та же логика `fetchPubliclyRoutable()` с ручной обработкой
хопов, применённая ВНУТРИ `page.goto` невозможна напрямую (Puppeteer сам
следует редиректам на уровне сети браузера, не через наш `fetch`) —
**решено (закрывает §13 п.6): делать всегда.** После КАЖДОГО `goto`
(и на `/explore`, и на каждом `/step`) — `page.url()` проверяется на
принадлежность тому же origin (доменный замок §8.1) И повторно
прогоняется через `assertPubliclyRoutableUrl(page.url())`. Решение
без реальной альтернативы, а не компромисс: сам вызов — один DNS-резолв
(миллисекунды) на фоне уже идущего запуска Chromium (секунды) — цена
неотличима от нуля, а цена пропуска — рабочая SSRF-дыра именно в том
месте, ради которого весь §8.2 существует. Максимальный профит здесь —
не платный выбор, а устранение риска репутационного/юридического
инцидента (наш сервер, отправленный третьей стороной на внутренний
адрес их или чужой инфраструктуры) почти бесплатно.

### 8.3 Одобрение оператором остаётся обязательным

Self-service снимает барьер «оператор вручную заводит `baseUrl`»
(§11.2 п.6 старого варианта), но НЕ снимает нужды проверить готовый
ролик перед показом — по двум независимым причинам, обе актуальны
именно из-за self-service: (1) пользователь мог случайно (или намеренно)
записать шаг, который на сайте заказчика сделает что-то необратимое
(оформит настоящий заказ, отправит письмо), и видео с этим шагом не
должно молча уйти в публикацию; (2) чужой сайт в кадре — потенциально
чужой брендинг/данные, и решение «публикуем от имени продукта» — по-
прежнему решение оператора, тем же принципом, что уже стоит на
штатной обучалке (§4.6/§4.11 TMA-спеки — «ничего не публикуется
автоматически»). Отсюда `ClientSiteTutorialDraftStatus.PENDING_REVIEW`
(§6.1): `/finish` НЕ ставит сразу в пост-продакшн, а ждёт `PATCH .../
approve` (аналог существующего одобрения `costly`-сценариев, §4.11) —
только после этого запускается сборка кадров/видео.

Текстовый эвристический стоп-лист (по видимому тексту кликнутой кнопки:
«оплатить», «удалить», «подтвердить заказ», «pay», «delete», «confirm
order» и т.п.) добавляется на уровне `/step` — если пользователь выбрал
кнопку с таким текстом, `/step` не отклоняет действие полностью (это
испортило бы легитимный кейс «а мне и нужно показать процесс оплаты
как часть обучалки»), а возвращает предупреждение в ответе
(`PageExploration.dangerWarning?: string`), чтобы фронтенд показал явное
«вы уверены?» перед тем, как шаг реально выполнится на настоящем сайте
заказчика — то же соображение «проверяемое кодом, а не только просьбой
к модели», что уже применено в этапе 99 этого же проекта (фильтр
`video`-действий консультанта, `actions.ts`).

**Реализовано на этапе 112** (`danger-words.ts`) с одной поправкой к
месту, где живёт метка. `PageExploration.dangerWarning` — это поле
ответа на УЖЕ ВЫПОЛНЕННЫЙ `/step`, то есть само по себе оно опаздывает:
заказ к тому моменту оформлен. Но список кнопок с их видимым текстом
визард отдаёт клиенту РАУНДОМ РАНЬШЕ — в `elements[]` предыдущего
ответа. Поэтому метка ставится в первую очередь там
(`PageElement.danger`): «вы уверены?» показывается в момент ВЫБОРА
кнопки, до отправки запроса, не тратя ни раунда суточного лимита, ни
запуска Chromium на сам вопрос. `dangerWarning` на раунде остался и
заполняется по факту нажатия — он нужен не для вопроса, а для оператора
при модерации. Сервер по-прежнему НИЧЕГО не блокирует.

Список намеренно короткий и состоит из действий, а не из тревожных слов
вообще, и совпадение считается только с начала слова: без этого
«Неоплаченные заказы» в меню сайта давали бы предупреждение на каждом
раунде, а предупреждение, которое горит всегда, перестают читать.

## 9. Тарификация и лимиты

Headless-сессия (Chromium + сеть до чужого сайта) — не бесплатна по
времени выполнения serverless-функции, даже без вызовов ИИ внутри
сценария. Добавляется:
- `PlanFeature` `siteTutorial` (`common/plans.ts`, тот же паттерн, что
  `brandManifest`/`avatarLipsync`) — какие тарифы допускают этот вид
  проекта вообще;
- лимит на число шагов в одном черновике (по аналогии с
  `MAX_SCENARIO_STEPS = 30` в `scenario-steps.types.ts` — то же число
  или отдельная константа, если владелец продукта захочет другой
  потолок для интерактивной записи, где шагов реалистично меньше, чем
  в ИИ-генерации) — тот же потолок заодно ограничивает и рост
  `draft.roundScreenshots` (§6.1/§15 п.1): раундов физически не может
  быть больше, чем шагов, так что предел на строку БД тоже фиксирован;
- лимит на число активных черновиков на пользователя — 1 незавершённый
  на проект уже обеспечен `@unique` на `projectId` в §6.1.

**Решение: число ПРОЕКТОВ типа `CLIENT_SITE` на пользователя НЕ
ограничивается** (закрывает §13 п.3) — та же модель, что уже действует
для `SINGLE`/`LINE` (искусственного потолка на число проектов в продукте
сегодня нет вообще). Максимальный профит — это ровно тот случай, где
запрет на большее число проектов прямо режет выручку: агентство/фрилансер,
ведущий обучалки для нескольких сайтов-клиентов одновременно — ЦЕЛЕВОЙ,
не краевой сценарий этой фичи (self-service, любой платящий пользователь).
Искусственный потолок «3 проекта на аккаунт» не защищает ни от чего, чего
не защищает уже заложенный по-сессионный лимит ниже — он просто выгоняет
самых активных (=самых платящих) пользователей к конкуренту либо на
второй аккаунт. Стоимость контролируется не числом проектов, а тем, что
реально стоит денег — самими headless/live-сессиями:
- дневной лимит НА ПОЛЬЗОВАТЕЛЯ на число `/explore`+`/step`-раундов
  (метрика уже посчитана в §5.1 как «холодный старт Chromium на раунд»
  — реальная цена);
- дневной лимит НА ПОЛЬЗОВАТЕЛЯ на число live-сессий (§7.4.8 — уже
  спроектирован отдельно, эти сессии дороже обычного раунда);
- общий потолок ОДНОВРЕМЕННЫХ live-сессий на всё реле (§7.4.8) — общий
  ресурс, не персональный, нужен независимо от лимита на пользователя.

**Решение по учёту стоимости (закрывает §13 п.5): отдельная метрика,
не растворяется в плоском `PlanFeature`.** Заводится собственный
счётчик использования (аналог `AiUsage` по форме — своя таблица/строка
расхода на каждый headless-раунд и каждую live-сессию, но НЕ через
`common/ai-pricing.ts`/`AiOperation`, так как здесь нет вызова ИИ) —
попадает в ту же вкладку «Расходы», что и остальные метрики продукта.
Максимальный профит здесь — не сиюминутный, а в горизонте: плоский
`PlanFeature`-флаг «включено/выключено» скрывает фактическую предельную
стоимость на пользователя, и при росте нагрузки маржа тихо схлопывается
у самых активных (=самых ценных) клиентов первой — именно там, где
терять её больнее всего. Отдельная метрика с первого дня — это ровно
та же информация, которая уже сегодня доступна для ИИ-операций через
`AiUsage`, и она открывает то, чего плоский флаг не даёт вообще: увидеть
реальную себестоимость по пользователю/по плану и позже вводить платные
надбавки за объём (доп. live-сессии, доп. проекты и т.п.) осознанно, а
не вслепую.

## 10. Очистка при удалении проекта

`ProjectService.deleteProject()`/`purgeSoftDeletedProjects()`
(`backend/src/modules/project/project.service.ts:259,302`) уже
физически удаляет `Project` (мягкое удаление → отложенное жёсткое, тот
же цикл, что и `ProductItem`). `ClientSiteTutorialDraft.projectId` с
`onDelete: Cascade` (§6.1) удаляется автоматически строкой БД —
дополнительного кода не требуется. `TutorialVideoAsset`, УЖЕ собранные
из такого черновика (§6.2, `clientSiteDraftId`) — мягкая ссылка,
переживает удаление черновика/проекта (тот же принцип, что и у
`scenarioId` для штатной обучалки — видео, уже показанное/
опубликованное, не должно пропадать вслед за черновиком, из которого
оно когда-то собрано).

**Решение (закрывает §13 п.4): видео остаётся, каскад не трогает
`TutorialVideoAsset`.** Максимальный профит здесь однозначен в одну
сторону: если ролик уже одобрен оператором и опубликован в YouTube/
TikTok (§8.3, весь смысл конвейера), это уже живой актив С РЕАЛЬНЫМ
охватом/ссылками вовне — удаление проекта в нашей внутренней панели
никак не отзывает опубликованное видео с площадки, но каскадное
удаление строки `TutorialVideoAsset` сломало бы админке/будущей
аналитике связь с уже существующим, приносящим охват контентом без
единой пользы взамен (экономится одна строка в БД). Тот же аргумент,
что уже был решён владельцем продукта для штатной обучалки — здесь
просто последовательно применён к self-service случаю, а не заново
поставлен под сомнение.

## 11. Фронтенд визарда — экраны

Единый экран `ClientSiteWizard` (или несколько маленьких, монтируемых
по состоянию — решение в духе остальных экранов ТМА, не блокирующее
для этого документа), состояния:

1. **Ссылка.** `Input` (URL) + кнопка «Исследовать» (disabled пока
   пусто/невалидный URL по простой клиентской проверке `new URL(...)`
   до отправки — не заменяет серверную `assertPubliclyRoutableUrl`,
   только UX). По ответу `POST /explore` — либо `Alert` с
   `UNSAFE_EXTERNAL_URL_MESSAGE`-подобным текстом (сервер уже отдаёт
   готовую формулировку, см. `external-url-guard.ts`), либо переход к
   экрану 2.

2. **Экран страницы** (повторяется в цикле). Показывает
   `screenshotDataUrl` как `<img>`, под ним — динамическая форма из
   `elements` (`tag==='input'|'select'|'textarea'`, сгруппированные как
   обычная форма продукта — `Field`+`Input`/`Select`), и отдельно —
   список кандидатов «продолжить с…» (`tag==='button'|'a'` с
   `visibleText`) как `Pills`/список кнопок один-в-один повторяющих
   надписи с реальной страницы. Если `looksLikeLogin === true` — вместо
   обычной формы (или поверх неё, если на странице логина есть другие
   поля) — блок «Понадобится вход» с полями по числу реально найденных
   элементов (любое число, не всегда ровно два — §5.2 обобщил `/login`),
   пометкой «сохраним и будем использовать при каждой пересборке
   ролика» и кнопкой, вызывающей `/login`, а не `/step`. Ненавязчивая
   подпись под ОБЫЧНОЙ (не логин) формой — «эти значения сохранятся
   в сценарии как есть, без шифрования — не вводите сюда реальные
   пароли/платёжные данные вне отмеченных полей входа» (найдено аудитом
   §14 п.3: `draft.steps` — обычный `Json`, не шифруется, кроме того,
   что явно прошло через `/login`; для self-service, где пользователь
   сам гоняет реальный чек-аут своего сайта, вероятность случайно
   ввести настоящие данные не нулевая — дешевле предупредить один раз в
   UI, чем шифровать каждое поле формы). Кнопка «Отмена последнего
   шага» вызывает `/undo` (недоступна сразу после шага live-входа —
   §5.2). Кнопка «Готово» видна всегда, переводит к экрану 3.

   Живой вход — ОТДЕЛЬНАЯ карточка на этом же экране, НЕ часть блока
   «Понадобится вход»: она показывается независимо от
   `looksLikeLogin`, как только backend сообщил `liveLoginAvailable`
   и черновик в статусе `DRAFTING`. Обоснование — в §5.4: под старым
   условием кнопка не появлялась на SSO-логинах, то есть ровно там,
   ради чего живой вход и сделан.

   Параллельно с самим прохождением шагов фронтенд МОЖЕТ копить у себя
   (в памяти состояния визарда, не в `localStorage`) список
   `{ roundIndex, screenshotDataUrl }` — ровно те же кадры, что уже
   пришли в ответах `/explore`/`/step`/`/login`/`/live-login/complete`,
   просто отложенные для мгновенного показа на экране 3 без лишнего
   запроса (по прямому предложению владельца продукта — предпросмотр
   серии скриншотов до начала генерации, §6.3). Это больше НЕ
   единственная копия (найдено вторым аудитом, §15 п.1): та же история
   персистится сервером в `draft.roundScreenshots` (§6.1) на каждом
   раунде и в любой момент восстановима через `GET /site-tutorial`
   (§5.2) — перезагрузка вкладки посреди визарда больше не роняет ленту
   для экрана 3 до одного текущего кадра. `/undo` синхронно выталкивает
   последний элемент локального списка — этот список зеркалит текущее
   состояние `draft.stepsPerRound` (§6.1) один в один по длине, а НЕ
   `draft.steps` (найдено вторым аудитом, §15 п.3: один раунд —
   `/step`/`/login` — может дописать НЕСКОЛЬКО `ScenarioStep` за один
   вызов, но всегда ровно один новый кадр — единица учёта здесь раунд,
   не отдельный `ScenarioStep`).

3. **Просмотр и отправка.** Первое, что видит пользователь на этом
   экране — не форма, а лента миниатюр: горизонтальный `filmstrip`/
   карусель кадров по одному на РАУНД (§15 п.3 — не на каждый
   `ScenarioStep`, форма+клик одного раунда дают ровно одну миниатюру),
   в порядке прохождения; источник — локальный кэш экрана 2, если он
   есть, иначе (после перезагрузки вкладки) — `draft.roundScreenshots`
   из `GET /site-tutorial` (§5.2/§6.3). Тап по миниатюре открывает её во
   весь экран (тот же кадр, что уже показывался live на экране 2 — здесь
   он просто пересобран в общую последовательность, чтобы можно было
   увидеть будущий ролик целиком, а не по одному шагу за раз). Это и
   есть предпросмотр — пользователь видит именно тот набор кадров,
   который ляжет в основу видео при одобрении оператором, ДО того как
   что-либо было сгенерировано (§6.3: генерация — это работа внешнего
   ffmpeg-api, она не запускается на этом экране и не запускается
   `/finish` — только `PATCH .../approve` на стороне оператора, §5.2).
   Под лентой — `Input` для `title` черновика (см. §4.2 — именно
   здесь, не на экране 1, спрашивается название — к этому моменту
   пользователь уже видел сайт и легче назвать проект осмысленно) и
   кнопка «Отправить на проверку», по нажатию которой фронтенд шлёт
   только `{ expectedVersion, title }` — САМИ кадры больше не едут в
   теле запроса (найдено вторым аудитом, §15 п.1: сервер заливает в
   Blob то, что сам же насчитал в `draft.roundScreenshots`, а не то, что
   прислал клиент, — лента на экране 3 показывает пользователю ровно то
   же самое, что уйдёт в Blob, но не является источником правды для
   этого) → сообщение «отправлено на проверку» (соответствует
   `PENDING_REVIEW`, §8.3) → переход на карточку проекта, где виден
   статус. Кнопка «Назад» с этого экрана возвращает на экран 2 к
   последнему пройденному шагу (лента — не более чем витрина уже
   накопленных данных, её просмотр ничего не меняет в `draft.steps`).

## 13. Решённые вопросы (закрыты владельцем продукта / по критерию «максимальный профит»)

Раздел раньше назывался «Открытые вопросы» — все шесть пунктов закрыты
и решения внесены в соответствующие разделы документа; здесь —

   (§7.4.9, Railway/Coolify проверены и отклонены), фаза — **сразу,

   спроса.
2. **Минимальный набор полей `Project` для `CLIENT_SITE`** — закрыто в
   §4.1. Колонки `countryCode`/`currency` остаются `NOT NULL` (без
   миграции), заполняются сервером автоматически (страна последнего
   проекта пользователя, иначе платформенный дефолт) — пользователь их
   вообще не видит на экране создания. Профит: ноль трения на входе в
   платную фичу, ноль миграций, ноль новых null-проверок в остальном
   коде.
3. **Лимит `CLIENT_SITE`-проектов на пользователя** — закрыто в §9.
   Число проектов НЕ ограничивается (та же модель, что у `SINGLE`/
   `LINE`) — ограничивается то, что реально стоит денег: дневные лимиты
   на headless-раунды и на live-сессии, общий потолок одновременных
   live-сессий на реле. Профит: не срезает выручку с целевого сценария
   этой фичи (агентства/фрилансеры с несколькими сайтами-клиентами),
   при этом стоимость под контролем через лимиты, которые бьют именно
   по дорогим операциям, а не по факту владения проектом.
4. **Судьба `TutorialVideoAsset` при удалении проекта** — закрыто в
   §10. Видео остаётся (мягкая ссылка, без каскада) — тот же принцип,
   что уже принят для штатной обучалки. Профит: не рвёт связь с уже
   опубликованным, приносящим охват контентом ради экономии одной
   строки в БД.
5. **Точная тарификация headless-сессии** — закрыто в §9. Отдельная
   метрика расхода (аналог `AiUsage` по форме, без `common/ai-pricing.
   ts` — здесь нет вызова ИИ), не растворяется в плоском
   `PlanFeature`-флаге. Профит: видимость реальной себестоимости на
   пользователя защищает маржу по мере роста нагрузки и открывает путь
   к будущим платным надбавкам за объём — то, чего плоский флаг просто
   не даёт увидеть.
6. **Постфактум-проверка origin после редиректа** — закрыто в §8.2.
   Делается всегда, после каждого `goto`. Профит: цена — миллисекунды
   DNS-резолва на фоне уже идущего запуска Chromium, цена пропуска —
   рабочая SSRF-дыра; выбора здесь по сути не было.

## 14. Аудит (глубокий проход)

Отдельный проход по прямому запросу владельца продукта — перечитан весь
документ построчно на внутренние противоречия, пробелы и техническую
точность утверждений (в т.ч. сверка с реальным кодом: паттерны
конкурентности/индексации/админ-эндпоинтов уже применённые в этом же
проекте, поведение Puppeteer/CDP API). Все найденные пункты уже внесены
в тело документа (правки §5.2/§6.1/§6.2/§7.4.0/§7.4.5/§8.1/§11 выше) —
здесь итоговый реестр находок, в порядке убывания серьёзности.

1. **Гонка на запись при параллельных раундах визарда — не была
   защищена.** Модель §5.1 («восстановить → выполнить один шаг →
   сохранить») ничего не говорила о конкурентности: двойной тап
   «дальше», две открытые вкладки на одном черновике или просто
   медленный ответ + повторный клик — два параллельных `/step`
   читают ОДНО и то же `draft.steps`/`cookiesEnc`, оба считают
   следующий шаг от одной и той же точки, и последняя запись тихо
   стирает первую (реальный шаг пользователя пропадает без следа и
   без ошибки). **Исправлено:** поле `version` (оптимистичная
   блокировка, `UPDATE ... WHERE version=?`) на всех мутирующих
   эндпоинтах (§5.2, §6.1) — первый прецедент такого поля в проекте,
   что явно отмечено там же.
2. **Одобрение оператором было заявлено прозой, но не специфицировано
   эндпоинтом.** §8.3 (до правки) утверждал «`/finish` ждёт `PATCH .../
   approve`», но §5.2 не содержал такого маршрута вообще, а `/finish`
   одновременно описывался как «порождает запись... и ставит в
   очередь... ПОСЛЕ одобрения» — неясно, кто именно выполняет действие
   постановки в очередь и когда. **Исправлено:** явный
   `ClientSiteTutorialDraftAdminController` (§5.2) — `GET
   ?status=PENDING_REVIEW`, `PATCH :id/approve` (тем же паттерном, что
   уже есть у `TutorialScenarioAdminController.approve`), `PATCH
   :id/reject`; `/finish` теперь явно НЕ ставит в очередь сама, только
   замораживает черновик — постановку делает `approve`.
3. **`draft.steps` хранит значения полей форм в открытом виде, кроме
   явно помеченных как логин.** Единственная описанная защита секретов
   (`credentialsEnc`) срабатывала только для того, что прошло через
   `/login` — любое другое значение, введённое пользователем в
   обычную форму через `/step` (в т.ч. потенциально реальные
   платёжные/персональные данные, если пользователь прогоняет вживую
   чек-аут своего же сайта), падает как есть в обычный `Json`-столбец
   без шифрования. Полное шифрование каждого поля — несоразмерно
   объёму фичи (это черновик собственного сайта пользователя, не чужие
   данные третьих лиц). **Исправлено (принятое ограничение, не
   полноценное шифрование):** явное предупреждение в UI экрана 2 (§11)
   — не вводить реальные пароли/платёжные данные вне отмеченных полей
   входа.
4. **Таксономия «капча/2FA/SSO» (§7.4.0) не покрывает коммерческую
   защиту от ботов** (Cloudflare Bot Management, DataDome, Akamai,
   PerimeterX) — та умеет блокировать headless Chromium по отпечатку
   ДО любого явного шага логина, независимо от credentials/live-сессии.
   Обход через stealth-плагины сознательно не рассматривался бы как
   решение (гонка вооружений, риск нарушения условий использования
   провайдера защиты). **Исправлено:** честно задокументированное
   ограничение объёма в §7.4.0 — явная, понятная ошибка пользователю
   вместо неопределённого зависания.
5. **Захват кук live-сессии (§7.4.5) мог молча терять куки SSO-домена.**
   Puppeteer `page.cookies()` без аргументов по умолчанию отдаёт куки
   только текущего URL, а не всего браузерного контекста — при этом
   §7.4.4 п.4 сам же явно разрешает временный заход на чужой SSO-домен
   (accounts.google.com и т.п.), куки которого могут быть нужны для
   последующего обновления сессии. **Исправлено:** реле собирает куки
   со всего контекста (все посещённые за сессию домены), не только
   текущей страницы.
6. **`/undo` был описан как расширение того же механизма, что обычный
   `/step`, хотя технически это другой путь.** §5.1 ввёл восстановление
   по `cookiesEnc` именно ЧТОБЫ не переигрывать всю цепочку с нуля на
   каждый раунд (§7.2 прямо называет полную переигровку более дорогой
   альтернативой) — но куки версионируются только как «последний
   снятый слепок», без истории по шагам, поэтому у `/undo` буквально
   нет данных, чтобы откатить именно один шаг иначе как переигровкой с
   нуля. Отдельно — что происходит с `/undo` сразу после шага
   live-входа (капча/2FA/SSO, §7.4.5), вообще не было оговорено, хотя
   переиграть такой шаг с нуля невозможно по конструкции (§7.4.1).
   **Исправлено:** `/undo` явно документирован как переигровка с нуля
   (не бесплатная, но ожидаемо редкая операция) и явно запрещён (409),
   если последний шаг — маркер live-входа.
7. **Доменный замок (§5.3/§8.1) — точное совпадение origin — не
   учитывал многодоменные сайты.** Обычный интернет-магазин/SaaS часто
   разносит витрину/чекаут/аккаунт по поддоменам одного бизнеса
   (`shop.`/`checkout.`/`accounts.example.com`) — строгий
   origin-замок отклонит переход между ними как «выход за пределы
   `baseUrl`», хотя весь трафик остаётся внутри домена, на
   автоматизацию которого дано согласие. **Решение (не блокер MVP):**
   замок остаётся строгим на первую поставку — понятная, безопасная
   граница по умолчанию; расширение до «тот же registrable domain»
   (eTLD+1 через `tldts`/`psl`, не наивное сравнение хвоста строки)
   явно вынесено как первое послемвп-расширение, отмечено в §8.1.
8. **`/login` (§5.2) был жёстко привязан к ровно двум полям
   (login+password).** Реальные формы входа нередко устроены иначе —
   отдельное поле организации/поддомена, разнесённые на разные экраны
   email и пароль (классический двухшаговый вход) — жёсткая пара не
   покрывает эти случаи, а обходного пути сохранить нужное для
   переигровки при пересборке (§7.3) не было. **Исправлено:** `/login`
   обобщён до списка `{selector, value, sensitive}` произвольной длины
   — помеченные `sensitive` шифруются в `credentialsEnc` как список,
   а не фиксированная пара.
9. **`TutorialVideoAsset.clientSiteDraftId` (§6.2) не получил
   `@@index`**, хотя тот же раздел сам же предполагает фильтр
   `WHERE clientSiteDraftId IS NOT NULL`, а прямой прецедент в этом же
   документе (`PublicationRequest.tutorialVideoAssetId`, этап 101) уже
   завёл индекс под ровно такой же мягкой ссылкой. **Исправлено:**
   `@@index([clientSiteDraftId])` добавлен.
10. **`REJECTED` (§6.1) был тупиковым состоянием.** Ни причины отказа,
    ни пути вернуться к редактированию без полного удаления и записи
    сценария с нуля не было предусмотрено — у существующего в проекте
    прецедента одобрения (`TutorialScenario.approved`) вообще нет
    понятия отказа, так что здесь не на что было опереться, и раздел
    просто не был доведён до конца. **Исправлено:** `rejectionReason`
    на черновике (заполняется `PATCH .../reject`) и `POST .../resume`
    — возврат в `DRAFTING` без потери уже накопленных `steps`.

## 15. Аудит (второй глубокий проход — предпросмотр и раунды)

Второй отдельный проход по прямому запросу владельца продукта
(«Аудит полный и исправления ТЗ») — сфокусирован на разделе,
добавленном последним (предпросмотр серии скриншотов до генерации, §5.2
`/finish`, §6.1 `previewFrameCount`, §6.3, §11 экран 3), и на его стыках
с уже существующими частями документа (§7.4 live-вход, §5.2 `/undo`).
Все найденные пункты уже внесены в тело документа (правки §5.2/§6.1/
§6.3/§7.4.5/§11 выше) — здесь итоговый реестр находок, в порядке
убывания серьёзности.

1. **Источником кадров для предпросмотра был клиент, а не сервер — и
   терялся при перезагрузке вкладки.** Первая версия фичи (эта же
   сессия, до этого аудита) копила `{stepIndex, screenshotDataUrl}`
   ТОЛЬКО в памяти фронтенда и отправляла их в теле `POST /finish`.
   Отсюда два независимых дефекта: (а) перезагрузка вкладки или потеря
   связи посреди визарда стирала всю историю кадров, кроме одного
   текущего (который `GET /site-tutorial` и так перегенерирует) — на
   экране 3 после такой перезагрузки предпросмотр физически не мог
   показать полную ленту, хотя весь `draft.steps` на сервере оставался
   цел; (б) сервер заливал в Blob РОВНО ТО, что прислал клиент, ничем
   не проверяя, что это действительно те кадры, которые соответствуют
   `draft.steps` — рассинхрон (баг фронтенда, устаревший кэш вкладки)
   тихо ушёл бы в предпросмотр оператора неотличимым от настоящего.
   **Исправлено:** новое персистентное поле `draft.roundScreenshots`
   (§6.1) — сервер сам сохраняет кадр на каждом раунде (`/explore`,
   `/step`, `/login`, и теперь `/live-login/complete`, см. п.2 ниже) в
   ту же строку БД, что и `steps`/`cookiesEnc`; `GET /site-tutorial`
   отдаёт эту историю целиком, `/finish` больше не принимает
   `screenshots` в теле — заливает в Blob то, что уже накоплено на
   сервере.
2. **Завершение live-сессии входа (§7.4.5) не производило кадра и не
   давало визарду способа продолжиться.** `/live-login/complete`
   отвечал только `{sessionId}`-квитанцией об успешном сохранении кук —
   ни `PageExploration`, ни строки в `stepsPerRound`/`roundScreenshots`.
   На практике это означало, что после live-входа фронтенду физически
   нечем было отрисовать экран 2 для следующей (уже авторизованной)
   страницы — ни скриншота, ни списка `elements`/кандидатов на клик —
   и в предпросмотре (экран 3) возник бы разрыв ровно в точке, где
   пользователь только что потратил живое время на капчу/2FA/SSO.
   **Исправлено:** `/live-login/complete` теперь сам выполняет обычный
   раунд по модели §5.1 (restore cookies → `goto(finalUrl)` → снять
   `PageExploration`) сразу после сохранения кук, и отвечает тем же по
   форме телом, что и `/step` — live-вход стал полноценным раундом
   визарда, а не исключением из общей модели.
3. **«Раунд» и «шаг» негласно считались одним и тем же — это неверно.**
   Один вызов `/step`/`/login` может дописать НЕСКОЛЬКО записей
   `ScenarioStep` в `draft.steps` (ноль-или-более `fill` + не более
   одного `click`), но всегда производит РОВНО ОДИН новый кадр. Первая
   версия §11 (экран 2) утверждала, что локальный список кадров «один в
   один» зеркалит `draft.steps` по длине — это было прямо неверно уже
   при первом же раунде с двумя и более заполненными полями формы.
   Отдельно, `/undo` был описан как «убирает последний шаг из
   `draft.steps`» — буквально это отрезало бы только последний
   `ScenarioStep` (обычно `click`), оставляя осиротевшие `fill`-шаги
   того же раунда без пары. **Исправлено:** новое поле
   `draft.stepsPerRound` (§6.1, массив количеств шагов на раунд) —
   `/undo` теперь снимает `stepsPerRound.pop()` записей с хвоста
   `draft.steps` целиком (весь раунд, не один шаг), а
   `draft.roundScreenshots`/локальный список кадров экрана 2 явно
   документированы как один-в-один с `stepsPerRound` (по числу раундов),
   а не с `draft.steps` (по числу отдельных `ScenarioStep`).
4. **Повторная заливка кадров в Blob на `/finish` могла оставлять
   «хвостовые» файлы-сироты.** Черновик можно отредактировать после
   `POST .../resume` (после отказа оператора, §6.1) и вызвать `/finish`
   повторно — если к этому моменту число раундов (а значит и кадров)
   СТАЛО МЕНЬШЕ, чем при первом `/finish` (например, пользователь
   отменил несколько шагов через `/undo` и не добавил новых), старая
   заливка `tutorial-video-frames/{draftId}/{n}.jpg` для `n ≥` нового
   `previewFrameCount` никуда не девалась — `/finish` просто
   перезаписывал первые N файлов, не трогая лишние старые. Отдельно,
   `DELETE /site-tutorial` вообще не упоминал очистку Blob — старое
   обоснование в §9/§10 («текущее решение — не складывать [в Blob]»)
   было верно ДО того, как `/finish` стал реально заливать
   предпросмотр, и не было пересмотрено при добавлении этой фичи: после
   хотя бы одного `/finish` удаление черновика оставляло бы уже
   залитые кадры в Blob осиротевшими навсегда. **Исправлено:** и
   `/finish` (перед новой заливкой), и `DELETE` (перед удалением строки)
   теперь явно стирают весь Blob-префикс `tutorial-video-frames/
   {draftId}/*`, если он существует.
