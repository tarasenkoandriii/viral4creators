## 1. Продукт и деньги: партии по каталогу и A/B-варианты

### Д-1.1 (высокая). Статус рендера партии/A-B никто не досматривает — оплаченный ролик недостижим через штатный интерфейс

Единственное место во всём бэкенде, которое реально опрашивает операцию
Veo, переводит статус в `COMPLETE`/`FAILED` и запускает постобработку —
`GenerationService.getVideoStatus()` (`generation.service.ts:523`). У
него один вызывающий — `GenerationController.getVideoStatus`
(`generation.controller.ts:57-61`), а его вызывает только
`useWorkflow.ts`'s `startVideoPolling` (`frontend/src/hooks/useWorkflow.ts:1094-1108`),
привязанный к сессии, **открытой в мастере**.

`CatalogBatchService.getStatus()` (`catalog-batch.service.ts:218-284`) и
`AbTestService.getStatus()` (`ab-test.service.ts:172-235`) для строк в
`GENERATING` делают только пассивное чтение уже сохранённого
`session.data.generatedVideo` — без единого обращения к Veo. Открыть
дочернюю сессию напрямую и тем самым запустить поллинг из прогресс-
экрана партии/A-B нельзя: `openable = item.status === 'DONE' &&
item.sessionId` и в `CatalogBatchProgressScreen.tsx:149`, и в
`AbTestProgressScreen.tsx:148` — а статус не станет `DONE`, пока никто
не откроет сессию. Замкнутый круг. Лично перепроверено чтением всех
перечисленных файлов — подтверждено.

**Сценарий.** Premium-продавец жмёт «Сделать так же для линейки» на 10
товаров. Воркер реально стартует Veo для каждого — деньги списаны,
ролики у Google рендерятся и готовы через минуты. `CatalogBatchItem.status`
навсегда остаётся `GENERATING`, прогресс-экран крутит спиннер каждые 8
секунд бесконечно, товар никогда не становится кликабельным. Оплаченные
ролики физически лежат в Blob, но ни один штатный экран не даёт до них
добраться. 20-минутный дедлайн зависшего рендера (В-2.8, этап 52) не
срабатывает — он живёт внутри того же никогда не вызываемого
`getVideoStatus`. Это тот самый класс «вечно идёт», заново внесённый в
обе новые пакетные фичи независимо от старого пайплайна.

### Д-1.2 (средняя). Перезапуск партии после частичного провала не отличает готовые товары от неудачных

`CatalogBatchService.create()` блокирует только товары, уже занятые
активной партией (`status IN (PENDING, GENERATING)`) — товары `DONE` в
проверку не попадают, а экран запуска отмечает по умолчанию **все**
выбранные товары чекбоксами (`CatalogBatchStartScreen.tsx:51-62`), не
подсказывая, какие уже сделаны. Продавец, довершающий партию после
единичного провала, рискует по невнимательности заново оплатить
генерацию для уже готовых девяти из десяти товаров.

### Д-1.3 (средняя). У партии по каталогу нет точечного повтора одной строки

`CatalogBatchController` даёт только создание всей партии и чтение
статуса — маршрута «повторить одну строку» нет (в отличие от решения,
явно принятого для A/B-варианта). Восстановление после единичного
провала требует полной ручной прокрутки экрана выбора (см. Д-1.2), а не
одной кнопки.

### Д-1.4 (высокая). «Метла» — единственная необратимая из десяти кнопок «Запустить» — не отличается от остальных девяти визуально и не спрашивает подтверждения

Независимо подтверждено тремя из шести параллельных проходов (продукт,
безопасность, фронтенд) и лично перепроверено: в `admin/src/app/cron/page.tsx`
кнопка «Запустить» у всех десяти карточек выглядит и ведёт себя
одинаково; чекбокс `Debug` выключен по умолчанию (`debugByJob[job.jobKey]
?? false`, строка 186). Для `sweep-orphans` тот же чекбокс маппится на
`dryRun` (`admin-cron.service.ts:195-223`) — то есть **первый клик
«Запустить» на карточке метлы без единого дополнительного действия
выполняет настоящее безвозвратное удаление файлов из Vercel Blob**,
единственная из десяти операций, для которой это так. Отличия от
остальных девяти карточек — только мелкая серая подпись под кнопкой; ни
`window.confirm`, ни другого цвета кнопки, ни блокировки по умолчанию
нет, хотя каждый другой деструктивный экран админки этого проекта
(`users`, `library`, `blog`, `payments`, `shared-videos`) использует
`window.confirm()`.

**Сценарий.** Оператор, впервые проверяющий новую вкладку «Кроны» (или
пробующий все десять кнопок подряд, чтобы убедиться, что страница
работает — вероятный первый заход именно потому, что вкладка новая),
кликает «Запустить» на карточке метлы, не заметив мелкую подпись и не
поставив галочку Debug. Удаление уже произошло; функция дебага, которая
могла бы показать «что было бы удалено» без риска, требует явного шага,
ничем на самой кнопке не подсказанного.

## 2. Бэкенд: надёжность и деньги

### Д-2.1 (средняя-высокая). Импорт фида: `addItem()` не идемпотентен — сбой между заведением товара и фиксацией строки создаёт дубликат при следующем тике

`product-feed-import-worker.service.ts:398-454` (`processItem`) сначала
безусловно создаёт `ProductItem` через `projectService.addItem(...)`, а
`resolveItem()` (метит строку `IMPORTED`) — отдельным вызовом со своей
транзакцией, без общей границы с созданием товара. Если `resolveItem()`
падает ПОСЛЕ того, как `addItem()` уже создал товар (обычный
транзиентный сбой БД, не экзотика), строка уходит в `FAILED` с
бэкоффом, но `productItemId` на ней остаётся `null` — признака «товар
уже создан» нет. Следующий тик забирает ту же строку и вызывает
`addItem()` второй раз с теми же данными → дубликат позиции в каталоге.
Для фида в 300+ позиций (лимит поднят до 500 именно ради этой фичи,
этап 68) единичный транзиентный сбой на сотнях строк — статистически
ожидаемое, не гипотетическое событие.

### Д-2.2 (средняя). Создание партии каталога: гонка между разными партиями при пересекающемся списке товаров

`catalog-batch.service.ts:167-186`: список «занятых» товаров читается
`findMany`, затем свободные строки создаются `createMany` в
транзакции — но между чтением и записью нет блокировки, а
`@@unique([batchId, productItemId])` защищает только внутри одной
партии, не между разными. Два быстрых подряд запроса с пересекающимся
списком товаров (двойной клик, две вкладки) оба читают «занято» до
коммита первого — оба создают строку для одного товара в двух разных
партиях, оба запускают платный Veo на один и тот же товар. Тот же класс
гонки, что В-2.2 раунда 3 (закрыт для одиночной генерации через
`claimWork`), не воспроизведённый здесь для межпартийной защиты, хотя
комментарий в коде прямо описывает такую защиту как замысел.

### Д-2.3 (средняя). `CronRunLog` на упавшей «метле» теряет числа уже нанесённого ущерба

`runSweepOrphans` (`cron-jobs.service.ts:322-475`) копит агрегаты
(`totals`, `byScope`) в локальной переменной по ходу цикла и при ошибке
чтения/удаления **перебрасывает** исключение (осознанно, чтобы не
молчать при протухшем токене — сам приём корректен). Но
`AdminCronService.run()` в `catch`-ветке (`:169-186`) пишет `status:
FAILED` без единого числа из `totals` — если на области `sessions`
метла уже реально удалила 500 файлов, а на области `projects` вторая
страница упала по сети, лог утверждает «не выполнилось», хотя реальный
ущерб уже нанесён частично. Повторный клик не опасен сам по себе (метла
стартует с начала, уже удалённые файлы не задвоятся), но искажённая
картина — именно тот сценарий, которого лог должен избегать.

### Д-2.4 (низкая). Молчаливые `.catch(() => undefined)` — три новых места, один опасный

`catalog-batch.service.ts:252-263` и `ab-test.service.ts:197-208` —
опортунистическая синхронизация статуса молча глотает ошибку записи
(безобидно, следующий опрос попробует снова). `product-feed-import-worker.service.ts:569-571`
(`attachCategoryAndPhoto`) — тот же приём, но строка к этому моменту уже
помечена `IMPORTED`, повторной попытки для категории/фото не будет
никогда, если этот `UPDATE` не удался.

### Д-2.5 (низкая, узкое окно). Ретрай партии/A-B после сбоя записи статуса повторно оплачивает GPT-5

Между успешным (уже платным) вызовом `generateVideo()` и завершением
попытки стоит отдельный необёрнутый `UPDATE` статуса строки партии/A-B.
Если этот `UPDATE` падает, `sessionId` уже сохранён, и следующий тик
вызывает `prompt.generatePrompt()`/`seedPrompt` заново для той же
сессии — платный вызов GPT-5 повторяется впустую, а
`session.generationPrompt` перезаписывается текстом, не соответствующим
уже рендерящемуся у Veo видео. Сама оплата Veo не задваивается —
`inFlight`-проверка это закрывает — а GPT-5-вызов такой защиты не
имеет.

## 3. Безопасность

### Д-3.1 (высокая). Импорт фида: SSRF-guard обходится обычным HTTP-редиректом

`assertPubliclyRoutableUrl` проверяется только для исходного URL перед
скачиванием (`product-feed-import-worker.service.ts:180-184` — фид,
`:580-583` — фото строки фида). `fetch` вызывается без `redirect:
'manual'` (подтверждено — этой опции нет нигде в кодовой базе), то есть
по умолчанию проходит до 20 редиректов на любой другой хост, не
пропуская их повторно через guard. Продавец (или атакующий с публичным
доменом) указывает `sourceUrl`, который проходит проверку, а сервер по
этому адресу отвечает редиректом на `169.254.169.254` (облачные
метаданные) или внутренний адрес хостинга — `fetch` уходит по редиректу
без повторной проверки. Тот же дефект независимо у второго вектора
(`photoUrl` любой строки фида).

### Д-3.2 (средняя). Предел размера фида проверяется постфактум, без потокового ограничения

`Content-Length` — заголовок, присылаемый сервером продавца; при
chunked-ответе без него первая проверка размера молча пропускается, а
`res.text()` уже буферизует весь ответ в памяти до второй проверки. При
сжатом ответе `Content-Length` (если есть) отражает сжатый размер, а
`fetch` автоматически разжимает — небольшой сжатый ответ может
развернуться в существенно больший объём до подсчёта. Вредоносный/
скомпрометированный источник (публичный IP, прошедший guard легитимно)
с бесконечным/гигабайтным chunked-ответом без `Content-Length` может
исчерпать память serverless-инстанса воркера импорта.

### Д-3.3 (средняя). Ручной запуск крона из админки — новый, более лёгкий источник гонки суточного денежного потолка

`assertCanSpendUser` — обычный `SELECT`-агрегат без блокировки; окно
между чтением бюджета одной сессией и записью расхода остаётся
открытым (тот же корень, что у В-3.1 раунда 3, до сих пор числится
открытым по «Сверке» раунда 3). Внутри одного тика воркер обрабатывает
строки партии строго последовательно, гонки нет. Но `runBatch()`/
`runAbTestRun()`/`runFeedImportRun()` не имеют джоб-уровневого замка —
только поштучный claim, который не мешает ДВУМ параллельным вызовам
одного и того же джоба обработать разные строки одной и той же партии
параллельно. До этапа 69 источником такого наложения могло быть только
совпадение расписания Vercel Cron; этап 69 добавил лёгкий человеческий
триггер — `POST /admin/cron/catalog-batch-run/run`, ограниченный 5
запросами за 15 секунд на IP (не на джоб). Двойной клик оператора (или
скомпрометированная admin-сессия — В-3.2 раунда 3 всё ещё открыт) может
запустить два параллельных `runBatch()`, которые пройдут проверку
бюджета для разных строк ДО того, как первый успеет записать расход.
Прямого пользовательского вектора нет (у пользователя нет публичного
эндпоинта для старта этих джобов) — это отличает находку от чистого
В-3.1 и снижает вероятность до «оператор кликнул дважды» или
«скомпрометированная admin-сессия».

## 4. База данных и производительность

### Д-4.1 (высокая). Три новые истории в админке воспроизводят закрытый В-4.5 — сортировка по `createdAt` без индекса

`CatalogBatchRun` (только `@@index([projectId])`), `AbTestRun` (только
`@@index([projectId])`), `ProductFeedImportRun` (`@@index([projectId])`
+ `@@index([status, nextAttemptAt])`, но не `createdAt`) — все три
сервиса истории сортируют `orderBy: {createdAt: 'desc'}` с пагинацией.
Ровно та же формула, что раунд 3 нашёл и раунд 4/этап 51 закрыл для
`publication_requests` (33,1 мс Seq Scan против 0,21 мс с индексом на 60
тыс. строк) — та модель несёт отдельный индекс по `createdAt` именно по
этой причине, приём не перенесён ни в одну из трёх моделей, добавленных
тремя этапами позже. Сегодня дёшево (Premium-only, малый объём), дорожает
линейно с ростом использования фич.

### Д-4.2 (средняя). `CronRunLog.getHistory()` без фильтра по джобу не использует свой единственный индекс

Единственный индекс — `@@index([jobKey, startedAt])`; composite-индекс с
`jobKey` слева бесполезен, когда `jobKey` не задан в `WHERE` (дефолтный,
самый частый режим экрана — «последние прогоны по всем джобам
вперемешку»). Планировщик не может использовать префикс без constant-
значения для равенства — тот же класс, что «пустой статус» у
`publication_requests` в замечании раунда 3.

### Д-4.3 (высокая, функциональная). `cron_run_logs` фактически пишется только вручную из админки — настоящий Vercel Cron строку не создаёт никогда

Подтверждено лично: `grep -n "cronRunLog"` находит запись только в
`admin-cron.service.ts` (и его тесте) — ни в `cron.controller.ts`, ни в
`cron-jobs.service.ts` упоминаний нет. Доккомментарий модели в
`schema.prisma` заявляет «одна строка на каждый прогон — и настоящий, по
расписанию Vercel, и ручной, из админки» — код это не делает.
Следствие: `GET /admin/cron/history`, единственная цель вкладки «Кроны»
(наблюдаемость реальных прогонов), структурно не может её выполнить —
там появляются только редкие ручные клики оператора (лимит 5/15с), а не
автоматические прогоны, которых для трёх из десяти джобов — сотни в
сутки. Оператор не может отличить «крон не запускался» от «крон
запускался, просто не логируется». Обратная сторона: реальной WAL-
нагрузки от частых прогонов на эту таблицу нет вовсе — она растёт
только вместе с ручными действиями оператора, то есть медленно.

### Д-4.4 (средняя). Три новые растущие без чистки таблицы не попали ни в TODO, ни в DEPLOYMENT

`runCleanupSessions()` — единственная периодическая уборка строк в
проекте — трогает `Session`, `AdminSession`, `UserSession`,
`alert_states`, `rate_limits`, `analysis_library`, но не
`CatalogBatchRun/Item`, не `AbTestRun/Variant`, не
`ProductFeedImportRun/Item`. Ни один джоб из реестра `JOB_REGISTRY` не
занимается их очисткой. `doc/TODO.md` (закрытый пункт В-4.6, этап 51) и
`doc/DEPLOYMENT.md` знают только про старую четвёрку. `AbTestVariant.promptText`/
`voiceoverScript` — `@db.Text`, полный текст промпта и скрипта озвучки
на вариант, никогда не удаляемый. При текущем масштабе (Premium-only)
цена умеренная — находка в том, что документ-трекер снова не
синхронизирован с фактом, тот же класс ошибки, что раунд 3 явно
предупреждал не повторять.

### Д-4.5 (низкая-средняя). N+1 в двух из трёх новых списков админки — осознанный компромисс, не пересчитанный под составную нагрузку

`admin-catalog-batch.service.ts`/`admin-ab-test.service.ts`: одна
страница истории — `findMany` + `Promise.all` из `pageSize` (обычно 20)
отдельных `groupBy`-запросов, по одному на строку. Осознанное решение
(в коде есть комментарий-ссылка на аналогичный приём в
`AdminMarketingService`), выполняется параллельно, поэтому по времени
ответа не так плохо, как по числу запросов — но не измерено под
composite-нагрузку нескольких одновременных операторов.
`AdminFeedImportService` этого дефекта не несёт — там сводка уже
денормализована в строку запуска.

### Д-4.6 (низкая). Проверка «занятости» товара в `CatalogBatchItem` — без индекса на `productItemId`

`findMany({where: {productItemId: {in: ...}, status: {in: [...]}}})` —
ни `@@unique([batchId, productItemId])`, ни `@@index([status,
nextAttemptAt])` не покрывают `productItemId` отдельно. Сегодня дёшево
(переходное состояние, малая доля строк) — отмечается для полноты, не
требует немедленного действия.
