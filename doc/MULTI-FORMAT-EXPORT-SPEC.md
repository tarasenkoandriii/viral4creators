# ТЗ: автоэкспорт одной генерации под несколько площадок и форматов

**Это документ-предложение, а не описание работающего кода** — тот же
статус, что у `doc/PUBLISHING-AND-VOICEOVER-SPEC.md` до реализации
своих разделов: ТЗ для TODO §III, «Уровень 6», пункт 35 («Автоэкспорт
одной генерации под несколько площадок сразу»). Идея — из обзора рынка
2026-09-09: у Creatify один клик «Clone» сразу отдаёт версии рекламного
ролика под разные платформы и форматы; здесь — как эта идея ложится на
реально существующий пайплайн Veo → постобработка → публикация, а не
абстрактно.

Каждый факт о существующем коде ниже проверен чтением файла и указан с
точным путём — как «что уже есть» в планах предыдущих этапов (см.,
например, план этапа 68). Открытые вопросы владельцу продукта — в конце,
это не формальность: без ответов на них реализация пойдёт не в ту
сторону как минимум дважды (см. §3 и §7).

---

## 1. Контекст

Сегодня формат кадра выбирается **один раз, до генерации**
(`AspectRatioPicker.tsx`, шаг «Генерация») из шести стандартных
(`STANDARD_ASPECT_RATIOS` в `backend/src/common/aspect-ratio.ts:20-27`:
`9:16, 16:9, 3:4, 4:3, 1:1, 4:5`) либо своего W:H. Получить готовый
ролик сразу в нескольких форматах сегодня можно только одним способом —
пройти весь визард заново с другим форматом, то есть заплатить за Veo
ещё раз. Это ровно то умножение стоимости, которого «Уровень 2»
документа (TODO.md) старается избегать во всех прочих пунктах (партии
по каталогу, A/B-варианты, субтитры — везде один дорогой шаг и дешёвое
размножение результата). Формат кадра — единственное измерение, где
сейчас дорогой шаг не переиспользуется.

## 2. Что уже есть (перепроверено чтением кода)

### 2.1. Постобработка — уже умеет резать кадр, но только один раз и только в кадр, выбранный ДО рендера

`backend/src/modules/postprod/postprod.service.ts` — `PostProductionService.start()`
запускается автоматически сразу после успешного рендера Veo (не по
кнопке пользователя) и решает, что делать, из `planWork()`
(строки 415-459): `crop` берётся из `video.aspectRatio` (то, что
пользователь выбрал ДО генерации) — **никакого способа запросить ещё
один целевой формат ПОСЛЕ того, как ролик уже готов, в коде нет.**
Открытый пункт «Переозвучка без новой генерации» в
`doc/PUBLISHING-AND-VOICEOVER-SPEC.md` (строки 91-99) констатирует ту
же дыру для звука: «сейчас озвучка живёт внутри постобработки и
случается ровно один раз, сразу после рендера». Автоэкспорт — тот же
пробел, но для кадра: нужен способ ЗАПУСТИТЬ постобработку повторно, с
другим целевым форматом, над уже готовым файлом, а не только один раз
автоматически.

### 2.2. Сама обрезка — чистая функция, уже размноженная под несколько выходов ЗА ОДИН ВЫЗОВ хостед-сервиса

`backend/src/common/reframe.ts` (`planReframe`) и
`backend/src/common/postprod.ts` (`planPostProduction`) строят ОДНУ
команду ffmpeg под ОДИН целевой формат — но `FfmpegApiService.submit()`
(`backend/src/modules/postprod/ffmpeg-api.service.ts:129-167`) уже
принимает `outputs: string[]` и `commands: string[]` **как массивы**:
`{ input_files, output_files, ffmpeg_commands }` — протокол «один POST,
карта входов, список команд, список имён выходов» изначально рассчитан
на несколько команд за один вызов. Сегодня в проекте он используется
только с массивом из одного элемента (`postprod.service.ts:269-273`:
`outputs: [plan.outputName], commands: [plan.command]`). То есть
**инфраструктура для «несколько форматов одним заходом» уже есть в
протоколе хостед-сервиса — её просто ни разу не попросили сделать
больше одной команды.**

### 2.3. Не все шесть форматов равноценны — они делятся на два «семейства» по тому, из какого нативного кадра Veo их можно вырезать

`backend/src/common/aspect-ratio.ts:121-126` (`veoFrameFor`) — решение,
уже принятое и реализованное на этапе 20: портрет и квадрат
(`9:16, 3:4, 1:1, 4:5`) рендерятся из **одного** нативного кадра `9:16`;
ландшафт (`16:9, 4:3`) — из **одного** нативного кадра `16:9`. Внутри
одного семейства обрезка забирает только верх/низ (в среднем — самая
безопасная зона по композиции, которую и так просит бриф), поперёк
семейств — обрезка забрала бы бо́льшую часть ширины и превратила бы
портретный ролик в почти пустой ландшафтный кадр. Это ключевое отличие
от того, как задачу формулирует TODO (там варианты названы через запятую,
как будто равноценны) — **на практике это два разных по цене и риску
действия**, и ТЗ ниже их разводит (§3).

### 2.4. Деньги за обрезку считаются за вызов, а не за формат

`backend/src/common/ai-pricing.ts` — ставка `ffmpeg-api`: `perCall: 0.01
* USD` (строка 198, помечена `ПРОВЕРИТЬ` — оценка одной обрезки
восьмисекундного ролика). Запись в журнал расходов — тоже за вызов:
`postprod.service.ts:274-278`, `await this.aiUsage.record({ operation:
'reframe', model: 'ffmpeg-api', sessionId })` — один раз на один
`api.submit()`, независимо от того, сколько команд внутри него. Если
несколько целевых форматов уйдут ОДНИМ `submit()` с несколькими
командами (см. §2.2), сегодняшний код журнала спишет **один** `reframe`
за произвольное число форматов — дешевле для пользователя, но, вероятно,
не отражает реальный счёт хостед-сервиса (который почти наверняка
считает по числу команд или по времени рендера). Это открытый вопрос,
не решение (§7.3).

### 2.5. Публикация — один ролик, одна платформа, свой снимок файла

`PublicationRequest` (`schema.prisma:595-...`) — `platform:
PublicationPlatform` (`enum { YOUTUBE, TIKTOK }`,
`schema.prisma:572-575`), `videoUrl`/`videoPathname` — снимок ОДНОГО
файла на заявку (`publication.service.ts:122-124`:
`videoUrl: video.downloadUrl, videoPathname: video.postPathname ?? video.pathname`
— то есть буквально «что бы ни лежало сейчас как готовый ролик сессии,
то и уйдёт»). Файл копируется в собственный путь заявки
(`publications/<requestId>/video.mp4`, `publication.service.ts:270`) —
заявка переживает TTL сессии (§22.5 SPEC). **Сегодня заявки на YouTube
и TikTok для одной и той же сессии получают ОДИН И ТОТ ЖЕ файл**,
каким бы форматом он ни был обрезан — если ролик обрезан в `9:16`
(TikTok), а оператор создаёт вторую заявку на YouTube, туда уйдёт тот
же портретный файл, а не ландшафтный. Это не гипотетический сценарий —
это заведомая точка расхождения формата с площадкой в уже работающем
коде, и автоэкспорт её закрывает как побочный эффект (§6).

### 2.6. Жизненный цикл файлов — новая инфраструктура не нужна

§22 SPEC: у каждого файла один владелец, `sessions/<id>/…` уходит с
сессией по TTL и подметается тем же подметателем, что уже есть
(`sweep-orphans`, префикс `sessions/`). Новые файлы вариантов
достаточно класть туда же по той же схеме имени, что уже использует
`finalPathname()` (`postprod.service.ts:618-629`:
`sessions/<id>/generated-<WxH>.mp4`) — **никакой новой сущности
хранения, нового префикса или нового крона очистки не требуется.**

### 2.7. Фича-гейт — уже есть готовый, семантически подходящий признак

`common/plans.ts:44-52` — `PlanFeature.customAspectRatio`: «Форматы кадра
сверх двух родных для Veo (§16)», сейчас гейтит выбор нестандартного
формата ДО генерации (`LITE.aspectRatios = NATIVE_ASPECT_RATIOS`,
`STANDARD/PREMIUM.aspectRatios = []` — любой). Ровно то же деление
уместно и здесь: автоэкспорт в форматы за пределами двух нативных —
семантически то же самое право, что уже продаётся этим признаком (§7.4).

### 2.8. Открытый вопрос §16.2 наследуется, не решается заново

«Стоит ли при не-нативном формате предлагать ещё и „дополнить полями“
(blur-pad) вместо обрезки» — открыт с этапа 20, не закрыт нигде. Каждый
дополнительный формат, который добавляет это ТЗ, — это ещё один случай,
где встаёт тот же вопрос. Ниже он не решается повторно, а осознанно
вынесен в §7.2 как одно решение сразу на все форматы, а не гейт по
каждому.

## 3. Архитектурное решение — два яруса, а не один список форматов

**Ярус A — дёшево, без нового Veo-рендера.** Целевой формат из того же
«семейства», что уже отрендерен (§2.3): один пакетный вызов
`FfmpegApiService.submit()` с N командами обрезки (по одной на
дополнительный формат ярусa A), один и тот же входной файл (готовый
ролик после текущей постобработки), без звука и субтитров второй раз —
они уже наложены в основном файле. Например, ролик отрендерен в `9:16`
→ доступны дёшево `3:4`, `1:1`, `4:5` (все из того же нативного кадра);
ролик отрендерен в `16:9` → дёшево доступен только `4:3`.

**Ярус B — дорого, второй настоящий рендер Veo.** Формат из ДРУГОГО
семейства (ролик снят в `9:16`, нужен полноценный `16:9` для YouTube, а
не обрезок с потерей почти всей ширины) — это не постобработка, а
**вторая генерация тем же промптом** (`generationPrompt`, уже
одобренным пользователем) с другим `aspectRatio`, то есть повторный
платный вызов Veo. Продуктово это не «автоэкспорт», а «сгенерировать
ещё раз в другом кадре» — разумно предложить отдельной кнопкой, явно
подписанной ценой, а не тихо включить в тот же список чекбоксов, что и
дешёвые форматы яруса A (иначе пользователь одним чекбоксом случайно
закажет полноценный повторный рендер, думая, что это обрезка).

Это ключевое расхождение с формулировкой TODO («один рендер плюс
автоматический кроп... без повторного обращения к Veo, дорогая — честный
перерендер под каждый формат») — там это было названо «дешёвая версия
против дорогой версии одного и того же пункта», в реальности это два
разных пользовательских действия с разной ценой и разным риском по
композиции, и ТЗ ниже описывает их как таковые.

## 4. Данные — расширение `GeneratedVideo`, не новая Prisma-модель

В отличие от партий по каталогу (`CatalogBatchItem`) и A/B-вариантов
(`AbTestVariant`) — там нужен был **крон** с claim/бэкоффом, потому что
каждая строка требует своего вызова GPT-5 и Veo (минуты, независимые
провалы, нужен повтор с бэкоффом на десятках строк). Ярус A — ОДИН
вызов `FfmpegApiService.submit()` с несколькими командами внутри, то
есть **одна** задача с одним `jobId`, которая опрашивается ТЕМ ЖЕ
маршрутом, что и сегодняшняя постобработка (`GET
/api/sessions/:id/generate`, тот же приём, что уже описан в §16.1: «второй
цикл опроса ради одной операции был бы лишним»). Значит новая Prisma-
модель и крон-воркер не нужны — нужно расширить существующую JSON-
структуру `GeneratedVideo` (`common/types/generation.types.ts:48-…`)
массивом вариантов, по аналогии с тем, как в неё уже встроены
`postStatus`/`postJobId`/`postPathname` для одного формата:

```ts
export interface ExportVariant {
  /** Формат W:H — тот же алфавит, что STANDARD_ASPECT_RATIOS. */
  format: string;
  /** Платформа-пресет, если вариант запрошен по имени пресета (§5), а не голым форматом. */
  preset?: 'youtube' | 'tiktok' | 'instagram-feed' | 'instagram-reels' | 'custom';
  tier: 'A' | 'B';
  status: 'pending' | 'complete' | 'failed';
  pathname?: string;
  url?: string;
  error?: string;
}

// В GeneratedVideo:
exportJobId?: string;       // id пакетной задачи ffmpeg (ярус A, один на все форматы)
exportVariants?: ExportVariant[];
```

Ярус B (повторный рендер) технически проще всего описать как **новую
дочернюю сессию** через уже существующий `createFromItem`
(переиспользован `AbTestVariant`, `catalogBatch` — тот же приём, что и
там: снимок промпта, новый `aspectRatio`, обычный платный рендер) — не
изобретать для него отдельную сущность.

## 5. Пресеты платформ — константа в коде, не таблица в базе

По образцу того, как `STANDARD_ASPECT_RATIOS` уже живёт константой в
`common/aspect-ratio.ts`, а не в базе — пресеты меняются с изменением
требований площадок (то есть редко и решением разработчика, не
пользователя):

| Пресет | Формат | Ярус (если основа — `9:16`) | Ярус (если основа — `16:9`) | Публикация уже есть? |
| --- | --- | --- | --- | --- |
| `tiktok` | `9:16` | — (уже есть) | B | да, `PublicationPlatform.TIKTOK` |
| `youtube` | `16:9` | B | — (уже есть) | да, `PublicationPlatform.YOUTUBE` |
| `youtube-shorts` | `9:16` | — (уже есть) | B | нет — тот же `YOUTUBE`, но ролик короче 60 с; сегодня в модели это не различается (см. §7.5) |
| `instagram-feed` | `4:5` | A | B | нет (§7.6) |
| `instagram-reels` | `9:16` | — (уже есть) | B | нет (§7.6) |
| `square` | `1:1` | A | B | нет |
| `classic` | `4:3` | — (уже есть у ландшафта) | A | нет |

«Ярус A» в ячейке означает: дёшево, доступно без нового рендера, если
исходный ролик снят в указанной в шапке колонки основе. Строка
`youtube-shorts` показывает, зачем в `ExportVariant` есть поле `preset`
отдельно от `format`: два разных пресета (`tiktok`/`youtube-shorts`)
дают физически одинаковый файл (`9:16`), но разный человекочитаемый
ярлык и, в будущем, разный лимит длительности.

## 6. Публикация — автоэкспорт закрывает несоответствие формата площадке

Сегодня (§2.5) заявка на публикацию берёт «что лежит», не «что нужно
площадке». После этого ТЗ создание `PublicationRequest` должно сначала
искать среди `exportVariants` готовый вариант нужного семейства для
`platform` (`YOUTUBE` → `16:9`-семейство, `TIKTOK` → `9:16`-семейство),
и только если исходный ролик УЖЕ в нужном семействе — брать его
напрямую, как сейчас. Это не отдельная фича, а исправление существующего
пробела средствами уже спроектированной новой структуры — стоит явно
отметить в реализации как побочный, а не основной эффект, иначе легко
принять решение «не трогать §14 в этом этапе» и оставить дыру
незакрытой.

## 7. Открытые вопросы владельцу продукта

7.1. **Предлагать ли ярус B вообще на первой итерации?** Это по сути
   кнопка «сгенерировать ещё раз в другом семействе формата» с явной
   ценой — самостоятельная небольшая фича, а не часть «автоэкспорта».
   Можно выпустить только ярус A (дёшево, без риска неожиданного
   списания) и оставить B как отдельный пункт бэклога.

7.2. **Обрезка или «дополнить полями» (blur-pad)** для форматов, где
   обрезка теряет много контента (наследует открытый вопрос 16.2 SPEC,
   решается один раз сразу на все форматы этого ТЗ, а не форматом за
   форматом).

7.3. **Как считать деньги за пакетный вызов.** Один `reframe` на весь
   батч (дёшево для пользователя, вероятно не отражает реальный счёт
   хостед-сервиса) или один `reframe` на каждый дополнительный формат
   внутри батча (безопаснее для маржи, требует менять текущую логику
   «один вызов — одна запись в `aiUsage`»). Ставка `AI_PRICE_FFMPEG_*`
   и так уже помечена `ПРОВЕРИТЬ` в коде (§2.4) — имеет смысл заодно
   свериться с реальным прайсом `verygoodffmpeg.com` по числу команд в
   задаче, а не только по числу задач.

7.4. **Фича-гейт.** Переиспользовать `customAspectRatio` (§2.7,
   рекомендация этого документа) или завести отдельный признак —
   например, если продукт захочет продавать автоэкспорт отдельной
   надбавкой, а не включать его в тот же тумблер, что и ручной выбор
   нестандартного формата при генерации.

7.5. **YouTube обычный vs YouTube Shorts.** Сегодня `PublicationPlatform`
   не различает их — оба уходят как `YOUTUBE`. Автоэкспорт впервые
   создаёт формат (`9:16`), физически подходящий только Shorts, а не
   обычному YouTube-ролику той же заявки — стоит ли расширять enum
   третьим значением, или это остаётся вне рамок этого этапа и
   ограничивается только файлом без автопубикации.

7.6. **Instagram/Facebook — только файл или тоже автопубликация?**
   Пресеты `instagram-feed`/`instagram-reels` в таблице §5 сегодня не
   имеют интеграции публикации (`PublicationPlatform` не включает
   Instagram) — в рамках этого ТЗ они дают только скачиваемый файл
   нужного формата, без выгрузки на площадку. Заводить OAuth-интеграцию
   с Instagram/Facebook (Meta Graph API) — отдельный по объёму этап,
   сопоставимый с §14, не входит в это ТЗ.

7.7. **Триггер экспорта — из экрана результата постфактум (рекомендация
   этого документа, ближе к тому, как это делает Creatify) или чек-
   боксами заранее, до самой генерации** («получить сразу три формата
   одним нажатием „Сгенерировать“» — дороже по умолчанию, но ближе к
   формулировке TODO «одной генерации сразу»). Рекомендация — постфактум:
   так пользователь не платит за форматы, которые в итоге не понадобились,
   и это ближе к уже принятому в продукте принципу «постобработка не
   блокирует выдачу и ничего не решает заранее» (§16.1/§15).
