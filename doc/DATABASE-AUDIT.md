Дата первой ревизии: 2026-09-04; дополнения — по мере появления миграций,
последнее от этапа 32. Полный аудит слоя БД по всему проекту — все модели,
все написанные вручную миграции (см. `doc/TELEGRAM-ADMIN.md`, §5, о
том, почему они написаны вручную, а не сгенерированы `prisma migrate
dev`), и весь код, который эти таблицы читает/пишет.

**Главный вопрос, с которого начался этот аудит: существует ли таблица
`User`?** Да. Она создаётся миграцией
`backend/prisma/migrations/20260904060000_telegram_auth/migration.sql`,
объявлена в `schema.prisma` (модель `User`, `@@map("users")`) и — см.
раздел "Как проверялось" ниже — её реальное появление в Postgres со
всеми колонками, индексами и внешними ключами было не просто
прочитано в коде, а проверено запуском настоящих SQL-миграций на
настоящем Postgres 16 в этой же песочнице.

## Как проверялось (не просто чтение кода)

`prisma generate`/`migrate dev`/`validate` в этой песочнице по-прежнему
не работают — перепроверено прямо сейчас: `npx prisma -v` падает с
`403 Forbidden` на `https://binaries.prisma.sh/...` даже с
`PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1` (то есть блокировка не в
проверке checksum, а на весь домен целиком). Это ограничение не новое,
но полезно было убедиться, что оно всё ещё то же самое, а не что-то
изменилось.

Однако в этой же песочнице отдельным пакетом (не через `prisma`) стоит
`psql` и сервер Postgres 16 (`apt install postgresql`, без Docker,
Docker-демон здесь недоступен). Это дало возможность провести
проверку, которая раньше не делалась — реально применить все пять
миграций к чистой базе, а не только прочитать их глазами:

```bash
createdb v2v_audit
psql -d v2v_audit -v ON_ERROR_STOP=1 -f 20260904000000_init/migration.sql
psql -d v2v_audit -v ON_ERROR_STOP=1 -f 20260904060000_telegram_auth/migration.sql
psql -d v2v_audit -v ON_ERROR_STOP=1 -f 20260904090000_user_sessions/migration.sql
psql -d v2v_audit -v ON_ERROR_STOP=1 -f 20260904120000_session_created_at_index/migration.sql
psql -d v2v_audit -v ON_ERROR_STOP=1 -f 20260904150000_drop_redundant_token_indexes/migration.sql
```

Результат: все пять — **без единой ошибки**. После этого `\d users`,
`\d sessions`, `\d admin_sessions`, `\d user_sessions` сверены со
`schema.prisma` колонка-в-колонку — совпадение полное: типы, `NOT
NULL`/nullable, дефолты, первичные ключи, уникальные индексы,
обычные индексы, внешние ключи с правильным `ON DELETE`/`ON UPDATE`.

Дополнительно — функциональный тест, не только структура:

```sql
INSERT INTO users (...) VALUES ('u1', 'dev-123', ...);
INSERT INTO sessions (..., "userId") VALUES ('s1', ..., 'u1');
INSERT INTO admin_sessions (..., "userId", ...) VALUES ('as1', 'u1', ...);
INSERT INTO user_sessions (..., "userId", ...) VALUES ('us1', 'u1', ...);

DELETE FROM users WHERE id = 'u1';

-- Результат:
-- sessions.userId стал NULL (история сессии сохранена, как задумано —
--   Session.user: User? @relation(..., onDelete: SetNull))
-- admin_sessions: 0 строк (каскадно удалилась вместе с пользователем —
--   AdminSession.user: User @relation(..., onDelete: Cascade))
-- user_sessions: 0 строк (та же логика, UserSession.user: onDelete: Cascade)
```

Ровно то поведение, что описано в комментариях `schema.prisma` — не
предположение, а проверенный факт. Это не заменяет накатку на реальную
Supabase (другая среда, PgBouncer, реальные права доступа), но снимает
риск синтаксической ошибки в SQL или расхождения миграций со
`schema.prisma`, который до этого момента был не более чем "написано
по аналогии с уже накатанной первой миграцией и должно быть похоже на
то, что сгенерировал бы сам Prisma".

## Находки

### 1. ✅ ИСПРАВЛЕНО — `AdminSession`/`UserSession` не чистились по расписанию

Тот же класс проблемы, что уже был найден и исправлен для `sessions` в
`VERCEL-READINESS-AUDIT.md` (находка №9) — но тогда ещё не
существовало `admin_sessions`/`user_sessions`, appeared они позже, в
рамках Telegram-логина, и cron-очистку никто не расширил.

Было: обе таблицы чистятся только "оппортунистически" — при каждом
новом логине (`AdminAuthService.pruneExpiredSessions()` /
`TelegramLoginService.pruneExpiredSessions()`, оба `private`, вызываются
только изнутри `devLogin()`/`loginWithTelegram()`). Если админ-панелью
или постоянным логином никто не пользуется какое-то время, истёкшие
строки просто накапливаются вечно — то же самое, из-за чего изначально
и появился cron для `sessions`.

Исправлено: `GET /api/cron/cleanup-sessions`
(`backend/src/modules/cron/cron.controller.ts`) теперь дополнительно
удаляет `admin_sessions`/`user_sessions` с истёкшим `expiresAt`, тем же
самым уже существующим ежедневным вызовом (Vercel Cron,
`backend/vercel.json`) — новый инфраструктурный вызов не понадобился.
Ответ эндпоинта расширен: `{ deletedCount, deletedAdminSessions,
deletedUserSessions }`.

### 2. ✅ ИСПРАВЛЕНО — не было индекса на `sessions.createdAt`

`AdminPanelService.getTelemetry()` (`createdLast24h`/`createdLast7d` —
фильтр по `createdAt >= X`) и `AdminPanelService.listSessions()`
(`orderBy: { createdAt: 'desc' }` с пагинацией) — оба новых для
админ-панели запроса, оба обращаются к `createdAt`, а индекс на
`sessions` был только на `lastActivityAt` (для TTL-очистки) и `userId`.
При текущем объёме данных (MVP) не критично, но при росте таблицы оба
запроса деградировали бы до полного скана.

Исправлено: `@@index([createdAt])` добавлен в `schema.prisma`,
миграция `20260904120000_session_created_at_index` — применена и
проверена тем же способом, что и остальные (см. выше).

### 3. ✅ ИСПРАВЛЕНО — `SessionService.getAllSessions()` без пагинации

`this.prisma.session.findMany()` без `where`/`take` — вернул бы вообще
все строки таблицы разом. На практике не использовался ни одним
контроллером (проверено `grep` по всему `src/`) — судя по комментарию
("for debugging/admin purposes"), метод остался от раннего этапа
разработки и был мёртвым кодом.

Исправлено: метод удалён из `SessionService`
(`backend/src/common/session.service.ts`) — раз он нигде не вызывается,
безопаснее убрать неограниченный по размеру метод целиком, чем оставить
его как соблазн для будущего кода вызвать без пагинации.

### 4. ✅ ИСПРАВЛЕНО — избыточный индекс на `token` у `admin_sessions`/`user_sessions`

Обе таблицы имели одновременно `UNIQUE INDEX ..._token_key` (от
`@unique` в Prisma) и обычный `INDEX ..._token_idx` (от явного
`@@index([token])` в схеме) на одну и ту же колонку — второй избыточен,
Postgres и так использует уникальный индекс для поиска по `token`.

Исправлено: `@@index([token])` убран из обеих моделей в
`schema.prisma`, миграция `20260904150000_drop_redundant_token_indexes`
(`DROP INDEX admin_sessions_token_idx`, `DROP INDEX
user_sessions_token_idx`) — применена и проверена тем же способом, что
и остальные (реальный локальный Postgres 16, все пять миграций подряд
с нуля, `\di` после — остались только `..._pkey`, `..._token_key`,
`..._userId_idx`, дубликата больше нет).

### 5. Проверено, проблем не найдено

- **`connection_limit=1`** в примере `DATABASE_URL` (`backend/.env.example`) —
  корректная, официально рекомендуемая Prisma-практика для serverless
  через PgBouncer в транзакционном режиме (каждый инстанс Vercel Function
  держит свой `PrismaClient`, `connection_limit=1` не даёт ему открыть
  больше одного соединения через пулер одновременно).
- **`id`-колонки без DB-default** (`cuid()`/`uuid()` генерируются на
  стороне Prisma Client, не в Postgres) — согласовано между всеми
  таблицами, включая уже давно существующую `sessions.id`; ничего не
  меняет по сравнению с уже работавшим поведением.
- **Секреты в БД**: токены (`admin_sessions.token`, `user_sessions.token`)
  — случайные 32 байта (`crypto.randomBytes(32).toString('hex')`), не
  обратимы, ни один API-ответ их не возвращает (проверено —
  `admin-auth.controller.ts`/`telegram-login.controller.ts` отдают
  только `expiresAt`, токен уходит исключительно в `httpOnly` cookie).
  `Session.data` не хранит секретов (см. `session.types.ts` — только
  описания видео/промпта/статусов).
- **Каскадное поведение** соответствует комментариям в `schema.prisma` и
  подтверждено функциональным тестом выше: удаление `User` не рвёт
  историю сессий (`SetNull`), но чистит его собственные login-сессии
  (`Cascade`).

## Дополнение: миграция `20260905120000_project_product_brand` (этап 2 плана Товар/Проект)

Шестая ручная миграция — пять новых таблиц (`projects`, `product_items`,
`product_analogs`, `brand_manifests`, `brand_characters`), два enum
(`ProjectType`, `ProductPriceSource`) и две опциональные колонки на
`sessions` (`projectId`, `productItemId`) — по `doc/PRODUCT-PROJECT-SPEC.md`
§5/§7.8/§12. Проверялась тем же способом, что и предыдущие пять, плюс два
новых приёма:

**`prisma validate` всё-таки удалось запустить.** Раньше считалось, что в
этой песочнице не работает ни одна prisma-команда. На деле блокируется
только СКАЧИВАНИЕ `schema-engine` с `binaries.prisma.sh`, а сам
валидатор/форматтер схемы — это bundled WASM внутри пакета `prisma`
(`node_modules/prisma/build/prisma_schema_build_bg.wasm`), сети не
требует. CLI просто проверяет наличие engine-бинарника ДО того, как
понять, что для `validate` он не нужен. Обход — подсунуть заглушку:

```bash
printf '#!/bin/sh\nexit 0\n' > /tmp/fake-schema-engine && chmod +x /tmp/fake-schema-engine
PRISMA_SCHEMA_ENGINE_BINARY=/tmp/fake-schema-engine PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1 \
  npx prisma validate   # → "The schema at prisma/schema.prisma is valid"
# то же самое работает для `prisma format`
```

Заглушка никогда не исполняется (validate/format её не вызывают) — это
НЕ годится для `migrate`/`generate`, тем действительно нужен настоящий
engine. Но синтаксис и связность `schema.prisma` (все relation-поля
парные, все FK ссылаются на существующие поля и т.д.) теперь проверяет
сам Prisma, а не глаза.

**Реальная накатка + проверка семантики FK.** Все шесть миграций
применены по порядку к чистой локальной Postgres 16 (`ON_ERROR_STOP=1`,
ни одной ошибки), `information_schema`/`pg_constraint` сверены со
схемой: 9 FK с правильным `ON DELETE` (`c`/`n`), 15 индексов, оба enum,
`DECIMAL(12,2)` у обоих `price`. И — главное, ради чего писалась схема —
функциональный тест решений §7.8/§12 на реальных строках:

| Действие | Ожидание по ТЗ | Результат |
| --- | --- | --- |
| `DELETE brand_manifests` | персонажи бренда — каскадом; проект ОСТАЁТСЯ, `brandManifestId` → NULL | ✅ |
| `DELETE product_items` | аналоги — каскадом; **Session ОСТАЁТСЯ**, `productItemId` → NULL, снимок в `data.productInformation` не тронут | ✅ |
| `DELETE projects` | товары — каскадом; Session остаётся, `projectId` → NULL | ✅ |
| `DELETE users` | ничего не удаляется, только `userId` → NULL у проектов/манифестов | ✅ |
| `INSERT` без `priceSource` | дефолт `MANUAL` | ✅ |
| `INSERT type='TRIPLE'` | отклонено enum'ом | ✅ (`invalid input value for enum`) |

Строка про `product_items` — самая важная: она и есть доказательство
того, что «Session самодостаточна, данные скопированы снимком, а не
живут по ссылке» (ТЗ §7.8) выполняется на уровне БД, а не только в
комментариях.

Что в этом аудите НЕ проверено (то же, что и раньше): таблица
`_prisma_migrations`, реальная Supabase (другая минорная версия,
PgBouncer, права), и что `prisma migrate diff` сгенерировал бы
байт-в-байт такой же SQL — имена FK/индексов следуют конвенции Prisma
(`<table>_<col>_fkey` / `<table>_<col>_idx`), но это стоит подтвердить
`migrate diff` там, где сеть есть, до первой накатки на прод.

объяснимая и должна меняться без миграций, а таблица на этом этапе
маленькая. Если библиотека вырастет до сотен тысяч строк — переносить
предфильтрацию в SQL по `category`/`audienceGender` (индексы уже есть).

FK `analysis_library.userId → users.id` стоит `ON DELETE SET NULL`:
удаление пользователя не должно уносить разборы — права на них у сервиса
(оферта §5.2), а `userId` здесь только происхождение записи.

`prisma validate` — ок, применена к локальному Postgres 16 тринадцатой по
порядку (итого 14 таблиц).

## Дополнение: миграция `20260907000000_user_plan` (этап 29)

Пятнадцатая ручная миграция — `CREATE TYPE "UserPlan" AS ENUM ('LITE',
'STANDARD', 'PREMIUM')` и две колонки в `users`: `plan` (`NOT NULL
DEFAULT 'LITE'`) и `planSince` (nullable). Новых таблиц нет — итого
по-прежнему **14 таблиц**.

Почему enum, а не строка: набор режимов маленький и меняется редко, зато
опечатка в значении должна ломаться на записи, а не тихо превращаться в
«режим, которого нет». На чтении подстраховка всё равно есть — `planOf()`
трактует любое непонятное значение как `LITE` (ТЗ §23), потому что старая
строка в базе не повод отдать пользователю права, которых у него нет.

`DEFAULT 'LITE'` закрывает миграцию существующих пользователей: все, кто
был заведён до этапа 29, оказываются в бесплатном режиме по умолчанию,
без отдельного UPDATE. `planSince` — только след того, когда режим
поменялся; на права он не влияет и нужен будущему биллингу.

Индекса на `plan` нет намеренно: по режиму не выбирают — его читают у
конкретного пользователя по первичному ключу. `prisma validate` — ок,
применена к локальному Postgres 16 пятнадцатой по порядку.

## Дополнение: миграция `20260907120000_blocking_and_ai_usage` (этап 31)

Шестнадцатая ручная миграция. Две несвязанные вещи в одном файле, потому
что пришли одним требованием: три колонки блокировки в `users`
(`isBlocked` `NOT NULL DEFAULT false`, `blockedAt`, `blockedReason`) и
новая таблица `ai_usage` — итого **15 таблиц**.

`ai_usage` — журнал расходов (ТЗ §26), одна строка на вызов. Решения по
схеме:

- **Деньги — `costMicroUsd INTEGER`, а не `numeric` и не float.** Целые
  микродоллары складываются точно; при ставке Veo $0.40/сек и восьми
  секундах одна строка это 3 200 000 — до предела `int4` (~2147 долларов
  на строку) далеко, а `SUM` в Postgres возвращает `bigint`.
- **`sessionId` без внешнего ключа.** Сессии удаляются по TTL (§22), а
  расход остаётся: удалить его вместе с сессией значит стереть историю
  затрат. Индекс на колонке всё равно есть — по нему считается средний
  расход на сессию.
- **`userId` — `ON DELETE SET NULL`.** Та же причина: расход уже понесён.
  Такие строки видны на вкладке как расход анонимных сессий.
- **`pricingVersion` и `unpriced` в каждой строке.** Без версии нельзя
  объяснить, почему одинаковые вызовы стоят разное; без `unpriced` вызов
  модели, забытой в прайсе, выглядел бы бесплатным.
- **Индексы**: `(userId, createdAt)` — расход пользователя за период,
  `createdAt` — срезы за 24ч/7д/30д, `provider` — разбивка, `sessionId` —
  средний на сессию. Разбивка по операциям и моделям идёт полным
  `groupBy` без индекса: таблица растёт на один-два порядка медленнее
  `sessions`, и заводить индексы под отчёт, который смотрят раз в день,
  преждевременно.

Индекса на `users.isBlocked` нет: заблокированных единицы, а фильтр в
админке идёт по той же выборке, что и остальной список. `prisma validate`
— ок, применена к локальному Postgres 16 шестнадцатой по порядку.

## Дополнение: миграция `20260907180000_ai_usage_cached_tokens` (этап 32)

Семнадцатая ручная миграция — одна колонка `ai_usage.cachedInputTokens`
(`INTEGER NOT NULL DEFAULT 0`). Новых таблиц нет, по-прежнему **15**.

Зачем отдельный счётчик: Gemini и OpenAI отдают повторно использованный

порядку.

### Что снято

`ai_usage(provider)`, `analysis_library(category)`,
`analysis_library(audienceGender)` — под них нет ни одного запроса.
`provider` встречается только в `groupBy` по всей таблице без `where`
(план его не берёт); `audienceGender` вообще не доходит до SQL —
ранжирование по аудитории делает JS после выборки; `category`
используется как `ILIKE '%q%'`, который btree обслужить не может.

Это не поломка, а налог: ~5 МБ на 800 тыс. строк и замедление **каждой
вставки в журнал расходов** — самого горячего пути записи в проекте.

Индексы по FK-колонкам без собственного `where` не трогали: они
обслуживают проверку внешних ключей при удалении родителя.

### Два смысла у `ai_usage.userId IS NULL`

Колонка означала и «вызов был анонимным», и «аккаунт удалили»
(`onDelete: SetNull`). Из-за второго расход удалённого пользователя
мгновенно перетекал в ОБЩИЙ потолок анонимных и выбивал его для всех
остальных. Добавлен `anonymous Boolean`, который ставится ПРИ ВСТАВКЕ и
больше не меняется; существующие строки размечены по текущему владельцу —
другого источника истины для них нет, и на момент миграции он верен.

### Уборка сессий доходит до конца

`cleanupExpiredSessions()` брала 500 строк и честно возвращала `hasMore`,
но по этому флагу никто крон второй раз не дёргал, а расписание суточное:
при 501+ истёкшей сессии в сутки очередь росла навсегда. Теперь крон
делает партии до конца — с потолком в 20 партий и 120 секунд, потому что
на Vercel он живёт 300 секунд, и лучше не доубрать остаток до завтра, чем
быть убитым посередине партии. Именно на предположении «`sessions`
маленькая» держались ещё две находки: телеметрия админки и список сессий.

### Каскад для личного каталога

`projects.userId` и `brand_manifests.userId` переведены с `SetNull` на
`Cascade` — см. §22.6 ТЗ. Библиотека и сессии остаются на `SetNull`
сознательно.

## Дополнение этапа 54: счётчики частоты, происхождение режима, триграммы

Миграция 25 (`20260911090000_rate_limits_plan_origin_trgm`) делает три
вещи одного этапа.

**`rate_limits`** (Б-3.7) — счётчики частоты запросов по ключу
«маршрут|IP», фиксированные окна; тот же приём, что `alert_states`:
состояние в базе, а не в памяти экземпляра, потому что на Vercel
экземпляров много и каждый обнуляется, не досчитав. Один
`INSERT … ON CONFLICT DO UPDATE … RETURNING count` на проверку; на живом
Postgres три параллельных вызова дали 1, 2, 3, следующее окно — 1.
Строки закрывшихся окон (старше часа) убирает суточная уборка; размер —
по числу разных адресов за час, то есть сотни строк.

**`users.planSelfService`** (Б-3.8) — режим, выбранный пользователем
самостоятельно, пока оплата выключена: функции режима доступны, суточный
потолок расхода — как у Lite. Существующие строки получают `false`
(поведение для них не меняется); оператор, назначая режим из админки,
сбрасывает флаг.

**pg_trgm и три GIN-индекса на `analysis_library`** (В-4.9) — `title`,
`category`, `sourceKey`: поиск оператора по подстроке читал таблицу
целиком. Замер на 60 тыс. записей (`v4c_audit3`): редкая подстрока —
**73,9 мс Seq Scan → 0,39 мс Bitmap Heap Scan**; без индекса на
`sourceKey` третья ветка `OR` возвращала план к чтению таблицы, поэтому
индексов три, а не два. Таблице `users` триграммы не нужны: на 3 000
строк планировщик читает её целиком за 2,5 мс против 3,3 мс с
принудительным индексом, и это правильно. Расширение выражено в
`schema.prisma` (`extensions = [pg_trgm]`, preview-флаг
`postgresqlExtensions`), чтобы `migrate diff` в CI видел его, а не считал
