## Критично (ломает продукт на Vercel, а не просто "не оптимально")

### 1. ✅ ИСПРАВЛЕНО — Нет serverless-адаптера для NestJS
Было: `backend/src/main.ts` вызывает `await app.listen(config.port)` —
персистентный HTTP-сервер, который слушает порт вечно, а Vercel так
бэкенды не запускает.

Исправлено добавлением `backend/server.js` — Vercel сам детектит файл
`server.{js,ts,...}` в корне проекта (или в `src/`), который вызывает
`.listen()` при старте модуля, и превращает его в один Vercel Function:
все запросы проксируются в него через внутренний порт, так что
внутренний роутинг Nest (глобальный префикс `api`, все контроллеры)
работает ровно как локально — без `vercel.json`, rewrites или
директории `/api`. Это официальный, framework-agnostic механизм
("Deploy a Node.js server",
`vercel.com/docs/functions/runtimes/node-js#deploy-a-node.js-server`),
я явно свёл его с документацией перед тем, как писать код.

`server.js` — сознательно обычный `.js`, требующий уже
СКОМПИЛИРОВАННЫЙ `dist/main.js` (не сам `main.ts` и не переписанный под
Express-адаптер вариант): DI в Nest держится на
`emitDecoratorMetadata` (см. `tsconfig.json`) — это даёт только настоящий
`tsc`-компилятор (наш `nest build`, он же Vercel Build Command через
`npm run build`), а не esbuild-трансформация, которую Vercel использует
для TS-файлов в zero-config `/api`/`server.ts` — там decorator metadata
не эмитится вовсе, и внедрение зависимостей в контроллеры/сервисы могло
бы просто не срабатывать. Подробное обоснование — в комментарии самого
файла.

`main.ts` не тронут — им по-прежнему пользуются `nest start`/`node
dist/main` для локальной разработки и Docker; `server.js` работает
только на Vercel.

Отдельный `vercel.json` для монорепо-роутинга по-прежнему не нужен —
рекомендация (пункт 5 ниже) остаётся: два отдельных Vercel-проекта
(`backend/`, `frontend/`) на одном репозитории.

### 2. ✅ ИСПРАВЛЕНО — In-memory `SessionService` не переживёт реальный деплой
`backend/src/common/session.service.ts` — обычный `Map` в памяти одного
Node-процесса (`@Injectable({ scope: Scope.DEFAULT })`, посчитан как
`@Global()` в `app.module.ts`). Весь продукт построен на многошаговом
флоу с поллингом с фронта (`GET /analysis`, `GET /generate` — уже видно из
`useWorkflow.ts` и `generation.controller.ts`): один запрос стартует
операцию, следующие несколько запросов её проверяют.

На Vercel нет гарантии, что второй HTTP-запрос попадёт в тот же тёплый
инстанс функции, что и первый — масштабирование, cold start после паузы,
несколько параллельных инстансов у конкурентных пользователей. `Map` живёт
только в памяти конкретного инстанса, поэтому `GET /generate` может
прилететь в инстанс, который никогда не видел соответствующий `POST` —
"Session not found" на ровном месте, случайным образом, не
воспроизводимо локально (там всегда один процесс).

Это не гипотетический edge-case — это то, ради чего вообще существует
Vercel Functions (короткоживущие, множественные, без общей памяти).

Исправлено переводом на Supabase Postgres через Prisma — подробности в
`PRISMA-SUPABASE.md`. Публичный интерфейс `SessionService` не менялся,
так что бизнес-логика в `analysis`/`video`/`prompt`/`product`/`generation`
не переписывалась, только добавлен `await` в местах вызова.

### 3. ✅ ИСПРАВЛЕНО — Fire-and-forget в `analysis.service.ts`
Было:
```ts
// analyzeVideo():
this.performAnalysis(sessionId, session.originalVideo).catch((error) => { ... });
return { analysisId, status: AnalysisStatus.PROCESSING };
```
Ровно та же проблема, что уже разбирали и чинили для видео-генерации
(старый Sora-флоу) — но здесь она оставалась: `performAnalysis` не
`await`-ился, ответ уходил клиенту немедленно, а промис продолжал
работать "в фоне". Vercel не гарантирует, что выполнение функции
продолжится после того, как ответ отправлен — анализ мог просто
оборваться на середине, и клиент вечно поллил бы `PROCESSING`, который
никогда не станет `COMPLETE`.

**Важное уточнение**: предыдущая правка (миграция на Supabase) сделала
`async` только сам callback внутри `.catch(...)` — сам вызов
`performAnalysis(...)` по-прежнему не был `await`-нут в `analyzeVideo()`,
то есть основная проблема сохранялась. Исправлено по-настоящему сейчас:
`analyzeVideo()` вызывает `await this.performAnalysis(...)` напрямую
внутри `try/catch` и возвращает клиенту уже финальный статус
(`COMPLETE`/`FAILED`), а не `PROCESSING`-заглушку. Эндпоинт
`POST .../analysis` соответственно возвращает `200 OK` с готовым
результатом вместо `202 Accepted` для фоновой задачи (`analysis.controller.ts`).
Это безопасно именно потому, что референсные ролики короткие (8–30с) и
укладываются в фиксированные 300с Vercel Hobby.

На фронтенде (`frontend/src/services/api.ts`, `triggerAnalysis`) таймаут
запроса поднят до 280с (был рассчитан на старое "мгновенное" поведение) —
логика поллинга в `useWorkflow.ts` не менялась вообще: она как ждала
`GET /analysis` в цикле, так и ждёт, просто теперь получает `COMPLETE`
на первой же итерации вместо нескольких.

### 4. ✅ ИСПРАВЛЕНО — Продуктовое изображение грузилось напрямую через тело функции
Было: `backend/src/modules/product/product.controller.ts` держал **два**
пути загрузки картинки — правильный presigned-URL (`POST
.../image/upload-url`) и Multer-эндпоинт (`POST .../image/upload`,
`fileSize: 10MB`, файл целиком в теле запроса), а фронтенд
(`uploadProductImage`) вызывал именно второй. Реальное фото товара с
телефона (3-8MB) превышало бы 4.5MB лимит тела Vercel-функции —
`413 FUNCTION_PAYLOAD_TOO_LARGE` систематически, не иногда.

Исправлено: Multer-эндпоинт и связанный с ним метод
`uploadProductImageDirect` в `product.service.ts` удалены полностью,
`MulterModule`/`multer` убраны из `product.module.ts`, неиспользуемый
`@types/multer` убран из `backend/package.json`. `uploadProductImage` во
фронтенде переписан на тот же двухшаговый паттерн, что уже используется
для видео (`uploadVideo`): `POST .../image/upload-url` → `axios.put`
напрямую в хранилище. Presigned-эндпоинт в бэкенде уже существовал и не
менялся — правка была именно там, где была реальная проблема. (На момент
этой правки — в S3; позже, пункт 12, картинка товара вместе с готовым
видео переехали на Vercel Blob, так что сейчас `axios.put` идёт уже
туда.)

## Важно, но не мгновенный крах

### 5. ✅ ДОКУМЕНТИРОВАНО — Нет `vercel.json` / не выбрана схема деплоя монорепо
Backend (NestJS) и frontend (Vite SPA) — разные типы сборки в одном
репозитории. Практичный путь на Hobby — два отдельных Vercel-проекта на
один и тот же git-репозиторий, у каждого свой Root Directory
(`backend/`, `frontend/`), а не один `vercel.json` с rewrites на
монорепо.

Это настройка в дашборде Vercel, не в коде — поэтому "исправление" здесь
не патч, а пошаговая инструкция: см. новый `DEPLOYMENT.md` (Root
Directory для каждого проекта, какие env-переменные куда положить,
разница Production/Preview). `vercel.json` для монорепо-роутинга
(rewrites между `backend/`/`frontend`) по-прежнему не нужен — подтверждено
тем же решением, что и в пункте 1. Один `backend/vercel.json` всё же
появился, но по отдельной причине, не связанной с роутингом — это
конфиг для Vercel Cron Jobs (см. пункт 9 ниже); он живёт внутри Root
Directory backend-проекта и на решение "два проекта вместо rewrites"
никак не влияет.

### 7. ✅ ИСПРАВЛЕНО — `CORS_ORIGIN` была одной жёстко заданной строкой

фронтенда достучаться до бэкенда.

Исправлено: `CORS_ORIGIN` теперь парсится как список через запятую

ИЛИ wildcard-суффикс вида `*.vercel.app`. Так одно значение переменной
одновременно пускает стабильный продакшн-домен фронтенда и любой
preview-деплой. Конкретные значения для Production/Preview — в
`backend/.env.example` и `DEPLOYMENT.md`.

### 9. ✅ ИСПРАВЛЕНО — `cleanupExpiredSessions()` нигде не вызывался
Было: метод существовал в `SessionService`, комментарий гласил "should be

Это ровно совпадает с дефолтным `SESSION_TTL_HOURS=24`. Эндпоинт защищён
`CRON_SECRET` — Vercel сам подставляет его как `Authorization: Bearer
<значение>` при вызове cron job'а (официальный механизм, см.

переменная не задана и проверка просто пропускается. Подробности — в

### 12. ✅ ИСПРАВЛЕНО — S3 и Vercel Blob одновременно, без единого архитектурного решения
Было: в проекте одновременно жили два провайдера объектного хранилища.
Vercel Blob использовался только для референсного видео (транзитом:
загрузили → скачали в Gemini Files API → удалили, `videoController`/
`video.service.ts`), а продуктовая картинка и готовое сгенерированное
видео шли через `S3Service` (`@aws-sdk/client-s3`,
`@aws-sdk/s3-request-presigner`, отдельные `AWS_REGION`/
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_S3_BUCKET`). Это не было
осознанным архитектурным решением — просто S3 появился в проекте первым,
а Blob позже добавили точечно только под один узкий кейс (лимит тела
Vercel-функции для видео, см. пункт 1). После того как появились Supabase
(пункт 2, постоянное хранилище сессий) и Blob для видео, встал резонный
вопрос — зачем вообще два провайдера файлов, если один явно лишний.

Разбор перед решением: на момент проверки (2026-09, документация
`vercel.com/docs/vercel-blob` и `vercel.com/docs/vercel-blob/usage-and-pricing`)
Vercel Blob поддерживает как `access: 'public'` (что уже использовалось
для видео), так и `access: 'private'` сторы — то есть закрытые файлы
технически возможны и на Blob, не только на S3. Единственная реальная
причина держать S3: у Vercel Blob на Hobby-плане есть soft-лимиты
использования (объём хранилища, операции, трафик), при превышении
которых доступ к Blob **блокируется на 30 дней** (не тарификация, именно
блокировка), тогда как S3 — pay-as-you-go без блокировки. Для текущего
объёма трафика проекта это не было признано риском, и было принято
решение: убрать S3 полностью, оставить один провайдер (Blob), все объекты
— `access: 'public'`, тот же режим безопасности, что и у сессий в целом
(в приложении и так нет аутентификации для MVP, см. `specs/`) и что уже
использовалось для референсного видео.

Исправлено:
- `BlobService` (`backend/src/modules/storage/blob.service.ts`) получил
  новый метод `uploadBuffer()` — серверная запись байтов в Blob
  (используется для готового видео от Veo: бэкенд сам скачивает результат
  у Google и пишет его в Blob, браузер тут не участвует). Уже
  существовавшие `createUploadUrl()`/`downloadBuffer()` переиспользованы
  для продуктовой картинки один в один как для видео — новой логики не
  потребовалось.
- `product.service.ts`: `generateProductImageUploadUrl()` теперь просит
  presigned-URL у `BlobService` вместо `S3Service`, сохраняет
  `productImagePathname`/`productImageMimeType` в сессии вместо
  `productImageS3Key`.
- `generation.service.ts`: продуктовая картинка скачивается из Blob
  (`downloadBuffer`) вместо S3 перед тем, как стать первым кадром для
  Veo; готовое видео пишется в Blob через новый `uploadBuffer()` с
  детерминированным путём `sessions/{id}/generated.mp4`
  (`allowOverwrite: true` — повторная генерация для той же сессии
  законно перезаписывает предыдущую попытку по тому же ключу).
- Побочный эффект, упрощающий код: публичный Blob-URL для
  фиксированного пути **не истекает** (в отличие от presigned S3 GET-URL,
  который жил ограниченное время и его приходилось перевыпускать на
  каждый опрос статуса). Поэтому `downloadUrl` теперь сохраняется в
  сессии один раз, в момент загрузки видео в Blob, а
  `getVideoStatus()` при уже завершённой генерации просто возвращает
  сохранённое значение — весь код повторного подписания URL на каждый
  поллинг убран.
- `S3Service` (`backend/src/modules/storage/s3.service.ts`) удалён
  полностью. `@aws-sdk/client-s3` и `@aws-sdk/s3-request-presigner`
  убраны из `backend/package.json` через `npm uninstall` (не руками —
  `package-lock.json` остался консистентным). Блок `AWS_REGION`/

  `Configuration`/`configuration.ts`, `.env`/`.env.example` и списка

- Фронтенд: типы `ProductInformation`/`GeneratedVideo` в

- Попутно найден и удалён `scripts/s3Service.js` — мёртвый, ничем не
