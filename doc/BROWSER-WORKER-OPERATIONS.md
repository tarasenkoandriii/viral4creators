# Автоматический контроль браузерного воркера

Обновлено 13.10.2026. Второй VPS работает по подтверждению владельца. Локальный Docker HEALTHCHECK и сторож worker-watch.sh реализованы в main 7ceab2e; установка сторожа на действующем VPS выполняется через bootstrap --update. 13.10.2026 обновление применено на VPS: сторож установлен, контейнер healthy, fail2ban sshd работает. Централизованный монитор ниже является планом до внедрения и приёмки.

## Что работает без нового задания

Воркер сам забирает задания через подписанный канал. Файл здоровья содержит время записи, browser, running, draining, lastClaimAt, lastError, completed и failed. Docker проверяет его каждые 30 секунд. Health-файл свежий до 60 секунд; claim до 90 секунд, при активном задании/дренаже до 420 секунд. Успешный пустой claim подтверждает связь, но не выполнение клиентского задания. Счётчики процесса сбрасываются после рестарта.

## Локальный сторож установлен на VPS

worker-watch.sh устанавливается как /etc/cron.d/bworker-watch с интервалом 5 минут. Остановленный контейнер поднимается, unhealthy после двух проверок перезапускается, cooldown — 30 минут. Состояние в /var/lib/bworker/status, журнал в /var/log/bworker-watch.log, первая отметка в /var/lib/bworker/first-job; vps-bootstrap.sh --check показывает их. Отметка основана на журнале или completed > 0, поэтому для строгой сквозной приёмки дополнительно нужна запись succeeded в backend. Внешних уведомлений и новых browser/AI заданий сторож не создаёт. Существующее недельное автообновление и немедленное --update описаны в DEPLOYMENT §6.25; обновление fail2ban и сторожа на действующем сервере проверено 13.10.2026.

## Автоматизация следующего этапа

1. Сборщик на VPS раз в минуту читает health-файл и Docker state через локальные средства. Не открывает входящий HTTP-порт, не выдаёт Docker socket приложению и не читает env/секреты. Передаёт по существующему аутентифицированному исходящему каналу только фиксированные поля: время, workerId, buildSha, состояние браузера, количество активных заданий, draining, время успешного claim, счётчики и разрешённую категорию ошибки. Сырые lastError, URL, credentials и пользовательские тексты не передаются. Расширение протокола сначала согласуется с обеими сторонами и покрывается тестами.
2. Backend сохраняет последнее состояние и историю агрегатов с ограничением хранения. В админке показывает online / busy / idle / stale / unhealthy, текущую версию, возраст состояния, очередь и результаты за час, день и неделю. Пустая очередь не является ошибкой. Расходы ИИ при сборе состояния отсутствуют.
3. Диагностический шаг cron раз в 5 минут читает эту информацию и журнал очереди: pending/running/succeeded/failed/cancelled, возраст старейшего задания и последний успешный результат по виду. Не ставит новые задания, не запускает crawl, не пересчитывает embeddings и не рассылает тревоги клиентам. Повторный запрос идемпотентен.
4. Только после трёх подряд плохих наблюдений отправляет операционную тревогу настроенному администратору; дубли подавляются ключом workerId + причина, есть cooldown и отдельное сообщение о восстановлении. Отсутствие заданий не вызывает тревогу. Активное длинное задание и дренаж учитываются, рестарт не выглядит уменьшением общего числа выполненных заданий. Отдельно проверяется, что активный worker принимает разрешённые виды, а не просто живёт.
5. Первую сквозную приёмку закрывает наблюдаемое succeeded реального задания с workerId, видом, временем и buildSha. Если подходящих заданий нет, остаётся pending acceptance. Контролируемый ui-snapshot только собственного verified-сайта может быть запрошен владельцем через штатный API; новый автоматический тест без согласования не создаётся. Развёрнутый сервер и completed из health-файла не заменяют серверную запись результата.

## Приёмка

Проверить здоровый idle, выполнение задания, временный backend outage и восстановление, падение Chromium, остановку контейнера, долгую задачу, дренаж, смену версии, сброс локальных счётчиков, зависшую очередь, неизвестный вид и отключение постановки. Тесты должны подтверждать отсутствие новых browser/AI задач и отсутствие клиентских уведомлений от диагностического cron. Новые секреты и клиентские данные не попадут в отчёт/лендинги.

## Разделение расписаний

Существующие crawl (2 минуты) и analytics (10 минут) создают работу по условиям сайта. Voice descriptor-resolve ограничен сутками для опубликованной версии. Монитор здоровья не является новым расписанием выполнения этих задач. Docker HEALTHCHECK сам не выполняет autoheal: ограниченное восстановление реализовано отдельным worker-watch.sh, две unhealthy-проверки и cooldown 30 минут.
