## 1. Пункт 30 — генерация по сценарию без референсного видео

### 1.1. Контекст

Второй, параллельный текущему путь: не «референс → разбор → товар →
промпт → ролик», а «сценарий → готовый AI-актёр из каталога → ролик».
TODO ссылается на пункт 11 («Шаблоны сцен без референса») как на
недостаточное решение той же аудитории — но пункт 11 сам нигде не
реализован (см. предисловие), так что это ТЗ не расширяет пункт 11, а
проектирует всю ветку с нуля.

### 1.2. Что уже есть (перепроверено чтением кода)

- **Промпт для Veo уже строится текстом**, а не только из разбора
  референса: `GenerationWizard`/`generation.service.ts` собирает
  `generationPrompt` из брифа + данных товара + стиля бренда. Значит
  «нет референсного видео» — это не архитектурный тупик: пайплайн
  генерации промпта и вызова Veo сам по себе не требует, чтобы на входе
  обязательно был разбор чужого ролика. Разбор сегодня — единственный
  ИСТОЧНИК данных для промпта (`sceneBreakdown`, `characters` и т.д.),
  но не жёсткая архитектурная зависимость.
- **Veo сегодня явно не предназначен для говорящей головы с точной
  липсинхронизацией.** Подтверждено дважды: §13 и §15.1
  `PRODUCT-PROJECT-SPEC.md` — в режимах `voiceover`/`dub` бриф прямо
  запрещает кадры говорящих голов, чтобы избежать рассинхрона губ и
  звука. Это не ограничение библиотеки промптов, а признанное
  ограничение самой модели Veo в текущем использовании — пункт 30
  прямо об это упирается: **нужен отдельный видеодвижок для говорящей
  головы**, Veo в сегодняшнем виде для этого не используется и,
  видимо, не подходит.
- **Персонаж как переиспользуемая сущность уже есть — `BrandCharacter`**
  (`schema.prisma`, модель `BrandCharacter`, поля `label`, `photoUrl`,
  `description`) — но это фото + текстовое описание, отправляемое в Veo
  как `referenceImage` (сходство по референс-изображению), а не
  обученная модель лица с точной идентичностью. Для каталога готовых
  AI-актёров (не «этот конкретный человек», а «выберите одного из N
  синтетических персонажей сервиса») эта модель концептуально ближе,
  чем `BrandCharacter`, но по объектам — другая: `BrandCharacter`
  принадлежит одному `BrandManifest` пользователя, каталог актёров п.
  30 — общий для всех пользователей сервиса, ближе к тому, как устроен
  каталог голосов ElevenLabs (`GET /shared-voices`, общий для всех) в
  §1.5 ниже.

### 1.3. Архитектурное решение

Новый модуль `modules/actors/` (по аналогии с тем, как `modules/tts/`
инкапсулирует внешнего провайдера синтеза речи):

1. `ActorCatalogService` — отдаёт список доступных синтетических
   актёров (`GET /actors`) — либо из БД (если каталог собственный, см.
   открытый вопрос 1.6.1), либо проксирует каталог внешнего провайдера
   говорящих голов (если решение — купить чужой движок, а не растить
   свой) тем же приёмом, что `TtsController.voices()` сегодня
   проксирует `/shared-voices` ElevenLabs.
2. Новый шаг визарда **до** текущего «Разбор референса» — «Сценарий без
   референса»: пользователь пишет сценарий сам или получает его от
   GPT-5 (тот же провайдер, что уже генерирует реплики для текущего
   пути — `openai.service.ts`, переиспользуется промпт-паттерн, не
   новый интеграционный код), выбирает актёра из каталога.
3. Рендер говорящей головы — **новый внешний вызов**, не `Veo`.
   Технически это отдельный видеодвижок (лицевая синхронизация текста
   и движения губ) — какой именно, открытый вопрос 1.6.2, вне
   компетенции этого ТЗ решать без сравнения цены/качества
   поставщиков. Результат этого вызова — либо готовый ролик с
   говорящей головой (тогда он идёт в ту же постобработку, что и
   сегодня — обрезка, наложение субтитров, что уже умеет
   `postprod.service.ts`), либо просто говорящая голова на нейтральном
   фоне, которую нужно скомпоновать со сценой отдельно (сложнее,
   вероятно вне первой итерации).

### 1.4. Данные

Новая Prisma-модель `SyntheticActor` (общая для сервиса, не привязана к
пользователю — как каталог голосов):

```prisma
model SyntheticActor {
  id          String  @id @default(cuid())
  label       String
  previewUrl  String?  // превью-кадр или короткий ролик, Blob
  gender      String?
  ageRange    String?
  provider    String   // ключ внешнего движка, если не собственная генерация
  providerActorId String? // id актёра на стороне провайдера
  active      Boolean  @default(true) // оператор может снять актёра с витрины, не удаляя записи прошлых генераций
  createdAt   DateTime @default(now())

  @@map("synthetic_actors")
}
```

`Session.data` (JSON, без новой миграции для самой сессии — тот же
приём, что и у прочих сценарных полей) получает
`scriptOnlyGeneration: { actorId, script, engineJobId }` — генерация по
сценарию не отдельная сущность, а вариант заполнения уже существующей
сессии, чтобы не дублировать весь остальной пайплайн (постобработка,
публикация, TTL, sweep-orphans) — они уже умеют работать с `Session`
как таковой.

### 1.5. Фича-гейт

Новый признак `PlanFeature`, не переиспользование существующего:
ближайший семантически (`brandManifest`) — про стиль и персонажей
бренда одного пользователя, а не про общий каталог сервиса; ни один из
восьми существующих признаков `common/plans.ts` не покрывает «доступ к
каталогу синтетических актёров». Предлагается `scriptOnlyGeneration:
boolean`, по умолчанию `false` для LITE/STANDARD (как и у конкурентов —
Arcads держит этот режим за самым дорогим пакетом, TODO уже отмечает
это в строке 1078).

### 1.6. Открытые вопросы владельцу продукта

1.6.1. **Источник каталога актёров** — лицензированный набор от
   стороннего провайдера (Arcads/Creatify держат сотни готовых
   «актёров» именно так) или генерация без привязки к реальному
   человеку своей моделью. Оба пути проходят через периметр §0, но
   разная степень контроля: чужой лицензированный набор — юридическая
   ответственность частично на провайдере, собственная генерация — вся
   на сервисе.

1.6.2. **Видеодвижок для говорящей головы** — сравнение цены/качества
   нужно делать отдельно, до архитектурного решения; это не входит в
   объём данного ТЗ и не должно решаться по умолчанию первым найденным
   вариантом.

1.6.3. **Компоновка со сценой** — говорящая голова на нейтральном фоне
   (проще, но менее похоже на рекламный ролик) или сразу в сцене с
   товаром (дороже интеграционно). Первая итерация разумно ограничена
   первым вариантом.

## 2. Пункт 31 — собственный цифровой двойник продавца или лица бренда

### 2.1. Контекст

Расширяет пункт 14 («Постоянный амбассадор бренда») — но, как и пункт
11, пункт 14 сам нигде не реализован (см. предисловие). Отличие от
`BrandCharacter` (§1.2 выше): гарантия идентичности конкретного
загруженного человека («играет то же лицо», не «похоже»), а не
референс-изображение для промпта Veo.

### 2.2. Что уже есть

- `BrandCharacter` — фото + описание, `referenceImage` для Veo,
  сходство «на глаз», не тренированная модель лица. Технически
  недостаточно для обещания идентичности п. 31 — Veo с референс-
  изображением может дать разное лицо от генерации к генерации при
  сложных сценах, это давно известное ограничение подхода
  «reference-image», а не баг конкретной реализации.
- `casting.service.ts` — замена персонажа в разборе на фото пользователя
  или `BrandCharacter`, гейт `characterReplacement`
  (`casting.service.ts:202`) — ближайший существующий механизм по духу
  (подстановка конкретного лица), но результат — тот же
  referenceImage-подход, той же степени точности.
- **Обученного «двойника» (в терминах TODO — как у HeyGen digital twin)
  в проекте нет нигде** — ни модели, ни интеграции с внешним движком
  для обучения лица по фото/видео.

### 2.3. Архитектурное решение

Технически это тот же видеодвижок, что нужен для пункта 30 (говорящая
голова с точной синхронизацией) — только с ДОПОЛНИТЕЛЬНЫМ шагом
«обучение» перед использованием: пользователь один раз загружает фото
или короткое видео, движок создаёт переиспользуемый идентификатор
двойника, дальше все генерации ссылаются на этот идентификатор вместо
загрузки заново. **Пункт 31 напрямую зависит от решения по пункту 30
(1.6.2)** — заводить для него отдельный, второй видеодвижок только ради
цифрового двойника, когда уже есть движок под п. 30, было бы двойной
интеграционной стоимостью без явной причины (см. §6, порядок
реализации).

### 2.4. Данные

```prisma
model DigitalTwin {
  id              String   @id @default(cuid())
  brandManifestId String
  brandManifest   BrandManifest @relation(fields: [brandManifestId], references: [id], onDelete: Cascade)

  label           String   // как показывать в UI
  sourcePhotoUrl  String?  // исходник обучения — Blob, см. §2.5 про хранение
  sourceVideoUrl  String?
  provider        String   // тот же движок, что и SyntheticActor.provider (§1.4), если решение по 1.6.2 — общий движок
  providerTwinId  String   // идентификатор обученного образа на стороне провайдера

  consentGivenAt  DateTime // явное согласие снимаемого человека — см. §2.6, ОБЯЗАТЕЛЬНОЕ поле, не Boolean-флаг
  consentText     String   // текст согласия на момент подписания — версионируется так же, как оферта (§0)

  createdAt DateTime @default(now())
  updatedAt DateTime @default(now()) @updatedAt

  @@index([brandManifestId])
  @@map("digital_twins")
}
```

`consentGivenAt`/`consentText` — обязательные, не опциональные поля:
без зафиксированного согласия запись создаваться не должна (в отличие
от обычного согласия на оферту, которое подразумевается самим фактом
использования сервиса, здесь пользователь загружает **чужой** для
сервиса образ — согласие явное и по объекту, снимаемому человеку, а не
по аккаунту, который его загружает; это то самое разграничение, что
сделано в §0).

### 2.5. Хранение исходников

`sourcePhotoUrl`/`sourceVideoUrl` — Blob, тот же механизм, что и у фото
товаров (`ProductItem.photoUrl`) и персонажей бренда
(`BrandCharacter.photoUrl`), но с более высокой ценой утечки (TODO уже
формулирует это открытым текстом, строка 1097–1099). Практическое
следствие: `SWEEP_SCOPES` (`common/orphan-sweep.ts:36-42`, сегодня
`sessions/projects/brand-manifests/publications/shared-videos`) должен
получить новую область `digital-twins/` с ТЕМИ ЖЕ гарантиями подметания
осиротевших файлов, что и у остальных пяти — иначе исходники обучения
двойника окажутся единственной категорией файлов сервиса без
автоматической уборки, что для чувствительных биометрических данных
хуже, чем просто «занимает лишнее место», как у остальных.

### 2.6. Открытые вопросы владельцу продукта

2.6.1. **Явное согласие снимаемого человека** — юридически отдельная
   история от согласия на обработку персональных данных в оферте (уже
   зафиксировано в самом TODO, строка 1093–1096). Механизм подписи
   (галочка в интерфейсе загрузки самим пользователем, если он же и
   есть снимаемый человек — вероятный первый случай использования
   «двойник продавца»; отдельный поток подтверждения, если загружает
   один человек, а снят другой, — сложнее и требует решения, входит ли
   такой сценарий в объём вообще).

2.6.2. **Право отозвать согласие** — если да (вероятно, обязано быть по
   GDPR-логике §7 `terms-of-use.md`), нужен эндпоинт удаления
   `DigitalTwin` вместе с исходниками и, по возможности, запросом на
   удаление обученного образа у внешнего провайдера — зависит от того,
   что позволяет API выбранного по 1.6.2 движка.

## 3. Пункт 32 — голос пользователя как самостоятельная функция

### 3.1. Контекст

Сегодня клонирование голоса — функция владельца бренда в целом
(`BrandManifest.voiceMode/ttsVoiceId/ttsModel`), не self-service на
уровне отдельного пользователя/проекта. Единственный из пяти пунктов
этого ТЗ, который **не зависит** от решения по видеодвижку (§1.6.2) —
чисто аудио-фича поверх уже существующего TTS-пайплайна.

**Решено (9 сентября 2026, `doc/TTS-PROVIDER-ALTERNATIVES-SPEC.md` §5.2):
провайдер — Resemble AI, не ElevenLabs.** Приоритет владельца продукта
— неотличимость от живого голоса важнее скорости клонирования
(обучение в несколько минут признано приемлемым). Это поменяло саму

поток обязан быть таким же — `UserVoice` создаётся в состоянии
`TRAINING`, готовность приходит вебхуком или подтягивается опросом.

### 3.3. Архитектурное решение (реализовано этапом 73)

Presigned-Blob поток — тот же приём, что у фото персонажа/сцены бренда
(`brand-manifest`/`reference-assets`), НЕ multipart/`FileInterceptor`
(в проекте их нигде нет): `POST /voices/upload-url` минтит `voiceId` и
даёт presigned PUT в Blob → браузер грузит запись напрямую → `POST
/voices/clone` подтверждает, что запись реально лежит в хранилище
(`head()` из `@vercel/blob`), проверяет согласие и лимит, и запускает
асинхронное обучение у Resemble (`POST https://app.resemble.ai/api/v2/voices`,
`ResembleService.cloneVoice()`) — Resemble отвечает мгновенно
`{uuid, status: "pending"}`, само обучение занимает от секунд до
десятков минут в зависимости от типа образца.

Готовность приходит одним из двух путей: вебхуком (`callback_uri`,
собранным из `API_PUBLIC_URL` + `RESEMBLE_WEBHOOK_SECRET`,
`POST /voices/webhook/resemble?secret=...`, секрет в query — у Resemble
нет отдельного поля под секрет заголовка) ИЛИ poll-фоллбеком: `GET
/voices` (список голосов пользователя) сам подтягивает актуальный
статус у Resemble для всех ещё обучающихся записей при каждом вызове —
рабочий путь на стенде без публичного HTTPS (например, при локальной
разработке), просто медленнее вебхука.

Голос принадлежит ПОЛЬЗОВАТЕЛЮ, не `BrandManifest` — self-service в
буквальном смысле: `UserVoicesController` за `TelegramIdentityGuard`
(та же идентичность, что у `/brand-manifests`), не привязан к
конкретному бренду или проекту. Выбор голоса при генерации ролика
не заведён отдельным третьим путём в `GenerationWizard` — READY-клон
подставляется в тот же `VoicePicker`, что и голос бренда: как только
`resembleVoiceId` выбран и сохранён как `BrandManifest.ttsVoiceId`,
дальше это обычный голос для `POST /tts/preview`/синтеза озвучки, без
отдельного параллельного пайплайна.

**Важное следствие однопровайдерной архитектуры (§4.1
`TTS-PROVIDER-ALTERNATIVES-SPEC.md`):** `TTS_PROVIDER` — одна
переменная окружения на весь стенд, не выбор на пользователя. Клон
можно создать и удалить в любой момент независимо от активного
провайдера (клонирование — прямой вызов `ResembleService`, не через
`TTS_PROVIDER`), но реально ЗАЗВУЧАТЬ в готовом ролике клонированный
голос может только тогда, когда `TTS_PROVIDER=resemble` — иначе синтез
уходит к ElevenLabs, для которого `resembleVoiceId` — чужой,
несуществующий идентификатор. Интерфейс сообщает об этом прямо (см.
`myVoices.providerNote`), не притворяется, что выбор сработает всегда.

**Найдено и закрыто в процессе той же реализации:** `GET /voices`
у Resemble отдаёт список голосов НА ВЕСЬ аккаунт — а
`RESEMBLE_API_KEY` в проекте один на всех подписчиков. Без явного
фильтра клон одного пользователя со своей личной подписью («Голос
Марии») попадал бы в общий каталог `GET /tts/voices`, который видят
ВСЕ пользователи стенда — межпользовательская утечка, не мелочь.
`TtsController.voices()` исключает из общего каталога любой
`voiceId`, для которого в `UserVoice` есть запись с таким
`resembleVoiceId` — собственные клоны видны их владельцу только через
`GET /voices` (`UserVoicesController`), отдельный от каталога
маршрут.

### 3.4. Данные (реализовано этапом 73)

```prisma
enum UserVoiceStatus {
  TRAINING
  READY
  FAILED
}

model UserVoice {
  id               String          @id @default(cuid())
  userId           String
  user             User            @relation(fields: [userId], references: [id], onDelete: Cascade)

  label            String          // как пользователь называет свой голос в UI
  status           UserVoiceStatus @default(TRAINING)
  resembleVoiceId  String?         // uuid голоса у Resemble — есть, когда обучение стартовало
  sampleUrl        String          // исходная запись в Blob, presigned-поток как у character-photo
  consentAt        DateTime        // явное согласие (§3.6.3) — момент подтверждения, не факт
  error            String?         // причина отказа/провала, если status = FAILED

  createdAt        DateTime        @default(now())
  updatedAt        DateTime        @updatedAt

  @@index([userId])
  @@index([resembleVoiceId])
  @@map("user_voices")
}
```

Выбор голоса при генерации ролика остаётся тем же, что и раньше —
`BrandManifest.ttsVoiceId`/`ttsProvider`, только теперь значение
`ttsVoiceId` может быть идентификатором собственного клона, а не
только голосом из общего каталога.

### 3.5. Фича-гейт (реализовано этапом 73)

Отдельный признак `PlanFeature.voiceCloning` (решение §3.6.1 ниже), не
расширение `brandManifest` — временно на том же тарифе (Standard и
выше), с явным доккомментарием в `plans.ts`, что это самостоятельное
решение, а не жёсткая привязка к одному флагу навсегда.

### 3.6. Открытые вопросы — решения, принятые при реализации (этап 73)

3.6.1. **Тот же гейт, что `brandManifest`, или отдельный** — решено:
   ОТДЕЛЬНЫЙ признак `voiceCloning` (`common/plans.ts`), временно на
   том же тарифе (Standard и выше), что `brandManifest` — коммерчески
   это разные обещания (право брендировать vs право клонировать
   голос), даже если сегодня продаются на одном тарифе; раздельный флаг
   не мешает продукту развести их по разным тарифам позже без миграции
   данных.

3.6.2. **Лимит клонированных голосов на пользователя** — решено: 3
   голоса на пользователя, FAILED-попытки в лимит не входят (неудача не
   должна сжигать квоту навсегда). Лимит — на нашей стороне
   (`UserVoicesService.assertUnderLimit`), не только через `ai-usage`:
   Resemble тарифицирует количеством голосов на АККАУНТ (общий на всех
   подписчиков), значит без своего лимита один активный пользователь
   мог бы исчерпать общую квоту аккаунта у Resemble.

3.6.3. **Согласие на запись голоса** — решено: явное булево поле
   `consent` в `POST /voices/clone` (не отдельная галочка «я прочитал»
   один раз в настройках, а подтверждение на КАЖДЫЙ клон) — запись
   используется для клонирования голоса, не просто хранится, и это
   должно быть осознанным выбором на каждый образец, а не одноразовым
   согласием, забытым через полгода.

## 4. Пункт 33 — замена актёра без пересборки сцены (рекаст)

### 4.1. Контекст

Актуален вместе с пунктом 30: перебор актёров под аудиторию — обычная
практика A/B-теста лица, полная цена генерации за каждую попытку убивает
экономику (та же логика, что уже действует в проекте для A/B-теста
сценариев — `AbTestVariant`, крон `ab-test-run`). **Пункт 33
технически бессмысленен без пункта 30 или 31** — рекастить нечего, если
в сервисе ещё нет ни каталога синтетических актёров, ни цифровых
двойников. Это не самостоятельная фича, а дешёвая надстройка над одним
из двух предыдущих пунктов (см. §6, порядок реализации).

### 4.2. Что уже есть

  РЕФЕРЕНСА на фото пользователя или `BrandCharacter`, гейт

  лицо», но результат сегодня — **обычная, полноценная генерация Veo
  с новым referenceImage**, не облегчённый проход. Дешёвого «только

## 5. Пункт 34 — курируемая витрина чужих удачных роликов («Ad Library»)

### 5.1. Контекст

Единственный из пяти пунктов, который **не зависит** от решения по
видеодвижку — расширяет уже существующую и полностью реализованную
Библиотеку разборов (§21 `PRODUCT-PROJECT-SPEC.md`), а не строит
фундамент с нуля. Самый дешёвый пункт этого ТЗ по объёму работы.

### 5.2. Что уже есть (перепроверено чтением кода)

- `AnalysisLibraryEntry` (`schema.prisma:851-…`) — уже есть
  `visibility` (`PUBLIC/PRIVATE/HIDDEN`), `moderatedAt`/`moderatedById`
  (оператор уже может скрывать записи через `AdminSessionGuard`),
  `sourceType` (`youtube | upload`), денормализованные поля для
  ранжирования (`category`, `audienceGender`, `audienceAgeRange`,
  `audienceInterests`, `usageCount`) и составной индекс под
  `GET /library/recommend`.
- **Отличие от текущего наполнения**: сегодня записи попадают в таблицу
  ТОЛЬКО как побочный эффект того, что пользователь сервиса что-то
  разобрал (`sessionId`/`userId` заполнены, `sourceType` —
  `youtube`/`upload` от лица пользователя). Курируемая витрина —
  записи от лица РЕДАКЦИИ/оператора, без пользователя-источника,
  потенциально массово (автосбор), а не по одной.

### 5.3. Архитектурное решение

Не новая модель — `sourceType` получает третье значение (`'curated'`),
`sessionId`/`userId` остаются `null` (уже `nullable` в схеме), новое
поле `curatedById` (кто из операторов добавил/одобрил) — расширение
существующей таблицы, тот же принцип «расширение, а не новая модель»,
что уже применён в `MULTI-FORMAT-EXPORT-SPEC.md`:

```prisma
// Добавить к AnalysisLibraryEntry:
curatedById String?
curatedBy   User?   @relation("LibraryCurator", fields: [curatedById], references: [id], onDelete: SetNull)
```

`GET /library/recommend` не меняется структурно — курируемые записи
участвуют в тех же ранжировании и фильтрации по `visibility`, что и
пользовательские; UI-отличие (см. §5.5) — не в бэкенде.

### 5.4. Источник роликов — два варианта, разная стоимость

- **Ручная курация оператором** — дёшево по объёму (используется
  существующий `POST /library`-подобный путь создания записи, вручную
  через админку, тот же принцип, что и модерация сегодня), дорого по
  постоянному труду редакции. Не требует нового кода за пределами
  админ-формы «добавить курируемую запись».
- **Автосбор из публичных рекламных библиотек площадок** (Meta Ad
  Library, TikTok Creative Center) — новый крон-воркер, аналогичный по
  структуре `feed-import-run` (этап 68, `ProductFeedImportWorkerService`
  — постраничный обход внешнего источника с курсором и бэкоффом), но
  **с иными правовыми требованиями к показу чужого ролика в
  интерфейсе сервиса**, чем у товарного фида (там — собственные данные
  продавца по фиду, тут — чужая реклама с площадки конкурента).
  Юридический вопрос отдельный от §0 (не про синтетический контент, а
  про право показа чужого материала) — не решается в этом документе.

### 5.5. Открытые вопросы владельцу продукта

5.5.1. **Ручная или автоматическая курация** — прямо влияет на объём
