# API — все маршруты бэкенда

Полный список того, что реально отдаёт `backend/` (глобальный префикс
`/api`, ответы завёрнуты `ResponseInterceptor` в
`{ success, data, meta }`). Появился на этапе 28 после сквозной сверки:
часть маршрутов не была описана нигде, а один — `GET /api/health` — был
описан в четырёх документах, но не существовал.

**Правило:** новый контроллер → строка в этой таблице. Здесь только
маршруты; смысл и решения — в `doc/PRODUCT-PROJECT-SPEC.md`, рецепты
локальных прогонов — в `doc/LOCAL-DEVELOPMENT.md`.

## Кто может звать

| Доступ | Что означает |
| --- | --- |
| **открыто** | без заголовков; предъявителем выступает UUID сессии (§7.8). С этапа 42 поверх стоит глобальный `SessionOwnerGuard`: если у сессии есть владелец, запрос обязан прийти от него — иначе 403 «Эта сессия принадлежит другому аккаунту». С этапа 49 первый опознанный запрос к ничьей сессии привязывает её к вошедшему (В-3.4) |
| **идентичность** | `TelegramIdentityGuard`: initData из Telegram, cookie обычного логина или `X-Dev-User-Id` при `ALLOW_DEV_AUTH`. Для cookie любой не-GET запрос дополнительно проверяется по `Origin` против `CORS_ORIGIN` (этап 41, `common/csrf.ts`) — 403 «Cross-origin request rejected» |
| **оператор** | `AdminSessionGuard` (cookie админки) + флаг `isOperator` (`assertOperator` первой строкой каждого обработчика) |
| **вход/выход** | маршруты `telegram-login/*` и `admin/auth/*` под `OriginGuard` (этап 49): форма с чужого сайта не может ни посадить посетителя в чужую сессию, ни выкинуть оператора. С этапа 54 входы (`callback`, `dev-login`) и `POST /api/sessions` ещё и под `RateLimitGuard` — 10 (входы) / 30 (сессии) запросов в минуту с одного адреса, счётчик в базе (`rate_limits`); сверх — 429 с `Retry-After` |
| **секрет крона** | заголовок `Authorization: Bearer $CRON_SECRET`, сравнение constant-time. Переменная не задана — 503 на всех маршрутах `cron.controller.ts` (на 30.09.2026 их двадцать пять — столько же, сколько записей `crons` в `backend/vercel.json`; этап 54, Б-3.3); открыты без секрета они только на dev-стенде (`ALLOW_DEV_AUTH=true` вне production) |

Раунды визарда (`/explore`, `/step`, `/login`) отвечают
`{ draft, exploration }`, где `exploration` — §5.4: `currentUrl`,
`screenshotDataUrl` (`data:image/jpeg;base64,…`, не Blob-ссылка — §6.3),
`elements[]` и `looksLikeLogin`. У `<select>` в элементе приходят
`options[]` — `fill` сопоставляет строку со ЗНАЧЕНИЕМ опции, а не с
надписью, и без списка вариантов заполнить его было бы нечем. У каждого
элемента может стоять
`danger` — предупреждение стоп-листа §8.3 по видимому тексту кнопки
(«Оплатить», «Удалить»); оно приходит РАНЬШЕ, чем пользователь выберет
кнопку, поэтому «вы уверены?» успевает спроситься до того, как шаг
выполнится на настоящем сайте. Сервер при этом ничего не блокирует. Если
раунд нажал такую кнопку, тот же текст возвращается в
`exploration.dangerWarning` — для оператора при модерации. Отдельный
код ответа: **503**, если headless-браузер не поднялся (внешняя
инфраструктура, не ошибка запроса) — слот суточного лимита при этом
возвращается, раунд не засчитывается.

`GET /site-tutorial` дополнительно несёт `liveLoginAvailable: boolean` —
явный канал мягкой деградации (§15.8 контракта реле): фронтенд прячет
кнопку живого входа по этому признаку, а не догадывается по тексту
ошибки после нажатия.

| `POST /api/admin/users/:id/lite-unlock` | оператор | вернуть разблокировку после отзыва. В §10 ТЗ этого маршрута не было, но без него приёмка этапа 135 невыполнима: автоматика доступ не возвращает — иначе отзыв отменялся бы первым же следующим приглашением


## Звуковые дорожки на других языках (ТЗ TZ-Multilingual-YouTube.md, этапы 138/139)

| Маршрут | Кто | Что делает |
| --- | --- | --- |
| `GET /api/v1/me` | ключ API | внешнее API (этап 144, docs-tz/TZ-Vneshnee-API.md): кто я — режим, суточный потолок (`limit`/`spent`/`remaining` в микродолларах) и id сработавшего ключа. **Форма ответа — общий конверт сервера:** успех приходит как `{success: true, data: {…}, meta: {timestamp, requestId}}`, отказ — как `{error: {code, message}, meta: {requestId}}`; `requestId` это тот номер, с которым идут в поддержку. Поля «заблокирован» в ответе нет намеренно: заблокированный аккаунт не доходит до обработчика, и поле, которое не может стать `true`, — это ветка в чужом коде, которая не выполнится ни разу. Вход по `Authorization: Bearer <ключ>`, режим не ниже Premium, заблокированный аккаунт не входит. Маршрут читающий и бесплатный намеренно: на него интегратор ходит в каждом healthcheck, и делать проверку ключа платной было бы дорого обоим. Суточный потолок расхода здесь НЕ проверяется — он относится к платному вызову, а не ко входу |

Генерация длится минуты, фона у serverless нет — доводит заявку крон `api-video`. Заголовок `Idempotency-Key` необязателен: повтор с тем же ключом И тем же телом отвечает **`200`** и ТОЙ ЖЕ заявкой (чужой клиент не знает, дошёл ли первый запрос после таймаута), тот же ключ с другим телом — `409` (это не повтор, а переиспользованный ключ). Суточный потолок проверяется на подаче: выбранный — `403` с числами, чтобы интегратор узнал о нём из ответа, а не из заявки, упавшей через минуту |
| `GET /api/v1/videos/:jobId` | ключ API | состояние заявки. Ссылка на ролик есть только у `DONE` (у `RUNNING` она указывала бы на ещё меняющийся файл), причина — только у `FAILED`. Чужая заявка по номеру не отдаётся: её просто нет |
| `GET /api/cron/api-video` | `CRON_SECRET` | тик заявок внешнего API (этапы 145–146): третьей фазой рассылает исходы на адреса вебхуков — тем же тиком, потому что доставок столько же, сколько закончившихся заявок; сначала двигает то, что уже рендерится (`getVideoStatus` — тот же вызов, что у мастера), потом берёт новое. Строка захватывается `lockedUntil` ДО платного вызова; что уже сделано, видно по СОСТОЯНИЮ сессии, а не по статусу строки, — оборванный тик доделывает недостающее, а не платит второй раз. Суточный потолок попытку не тратит и ждёт полуночи |
| `GET /api/api-keys` | идентичность | `{keys, maxActive}`: свои ключи API (имя, открытое начало, когда выдан, когда использовался, когда отозван) и потолок живых ключей. Секрета среди них нет — он существовал ровно один раз, в ответе на выдачу. Потолок отдаётся сервером, а не живёт копией в интерфейсе (находка аудита этапа 145): копии таких чисел расходятся с оригиналом всегда в худшую сторону — человеку показывают кнопку, которую сервер потом запрещает |
| `POST /api/api-keys` | идентичность | выдать ключ (`{name?}`). Секрет в ответе — единственный раз, когда он вообще существует за пределами памяти запроса; потерянный не восстанавливают, а перевыпускают. Право `externalApi` (Premium) проверяется на выдаче, не только на входе; живых ключей не больше пяти; под `RateLimitGuard` (10/час) |
| `PATCH /api/api-keys/:id/webhook` | идентичность | куда сообщать об исходе заявки (`{webhookUrl}`, пустая строка — не сообщать). Адрес проверяется ЗДЕСЬ: по нему пойдёт наш сервер изнутри нашей сети, поэтому только `https`, только публичный хост, без логина с паролем. Список сам дозабирает завершившиеся сборки ffmpeg — отдельного крона для них нет намеренно: дорожек в сутки единицы, а экран открывает тот же человек, который их ждёт |

| `POST /api/admin/audio-tracks/track/:id/uploaded` | оператор | отметка «залито в Studio» (`{uploaded?: boolean}`, пустое тело — «залито»). Именно отметка, а не проверка: API звуковых дорожек у YouTube нет вовсе, убедиться машиной нечем. Снятие стирает и дату, и того, кто отметил |

### «Я в кадре» (за флагом `PERSONA_ENABLED`, `doc/DEPLOYMENT.md`)

Флаг выключен — маршруты ниже отвечают 404 `PERSONA_DISABLED`, кроме
`GET /api/personas/me` при уже созданной персоне (`enabled: false`) и
удаления (`DELETE /api/personas/me`, `DELETE …/looks/:id`) — право на
удаление.

### Коды отказов поздравления

`backend/src/common/greeting-errors.ts` (`GREETING_ERROR_CODES`). Клиент
переводит код словарём `greetingErrors`; незнакомый код — показывается
текст сервера.

| Код | HTTP | Где | Смысл |
| --- | --- | --- | --- |
| `GREETING_NOT_GREETING_SESSION` | 400 | `greeting-video`, `greeting-prompt`, правки из сессии, `greeting-references` (upload-url, generate, settings) | у сессии нет брифа поздравления |
| `GREETING_SCRIPT_MISSING` | 400 | `POST …/greeting-video` | сценария ещё нет |
| `GREETING_SCRIPT_FLAGGED` | 400 | `POST …/greeting-video` | сценарий помечен проверкой (FLAGGED или BYPASSED) — исправить текст на шаге «Сценарий» |
