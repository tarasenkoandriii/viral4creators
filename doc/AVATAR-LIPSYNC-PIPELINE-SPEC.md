**Admin-only пилот реализован на этапах 72/72а** (см. §50
`doc/PRODUCT-PROJECT-SPEC.md`, «Сделано (этап 72…)» и «Сделано (этап

(`GenerateAvatarRequestDto.subtitles`), выключены по умолчанию,

будущее расширение пилота. **Аудит пайплайна** — отдельный документ
`doc/AVATAR-PIPELINE-AUDIT-2026-09-09.md`.

**Этот документ закрывает открытый вопрос 1.6.2**
`doc/AI-ACTORS-NO-REFERENCE-SPEC.md` §1 («видеодвижок для говорящей
головы — сравнение цены/качества нужно делать отдельно, до

Решение здесь напрямую влияет на пункт 31 того же документа (§2,

14/31 (постоянный амбассадор бренда), 17 (синхронизация губ), 30

**Голос — не открытый вопрос, а уже принятое и реализованное решение**:

**Повод и источники** — тот же скриншот вакансии студии AI UGC-рекламы

естественно про него говорит»; нужен специализированный движок
говорящего аватара. Владелец продукта явно выбрал направление: Hedra
или Sync Labs на видео, Resemble на голос, отдельной веткой пайплайна
«по образцу первого» (пайплайна Veo: сессия → генерация → пост-
обработка).

## 0. Юридический периметр — тот же нерешённый вопрос, что и у пунктов 30/31/34

отдельного юридического ревью. Этот пилот собирается ровно из тех же
компонентов (фото человека → видео с его лицом, произносящим текст) —
периметр применяется без изменений, повторно решать его в этом
документе смысла нет. Ниже (§5.1) — только техническая сторона вопроса,
без предположения, что юридическая часть уже закрыта.

## 1. Что уже есть в проекте (перепроверено чтением кода)

### 1.1. Пайплайн сессии — три отдельных модуля, три отдельных внешних вызова

`video` (приём референса) → `generation` (сам рендер, `GenerationService`)
→ `postprod` (кроп/озвучка/субтитры, `PostProductionService`) — три
разных внешних сервиса на трёх стадиях одной `Session`. Ключевые для
нового пайплайна приёмы, все уже отработаны и протестированы:

- `GenerationStatus { PENDING, PROCESSING, COMPLETE, FAILED }`
  (`common/types/generation.types.ts`) — достаточно общий enum, чтобы
  переиспользовать без изменений для нового движка.
- `sessionService.claimWork(sessionId, kind, ttlMs)` — атомарный DB-лок
  через `data.workLocks.<kind>`, предотвращающий два параллельных старта
  одного и того же платного рендера. Новый `kind: 'avatar-generate'` —
  тот же приём, без нового механизма.
- `RENDER_DEADLINE_MS` / `renderExpired()` (В-2.8) — «зависший» рендер
  считается проваленным через 20 минут, чтобы сессия не «пропадала»
  навсегда при сбое стороннего API. Тот же паттерн нужен и для Hedra
  (см. §3.5).
- `creditLedger.reserveForGeneration()` / `aiUsage.record()` — списание
  происходит в момент СТАРТА платного вызова, не завершения («деньги
  считаются потраченными, даже если рендер потом не удастся») — тот же
  принцип для нового движка.
- Постобработка не блокирует показ результата и не падает единым куском
  при частичном сбое («деградация, а не поломка») — субтитры и кроп
  независимы друг от друга уже сегодня; тот же принцип пригодится в
  §3.2, когда пилот получит субтитры отдельным необязательным шагом.

### 1.2. `TtsProvider`/`ResembleService` — переиспользуются без изменений

`backend/src/modules/tts/tts.types.ts` — интерфейс `synthesize(text,
voiceId?, model?, language?, timestamps?)` → `{audio, mimeType,
characters, voiceId, model, alignment?}`. `ResembleService`
(`resemble.service.ts`) уже реализует его, `POST
https://f.cluster.resemble.ai/synthesize` отдаёт `audio_timestamps`
нативно в том же ответе — то есть **аудио для аватара уже сегодня можно
синтезировать одним вызовом, без нового кода в `tts/`.** Единственная
тонкость: сегодня `synthesize()` вызывается только из `postprod.service.ts`
ПОСЛЕ рендера Veo (озвучка накладывается на готовое видео). В новом
пайплайне порядок обратный — **аудио нужно синтезировать ДО вызова
видеодвижка**, оно и есть входной параметр, управляющий движением губ.
Это не проблема интерфейса `TtsProvider` (он ничего не знает про Veo и
вызывается независимо), но реальная новая точка вызова — прямо из
нового модуля `actors` (см. §3.3), а не из `postprod`.

### 1.3. Источник портретного фото — `BrandCharacter.photoUrl`, уже готов к передаче внешнему движку

`brand-manifest.module` уже умеет: `POST
/brand-manifests/:id/characters/:cid/photo/upload-url` → presigned Blob
PUT → `POST .../photo/confirm` (`head()`-проверка, что файл реально
залит) → `BrandCharacter.photoUrl` — публичный URL, только PNG/JPEG,
доккомментарий сервиса прямо говорит: «этот файл предназначен для
Veo 3.1 как `referenceImage`». Формат (одно портретное фото, публичный
URL, уже проверенное на существование) — **ровно то, что просит Hedra
Character-3 как `start_image`** (см. §2) — интеграция сводится к
передаче уже существующего `photoUrl` новому клиенту, без нового
аплоад-флоу.

### 1.4. Товар в кадре — фото уже есть, компоновки нет нигде

`ProductItem.photoUrl` — уже готовый Blob URL (см. отчёт по
product-feed-import, этап 68). Но в проекте **нет ни одного модуля
генерации/редактирования изображений** (проверено: `grep -rn
"nano-banana|image-edit|imageEdit|generateImage" backend/src` — ноль
совпадений) — то есть «сфотографировать» человека, держащего товар,
сегодня нечем, кроме реальной фотосъёмки. Ни Hedra, ни Sync Labs не
решают эту задачу сами (см. §2) — это открытый вопрос §5.2, не
техническая недоработка данного ТЗ.

### 1.5. Крон/claim-lock (`catalog-batch`) — для будущего масштабирования, не для пилота

Паттерн «атомарный `updateMany` с `lockedUntil` перед платным вызовом +
экспоненциальный бэкофф при ошибке» (`catalog-batch-worker.service.ts`)
— готовый образец для дня, когда пилот перейдёт в пакетный режим (по
образцу этапов 65/66). Первая итерация (§3) сознательно её не требует —
один аватар-ролик воркеру не нужен, хватает того же синхронного
запрос-статус цикла, что уже есть у `generation.controller.ts`.

## 2. Сравнение кандидатов — по официальной документации провайдеров, не по агрегаторам

Рыночная разведка того же дня (`video-market-research.md`) опиралась на
блог-агрегаторы (ofox.ai, hyperfx.ai, crazyrouter.com) — этого хватало
для выбора КЛАССА инструмента (говорящий аватар против кинематографичной
T2V-модели), но недостаточно для архитектурного решения. Ниже —
перепроверка по официальной документации `sync.so/docs` и
`hedra.com/docs`, 9 сентября 2026.

**Вывод**: Sync Labs — это инструмент дубляжа/релипсинка **реальной,
уже отснятой** видеосъёмки актёра (нужен реальный человек перед
камерой, произносящий что угодно — движок просто переозвучит рот).
Hedra — инструмент генерации целиком **из одной фотографии**. Для
задачи «блогер держит товар и говорит текст» без готовой видеосъёмки
на входе (то есть именно сценарий этого пилота — «отдельная ветка,
без изменения остального пайплайна, откуда сегодня берётся только
фото, не видео персонажа») Sync Labs технически неприменим без
дополнительного шага: где-то раздобыть реальное отснятое видео
говорящего человека. Hedra работает с уже существующим в проекте типом
актива (`BrandCharacter.photoUrl`) без нового источника контента.

## 3. Архитектурное решение

### 3.1. Выбор: Hedra Character-3 — для этого пилота; Sync Labs — задокументированная альтернатива на будущее

По той же логике, что и решение 5.2 в TTS-спеке («Cartesia остаётся в
документе не как отменённая идея, а как решение для другой задачи»):
Sync Labs становится осмысленным выбором **в день, когда** у проекта
появится реальная отснятая видеозапись говорящего человека, которую
нужно перевести на другой язык/текст с сохранением его настоящей мимики
(визуальный дубляж — TODO уже касается этого косвенно через
локализацию, пункт 12). Формулировка задачи «сделать под Sync Labs» без
такого видео-источника не имеет смысла при сегодняшнем состоянии
проекта — она отвечает на другой вопрос.

### 3.2. Порядок шагов пайплайна

Новый, не переиспользующий текущий `GenerationService` поток (см. §3.4,
почему — намеренно):

1. **Текст реплики** — тот же источник, что сегодня формирует
   `generationPrompt`/`voiceover`-скрипт (`PromptService`,
   `voiceover-script.ts`) — переиспользуется без изменений, реплика
   пишется один раз для обоих движков.
2. **Синтез голоса — Resemble, ДО видео, не после.**
   `resembleService.synthesize({text, voiceId, timestamps: true})` →
   `{audio, alignment}`. Аудио заливается в Blob
   (`sessions/:id/avatar-voiceover.mp3`) — публичный URL нужен для
   передачи Hedra на следующем шаге.
3. **Генерация аватар-видео — Hedra.**
   ```
   POST https://api.hedra.com/v3/models/hedra-character-3
   { prompt: <краткое описание сцены/персонажа>,
     start_image: <BrandCharacter.photoUrl>,
     audio: <URL аудио из шага 2>,
     aspect_ratio: "9:16", resolution: "720p" }
   ```
   → `202`, тело содержит `job_id`. Эндпоинт и метод выверены при аудите
   этого ТЗ (см. «Аудит», находка 1) — до исправления здесь был указан
   другой, не относящийся к Character-3 путь.
4. **Статус** — поллинг `GET https://api.hedra.com/v3/jobs/{job_id}`,
   либо вебхук `JobCompleted`/`JobFailed` как более быстрая альтернатива
   при доступном публичном HTTPS-эндпоинте — тот же принцип фоллбека,
   что уже решён для Resemble в `TTS-PROVIDER-ALTERNATIVES-SPEC.md` §5.4
   (вебхук первичен, поллинг — рабочая резервная альтернатива для
   dev-стенда).
5. **Результат** — скачивается и перезаливается в НАШ Blob (внешние
   ссылки недолговечны — тот же принцип, что уже применён в
   `postprod.service.ts` для Veo/ffmpeg-service).
6. **Субтитры — реализовано этапом 72а, явным чекбоксом, не «опционально
   как получится».** `alignment` из шага 2 уже есть, `common/subtitles.ts`
   строит `.srt` из пословного тайминга; прожиг через тот же
   `FfmpegApiService`, что и сегодня — но **только субтитры**, не замена
   аудио (аудио уже часть выхода Hedra, дублировать наложение не нужно),
   и ВТОРЫМ, отдельным проходом ffmpeg ПОСЛЕ шага 5 (в отличие от
   Veo-пути, где всё накладывается на уже существующий файл одним
   проходом — здесь этот файл появляется только после Hedra). Кроп/
   реформат не нужен — Hedra уже рендерит нужное `aspect_ratio`
   нативно, в отличие от Veo. Чекбокс `GenerateAvatarRequestDto.subtitles`
   — выключен по умолчанию, тот же принцип, что у `subtitlesMode` Veo-пути
   (владелец продукта: «не всем роликам они нужны»).

### 3.3. Новый модуль `modules/actors/` — первый (генерационный) срез уже предложенного модуля, не новое имя

Отдельный модуль, не правка `generation.module.ts` — по прямой аналогии
с тем, как в этапе 71 (находка Д-4.3) решили НЕ трогать протестированную
`AdminCronService.run()`, а добавить рядом новую, отдельную
возможность: `GenerationService`/Veo-путь — единственный сегодня
протестированный, стабильный код, трогать его ради нового движка не
нужно и рискованно.

Имя модуля — **не новое**: `doc/AI-ACTORS-NO-REFERENCE-SPEC.md` §1.3
уже предложил `modules/actors/` именно под «новый внешний вызов, не
Veo» для говорящей головы, оставив открытым вопросом 1.6.2 только
КАКОЙ движок. Этот документ отвечает на 1.6.2 и реализует ровно ту
часть модуля, которую можно закрыть без ответа на остальные открытые
вопросы того ТЗ — генерацию. `ActorCatalogService`/`SyntheticActor`
(§1.3–1.4 того документа — общий, межпользовательский каталог готовых
синтетических актёров, TODO п. 30) в этот пилот **сознательно не
входят**: пилот переиспользует уже существующий `BrandCharacter`
(персонаж одного бренда, не общий каталог сервиса) — заводить каталог
раньше первого работающего рендера преждевременно.

```
modules/actors/
  actors.module.ts
  actors.service.ts       // generateAvatarVideo(sessionId), getAvatarVideoStatus(sessionId)
  hedra-client.service.ts // тонкая обёртка HTTP над Hedra API
  actors.controller.ts    // POST/GET /sessions/:sessionId/avatar (по образцу generation.controller.ts)
```

### 3.4. Данные — новое поле, не расширение `GeneratedVideo`

`Session.data` получает независимое поле `avatarVideo` (не трогает
`generatedVideo`, которым занят Veo-путь — исключает риск случайно
что-то сломать в уже протестированной ветке):

```ts
export interface AvatarVideo {
  status: GenerationStatus;         // переиспользуем существующий enum
  provider: 'hedra';                // задел под 'sync-labs' позже
  providerJobId: string | null;
  characterId: string;              // BrandCharacter.id — источник start_image
  voiceoverPathname: string;        // из шага 2, свой Blob
  renderedUrl: string | null;       // сырой результат Hedra
  downloadUrl: string | null;       // после (опциональных) субтитров
  initiatedAt: string;              // для дедлайна, по образцу RENDER_DEADLINE_MS
  subtitleStatus: 'skipped' | 'pending' | 'done' | 'failed';
  costMicroUsd: number | null;
  error: { code: string; message: string; retryable: boolean } | null;
}
```

Миграция схемы не нужна — как и `characterCasting`/`generatedVideo`
сегодня, поле живёт в существующей JSON-колонке `Session.data`.

### 3.5. Дедлайн зависшего рендера

`AVATAR_RENDER_DEADLINE_MS` — по аналогии с `RENDER_DEADLINE_MS`
(20 минут для Veo). У Hedra Character-3 верхний предел длины ролика
сам по себе 10 минут аудио — стоит взять дедлайн ожидания ответа с
большим запасом (например те же 20 минут) и скорректировать по факту
первых реальных прогонов пилота, а не гадать заранее.

### 3.6. Товар в кадре — решено этапом 73: регламент, не код

`start_image` — один портрет. Hedra не компонует чужой объект в кадр
поверх фото и не «дорисовывает» товар в руки по отдельной ссылке —
у него в принципе нет такого API-параметра (в отличие от Creatify,
единственного в разведке рынка с нативной вставкой товара по ссылке —
но с оговоркой «аватары заметно синтетические», см.
`video-market-research.md`). Практический путь — исходное фото
персонажа уже должно показывать его с товаром в руках (реальная
фотосъёмка).

**Решение (этап 73, прямой выбор владельца продукта из трёх вариантов
§5.2)**: первый вариант — регламент, НЕ генеративная компоновка
изображения (эта опция явно отклонена — «Ноль кода, но зависит от
наличия такого фото» и есть выбранная цена). Раз в проекте нет и не
появляется инфраструктуры компоновки/генерации изображений (§1.4), а
Hedra не принимает такой параметр вовсе, единственная проверка,
которую МОЖЕТ сделать код — не пропустить оператора к платному запуску
без явного подтверждения. Реализовано как обязательный чекбокс в
`admin/src/app/actors/page.tsx` («Регламент товара в кадре»,
блокирует кнопку «Запустить рендер», пока не отмечен, сбрасывается при
смене сессии/индекса персонажа) — не сохраняется в БД и не проверяет
содержимое фото автоматически (никакого vision-вызова), это
намеренная граница: код физически не может проверить, ЧТО на фото, он
может только заставить оператора подтвердить, что он сам проверил.

## 4. Фича-гейт и стоимость

### 4.1. `PlanFeature`

Ни один из девяти существующих признаков `common/plans.ts` не подходит
семантически (`characterReplacement` — про замену лица в РАЗБОРЕ
референса Veo, не про отдельный движок). Новый признак —
`avatarLipsync: boolean`, по умолчанию `false` до конца пилота на всех
тарифах (сначала — только ручной доступ оператора, см. §5.3), позже —
вероятно Premium (у Arcads/HeyGen конкурентный аналог всегда за самым
дорогим пакетом).

### 4.2. Учёт расхода

Новый ключ `ai-pricing.ts`: `'hedra-character-3': { provider: 'HEDRA',
perSecond: ... }` — ставка **оценочная** (§2, ≈$0.03–0.06/сек по
опубликованным тарифным планам, не по прямому прайсу за API-вызов —
тот же класс предупреждения, что уже стоит у `'resemble-tts'` в
`ai-pricing.ts`: «ОБЯЗАТЕЛЬНО перепроверить из личного кабинета перед
реальным переключением в продакшн»). `aiUsage.record({operation:
'avatar-generation', model: 'hedra-character-3', seconds, sessionId})`
— по образцу того, как сегодня учитывается Veo (`operation:
'generation'`). Использовать `POST /models/{model}/estimate` Hedra
ПЕРЕД стартом рендера как дополнительную защиту, аналогичную
`plans.assertCanSpendSession()`, — Hedra, в отличие от Veo, отдаёт
точную цену до реального списания.

## 5. Открытые вопросы владельцу продукта

5.1. **Источник портретного фото модели/актёра.** Реальная фотосессия
   с письменным согласием снимаемого человека (самый чистый путь
   юридически, но требует реальной съёмки и не решает «неограниченный
   каталог актёров») или синтетическое лицо, сгенерированное отдельной
   image-моделью (снимает вопрос согласия конкретного человека, но
   создаёт другой юридический риск — случайное сходство со случайным
   реальным человеком; в проекте сегодня нет инфраструктуры генерации
   изображений вовсе, §1.4). Оба пути проходят через периметр §0.

5.2. **Товар в кадре — РЕШЕНО этапом 73.** Владелец продукта выбрал
   первый вариант из трёх ниже (плюс звуковой чек и клонирование
   голоса — не про этот пункт): заказывать у той же модели/актёра
   фотосессию уже с товаром в руках — регламентом, закреплённым
   обязательным чекбоксом оператора в `/actors` (см. §3.6), а не
   генеративной компоновкой изображения (этот путь явно отклонён).
   Исходные варианты, для истории:
   - **Выбрано.** Заказывать у той же модели/актёра фотосессию уже с
     товаром в руках (просто, но по одной новой фотосессии на каждый
     товар/бренд).
   - Считать пилотом только говорящую голову без товара в руках (товар
     — отдельным способом в остальной части ролика, вне объёма этого
     документа). **Детализирован полностью**, все пять неоднозначных
     деталей додуманы автором ТЗ (не оставлены открытыми вопросами) —
     см. `doc/AVATAR-NO-PRODUCT-PHOTO-WORKFLOW-SPEC.md` (товарная
     вставка, отрендеренная тем же Veo-промптом дочерней сессией — либо
     переиспользован уже готовый ролик той же сессии, если подходит по
     формату — и автоматически склеенная с роликом Hedra). Только ТЗ,
     не реализовано.
   - Отклонено. Заводить отдельную, новую задачу на компоновку фото
     человека и товара (генеративная правка изображения, нигде в
     проекте сегодня не реализована, полноценная отдельная фича, не
     два часа работы).

5.3. **Масштаб и видимость пилота.** Предлагается держать
   `avatarLipsync` доступным только оператору (ручной запуск, как
   сегодня админ вручную гоняет крон-джобы) до результатов нескольких
   тестовых роликов — не выкатывать пользователям продукта до
   подтверждения качества и реальной цены за ролик.

5.4. **Пакетный режим позже, не сейчас.** §1.5/§3 сознательно не
   заводят крон-воркер для этого пилота — если результат пилота
   положительный, следующий естественный шаг (отдельная задача) —
   `catalog-batch`-подобный воркер поверх уже готового `ActorsService`,
   тем же приёмом, что этапы 65/66.

5.5. **Технические детали, требующие проверки перед реализацией, не
   перед написанием ТЗ:** точная схема подписи вебхука Hedra (HMAC?
   секрет в заголовке?) — не найдена в зафетченных страницах
   документации; точный список полей эндпоинта `run-hedra-character-3`
   (в отчёте выше приведено по прочитанному фрагменту документации,
   не по официальному OpenAPI-файлу целиком) — сверить перед первой
   реализацией, а не полагаться на пересказ в этом ТЗ.

## Аудит этого ТЗ

Повторная проверка сразу после написания, по прямому запросу владельца
продукта — тот же приём, что уже применён к
`doc/TTS-PROVIDER-ALTERNATIVES-SPEC.md`. Часть находок ниже — не про
сам этот документ, а про его непосредственного соседа
(`video-market-research.md`, доставлен раньше в этом же разговоре):
разбирается и это тоже, раз именно там обнаружилось расхождение,
которое стало поводом для аудита.

### Находка 1 (ИСПРАВЛЕНА). §3.2, шаг 3 — эндпоинт Hedra в первой версии был перепутан между двумя разными API-поверхностями

Первая версия этого документа приводила `POST
https://api.hedra.com/web-app/public/generations` с полем `model_slug:
"together/hedra-character-3"` — это сборка из двух РАЗНЫХ прочитанных
страниц документации: `model_slug: "together/hedra-avatar"` в примере
относился к другой модели («Hedra Avatar», не «Character-3»), а сам
формат `POST /web-app/public/generations` — к более старой, отдельной
поверхности API, не к тому эндпоинту, который отвечает на параметры
Character-3 (`prompt`, `start_image`, `audio`, `aspect_ratio`,
`resolution`), задокументированные на СВОЕЙ отдельной странице.
Целенаправленная повторная проверка (не по пересказу, а прямым чтением
двух дополнительных страниц — `run-hedra-character-3` и `get-job` —
9 сентября 2026) дала другой, внутренне непротиворечивый результат:
Character-3 живёт на более новой платформе `/v3` — `POST
https://api.hedra.com/v3/models/hedra-character-3` (создание задачи,
`202` + `job_id`), статус — `GET
https://api.hedra.com/v3/jobs/{job_id}`. Текст §3.2 исправлен на этот,
подтверждённый вариант. Урок: смешивать примеры кода с двух разных
страниц документации одного вендора в один блок — то же нарушение
методологии, что уже случалось в `TTS-PROVIDER-ALTERNATIVES-SPEC.md`
(находка 6.1 там) — при следующем ТЗ такого рода стоит явно
перепроверять, что все поля примера взяты с ОДНОЙ страницы, а не
собраны по смыслу из нескольких.

### Находка 2 (ИСПРАВЛЕНА). §3.3 — новый модуль изначально получил имя `avatar-generation`, хотя проект уже предложил для этой же задачи имя `actors`

`doc/AI-ACTORS-NO-REFERENCE-SPEC.md` §1.3 (открытый вопрос 1.6.2,
который этот документ и закрывает) уже спроектировал модуль
`modules/actors/` именно под «новый внешний вызов, не Veo» для
говорящей головы — первая версия этого ТЗ не сверилась с этим и завела
параллельное имя. Исправлено: модуль переименован в `modules/actors/`
(`actors.service.ts`, `actors.controller.ts`), с явной оговоркой, что
это только генерационный срез — `ActorCatalogService`/`SyntheticActor`
(общий каталог актёров сервиса, TODO п. 30) в пилот не входят и
остаются будущей задачей, использующей тот же модуль позже.

### Находка 3 (ИСПРАВЛЕНА). §4.1 — «восемь» признаков `PlanFeature` было устаревшим/неполным пересказом, не прямой проверкой

Число «восемь» пришло из отчёта параллельного агента-исследователя, чей
вывод оборвался на комментарии к девятому признаку
(`fullQualityVideo`), не попавшему в цитату. Прямая проверка
`backend/src/common/plans.ts` при аудите (9 сентября 2026) показала
девять: `library, relevance, audit, publication, brandManifest,
referenceAssets, characterReplacement, customAspectRatio,
fullQualityVideo`. Текст §4.1 исправлен на «девяти». Вывод раздела
(ни один не подходит) не меняется — `fullQualityVideo` тем более не
про говорящего аватара, он про параметр качества рендера Veo.

### Находка 4 (не про этот документ, про `video-market-research.md`) — рекомендация «добавить Cartesia» в утреннем разведочном отчёте противоречила уже принятому в проекте решению

Первый разведочный отчёт этой сессии (`video-market-research.md`, §5,
п. 5) рекомендовал добавить Cartesia Sonic как третий провайдер TTS —
и та же формулировка попала в сопроводительный текст ответа. Это
избыточно и неверно по направлению: `doc/TTS-PROVIDER-ALTERNATIVES-SPEC.md`
§5.2 уже сравнил Cartesia и Resemble **в тот же день**, по тому же
поводу (тот же скриншот вакансии) и по тому же критерию
(неотличимость от живого голоса) — и явно отклонил Cartesia в пользу
Resemble, с обоснованием, что Cartesia сознательно жертвует реализмом
ради задержки (позиционирование под голосовых агентов/телефонию, не
под контент). Resemble на голос уже реализован (этап 70). Причина
ошибки — методологическая: разведка рынка в то утро велась чтением
внешних источников (веб-поиск, блог-агрегаторы) без предварительной
проверки, не решён ли этот же вопрос уже внутри самого проекта
(`doc/TTS-PROVIDER-ALTERNATIVES-SPEC.md` был прочитан только позже,
при подготовке этого ТЗ, а не до написания разведки рынка). Следствие
для будущих задач такого рода: перед внешним рыночным исследованием
всегда проверять `doc/*-SPEC.md` на предмет уже принятых решений по
тому же вопросу — то, что должно было быть первым шагом, а не
последним. `video-market-research.md` исправлен отдельно (см. ниже);
этот документ (ТЗ на пайплайн) ошибки не наследует — голос в нём с
самого начала был Resemble, без Cartesia в рекомендациях (единственное
упоминание Cartesia в §3.1 — цитата чужого решения для объяснения
аналогии, не предложение её использовать).

### Проверено и не вызывает вопросов

- Ключевое техническое различие §2 (Sync Labs требует готовое видео с
  естественной артикуляцией; Hedra работает от одного фото) — проверено
  прямым чтением `sync.so/docs/models/lipsync` и
  `hedra.com/docs/.../generate-avatar-video.md`, не вторичных
  источников; при повторной проверке расхождений не найдено.
- Цепочка переиспользования `ResembleService`/`BrandCharacter.photoUrl`
  (§1.2–1.3) — перепроверена чтением тех же файлов повторно, без
  расхождений.
- Отсутствие в проекте инфраструктуры компоновки изображений (§1.4) —
  `grep` не находит совпадений и при повторном запуске.
- Ценовые ориентиры Hedra (§2, §4.2) — остаются оценкой со вторичного
  источника (`makefun.ai`), как и было прямо указано в первой версии;
  предупреждение о перепроверке из личного кабинета сохранено без
  изменений — сам факт «оценка, не официальный прайс» подтверждён
  повторно (официальная страница с точными $/сек не нашлась и во второй
  попытке).
