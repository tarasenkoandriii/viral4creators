# Восьмой аудит — 15 сентября 2026 (лендинг + ИИ-советник, этап 82)

По прямому запросу («полный аудит лендинга включая советника, исправить
высокие в одном заходе») — точечный аудит `landing/`, в фокусе только
что реализованный ИИ-консультант (этап 82,
`doc/LANDING-TUTORIAL-AI-CONSULTANT-SPEC.md`): виджет
`AssistantWidget.tsx`, его точки монтирования (`app/[locale]/page.tsx`,
`app/[locale]/how-it-works/page.tsx`), кнопки-триггеры в
`HowItWorks.tsx` и связанные правила `globals.css`. Второй проход —
остальной код лендинга, тронутый или соседний с этими правками
(`Header.tsx`, `Faq.tsx`, словари пяти локалей) — на предмет
рассогласований, внесённых тем же этапом. Backend/admin этого
ИИ-советника (`modules/assistant/`) в этот раз не аудировались — они
уже прошли собственную проверку при реализации этапа 82 (typecheck,
lint, 56 тестов, сверка SSE-контракта с фронтом).

**Методика.** Построчное чтение `AssistantWidget.tsx` (868 строк)
целиком, с прослеживанием каждого пути ошибки (`!res.ok`, SSE-событие
`error`, сетевой `catch`) и каждого условия рендера до конкретного
DOM-состояния; сверка с уже устоявшимися в проекте паттернами
(fail-closed по `CORS_ORIGIN`/CSRF — см. их же комментарии в коде) для
понимания, какое поведение здесь задумано. Рассмотрено ~30 кандидатов
(SSE-парсинг на границе чанков, `IntersectionObserver` на повторный
триггер, фокус-ловушка, `index` как React `key`, CORS/credentials на
`fetch`, определение pointer-типа для exit-intent, границы лимита
символов, сохранение `actions` в `sessionStorage`, дедуп проактивных
подсказок, устаревание `activeStepId` между вопросами, CLS от загрузки
конфига, «мёртвые» кнопки «Спросить об этом шаге» при выключенном
советнике) — все, кроме трёх, оказались либо уже корректны, либо
явные ложные тревоги.

Три находки — высокие, все устранены в этом же заходе. Одна —
средняя, отложена сознательно (по инструкции «исправить высокие»).

## Что исправлено (высокие)

| ID | Где | Что было | Что сделано |
|---|---|---|---|
| Н8-1 | `AssistantWidget.tsx`, `sendMessage` | Путь `!res.ok` убирал пустой временный пузырь ответа ассистента (`setMessages(prev => prev.slice(0,-1))`), а SSE-событие `error` (пришедшее уже после старта стрима) и сетевой `catch` — нет: пустой пузырь навсегда оставался в транскрипте и в `sessionStorage`. Отдельно кнопка «Повторить» всегда вызывала `sendMessage(last.content)`, которая безусловно дописывает текст новым сообщением пользователя — вопрос задваивался и в транскрипте, и в том, что уходит на бэкенд | Все три пути ошибки теперь одинаково убирают пустой плейсхолдер. `sendMessage` получил третий параметр `opts?: { retry?: boolean }`: в режиме retry история берётся как есть (`messagesRef.current`), без повторного добавления вопроса — это корректно, потому что после любой ошибки история уже заканчивается тем самым вопросом (плейсхолдер только что убран). Кнопка «Повторить» теперь зовёт `sendMessage(last.content, 'user', { retry: true })` |
| Н8-2 | `AssistantWidget.tsx:685` (было) | Гейт рендера — `if (config !== null && config.enabled === false) return null;`. Пока `config === null` (ещё грузится ИЛИ запрос `/assistant/config` не удался вовсе — например, из-за не заданного в проде `NEXT_PUBLIC_API_BASE_URL`, переменной, впервые введённой тем же этапом 82), виджет всё равно рендерил кнопку/панель — нерабочими для посетителя. Fail-open вместо fail-closed, вопреки уже принятому в проекте принципу (`CORS_ORIGIN`/CSRF: «незаданная переменная в проде закрывает, а не открывает») — и вопреки собственному комментарию в коде тремя строками выше (`// enabled неизвестен → false`), который этому поведению не соответствовал | Гейт заменён на `if (!config?.enabled) return null;` — виджет показывается только после явного подтверждения `enabled === true` из успешно загруженного конфига |
| Н8-3 | `globals.css`, `.how-it-works-layout` | `assistant.enabled` по умолчанию **выключен** в проде (§13 ТЗ: «запуск сначала с assistant_enabled=off»). До Н8-2 виджет в этом состоянии всё равно что-то рендерил, поэтому пустая 360px-колонка `<aside class="how-it-works-assistant">` на `/how-it-works` была не видна. После фикса Н8-2 `AssistantWidget` при выключенном советнике корректно возвращает `null` — и колонка `1fr 360px`, зарезервированная в CSS безусловно (`@media (min-width:1100px){ grid-template-columns:1fr 360px; }`), превращается в гарантированно пустой блок у каждого посетителя при первом запуске | Добавлено `.how-it-works-assistant:empty { display:none; }` (React `null` — truly childless DOM-узел, `:empty` матчит его корректно) и `.how-it-works-layout:has(.how-it-works-assistant:empty){ grid-template-columns:1fr; }` — сетка схлопывается в одну колонку, когда aside пуст; в браузере без `:has()` деградация — до пустого места, не до сломанной вёрстки |

Файлы: `landing/src/components/AssistantWidget.tsx`,
`landing/src/app/globals.css`.

## Закрыто вторым заходом (среднее)

- **М8-1 (ИСПРАВЛЕНО).** `HowItWorks.tsx` рендерит кнопку «Спросить об
  этом шаге» (`data-assistant-ask-step`) безусловно для обоих вариантов
  (`full` на `/how-it-works`, `teaser` на главной в `#how`) — она
  серверная (SSR, без JS работать не может по дизайну), но при
  выключенном `AssistantWidget` оставалась видимой и на вид кликабельной,
  просто ничего не делая по клику (слушатель есть, реагировать нечему).
  `HowItWorks.tsx` — серверный компонент без доступа к рантайм-флагу
  `enabled`, так что фикс — тот же CSS-приём, что и у Н8-3:
  `AssistantWidget` при выключенном советнике не рендерит вообще ничего
  (ни `.assistant-widget-floating`, ни `.assistant-widget-embedded`), и
  правило `body:not(:has(.assistant-widget)) .step-ask-btn { display:
  none; }` (`globals.css`) прячет кнопку на уровне всей страницы по
  отсутствию узла — не оставляя её видимой, но нерабочей. Деградация без
  `:has()` — кнопка снова видна, но вёрстка не ломается.

## Что проверено и подтверждено корректным

- Обработка SSE (`parseSseBlock`, разбор по `\n\n`, буферизация неполных

  корректно снимает `stepId`/`title` и открывает панель с контекстом.
