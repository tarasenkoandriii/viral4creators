### 4.3 Живой прогон на Gemini — blocked

- **Причина:** ключа `GEMINI_API_KEY` нет, стоимость не утверждена (§17 плана).
- **До запуска рекомендуется закрыть D2-01 и D2-04.** Иначе протокол будет без параметров вызова (§16), а допуск можно будет получить повторами.
- **Команда (владелец, рабочая база, eval-продукт `kind=eval`):**
  ```
  cd sites-backend
  GEMINI_API_KEY=<ключ владельца, не в репозитории> SITES_DATABASE_URL=<рабочая база> \
  npm run eval:publisher -- --mode=live --product=<id eval-продукта> --seed \
    --config=f9bee424c485141ac4d40321cd01f93a2c5a622eb3b24ac726ca5e125f7cee56 \
    --max-usd=2 --out=publisher-eval-live.md --json=publisher-eval-live.json
  # вариативность: ×3 повтора критических задач в ТОТ ЖЕ прогон (провал любого повтора блокирует допуск):
  npm run eval:publisher -- --mode=live --product=<id> --run=<runId> \
    --only=AI-05,AI-06,AI-09,AI-10,AI-25,AI-26,AI-27,AI-28,AI-29,AI-30 \
    --config=f9bee424…ee56 --max-usd=2      # выполнить 3 раза
  ```
  `--config` совпадает, только если `GEMINI_MODEL` не задан или равен `gemini-3.6-flash`. Модель без ставки получает отказ, если не указан `--allow-unpriced`.
- **Стоимость по прайсу** (`shared/ai-pricing.ts`, gemini-3.6-flash: $0.75/M вход, $3.75/M выход — вводная ставка до 31.12.2026, дальше $1.50/$7.50):
  - Верхняя оценка кода на прогон 30 задач — **3,01 USD**: потолок промпта 120 000 токенов × 30. Поэтому `--max-usd` останавливает прогон раньше потолка — не запускает задачу, если `потрачено + оценка > лимит`.
  - Реалистичная оценка. Системный промпт ≈ 2,0–2,4 тыс. символов, пользовательский — 0,3–1,0 тыс. (A1), то есть ≈ 1,5–2 тыс. токенов входа. Вывод ≈ 0,3–0,9 тыс. токенов плюс до 1024 токенов размышлений. Это ≈ $0,008–0,01 на вызов, **≈ $0,25–0,30 на 30 задач** и столько же на 3×10 повторов. **Итого ≈ $0,5–0,6** по вводной ставке, ≈ $1–1,2 после 2026-12-31.
  - **Предлагаемый лимит к утверждению:** `--max-usd=2` на каждый запуск (4 запуска — жёсткий потолок $8, ожидаемо ≈ $0,6).
- **Что нужно от владельца:**
  1. Ключ Gemini в окружении запуска.
  2. Утверждённая стоимость.
  3. Id eval-продукта в рабочей базе.
  4. Оценщики PO/ED: разбор флагов, critical/usefulness для 30 строк и 30 строк повторов, второй оценщик при споре.
  5. Решение по D2-01/D2-04 до запуска.
  6. После `passed` — привязка рабочего продукта (`POST …/ai/bindings`).

## 7. Наблюдения без карточки

1. **Смысловые нарушения контур не ловит, и это ожидаемо.** Неподдерживающий источник, выдуманный кейс, однозначное выдуманное число вместо диапазона ловит только живая модель плюс человек. Находки контура — предупреждения. Поэтому живой прогон — обязательное условие допуска, а не формальность.
2. **Канарейки проверяются только в прогоне набора.** В рабочем режиме выход модели на маркеры не проверяется. Это верно по дизайну: в контекст закрытое не попадает (X-09/X-10).
3. **Гейт не сверяет `evalSetVersion`.** Если набор задач выйдет в версии 2.3, конфигурации, допущенные по 2.2, останутся `passed`. Набор 2.2 требует полного прогона только при смене модели, провайдера или правил; решение — за владельцем.
4. **Модель задаётся именем `gemini-3.6-flash`** (алиас провайдера). Если провайдер обновит модель под тем же именем, hash не изменится. Нужна внешняя сверка и, по возможности, закреплённое имя версии.
5. **Маска не покрывает** `(at)`-обфускацию email и ссылки на соцсети (`instagram.com/…`). Единое правило P-A1 их тоже не считает контактом (согласовано, `pure-probe.json`).
6. **Строка без ответа в протоколе** помечается жёстким провалом `schema`, а итоги показывают `hardFailed 1` при `thresholdsMet true`. Это противоречие входит в D2-01.
7. **Очередь `/cron/publisher-minute` требует поминутного крона** (Vercel Pro) — это из отчёта P-B2 §9.5. На Hobby вызовы после 202 будут ждать перевода задания на tick.
8. Кэш `/tmp/jest_0` (28 МБ) не удалял, чтобы не мешать параллельным агентам.
