# Проверка качества демо через Gemini

Проектирование, 06.10.2026. Это план реализации; проверка ещё не включена.

## Цель и границы

После существующей сборки демо автоматически находить непригодные записи
и отдавать оператору отчёт с таймкодами. Поддержать рекламный сценарий,
поздравления и обучалку по сайту, ru/uk/en/de/es, light/dark, browser/TMA.
Каждая комбинация проверяется отдельно; качество светлой версии не
подтверждает тёмную. ИИ не выставляет `reviewed=true`.

Повторно использовать `createGeminiClient`, `GEMINI_MODEL`,
`GeminiFilesService` и `AiUsageService`. Существующий `VideoAuditService`
оценивает сгенерированные пользовательские ролики и привязан к сессиям:
демо нужен собственный prompt и отдельный сервис, без изменения сессии,
промпта генерации, лимитов или баланса пользователя.

## Место в существующем кроне

1. Съёмка и сборка работают как сейчас. После `assemblyStatus=complete`
   создать задачу проверки готового MP4; ошибка проверки не меняет статус
   успешной сборки.
2. Существующий `tutorial-assembly-poll` вызывает ограниченный обработчик
   очереди качества. Не запускать весь анализ внутри callback сборщика:
   долгие Gemini upload/processing не должны задерживать его ответ.
3. Начать с одного актива за тик и одного параллельного анализа. Проверять
   оставшийся бюджет времени функции; загрузку/ожидание/анализ сохранять
   как отдельные фазы между тиками. Текущий uploadAndWaitActive ждёт внутри
   вызова: для очереди выделить upload и проверку состояния файла, не меняя
   поведение остальных клиентов сервиса.
4. Атомарный claim с lease и восстановлением после падения. Ключ
   дедупликации: assetId + contentHash + rubricVersion + modelId. Повторный
   cron не оплачивает уже выполненную проверку. Изменение файла создаёт
   новую проверку; смена рубрики — только явно запланированную переоценку.
5. 429/сетевые/5xx — максимум три попытки с отложенным exponential backoff.
   После лимита — `error`, отдельно от заключения «плохое видео». Невалидный
   ответ, safety refusal и неопределённость дают `needs_review`, не `pass`.
6. Флаг включения, дневной лимит расходов и лимит минут видео. При
   превышении бюджета задача остаётся pending до следующего окна.
   Учитывать реальное token usage через AiUsageService; не списывать деньги
   с пользователя. Для неизвестной цены сохранять unpriced и не считать
   её нулевой.

## Вход и проверка

Передавать готовое видео и ожидаемый сценарий: предмет темы, список шагов,
ожидаемые подписи/результат, локаль, тему, viewport, режим browser/TMA,
frontend commit/build, дату съёмки и безопасные контрольные кадры этой
же версии UI. Метаданные сохранять во время съёмки, а не угадывать из MP4.
Без этих данных проверка актуальности получает `unknown`.

Сначала технический preflight в существующем media/ffmpeg-контуре:
файл декодируется, длительность/размеры допустимы, кадры не полностью
чёрные, нет длинного пустого начала/конца. Проверка freeze учитывает
сценарий: неподвижный учебный слайд сам по себе не ошибка.

Gemini оценивает:

- Читаемость текста и кнопок при целевом мобильном размере, обрезанные
  элементы, перекрытия, контраст в выбранной теме.
- Покрытие обещанных шагов и наличие результата; соответствие заголовка
  теме, последовательность действий и ясность переходов.
- Спиннеры, страницы ошибок, неожиданную авторизацию, недогруженные
  изображения, неверную локаль и тему.
- Темп: хватает ли времени прочесть подпись; лишние паузы и резкие обрывы.
- Соответствие озвучки и подписей видимым действиям, если они есть.
  Нет звуковой дорожки у намеренно беззвучного демо — не ошибка.
- Видимые персональные данные, токены и неприкрытые реальные аккаунты.
  Для демонстрации ожидаются fixture-данные; наличие утечки — блокирующий
  сигнал. Отчёт хранит категорию и таймкод, не копирует секрет целиком.

Gemini поддерживает анализ видео с привязкой к таймкодам
([официальная документация](https://ai.google.dev/gemini-api/docs/video-understanding)).
Его заключение вероятностное: краткий дефект может не попасть в выборку.
Для подозрительного интервала использовать дополнительный анализ
контрольных кадров; технические показатели получать из декодера.
«Актуально» нельзя вывести только из хорошей картинки: сравнивать
capture build с текущей версией frontend; несовпадение означает
`stale_candidate`, а не автоматическую порчу или удаление видео.

## Контракт результата и хранение

Отдельная запись TutorialDemoQualityCheck, связь с TutorialVideoAsset:
status (`pending/running/complete/error`), verdict
(`pass/needs_review/reject`), assetHash, rubricVersion, modelId,
captureBuild, captureTheme, captureMode, locale, checkedAt, attempt,
leaseUntil, nextAttemptAt, providerFileName, tokenUsage, estimatedCost.
JSON отчёта: оценки 0–100 по читаемости/покрытию/темпу/согласованности,
`issues[]` с code, severity, startMs, endMs, explanation, confidence,
`missingEvidence[]`, freshness (`current/stale_candidate/unknown`).

Ответ ограничить JSON Schema и валидировать на сервере: допустимые enum,
диапазоны оценок, таймкоды внутри длительности, лимит числа/длины проблем.
Текст внутри видео считать данными, не инструкциями модели.
Не принимать рекомендацию без конкретного наблюдения/таймкода.
Итоговый verdict вычисляет сервер по проверенной рубрике, а не произвольный
текст модели. Предварительный порог pass: все оценки ≥80, нет critical,
нет missingEvidence; калибровать на размеченных примерах до включения gate.

Удалять файл Gemini после завершения/ошибки; имя сохранять сразу после
upload, чтобы уборка находила файл после падения функции. Очистка при
удалении актива каскадно убирает проверки и внешние временные файлы.
Не допускать удаления актива retention-процессом во время живого lease.

## Оператор и публикация

В админке: статус проверки, оценки, версия/тема/режим, таймкоды дефектов,
просмотр соответствующего фрагмента, повторить проверку, одобрить/отклонить.
Операторское override требует причины и сохраняется в журнале.
Не переобозначать старые `reviewed` ролики как прошедшие ИИ. Отдельного
статуса `unchecked` в контракте нет (см. «Контракт результата»: `status` —
состояние прогона `pending/running/complete/error`, `verdict` —
`pass/needs_review/reject`, есть только у `complete`). «Не проверен ИИ» —
это актив БЕЗ записи TutorialDemoQualityCheck; админка показывает его так,
а не как pass. Backfill создаёт для таких активов записи со
`status: pending`, с ограничением бюджета.

Первая фаза — наблюдение: отчёты не меняют действующую публичную выдачу.
Фаза (наблюдение / gate) сейчас задаётся флагом включения (см. «Приёмка»,
п.1); поле `phase` в записи проверки — **предлагается, в контракте пока
нет**.
После калибровки новые публикации требуют pass либо явного override
оператора; старые опубликованные материалы сохраняются до отдельного
решения. При плохом новом ролике публичный API оставляет последний
одобренный, а не публикует сырую запись и не показывает пустой плеер.
Ввести тему/режим в TutorialVideoAsset и публичную выдачу отдельной
миграцией; `unknown` не выдавать за light или TMA.

## Дашборд внимания — первая страница админки

Сейчас `admin/src/app/page.tsx` перенаправляет на `/sessions`. Заменить
его основной страницей и добавить «Обзор» первым пунктом AdminNav.
Текущие рабочие страницы остаются местом подробного разбора и действий.

Основное содержимое — общая очередь, а не графики успешных запусков:

1. Блокирующие проблемы: сбой/просроченный ожидаемый cron, зависшая сборка,
   исчерпанные повторы качества, critical-дефекты и утечки в демо.
2. Решения оператора: демо с `needs_review`, готовые проверки на одобрение,
   публикации, ожидающие существующей ручной модерации.
3. Обслуживание: подозрение на устаревший интерфейс, нет пригодного демо
   для обязательной комбинации сценарий/язык/тема/режим, лимит бюджета.

Для каждого пункта: тип, краткая причина, severity, первое появление,
возраст, последнее обновление, число повторов и ссылка на конкретную
запись/задачу. Сортировка severity → возраст; фильтры тип/сценарий/локаль.
Порог отсутствующего cron считать по его расписанию и часовому поясу,
с допуском на завершение. Ночной/дневной перерыв сценарного cron не ошибка.
Матрица обязательных демо задаётся явно; не требовать все возможные
комбинации и не выводить сотни искусственных предупреждений.

Backend агрегирует существующие источники через защищённый
`GET /api/admin/attention`: ограниченная пагинация, стабильный cursor,
счётчики по severity, fetchedAt и состояние источников. Источники
проверяются независимо: недоступный источник отображается как «не удалось
проверить», а не зелёный ноль. Использовать существующий admin guard.
Не отдавать секреты, сырые промпты или персональные данные в карточках.

Не хранить вторую копию бизнес-статусов: элемент закрывается при устранении
причины в исходном объекте. Если нужен отложенный разбор — отдельные
assignment/snooze со сроком, автором и причиной; это не одобрение и не
скрытие ошибки для всех. Дедупликация по типу и объекту; повторный cron
обновляет запись, не создаёт новую карточку на каждый тик.

В первой версии только чтение и переходы к существующим действиям;
никаких массовых одобрений с обзорной страницы. Автообновление раз в
минуту с паузой на скрытой вкладке, кнопка обновления, явное время
последней успешной загрузки. Состояние «нет задач» показывать лишь после
успешного ответа всех подключённых источников.

Приёмка: root открывает обзор после обычной авторизации; критическая
ошибка выше ожидающего ролика; устранённая проблема исчезает;
повторный запуск не дублирует карточку; ночной перерыв не помечается как
сбой; частичный отказ источника виден; ссылки открывают правильный объект;
неавторизованный запрос не получает очередь. Операторский TODO:
согласовать обязательную матрицу, пороги просрочки и источники модерации.
