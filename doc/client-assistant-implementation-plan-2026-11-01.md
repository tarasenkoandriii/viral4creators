# Клиентский помощник: этапы реализации

Дата: 1 ноября 2026. Основание: клиентское ТЗ v1.2 и повторный сквозной аудит от 01.11.2026.

## Правила работ

Развивать существующий контур, без второго помощника и дублирующей библиотеки. Не менять конфигурации других клиентов, Nova и принятую сборку. Платные проверки только с отдельно согласованным бюджетом. Зелёные локальные тесты не заменяют браузерную и аппаратную приёмку. Ранее локальные этапы не включали deployment. 7 ноября владелец отдельно разрешил выпуск подготовленных изменений; статус релиза приведён ниже.

## Этап 4B — первый реальный источник

Общая запись `generatedVideo` в SessionService стала producer для сессионного видео. Проекция строится из строки, возвращённой реальным UPDATE (включая владельца), а не из присланного client userId. Одна транзакция включает обновление сессии и upsert журнала; ошибки не проглатываются и не вызывают повторный provider request. Невидеоправки используют прежний путь без дополнительной транзакции. Гостевые и явно удалённые сессии не получают личную запись.

Статусы pending/processing/complete/failed отображаются в queued/processing/complete/failed; один generatedVideoId — одна попытка. Revision здесь отражает стадию (queued=0, unknown=1, processing=2, terminal=3), а не полный журнал переходов. Terminal-исход не откатывается поздним событием. Provider/resolution берутся из фактического видео; модель и источник не выдумываются: при отсутствии метаданных source=`unknown`, model остаётся null. createdAt — момент первой записи в журнал, не доказанное время клика/начала provider job.

## Этап 4D — сетевой исход dispatch и фоновые очереди

После отправки платного POST отсутствие подтверждённого результата не доказывает отказ. Новый ProviderDispatchUnknownError с безопасным текстом и кодом GENERATION_RECONCILIATION_REQUIRED используется для timeout, сетевых обрывов, нетипизированных ошибок SDK, 5xx и неожиданных ответов. Явные 4xx рассматриваются как отказ, кроме 408/409/499: эти ответы тоже требуют сверки. Это консервативное правило приложения, а не обещание протокола провайдера.

- [x] Veo generateVideos и Grok start: нет автоматического повторного send при неопределённом исходе; журнал получает unknown, автоматический refund кредитного резерва запрещён до сверки. Локальная ошибка подготовки ДО send по-прежнему failed и обрабатывается прежним безопасным refund.
- [x] Fallback Veo 9:16 → 16:9 возможен только после явного отказа, не при неизвестном исходе с похожим текстом.
- [x] Grok sync: 2xx без request_id и неуспешные неоднозначные ответы требуют сверки; локальные проверки входа остаются до сети.
- [x] Grok batch: outcomeUnknown проходит через create/add/submit, включая потерянный ответ добавления запросов и частичное принятие. Best-effort cancel не считается доказательством, что расход не возник.
- [x] Catalog batch сохраняет pending-маркер при outcomeUnknown; очередной тик не переподаёт его автоматически. Существующее предупреждение о старом маркере требует ручного разбора.
- [x] Catalog/A-B worker не планирует новую оплачиваемую попытку при ProviderDispatchUnknownError. FAILED в очереди означает остановку automation, не доказательство того, что внешний рендер не состоялся; текст ошибки и личный journal unknown сохраняют это различие.
- [ ] Безопасный интерфейс reconciliation и сверка provider handles ещё не реализованы. Автоматически снимать блокировку/размораживать резерв по таймеру нельзя.
- [ ] Scene extension/продления, Hedra/аватары и прочие пути не объявляются покрытыми этим изменением. Grok extend оставлен вне нового dispatch wrapper; read-only polling допускает собственные повторы без новой платной генерации.
