## 1. Выбранное направление (вариант C)

Версия Veo — **не пользовательский выбор**. Пользователь видит только
одно новое поле: **«Чего избежать»** (свободный текст, необязательное).
Версия модели подбирается автоматически:

- **Нет персонажей бренда** у сессии (`plan.legacyFirstFrame === true`,
  `buildReferencePlan`) → **Veo 3.0**, поле «Чего избежать» уходит в
  `negativePrompt`.
- **Есть хотя бы один персонаж бренда** (режим `referenceImages`) →
  **Veo 3.1**, как сейчас — Veo 3.0 официально не принимает
  `referenceImages` (см. §2 ниже, без изменений с прошлой версии ТЗ).

Пользователь не выбирает версию и, по умолчанию, не обязан знать, что
версии вообще две — только видит эффект (можно попросить не делать
что-то) и результат (какой моделью получилось, см. §4).

**Пересмотрено при аудите (§12), после появления §10–11.** Когда
писалась эта версия, единственным способом получить `negativePrompt`
было незаметное переключение на Veo 3.0. Теперь у пользователя есть
прямой путь к тому же результату — вручную выбрать Grok (§11), у
которого нет статуса deprecated-модели (§9.2) и нет неподтверждённости
`negativePrompt` именно на 3.1 (§3). Это НЕ отменяет §1 — авто-
переключение по-прежнему полезно ТЕМ, кто вообще не задумывается о
выборе провайдера, — но снижает срочность: часть ценности, ради
которой затевался весь §1, пользователь теперь может получить сам,
просто выбрав Grok в §11, без единой строки нового кода. Стоит
учитывать при расстановке приоритетов реализации — не обязательно
делать в первую очередь, если §11 уже есть.

### 1.1 Реализовано (этап 5 плана §14 — доведён до конца по прямому запросу)

- `common/veo-model-choice.ts` — `pickVeoModel()`/`usesVeo30()`, чистые
  функции с тестами. Область — только `quality === 'standard'`: у
  Veo 3.0 нет задокументированного Lite-аналога (более старое
  поколение, чем сам сплит Lite/Standard), поэтому `fast` всегда
  остаётся на Veo 3.1 Lite, как и раньше.
- Поле «Чего избежать» (`avoidText`) — от DTO до промпта: настоящий
  `negativePrompt`, когда включился Veo 3.0; иначе (Veo 3.1, `fast`,
  Grok) — best-effort строкой в промпт (§4.1 ТЗ). Для Grok это и есть
  ответ на открытый вопрос из §9 («одно поле на все провайдерские
  пути») — решено: да, тот же best-effort приём, не отдельная логика.
  Перенесено и на продолжения цепочки (§9), не только на первый
  сегмент.
- ⚠️ Точный ID модели Veo 3.0 (`veo-3.0-generate-001`) — ДОГАДКА, не
  подтверждённый факт (Veo 3.0 к тому же официально deprecated, §9.2)
  — тот же принцип «ПРОВЕРИТЬ перед стройкой», что уже применяется к
  остальным моделям в `common/ai-pricing.ts`.
- При реализации нашёлся и исправлен реальный регресс: продолжение
  цепочки (`continueVeoChain`, §9) пересчитывало модель заново через
  `VEO_MODELS[quality]`, не учитывая, что базовый сегмент мог уже идти
  на Veo 3.0 — расширение чужой моделью почти наверняка не сработало
  бы вовсе. Исправлено — продолжение теперь берёт модель из того же
  плана персонажей, что и базовый сегмент.

## 2. Несовместимость с персонажами — почему правило именно такое

Без изменений от прошлой версии этого ТЗ: `referenceImages` — не
редкий путь, а стандартный режим для любого бренда, где заведён хотя
бы один персонаж (платная функция §10.2, Standard и выше). Официальная
таблица параметров Veo отмечает `referenceImages` как `n/a` для
Veo 3/3 Fast. Правило переключения в §1 — прямое следствие этого
факта, не гипотеза.

## 3. Что подтверждено / не подтверждено (без изменений по сути)

Подтверждено: Veo 3.0 принимает `negative_prompt` (официальный пример
Google) и `image` (первый кадр, путь `legacyFirstFrame` не меняется).

Не подтверждено (снимается ручной проверкой ДО реализации, не после):
- Точные ID моделей Veo 3.0, доступные сегодня через `@google/genai` —
  preview-алиасы или только deprecated GA (`-001`).
- Написание поля в TS-клиенте — `negativePrompt` (camelCase, по
  аналогии с `durationSeconds`/`aspectRatio`) — предположение, не факт.
- Тарификация Veo 3.0 в `common/ai-pricing.ts` — та же, что 3.1, или
  другая.
- Ограничения Veo 3.0 по `aspectRatio`/`durationSeconds` — не факт, что
  совпадают с 3.1.

**Рекомендация не изменилась**: один ручной тестовый вызов вне
продакшн-трафика перед стройкой — тот же метод, которым в этом
проекте уже ловили `generateAudio`.

## 4. Новое требование: версия видна и клиенту, и оператору

`GeneratedVideo` (бэкенд и фронтенд зеркала) получает поле
`veoModel: '3.0' | '3.1'` — заполняется в момент старта рендера, вместе
с `generatedVideoId`.

Оба уже существующих места показа истории версий (этот же разговор,
предыдущая фича) получают эту метку, без новых экранов:
- **Админка**, список сессий → «▾ Версии» → в строке каждой попытки
  рядом со статусом/качеством/форматом добавляется «Veo 3.0» или
  «Veo 3.1».
- **Визард пользователя**, экран «Готово» → переключатель вариантов
  ролика (`VideoPlayer.variants`) → в подпись каждой прошлой попытки
  (`previousAttemptLabel`, уже показывает дату) добавляется версия
  модели: «Спроба від {{date}} (Veo 3.0)».

Обоснование по кнопке «Проверить на артефакты» отдельно: если аудит в
будущем будет знать версию модели (не входит в это ТЗ, см. §6), это
уже пригодится для сравнения, какая версия даёт меньше проблем на
практике — без сбора этих данных такое сравнение никогда не станет
возможным.

Одна попытка — одно значение `veoModel`, история версий (`videoHistory`)
может содержать РАЗНЫЕ значения на разных попытках одной сессии (если
персонажа бренда завели между попытками) — это ожидаемо, отдельной
обработки не требует: та же история уже смешивает разные `quality`/
`aspectRatio` между попытками сегодня.

### 4.1 Что происходит с полем «Чего избежать» на Veo 3.1 — решено

Текст поля не молчит и не блокируется предупреждением: на Veo 3.1 он
вставляется в основной (положительный) промпт как отдельная явная
строка — например, добавочная строка вида «Avoid: <текст
пользователя>» в конец `promptText` перед отправкой в Veo (тот же
`generation.service.ts`, где сейчас собираются `referenceMappingText`
и `render.compositionNote` — присоединяется туда же, тем же
`.filter(Boolean).join('\n')`).

Важная оговорка для реализации: это **не то же самое**, что
`negativePrompt` — модель получает просьбу «не делай X» внутри общего
описания сцены, а не как отдельный параметр с более сильным весом.
Эффект слабее и без гарантии (то, ради чего изначально всё
затевалось), но это честный компромисс: лучше слабый эффект и видимый
пользователю текст, чем тихая потеря его ввода. В интерфейсе имеет
смысл не обещать того же результата, что даёт настоящий
`negativePrompt` на Veo 3.0 — например, не называть поле одинаково
многообещающим для обоих путей.

## 5. Обратимость — по вашей просьбе

Фича задумана как временная/experимental: если поле «Чего избежать»
не наберёт использования, авто-переключение на Veo 3.0 предполагается
снять. Чтобы это было дешёвой правкой, а не повторным проектированием:

- Вся логика выбора версии — в ОДНОЙ функции (например,
  `pickVeoModel(plan): '3.0' | '3.1'`), вызываемой из одного места
  `generateVideo()`. Откат — заменить её тело на константу `'3.1'`.
- Поле «Чего избежать» в UI — за одним условным рендером (не размазано
  по нескольким экранам), чтобы его можно было убрать одним изменением.
- `veoModel`/история версий (§4) — НЕ убираются при откате: это чистые
  данные о прошлом, а не часть механизма выбора; они остаются
  полезными сами по себе (см. последний абзац §4).
- Порог/момент, когда считать фичу «без клиентов» — **решено**, см.
  §6 п.4: 4 недели, порог 5% сессий с заполненным полем.

## 8. Новое предложение: отдельный шаг генерации текстов (доп. запрос

не предлагал и не проводил.

### 8.1 Почему повтор генерации не помогает — два разных дефекта, не один

Важно не смешивать их в одном исправлении:

**(а) Veo сам путает реплику.** И `veo`, и `voiceover`, и `dub` режимы
одинаково просят Veo озвучить реплику словами, зашитыми ВНУТРИ одного
большого промпта сцены (`prompt.service.ts` — реплика формируется тем
же вызовом модели, что пишет камеру/свет/действие, а не отдельно и не
дословно). Модели сцены ничего не мешает перефразировать, повторить
или смешать реплику с остальным текстом промпта — она не видит эту
строку как «сказать один раз буквально», она видит её как часть
описания сцены.

**(б) Двоение в режиме `voiceover` — отдельная, архитектурная причина,
не только промпт.** Проверил `common/postprod.ts`: в `voiceover`
исходная дорожка Veo НЕ вырезается, а лишь приглушается (`DEFAULT_DUCK
= 0.25`, то есть 25% громкости) и подмешивается (`amix`) под
наложенный TTS-голос — комментарий в коде объясняет это тем, что
дорожка Veo несёт атмосферу и музыку, которую жалко терять. Это верно
для ФОНОВОГО шума, но Veo в этом же аудио обычно ещё и произносит
реплику — то есть под наложенным чистым голосом TTS ВСЕГДА звучит
второй, тише, но разборчивый голос, произносящий похожий текст. Это
воспринимается как «двоение — троение», и никакая перегенерация видео
это не починит: причина не в конкретной попытке, а в том, как ролик
собирается КАЖДЫЙ раз. (В `dub` эта причина отсутствует — там дорожка
Veo не подмешивается, а полностью заменяется: `mode === 'dub'` ветка.)

### 8.2 Предложение (как в сообщении) — отдельный шаг, буквальное использование

Новый, узкий шаг генерации — до/рядом с основным написанием промпта
сцены — выдаёт РОВНО два текста, а не один большой промпт:
- `dialogueText` — реплика(и) дословно, как должны прозвучать;
- `onScreenText` — текст на экране дословно, если он вообще нужен
  (короткий — до 100 символов, см. открытый вопрос 3).

Возможно другой моделью, чем основной промпт сцены (дешевле/быстрее —
задача узкая, не требует творческого описания камеры и света).

Финальный промпт для Veo получает эти строки уже готовыми и
ЦИТИРУЕТ их буквально, с явным запретом на повтор/перефраз — например:
```
The character says this line once, exactly as written — do not repeat,
rephrase, or add anything else to it:
"{{dialogueText}}"
```
```
On-screen text reads exactly, once, and nothing else visible:
"{{onScreenText}}"
```
Это меняет роль `voiceoverBriefText`/`voiceModeBriefText`
(`common/voiceover.ts`) — сейчас это инструкция для модели сцены,
которая сама пишет реплику; станет инструкцией/ограничением для
НОВОГО узкого шага, который реплику фиксирует один раз и передаёт
дальше без изменений.

### 8.3 Как это ложится на три воркфлоу (`veo` / `voiceover` / `dub`)

- **`veo`.** Единственный слой звука — то, что сгенерировал сам Veo.
  Буквальная цитата реплики снижает шанс, что Veo сам её повторит или
  смажет — это прямое попадание §8.2 в цель.
- **`voiceover`.** Буквальная цитата снижает шанс, что РЕПЛИКА ВНУТРИ
  видео Veo будет искажена/повторена, — но не решает §8.1(б) саму по
  себе: пока `DEFAULT_DUCK` подмешивает дорожку Veo под TTS-голос,
  второй голос слышен независимо от того, насколько точна реплика.
  Предлагается решать §8.1(б) отдельно, в этом же заходе, одним из:
  - **(i)** сильнее приглушать дорожку Veo именно когда в ней есть
    речь (например, 0.10–0.15 вместо 0.25) — дёшево, но теряет больше
    атмосферы/музыки, чем сейчас;
  - **(ii)** фильтр подавления голосовых частот на дорожке Veo ПЕРЕД
    `amix` (полосовой/вокал-ремувер поверх `[0:a]`, до `volume=`), так
    что после дакинга остаётся в основном фон, а не тише-голос-плюс-фон
    — точнее, но требует отдельного аудио-инженерного захода
    (подбор параметров фильтра, проверка на реальных роликах), не
    угадывается с одного раза.
  Без явного решения по (i)/(ii) эта часть проблемы останется даже
  после §8.2 — стоит проговорить это пользователю в самом ТЗ, чтобы
  «сделали, а не починилось» не стало сюрпризом.
- **`dub`.** Дорожка Veo не участвует в микшировании вовсе — двоения
  звука здесь и так нет по конструкции. Буквальная цитата реплики
  всё равно полезна — для точности движения губ персонажа относительно
  текста дубляжа (артикуляция Veo ориентируется на то, что написано в
  промпте, даже если этот звук потом выбрасывается).

### 8.4 Что это НЕ чинит

Это снижает риск дублирования/перефраза и повышает шанс, что Veo
буквально произнесёт/покажет то, что написано — но не устраняет саму
слабость Veo в точной прорисовке мелкого текста на экране (особенно
кириллицы) как таковую. Для текста, где важна точная читаемость
(цена, номер телефона, точное написание бренда), в проекте уже есть
более надёжный путь — вшитые субтитры (рендерятся из настоящего
текста через ffmpeg, а не рисуются Veo по описанию) — стоит усилить
это направление пользователю в интерфейсе, а не полагаться на Veo для
критичного текста даже после этого исправления.

## 9. Ролики до минуты через Veo Scene Extension (решено и реализовано)

**Повод:** запрос поддержать до 5 фраз по 80 символов в `onScreenText`
(§8) был на самом деле про ролики другой длины, не про один
8-секундный клип — при таком контексте 5 фраз по одной на несколько
сегментов длинного ролика имеют смысл, чего не было бы в рамках одной
8-секундной генерации. Обсуждаем отдельно от §1–8, это самостоятельная
фича со своими рисками.

### 9.1 Что подтверждено официально

- Veo 3.1 имеет функцию **Scene Extension**: продолжает существующий
  клип, отталкиваясь от последней секунды предыдущего сегмента,
  сохраняя стиль/персонажей/звук. Официальный блог Google:
  «create longer videos, even lasting for a minute or more». Заявлено
  доступной **через Gemini API** (не только Vertex) —
  `ai.google.dev/gemini-api/docs/veo`, раздел «Video extension».
- Каждый сегмент — около 7 секунд (по независимым источникам,
  «7s extension hops»); выход одного вызова расширения — уже ПОЛНОЕ
  склеенное видео (исходный + новый сегмент), а не только новый
  кусок — отдельного шага склейки через ffmpeg на нашей стороне,
  похоже, не требуется.
- Модель `veo-3.1-generate-preview` (то, что у нас сейчас — `standard`
  качество) в принципе подходит.

### 9.2 Риски — тот же класс, что уже дважды ловили в этом ТЗ

- **Официально задокументировано, но нестабильно на практике.** На
  форуме Google (discuss.ai.google.dev, конец октября 2025) —
  открытый, на вид неразрешённый тред «How to correctly structure the
  'video' object for Veo 3.1 endpoint?»: разработчик шлёт `video`
  ровно по документации на `veo-3.1-generate-preview:predictLongRunning`
  и получает отказ с жалобой на формат объекта. Отдельный форумный тред
  (декабрь 2025) — та же жалоба про `reference_images`: «показано в
  документации как доступное, код 400 INVALID_ARGUMENT "Your use case
  is currently not supported"». Это тот же паттерн, что уже был с
  `generateAudio` и `negativePrompt` в этом самом ТЗ — необходима
  ручная проверка живым вызовом ДО реализации, не после.
- **`fast`-качество не поддерживает расширение вовсе.** Официальная
  страница модели: «Veo 3.1 Lite Preview... does not support 4K outputs
  or Extension». Наш `quality: 'fast'` — это именно
  `veo-3.1-lite-generate-preview` (`VEO_MODELS`,
  `generation.service.ts`) — то есть длинные ролики физически доступны
  ТОЛЬКО через `standard`, не через `fast`, каким бы качество ни было
  выбрано пользователем сейчас по умолчанию (`DEFAULT_QUALITY =
  'fast'`).
- **Стоимость растёт линейно с числом сегментов, не с длиной один раз.**
  Каждый «hop» расширения — отдельный биллингуемый вызов Veo, похожий
  по цене на обычную генерацию. Ролик в 2 минуты — это база (8 с) плюс
  ~16 сегментов по 7 с — то есть **порядка 15–17-кратной стоимости**
  одной обычной генерации. Это несовместимо с текущими дневными
  лимитами как есть (`common/spend-limits.ts` — Lite $2/сутки, Premium
  $100/сутки после недавнего повышения): один такой ролик на Lite
  невозможен в принципе, а на Premium — это ощутимая доля дневного
  лимита за ОДИН ролик.
- **Совместимость с остальным ТЗ.** `referenceImages` (персонажи
  бренда, §2) и `video` (расширение) — разные параметры запроса; не
  проверено, можно ли использовать оба одновременно в одном вызове —
  если нет, длинные ролики с персонажами бренда могут оказаться
  недоступны тем же способом, что и Veo 3.0 в §1–2.
- **Направление продукта Google.** Та же официальная страница видео-
  генерации называет Veo 3.1 инструментом «for specific capabilities
  like scene extension... when required», а НОВУЮ модель Gemini Omni
  Flash — рекомендуемым выбором по умолчанию для видео вообще. Это не
  блокирует использование Veo Extension сегодня, но стоит иметь в виду
  при оценке того, насколько долгосрочно поддерживаемый это путь.

### 9.3 Как это соотносится с §8 (отдельный шаг генерации текстов)

Изначальный вопрос (5 фраз по 80 символов) обретает смысл именно
здесь: при многосегментном ролике логично распределить `onScreenText`
по сегментам (не более одной фразы на сегмент одновременно, то же
ограничение читаемости, что в §8.2, просто на несколько экранов
времени, а не один), а не пытаться показать 5 фраз одновременно в
одном 8-секундном кадре. `dialogueText` из §8.2 тоже становится ЛИСТОМ
реплик (по одной на сегмент), а не одной строкой — естественное
расширение той же архитектуры, не с нуля.

### 9.4 Решение (по вашему сообщению) — закрыто

**Триггер.** Разбор референса (`AnalysisService`, уже существующий
вызов Gemini для анализа загруженного видео) сообщает длительность
референсного ролика как **новое поле существующего структурированного
вывода** — отдельного вызова/ffprobe ради одной только длительности не
заводим (тот же принцип экономии вызовов, что уже применяется в
проекте — см. `common/reframe.ts`, «Почему без ffprobe»). Сейчас этого
поля нет вовсе — обнаружено при подготовке этого ТЗ, отдельная,
маленькая правка в схему анализа. Если длительность референса больше
8 секунд — предлагаем длинный ролик.

**Лимит.** До 7 вызовов Veo на один ролик (база + до 6 расширений) —
около минуты суммарно. Максимальная длительность генерации — МЕНЬШЕЕ
из: (а) длительности исходного референса, (б) 7×8 = 56 секунд. Точная
длина одного «хопа» расширения (по независимым источникам — около 7,
не 8 секунд) — подтверждается тем же ручным тестовым вызовом, которым
проверяется сама доступность параметра (см. ниже); если хоп короче
8 секунд, потолок в секундах и число вызовов для достижения
референсной длины могут немного разойтись — не блокирует реализацию,
уточняется на этом же тесте.

**Лимит по провайдеру (решено при закрытии §12.2 — единая функция для
обоих провайдеров §11, не два разных механизма).** Триггер, алерт и
явная длительность в секундах — одни и те же независимо от провайдера;
разнится только предельная длина цепочки, потому что у провайдеров
разные технические потолки:
- **Veo** (`standard` — `fast`/`veo-3.1-lite-generate-preview` Extension
  не поддерживает, §9.2): до 7 вызовов, максимум — меньшее из
  (длительность референса, 7×8=56 секунд).
- **Grok** (§10.1): свой Extend, официальный потолок — 30 секунд
  суммарно; максимум — меньшее из (длительность референса, 30 секунд),
  независимо от того, какое разрешение выбрано в §11.

Если пользователь выбрал Veo `fast` — экран предлагает переключить на
`standard` для этой генерации (как и было); если выбран Grok — версия
качества (`fast`/`standard`) здесь ни при чём вовсе, действует потолок
самого Grok Extend.

**Алерт перед запуском.** Прежде чем цепочка вызовов начнётся —
подтверждение с ориентировочной ценой (кратной числу сегментов) и
явной пометкой «только качество standard». Стоимость всей цепочки
проверяется ЗАРАНЕЕ, целиком, а не по одному вызову за раз: если
бюджета хватает на 3 сегмента из 7, ролик не должен обрываться
посередине от нехватки денег — это либо разрешается целиком, либо не
начинается вовсе. Отдельного нового гейта по тарифу заводить не
нужно — существующая проверка бюджета (`assertCanSpendUser`,
`common/plans.ts`) естественно справляется, если применить её к полной
стоимости цепочки, а не к каждому вызову изолированно.

**Явный запрет по тарифу — только Lite, решено окончательно.** По
вашей просьбе: на бесплатном (Lite) тарифе длинный ролик **не
предлагается вовсе**, независимо от провайдера — явный запрет, а не
тихий отказ бюджета по факту. Не только из-за Veo: цепочка из 7
сегментов даже на самом дешёвом Grok 480p — 7×8×$0.08 ≈ **$4.48**,
при потолке Lite $2/сутки это тоже недостижимо (44%). Проверка ради
полноты: САМАЯ короткая возможная цепочка (база + одно расширение,
2 вызова) на Grok 480p — $1.28, что технически уложилось бы в $2
Lite. Это сознательно не отменяет запрет: длинные ролики — это про
минуту, а не про 16 секунд, и городить отдельное правило ради одного
пограничного случая ради простоты интерфейса не стоит — Lite видит
однозначное «недоступно на вашем тарифе» всегда, без исключений
по длине.

**Standard и Premium — никакого отдельного правила не нужно.** Это и
есть решение того, что раньше было открытым вопросом: НЕ вводим
хардкод «Standard может/не может» — вместо этого работает уже
существующий общий механизм (см. «Алерт перед запуском» выше):
точная стоимость КОНКРЕТНО выбранной цепочки (нужная длина + выбранный
в §11 провайдер/качество/разрешение) считается заранее и сравнивается
с остатком дневного бюджета. Для Standard это автоматически означает:
цепочка на Grok 480p ($4.48) — доступна и разрешится сама, цепочка на
Veo `standard` ($22.40) — заблокируется сама, без единой новой строчки
кода сверх того, что уже решено выше. Дисклеймер (§11.3) заранее
показывает пользователю, какая комбинация ему по карману, — он видит
цену до того, как бюджет откажет, а не после.

**Длительность в секундах — явно.** Пользователь видит точное число
секунд (не «длинное видео») и может подтвердить или уменьшить его в
пределах потолка (б) перед запуском.

**Ручная проверка (закрывает п.4 и п.6 из предыдущей версии одним
заходом).** Один тестовый прогон вне трафика — как параметр `video`
себя ведёт на `veo-3.1-generate-preview` через `@google/genai` САМ ПО
СЕБЕ, и как он ведёт себя ВМЕСТЕ С `referenceImages` в одном вызове
(персонажи бренда, §2) — оба вопроса снимаются одним и тем же тестом,
до того как код появится на реальном трафике.

### 9.5 Реализовано в этом заходе

**Сделано:**
- `AnalysisService` — длительность референса выводится из
  `scenes[last].end` (уже разобранные сцены), не отдельным полем
  Gemini и не через ffprobe — найденный при подготовке ТЗ пробел
  закрыт без нового вызова.
- `common/video-extension-plan.ts` — чистая, полностью протестированная
  функция расчёта цепочки: число вызовов, итоговая длительность,
  урезана ли она потолком провайдера/референса. Один расчёт
  используется и для проверки бюджета, и мог бы использоваться для
  дисклеймера (§11.3) — не расходятся по построению.
- `generateVideo()` — явный запрет для Lite (независимо от провайдера)
  и проверка бюджета ВСЕЙ цепочки заранее, целиком — ровно то, что
  решено в §9.4.
- **Сам цикл продолжений — реализован, не только рассчитан.**
  `continueVeoChain()`/`continueGrokChain()` — когда сегмент готов, но
  `chainSegmentsDone < chainSegmentsTotal`, вместо финализации
  запускается следующий сегмент (Veo: параметр `video` с байтами
  только что скачанного сегмента; Grok: `extendVideoUrl` на только что
  залитый в Blob URL) — ролик остаётся `PROCESSING`, пока цепочка не
  дойдёт до конца, тогда включается обычная финализация (Blob,
  `videoHistory`, постобработка) без изменений.
- Тесты на обе ветки (продолжение/финализация/сбой продолжения) для
  обоих провайдеров.

**Степень неопределённости — выше, чем у остального этого ТЗ, и это
осталось так же после реализации, не снято ею:**
- **Veo**: официальный REST-пример показывает `video: {inlineData:
  {mimeType, data}}`, но УЖЕ РАБОТАЮЩИЙ в этом же файле код для
  параметра `image` (тот же SDK, `@google/genai`) использует другое
  имя поля — `{imageBytes, mimeType}`, не `inlineData`. Реализовано ПО
  АНАЛОГИИ с `image`/`imageBytes` — `video`/`videoBytes` — это
  логичная догадка (тот же SDK, вероятно та же конвенция для соседнего
  типа параметра), но не подтверждённый факт. Есть и отдельный
  открытый баг-репорт (discuss.ai.google.dev, 31 окт 2025) о том, что
  сам параметр `video` вообще отклоняется на этом эндпоинте.
- **Grok**: форма лучше подтверждена официально (`docs.x.ai`, поле
  `video_url`, `client.video.extend(video_url=..., duration=...)`),
  но тоже не проверена живым вызовом.
- Ручная проверка из этого же раздела (выше) остаётся ОБЯЗАТЕЛЬНЫМ
  шагом перед реальным трафиком — реализация не заменяет её, она
  дальше того же класса риска, что уже трижды применялся в этом ТЗ.

**Покрыто этим же заходом (обновление):**
- UI — поле ввода желаемой длительности в секундах и дисклеймер с
  ориентировочной ценой ЦЕЛОЙ цепочки (число сегментов, урезано ли)
  — на экране генерации, рядом с провайдером/качеством. Тот же
  расчёт (`common/video-extension-plan.ts`), что и в проверке
  бюджета — не второй, отдельный.

## 10. Альтернатива/дополнение к Veo — Grok Imagine Video (решено)

**Повод:** прямой запрос — проверить, не дешевле ли генерировать видео
через Grok (xAI) вместо Veo. Ответ по цене — да, дешевле; но это
самостоятельное решение о смене/дополнении провайдера, не строчка в
существующей архитектуре, и требует отдельной проверки перед тем, как
на него полагаться — по той же причине, по которой в этом ТЗ уже трижды
(§3, §8.5 п.5, §9.4) не принимались решения по одним только словам
документации.

### 10.1 Что подтверждено (официальная документация docs.x.ai — не агрегаторы)

Первая версия этого раздела опиралась на пересказы третьих лиц.
Перепроверено напрямую по `docs.x.ai`:

- **Модель уже общедоступна, не preview.** «Imagine Video 1.5 is out
  of preview and generally available in the xAI API as
  `grok-imagine-video-1.5»` (официальный анонс xAI, 16 июня 2026) —
  снимает опасение про статус «⊘ ограниченная доступность» из первой
  версии этого раздела, то была устаревшая информация об одном из
  предыдущих превью.
- **Нативный 1080p подтверждён.** «Native 1080p is now supported with
  text-to-video and image-to-video» (официальный анонс, 31 июля 2026)
  — 480p/720p как потолок из первой версии раздела тоже устарел.
- **Reference-to-video — подтверждён и щедрее, чем у Veo.** «Up to
  seven references per generation» — Veo 3.1 ограничен тремя. Каждый
  референс явно фиксирует одно — лицо, товар, локацию; можно менять
  сцену при том же персонаже или наоборот. Это прямое попадание в
  задачу персонажей бренда (§2) — возможно, даже более гибкое решение,
  чем нынешнее.
- **REST API — простой и задокументирован официально.**
  `POST https://api.x.ai/v1/videos/generations` возвращает
  `request_id`, дальше опрос статуса («Keep polling every few seconds
  until the video is ready») — тот же принцип, что уже реализован для
  Veo (`predictLongRunning` + `getVideoStatus`), не новая парадигма
  ожидания.
- **Готовый TypeScript SDK.** Пакет `@ai-sdk/xai` (Vercel AI SDK) —
  `experimental_generateVideo({ model: xai.video(...), ... })`. Не
  обязательно писать сырой HTTP-клиент с нуля, как для Veo.
- **`duration` — свободный параметр**, не фиксированный список (в
  официальных примерах — 8, 10, 12 секунд) — 8 секунд
  (`VIDEO_DURATION_SECONDS`) укладывается без округления.

### 10.2 Цена — официальная, по разрешению (важная правка первой версии)

Первая версия сравнивала Veo с ЕДИНОЙ ценой Grok $0.08/сек — это была
цена только младшего тарифа (480p). Официальная цена
**зависит от разрешения**:

| Разрешение Grok | $/сек | $/8с-ролик |
|---|---|---|
| 480p | $0.08 | $0.64 |
| **720p** | **$0.14** | **$1.12** |
| 1080p | $0.25 | $2.00 |

Наши текущие вызовы Veo **не указывают разрешение явно** —
используется дефолт Veo (обычно 720p). Честное сравнение — с Grok на
720p, не на 480p:

| Провайдер / модель | $/8с-ролик | Разница с Grok 720p |
|---|---|---|
| Veo 3.1 Lite (`fast`) | $1.20 | Grok дешевле всего на **7%** |
| Veo 3.1 (`standard`) | $3.20 | Grok дешевле на **65%** |
| Grok 720p | $1.12 | — |

Вывод меняется по сравнению с первой версией раздела: против
`standard` экономия по-прежнему существенная (65%), но против `fast`
(то, что выбрано по умолчанию, `DEFAULT_QUALITY`) экономия почти
незаметна — 7%, в пределах погрешности реальных условий (округление
длительности, региональные тарифы). Если для качества `fast` важнее
цена, чем что-либо ещё, Grok здесь не даёт решающего преимущества;
основной довод в пользу Grok — сравнение со `standard`, не с `fast`.

### 10.3 Риски — уточнено официальной документацией (10.1), часть снята

Первая версия раздела называла пять рисков; ниже — что осталось после
проверки по `docs.x.ai`, что снято, и что добавилось.

**Сняты этой проверкой:**
- ~~Статус доступности неясен~~ — модель GA, не preview (10.1).
- ~~Потолок разрешения ниже~~ — 1080p подтверждён; выбор
  480p/720p/1080p — управляемый параметр с понятной ценой за
  каждый (10.2), а не жёсткий потолок.

**Остаются:**
- **Качество для ЭТОГО продукта не проверено вовсе.** Veo 3.1 уже
  прошёл реальный аудит внутри этого проекта (пролив пива, битый
  текстовый оверлей, лишний звук, обрыв в конце) — то есть о его слабых
  местах известно предметно. Про Grok на тех же вводных (тот же
  референс, тот же бренд) данных нет никаких — официальная цена и
  параметры ничего не говорят о том, повторятся ли те же артефакты,
  появятся другие, или станет лучше. Это единственный риск, который
  документация принципиально не снимает — нужен реальный тестовый
  прогон (см. 10.5).
- **Новая интеграция, объём которой теперь понятнее (10.1), но не
  нулевой.** В проекте уже есть `GrokModule`, но ТОЛЬКО для перевода
  текста — видео-эндпоинт xAI не подключён никак. Понадобится: ключ и
  клиент (готовый `@ai-sdk/xai` снижает объём этой части), новая
  запись в `common/ai-pricing.ts` с ценой по разрешению (10.2, не
  плоская ставка, как у Veo сейчас), и обработка статуса генерации по
  тому же принципу опроса, что уже есть для Veo (`request_id` + poll,
  10.1) — форма другая, идея та же.
- **Экономия зависит от выбранного качества.** При сравнении со
  `standard` — экономия 65%, весомо. При сравнении с `fast` (текущий
  дефолт по умолчанию) — всего 7% на сравнимом разрешении (10.2), то
  есть решающего довода в пользу замены именно `fast` нет.

### 10.4 Как это ложится на архитектуру — решено

Изначально предлагалось два варианта. С уточнением 10.1 (reference-to-
video подтверждён и даже щедрее, чем у Veo — 7 референсов против 3)
причина, оправдывавшая вариант (B) — привязку к ветвлению §1 —
ослабла: технической несовместимости с персонажами бренда, похоже,
нет. Единственный оставшийся риск — качество для конкретно этого
продукта (10.3), а не архитектурная несовместимость.

**Решено: вариант (A).** Провайдер наравне с существующими — тот же
паттерн, что уже есть для озвучки (ElevenLabs/Resemble/Veo passthrough,
`TtsProviderResolverService`, этот же разговор): оператор выбирает
провайдер видео по умолчанию через админку, независимо от ветвления
§1 (персонажи бренда/нет). Это также прямо соответствует §5
(обратимость) — тот же принцип «одна точка переключения, дешёвый
откат», которым уже руководствовались для Veo 3.0.

## 11. Выбор провайдера и разрешения пользователем + расчёт цены заранее

**Повод:** прямой запрос — дать пользователю выбирать провайдера (Veo
или Grok) и для Grok — разрешение видео, начиная с 480p. Перед
генерацией, при выборе, сразу считать стоимость и показывать в
дисклеймере.

### 11.1 Меняет решение §10.4 — уточнено, не отменено

§10.4 отдавал выбор провайдера оператору (админка, значение по
умолчанию — тот же паттерн, что у `TtsProviderResolverService`). Этот
запрос — другой уровень: выбор нужен ПОЛЬЗОВАТЕЛЮ, на каждую
генерацию, не только оператору по умолчанию для всех.

**Решено: оба уровня одновременно, не один вместо другого.** Админка
по-прежнему хранит провайдера/разрешение **по умолчанию** (§10.4, тот
же смысл, что у `default_voiceover_provider` в
`PlatformSettingsService`) — это то, что предзаполнено при первом
открытии экрана генерации. Пользователь может это значение поменять
на КОНКРЕТНОЙ генерации — так же, как уже работает `quality`
(`fast`/`standard`) сегодня: у `quality` тоже есть код-дефолт
(`DEFAULT_QUALITY = 'fast'`), но пользователь каждый раз может его
переопределить.

**Найдено при аудите (по прямому запросу, после решения «Grok по
умолчанию», §20).** Админская половина этого решения — НЕ была
реализована никогда: в кодовой базе нет ни `AdminVideoProviderSettingsService`,
ни ключа `default_video_provider` в `PlatformSettingsService`, ни
эндпоинта, ни карточки в `/settings` — только код-дефолт в самом
`GenerationWizard.tsx` (`useState<'veo' | 'grok'>(...)`), который и
был единственным местом, где «Grok по умолчанию» физически можно было
применить в этом заходе. Разница практически важна: код-дефолт
требует деплоя фронтенда, чтобы его сменить; админская настройка (как
уже есть у озвучки/разбора видео, §17/§18) менялась бы оператором на
лету, без передеплоя — то, ради чего вся эта архитектура в §11.1 и
предлагалась изначально.

**Реализовано продолжением того же аудита.** `default-video-provider.ts`
(тот же паттерн, что у озвучки/разбора), `AdminVideoProviderSettingsService`,
эндпоинты `GET/PATCH /admin/settings/video-provider`, карточка на
`/settings`. `GenerationWizard.tsx`/`CatalogBatchStartScreen.tsx`
теперь читают это значение через новый публичный (не админский)
эндпоинт `GET /generation-settings/default-provider` при открытии
экрана — код-дефолт `'grok'` в `useState` остался только как фолбэк
на время загрузки или на случай сбоя запроса, не единственный
источник. Публичный эндпоинт — отдельный контроллер
(`GenerationPublicSettingsController`), не вложенный в
`GenerationController` (тот целиком завязан на `:sessionId`, этот
дефолт — глобальная настройка платформы, не сессии).

### 11.2 Как это выглядит на экране генерации

Тот же экран, где сегодня выбирается `quality`. Провайдер — новый
переключатель РЯДОМ с ним, не вместо:

- **Провайдер = Veo** (сегодняшнее поведение без изменений) —
  показывается `quality`: `fast`/`standard`.
- **Провайдер = Grok** — `quality`-переключатель ЗАМЕНЯЕТСЯ на
  переключатель разрешения: `480p` (по умолчанию — самый дешёвый,
  как в запросе «начиная с 480p») / `720p` / `1080p`. У Grok нет
  понятия `fast`/`standard` — одна модель, разная цена по разрешению
  (§10.2), поэтому это не третий параметр вдобавок к `quality`, а
  замена его на то, что у этого провайдера действительно есть.

### 11.3 Дисклеймер с ценой — сразу при выборе, не после

Общий принцип, а не разовое решение только для Grok: **любой выбор,
меняющий стоимость, сразу показывает пересчитанную цену** — тот же
принцип, что уже решён в §9.4 для длинных роликов («Алерт перед
запуском»), здесь распространяется на КАЖДУЮ генерацию, не только
многосегментную. Смена провайдера, качества или разрешения — цена под
кнопкой «Сгенерировать» обновляется сразу, без отдельного клика
«посчитать». Дисклеймер — не блокирующее окно (в отличие от алерта в
§9.4 для по-настоящему крупной суммы) — постоянно видимая строка,
которая просто пересчитывается.

### 11.4 Данные — новые поля

`GeneratedVideo` (бэкенд и фронтенд зеркала) получает:
- `provider: 'veo' | 'grok'`
- `resolution?: '480p' | '720p' | '1080p'` — только когда
  `provider === 'grok'`; для Veo не заполняется (Veo здесь по-прежнему
  не запрашивает разрешение явно, §10.1).

Оба поля сохраняются в истории версий (§9, `videoHistory`) и
переносятся на «Повторить»/«Исправить и перегенерировать» тем же
способом, что уже переносятся `quality`/`aspectRatio` — не нужно
отдельно проектировать перенос, расширяется существующий список полей.

**Полезное следствие, стоит явно упомянуть пользователю в интерфейсе:**
если Veo дал брак (пролив, битый текст — повод всего этого разговора),
«Исправить и перегенерировать» (админка) или «Повторить» (визард)
теперь может пойти на ДРУГОМ провайдере, не обязательно на том же,
что дал брак — раньше повтор всегда оставался на исходном провайдере,
потому что другого не было.

### 11.5 Пробел в текущей схеме цен — найдено при подготовке этого раздела

`common/ai-pricing.ts` хранит одну ставку `perSecond` НА МОДЕЛЬ (`{
'veo-3.1-generate-preview': { perSecond: 0.40 } }`). У Grok — ОДНА
модель (`grok-imagine-video-1.5`) с ТРЕМЯ разными ставками по
разрешению (§10.2: 480p/720p/1080p). Текущая схема этого не выражает
— нужна правка структуры (например, `perSecond` — не число, а
`Record<Resolution, number>` для записей с разрешением) ДО того, как
писать код подсчёта цены, иначе дисклеймер (§11.3) и реальное
списание бюджета неизбежно разойдутся.

### 11.6 Пересечение с §9 (длинные ролики) — новый вывод, стоит зафиксировать

§9 запрещал Lite ролики длиннее 8 секунд явно, посчитав, что цепочка
на Veo `standard` стоит ≈$22.40 — недостижимо и для Lite ($2/сутки), и
фактически для Standard ($10/сутки, покрывает 45%). С Grok как вторым
провайдером картина для Standard меняется:

- Та же цепочка (7 сегментов) на Grok 480p: 7×8×$0.08 ≈ **$4.48** —
  Standard ($10/сутки) свободно покрывает, Lite ($2/сутки) всё ещё нет
  (покрывает 45%, тот же порядок, что раньше был у Standard на Veo).

**Вывод: явный запрет длинных роликов (§9.4) остаётся в силе только
для Lite и только всегда; для Standard он больше не универсален** —
зависит от того, какой провайдер выбран для длинного ролика. Это не
меняет решение §9.4 (Lite — запрет), но снимает то, что было
сформулировано там как незакрытый нюанс про Standard: при выборе Grok
Standard такой ролик может себе позволить, при выборе Veo — нет.
Точная реализация — тот же принцип «бюджет всей цепочки заранее»
(§9.4), просто цена цепочки теперь зависит от выбранного в §11
провайдера/разрешения, а не только от Veo `standard`.

**Закрыто.** Ровно это и стало финальным решением в §9.4: явный запрет
только для Lite (независимо от провайдера — не влезает ни в один),
для Standard/Premium — никакого отдельного правила, общий механизм
проверки бюджета делает то же самое сам.

## 13. Grok Batch API для видео (по образцу перевода статей блога) — решено и реализовано, включая воркер (§13.5)

**Повод:** прямой запрос — использовать тот же Batch API xAI, что уже
реализован в проекте для перевода статей блога
(`GrokBatchService`, ТЗ §35.1), для видео-генераций Grok.

### 13.1 Что подтверждено официально

- **Механизм реален.** Официальные release notes xAI (`docs.x.ai`,
  март 2026): «Batch API supports Image and Video generation — The
  Batch API now supports image generation, image editing, and video
  generation in addition to chat completions». Раньше Batch API
  принимал только chat completions — для видео это новая, но
  подтверждённая первым лицом возможность.
- **Формат подачи** — тот же, что уже реализован в
  `GrokBatchService`: JSONL-файл через Files API, «Supports all batch
  endpoints including chat, image, and video in a single file» — то
  есть видео-задания технически могли бы лечь в ТУ ЖЕ инфраструктуру
  подачи батча, что уже есть для перевода, не отдельный протокол.
- **Ограничение результата.** Официально: «Image and video URLs in
  batch results expire after 1 hour» — результат нужно скачать/
  сохранить в Blob сразу после получения, окно короткое.
- **SLA — до 24 часов, best-effort**, не гарантировано — тот же режим
  ожидания, что уже описан в доккомментарии `GrokBatchService` для
  перевода статей.

### 13.2 Цена — расхождение источников, не блокирует решение

В отличие от остальных числовых фактов в этом документе, здесь
источники прямо противоречат друг другу, и это не «агрегатор устарел»
(как было с 480p-потолком в §10) — расхождение свежее и с обеих
сторон:

- **Большинство источников (несколько независимых обзоров, включая,
  по всей видимости, официальную страницу цен xAI) говорят: скидка
  Batch API НЕ распространяется на image/video — «image and video
  generation doesn't qualify for the batch discount and remains at
  standard rates», «the discount applies to text and language models
  only».
- **Один источник, датированный ТЕМ ЖЕ днём, что и сам релиз (22 марта
  2026)**, утверждает обратное — конкретную скидку 50% именно для
  видео: «$0.05 per second… With the batch discount, those drop to…
  $0.025».

**Решено: не закладывать скидку в расчёт стоимости, и не считать это
блокером.** Тот же принцип, что уже трижды применялся в этом ТЗ к
неподтверждённым деталям Veo (§3, §8.5, §9.4) — не полагаться на
цифру, которую невозможно сейчас проверить живым вызовом, тем более
когда источники прямо расходятся. Если скидки на самом деле нет —
предположение о ней сломало бы дисклеймер (§11.3) и бюджетную проверку
(§9.4) сразу на первом батч-задании. По вашему уточнению — это и не
нужно решать заранее: при реальном объёме генераций условия у xAI
обсуждаются напрямую, публичная ставка на странице цен перестаёт быть
единственным источником истины. Дисклеймер (§11.3) считает по
СТАНДАРТНОЙ (без батча) цене, что заведомо не занижает ожидания
пользователя — реальная цена с батчем/переговорами может быть только
ниже, не выше.

### 13.3 Где это применимо — не в основном сценарии генерации

**Решено: НЕ для интерактивного экрана генерации (§11), а для уже
существующих офлайн-батч-функций.** SLA «до 24 часов, best-effort» —
то же самое ограничение, что уже принято для перевода статей блога
(фоновая, не интерактивная задача) — и оно прямо противоречит тому,
как сегодня устроен основной экран генерации: пользователь видит
статус и ждёт минуты, не сутки (`RENDER_DEADLINE_MS`, активный опрос
на экране «Готово»). Подключать сюда батч означало бы либо соврать
пользователю про время ожидания, либо полностью менять этот экран —
ни то, ни другое не было целью исходного запроса.

Естественное место — уже существующие офлайн-функции пакетной
генерации (`CatalogBatchWorkerService`, `AbTestWorkerService`,
Premium-функции с воркером, который забирает задания и не требует
живого присутствия пользователя) — их устройство (claim/worker,
не диалог с пользователем в реальном времени) уже совместимо с режимом
«сутки, best-effort» так же, как уже совместим перевод статей.
Это соответствие, а не новое решение — сама механика этих сервисов
уже сегодня рассчитана на асинхронную, не мгновенную обработку.

### 13.4 Открытые вопросы — закрыты

1. ~~Подтвердить реальную скидку Batch API для видео~~ — **закрыто как
   неактуальное**: при наличии реального объёма генераций публичная
   ставка перестаёт быть решающей — с xAI можно обсудить отдельные
   условия под трафик напрямую, независимо от того, что написано на

   вообще, см. §13.1) — но не как способ узнать «настоящую» цену: она
   в любом случае предмет переговоров при масштабе, не факта из
   документации.
2. ~~Стоит ли вообще заводить интеграцию, если скидки нет~~ —
   **закрыто как неактуальное по той же причине**: решение не
   зависит от того, есть ли ПУБЛИЧНАЯ скидка сегодня. Стандартная
   (без батча) цена Grok уже выгоднее Veo `standard` (§10.2) — это

   скидки; сам батч — дополнительная возможность снизить цену ещё
   больше через прямые переговоры при появлении трафика, не
   предварительное условие для решения «делать или нет».
3. ~~Объём работы: какой из двух паттернов повторить~~ — **закрыто:

   `CatalogBatchWorkerService` — это ДРУГОЙ слой, не конкурирующий с
   `GrokBatchService`: воркер (`GET /api/cron/catalog-batch-run`,
   джоб-лок, claim до `cronBatch` строк за прогон) решает, ЧТО и КОГДА
   генерировать — доменная логика; `GrokBatchService` — тонкий клиент
   ИМЕННО к batch-эндпоинту xAI (создать батч, опросить статус,
   забрать результаты) — инфраструктура, без знания о видео, каталоге
   или чём-либо предметном. Для видео нужен `GrokVideoBatchService` —
   тот же тонкий клиент, что `GrokBatchService`, но под video/image
   эндпоинты вместо chat — и он вызывается ИЗ существующего цикла
   `CatalogBatchWorkerService` (или его аналога для нужного сценария),
   а не образует третий, отдельный воркер. Строить с нуля — только
   тонкий xAI-клиент; цикл claim/джоб-лок уже есть, переиспользуется
   как есть.

  `provider`/`resolution`/`xaiBatchId`, `CatalogBatchItemStatus` —
  новое значение `BATCH_QUEUED`. `processOne()` для `provider='grok'`

  - `submitReadyGrokBatches()` — партия подаётся ОДНОЙ xAI-пачкой

    подавать частями было бы некуда записывать второй ID.
  - `pollInFlightGrokBatches()` — опрашивает поданные пачки, по

    счастливый путь, строка без готового промпта/фото, отказ xAI,
    незавершённая пачка, готовая пачка с/без результата на строку).

**Найден и исправлен реальный регресс при подготовке тестов**: мок
`prisma.catalogBatchRun.findMany`/`.update` и `catalogBatchItem.count`
в существующем тестовом файле воркера вообще не существовали — новый
код вызывал бы их на КАЖДОМ тике безусловно и уронил бы ВСЕ
существующие тесты воркера (`TypeError: ... is not a function`).
Добавлены безопасные дефолты (пустой список/ноль) — существующие
Veo-сценарии тестов не видят разницы.

**НЕ снято — остаётся тем же риском, что и раньше:**
- **Форма запроса Batch API для видео так и осталась неподтверждённой
  реальным вызовом.** Ключ `videos_generations` — по-прежнему ДОГАДКА

## 15. Grok reference-to-video — персонажи бренда (реализовано)

**Повод:** этап 1 (§14, §10.5) намеренно ограничил Grok одним фото
товара — множественные референс-изображения персонажей бренда были
исследованы недостаточно тщательно для честной реализации. По прямому
запросу — доисследовано и реализовано в этом заходе.

### 15.1 Что подтверждено официально (перепроверено, не пересказ)

Источник — `docs.x.ai/developers/model-capabilities/video/reference-to-video`,
первоисточник, не агрегатор:

- **Поле запроса** — `reference_images`, массив объектов `{ "url": "..." }`
  (НЕ голых строк) — до **7** изображений за запрос.
- **Несовместимо с `image_url`** — «Only one mode can be active per
  request» — то же взаимоисключение, что уже реализовано у Veo
  (`image` XOR `referenceImages`, `generation.service.ts`) — архитектуру
  переиспользовали, не изобретали заново.
- **Разрешение ограничено 720p** в этом режиме — ниже потолка обычного
  text/image-to-video у той же модели (там доступен 1080p, §10.1).
- **Формат картинки** — публичный HTTPS URL, base64 data URI или
  `file_id` — принято решение использовать URL (проще всего: наши Blob
  URL уже публичные).
- **Конвенция промпта** — модель ожидает метки `<IMAGE_1>`, `<IMAGE_2>`
  … ПРЯМО в тексте там, где должен появиться этот референс
  (официальный пример: «they wear the shirt from <IMAGE_2>»), а не
  отдельным списком-приложением, как у Veo.

### 15.2 Реализовано

- `BlobService.getPublicUrl(pathname)` — новый метод, тот же `head()`
  из `@vercel/blob`, что уже использовал `downloadBuffer()`, просто без
  второго шага (скачивание не нужно — Grok сам заберёт по ссылке).
- `GrokVideoService.startGeneration()` — принимает `referenceImageUrls`
  наравне с `imageUrl` (взаимоисключающе, ошибка при обоих сразу);
  сам понижает `1080p` до `720p`, если переданы референсы — тихая
  деградация качества, не отказ (вызывающий мог не знать про этот
  частный потолок).
- `common/reference-plan.ts` — новая функция `grokReferencePromptText()`
  рядом с существующей `referenceMappingText()` — та же структура
  (кто на каком референсе, что не показано как картинка), метки
  `<IMAGE_N>` вместо номеров.
- `generation.service.ts` — `startGrokGeneration()` больше не
  отклоняет сессии с персонажами: строит `referenceImageUrls` через
  новый `resolveReferenceUrl()` (та же проверка `isOwnBlobUrl`/
  `FOREIGN_BLOB_URL_MESSAGE`, что уже есть у `fetchReference()` для
  Veo — доверие к источнику URL не должно быть слабее оттого, что
  скачивает не наш сервер).
- `generation.service.ts` — новый `isReferenceMode(sessionId)`,
  используется `GET /generate/estimate` (§11.3): дисклеймер цены
  теперь тоже понижает `1080p` до `720p` для сессий с персонажами —
  иначе показал бы цену дороже, чем реально спишется.

### 15.3 Улучшено — метки теперь вплетаются в действие, не списком после (реализовано по прямому запросу — не отложено)

Первая версия (`grokReferencePromptText()`) была честно помечена как
приближение: список «Reference <IMAGE_2> shows the person "Anna"…»
рядом с текстом сцены, а не метка внутри самого действия, как того
хочет официальная конвенция xAI («they wear the shirt from <IMAGE_2>»).

**Реализовано сразу, не отложено на будущее**, по прямому запросу — то
самое улучшение через отдельный узкий шаг переписывания текста, о
котором говорилось выше как о кандидате:

- `PromptService.rewriteForGrokReferences(sceneText, plan)` — новый
  метод, узкий и точный (не творческий — сцена уже придумана GPT-5 для
  Veo, здесь только вплетаются метки), поэтому отдельная, более дешёвая
  модель — `OPENAI_FAST_MODEL` (config.openai.fastModel, по умолчанию
  `gpt-5-mini` — имя ПРОВЕРИТЬ перед стройкой, тот же принцип, что у
  всех моделей в этом ТЗ), а не основной `OPENAI_GPT_MODEL`.
- Результат ЗАМЕНЯЕТ исходный текст сцены целиком (не добавляется
  рядом с ним) — переписанная версия уже содержит всё содержимое
  сцены, просто с метками внутри действий; при подготовке кода это
  едва не привело к дублированию всего описания сцены (текст сцены
  дважды: один раз без меток, один раз с ними) — поймано и исправлено
  на этом же проходе, до того как код ушёл дальше.
- Отказоустойчиво: сеть, отказ модели, пустой ответ — лог и откат на
  прежнее приближение (`grokReferencePromptText()`, теперь
  используется только как fallback) — генерация не должна падать
  из-за необязательного шага косметики промпта.
- Именно тот путь развития, что и предполагался: тот же класс задачи,
  что и §8 (отдельный узкий шаг генерации текста для Veo), просто
  реализован раньше и для Grok конкретно, а не как часть общего §8.

### 15.4 Не покрыто этим заходом (осталось на будущее)

- UI не предупреждает явно, что выбор 1080p при персонажах бренда
  будет понижен — дисклеймер (§11.3) уже показывает верную (720p)
  цену, но сам переключатель разрешения не отключает 1080p и не
  поясняет, почему цена не совпадает с ожидаемой по выбранной кнопке.
- Ручная тестовая проверка (§10.5 п.2, то же правило, что применялось
  трижды в этом ТЗ) распространяется и на reference-to-video отдельно:
  простой `image_url` и `reference_images` — разные параметры запроса,
  подтверждение одного не подтверждает автоматически другой.

### 16.2 Оценка цены не учитывала реально выбранную модель

### 16.4a Критическое — новый статус ронял экран прогресса

- **[исправлено]** `BATCH_QUEUED` (§13, этап 2) не учитывался НИГДЕ:
  - `CatalogBatchService.getStatus()` (пользовательский путь) — сводка
    `{pending, generating, done, failed}` не включала эту категорию,
    сумма не сходилась с реальным числом строк партии.
  - `AdminCatalogBatchService` — тот же самый пробел в агрегированном
    подсчёте для списка партий в админке.
  - **Фронтенд `CatalogBatchProgressScreen.tsx`** — `switch` по статусу
    строки не имел ветки для `'BATCH_QUEUED'` И не имел `default` —
    функция возвращала `undefined`, а вызывающий код деструктурировал
    `{label, icon, tone}` без проверки. Первая же Grok-партия с хотя
    бы одной строкой в очереди на подачу **уронила бы весь экран
    прогресса** при попытке его открыть.
  - Корень пробела — **тип `CatalogBatchItemStatus` во фронтенде
    вообще не знал о `'BATCH_QUEUED'`** (отдельный, вручную
    поддерживаемый union, не разделяемый с бэкендом) — из-за этого
    TypeScript и не мог заранее подсветить недостающую ветку `switch`.
  - Исправлено везде: обе сводки считают `BATCH_QUEUED` вместе с
    `PENDING` (та же категория «ожидание» для читателя), фронтенд-тип
    дополнен, добавлена явная ветка + защитный `default` на случай
    будущего забытого статуса, добавлен тест на сумму сводки.

### 16.4b Критическое — таймаут копился по всей цепочке, а не по сегменту

- **[исправлено]** `renderExpired()` сравнивает `now - video.initiatedAt`
  с `RENDER_DEADLINE_MS` (20 минут) — рассчитан на ОДИН рендер.
  `continueVeoChain()`/`continueGrokChain()` (§9, этап 4 плана §14)
  запускали новый сегмент через `{...current, ...}`, НЕ обновляя
  `initiatedAt` — то есть отсчёт времени начинался с самого первого
  сегмента и продолжал копиться через всю цепочку. Цепочка из 5–7
  сегментов (реалистично по 2–4 минуты на сегмент) почти неизбежно
  упёрлась бы в мнимый таймаут «Veo не ответил за 20 минут» на
  середине — даже если КАЖДЫЙ отдельный сегмент завершался быстро и
  успешно. Это была бы систематическая, а не редкая поломка — именно
  та функция (§9), которая специально просит МНОГО последовательных
  вызовов, была бы наименее надёжной из всех при том, что каждый
  вызов по отдельности работал нормально.
- Исправлено: `initiatedAt` сбрасывается на текущее время при СТАРТЕ
  каждого нового сегмента — дедлайн применяется к сегменту, не к
  цепочке целиком. Добавлен тест, напрямую воспроизводящий сценарий
  «первый сегмент почти у дедлайна» и проверяющий, что после
  продолжения точка отсчёта — свежая, а не унаследованная.

### 16.4d Промпт продолжения — не проговаривал намерение

- **[исправлено]** По прямому запросу — аудит всего пайплайна
  многосегментного видео. `continueVeoChain()`/`continueGrokChain()`
  передавали на каждый сегмент цепочки БУКВАЛЬНО тот же текст сцены,
  что и первый сегмент, без единой оговорки, что это продолжение, а
  не новая попытка. Для сцены с законченным действием («открывает
  подарок и улыбается») это могло означать для модели «начни действие
  заново» на каждом следующем сегменте — то есть цепочка рисковала
  зацикленно повторять одно и то же вместо естественного продолжения,
  что подрывало бы саму цель §9 (длинные, связные ролики).
  Официальный механизм расширения и так подхватывает
  стиль/персонажей/сцену с последнего кадра — добавлена одна явная
  строка-оговорка («это продолжение, сохраняй действие/персонажей/
  обстановку непрерывными, не начинай заново»), не переписывающая
  сцену — только уточняющая намерение. Исправлено для обоих
  провайдеров; два существовавших теста проверяли точное равенство
  промпта — переведены на `stringContaining` + отдельную проверку
  наличия оговорки.

### 16.4e Критическое — субтитры считались на 8 секунд для любой длины ролика

- **[исправлено]** `heuristicCueTimings()` (эвристика тайминга
  субтитров в режиме `veo`, без пословного выравнивания) вызывалась с
  жёстко зашитой `VIDEO_DURATION_SECONDS` (8) вместо реальной длины
  ролика. Для обычного 8-секундного видео это было верно всегда —
  ошибка была НЕВИДИМА до появления §9 (ролики длиннее 8 секунд): для
  цепочки Scene Extension субтитры считались бы так, будто видео
  длится 8 секунд, а не до 56 (Veo) или 30 (Grok) — реплики сжимались
  бы в первые 8 секунд, а оставшаяся часть реального ролика шла бы без
  субтитров вовсе. Исправлено — `Work.totalDurationSeconds` (новое
  поле, заполняется из `video.chainTargetDurationSeconds ??
  VIDEO_DURATION_SECONDS` в `planWork()`) передаётся в эвристику
  вместо константы. Добавлен тест, воспроизводящий цепочку из 3
  сегментов (24 секунды) и проверяющий, что тайминг субтитров реально
  доходит до конца ролика, а не обрывается на 8-й секунде.

### 16.4f Проверено — учёт кредита корректен для цепочки, исправление не требуется

- Резерв кредита (`creditLedger.reserveForGeneration`) происходит ОДИН
  раз на `generatedVideoId`, который не меняется на протяжении всей
  цепочки (только `veoOperationName`/`grokRequestId` обновляются на
  каждом сегменте) — кредит логично покрывает «одно готовое видео»,
  независимо от того, сколько провайдерских вызовов потребовалось
  внутри. Возврат кредита при провале (`markFailed()`, вызывается и
  при сбое продолжения цепочки) использует тот же неизменный
  `generatedVideoId` — падение НА ЛЮБОМ сегменте корректно возвращает
  кредит, как и при провале обычной, однократной генерации. Отдельная
  дневная проверка бюджета в долларах (`aiUsage.record()`) уже
  считается по каждому сегменту отдельно (см. §16.2) — это две разные,
  не пересекающиеся системы учёта, обе работают правильно.

### 16.4g Фронтенд не мог показать прогресс по сегментам — данные приходили, но тип их не знал

### 16.9 Самая серьёзная находка за весь аудит — Grok-партии по каталогу полностью обходили учёт денег

- **[исправлено, критично]** По прямому запросу — повторный аудит
  Grok Batch API. `submitReadyGrokBatches()`/`pollInFlightGrokBatches()`
  (`CatalogBatchWorkerService`, §13) вызывают `GrokVideoBatchService`
  НАПРЯМУЮ, минуя `GenerationService.generateVideo()` — единственное
  место в проекте, где для ВСЕХ ОСТАЛЬНЫХ путей генерации живут и
  проверка дневного бюджета, и запись фактического расхода. Из этого
  следовало два независимых, оба финансово значимых пробела:
  1. **Ноль проверки бюджета перед подачей** — партия на сотни товаров
     могла уйти в xAI без единого взгляда на дневной лимit
     пользователя.
  2. **Ноль записи расхода после подачи** — даже при успехе стоимость
     НИКОГДА не попадала в `aiUsage`/отчёты о расходах — реальные
     деньги, потраченные у xAI, были бы систематически невидимы для
     всей системы учёта, не разовая недостача, а постоянная дыра.
- Исправлено: `PlanService`/`AiUsageService` внедрены в
  `CatalogBatchWorkerService` (оба уже `@Global()` — нового связывания
  модулей не потребовалось). Перед подачей — тот же принцип, что уже
  применён к цепочкам Scene Extension в §9.4: стоимость ВСЕЙ партии
  считается заранее, целиком, через тот же `estimateCost()`; если
  остаток дневного лимита не покрывает — партия помечается FAILED
  целиком, не подаётся частично. После успешной подачи — одна запись
  `aiUsage.record()` на всю партию (не по элементу — xAI выставит счёт
  за пачку целиком, отчёт должен отражать то же самое). Добавлен
  геттер `modelName` в `GrokVideoBatchService` (по образцу уже
  существующего в синхронном сервисе) для составного ценового ключа.
  Добавлены тесты на обе стороны находки (расход пишется при успехе;
  партия не подаётся и помечается FAILED при недостатке бюджета).

### 16.10 Retry/переэкспорт не сохраняли длину цепочки — тот же класс ошибки, что уже был для provider/resolution

  терял `provider`) — при повторном проходе нашлось, что ТО ЖЕ САМОЕ
  верно для `chainTargetDurationSeconds` (§9, этап 4 плана §14), но

  заходе. Три места читали `quality`/`aspectRatio`/`provider`/
  `resolution` из провалившейся/исходной записи для повтора, но не
  длину цепочки:
  - `admin-generation-retry.controller.ts` — `retry()` и
    `applyFixAndRetry()`;
  - `export.service.ts` — `startRerender()`.

  Без исправления повтор упавшего НА СЕРЕДИНЕ цепочки сегмента или
  переэкспорт готового 56-секундного ролика в другой формат тихо
  откатывались бы на обычную однократную 8-секундную генерацию —
  пользователь получил бы куда более короткий ролик, чем изначально
  просил, без единого предупреждения. Исправлены все три; добавлены
  тесты на сохранение длины при повторе и при переэкспорте.

### 16.11 «Занятость» товара не учитывала BATCH_QUEUED — риск задвоенного оплаченного рендера

- **[исправлено]** Тот же класс пробела, что уже был найден в §16.4a
  (сводка прогресса) — «busy»-проверка в `CatalogBatchService`
  (`create()` — дважды, вне и внутри транзакции сериализации; `retry()`
  — один раз) фильтровала занятые товары по
  `status: { in: ['PENDING', 'GENERATING', 'DONE'] }`, не включая
  `'BATCH_QUEUED'`. Смысл проверки — не дать одному и тому же товару
  попасть в ДВЕ параллельные партии одновременно (оплата за рендер
  задвоилась бы) — сам код рядом прямо объясняет эту цель для
  PENDING/GENERATING/DONE, но не учитывал, что «стоит в очереди на
  подачу как Grok-пачка» — ровно та же занятость, просто для статуса,
  появившегося позже (§13, этап 2 плана §14). Товар, ждущий подачи в
  Grok-пачке, считался бы свободным — вторая партия или точечный повтор
  могли бы завести для него ещё одну оплаченную генерацию параллельно
  с уже идущей. Исправлено во всех трёх местах; три существующих теста
  проверяли точную форму этого списка — обновлены под исправленный
  список статусов.

## 17. Выбор модели для анализа референсного видео — Gemini/Grok

**Повод:** прямой запрос — сейчас разбор референса (`AnalysisService`)
жёстко привязан к Gemini; нужен тот же ручной селектор, что уже есть
для озвучки (`AdminVoiceoverSettingsService`, `/settings`).

### 17.1 Что подтверждено официально — и это меняет объём реализации

Официальная навигация `docs.x.ai` (проверено напрямую, не пересказ)
перечисляет под «Text»: «Text Generation · Streaming · Reasoning ·
Structured Outputs · **Image Understanding**» — и отдельно под
«Imagine»: «Video Generation · Image-to-Video · Reference-to-Video ·
Video Editing · Video Extension». **«Video Understanding» в этом
дереве нет вовсе** — все упоминания видео относятся к ГЕНЕРАЦИИ, не к
АНАЛИЗУ. Подтверждена официально только **картинка** как вход для
понимания (Image Understanding), не видеофайл целиком.

Это прямо противоречит части сторонних источников (не docs.x.ai) —
один называет «native video input» у Grok 4.3, другой пишет «Grok can
now… watch videos» — но ни один не первоисточник, и оба ровно того
типа, который уже дважды подводил в этом ТЗ (см. §3, §9.1 — «в
документации есть, а на практике не так»). Решение — не доверять
пересказу больше, чем уже дважды позволяло себе это ТЗ, и проектировать
от подтверждённого (картинки), а не от заявленного (видео).

**Практическое следствие**: у Gemini разбор видит ролик целиком и сам
раскладывает его по времени. У Grok прямого аналога нет — путь через
Grok в этой версии сделан **приближением**: несколько кадров
(`ffmpeg`, тот же инструмент, что уже используется в проекте для
кадрирования, `common/reframe.ts`) отправляются как набор картинок в
`/chat/completions` (Image Understanding, подтверждено) с той же
инструкцией/схемой, что уже пишет Gemini. Разбивка по сценам и
таймкоды в этом пути — оценка модели по нескольким снимкам, не
буквальный просмотр видео целиком, точность заведомо ниже, чем у
Gemini, особенно там, где важно ВРЕМЯ (когда что происходит), а не
только ЧТО происходит.

### 17.2 Реализовано

- `common/default-analysis-provider.ts` — те же три функции, что уже
  есть для озвучки (`resolveDefaultAnalysisProvider`,
  `isAnalysisProviderKey`, `DEFAULT_ANALYSIS_PROVIDER_SETTING_KEY`) —
  сознательно скопирован тот же паттерн `default-tts-provider.ts`, не
  изобретён заново.
- `admin-panel/admin-analysis-settings.service.ts` — тонкая обёртка
  над `PlatformSettingsService`, зеркало
  `AdminVoiceoverSettingsService` один в один по структуре
  (`get()`/`setDefault()`, `source: 'admin' | 'env-default'`).
- Экран `/settings` — новая карточка «Разбор референса по умолчанию»
  рядом с уже существующей «Озвучка по умолчанию», тот же компонент.

### 17.3 Открытые вопросы (не решены — требуют отдельного захода)

1. Полная реализация Grok-пути разбора (извлечение кадров, вызов
   `/chat/completions`, разбор ответа в ту же схему `VideoAnalysis`) —
   заложена архитектурно (селектор провайдера уже переключает путь),
   но САМ разбор через Grok в этом заходе не реализован целиком —
   слишком большой самостоятельный объём (по сути отдельный
   AnalysisService), чтобы делать его вперемешку с настройкой
   селектора и аудитом озвучки в одном заходе.
2. Ручная проверка качества Grok-пути на реальном референсе — то же
   правило, что уже трижды применялось в этом ТЗ к неподтверждённым
   деталям Veo.
3. Сколько кадров извлекать и с каким шагом — компромисс между
   точностью и ценой (`/chat/completions` с картинками тарифицируется
   по токенам за каждое изображение, не за секунды видео, как Gemini).

## 20. Референс-изображение с готовым текстом вместо генерации текста моделью

**Статус: детальный дизайн, открытые вопросы закрыты по прямому
запросу («максимальный профит») — но ГЛАВНАЯ гипотеза (§20.1) всё ещё
НЕ проверена реальным вызовом. Ничего из этого раздела не

**Повод.** §8.4 объяснил, ПОЧЕМУ Veo/Grok коверкают кириллицу на
экране (модель рисует форму букв по описанию, не печатает текст), а
§19 усилил инструкцию промпта требованием дословности — но два
реальных прогона (2026-09-13/14) показали, что этого недостаточно:
«Кернйвсыке — Чейке…», «ДНІРШЕЯКЕ ІНАФДЬЖ» — второй пример уже не
читается вовсе.

**Идея (ваша).** Veo (до 3 изображений) и Grok (до 7) уже копируют
ВИЗУАЛЬНЫЙ материал из референсов — лицо персонажа, вид товара. Если
заранее отрендерить картинку с нужным текстом настоящим шрифтом и
подать её тем же механизмом — модели, возможно, проще СКОПИРОВАТЬ
готовую картинку, чем нарисовать текст с нуля по словесному описанию.
По вашей следующей просьбе: генерировать столько таких карточек,
сколько реально нужно тексту в ролике — не одну обобщённую, а под
каждый отдельный текстовый момент.

### 20.1 Главная неопределённость — ПОДТВЕРЖДЕНА пользователем на реальной генерации (2026-09-14)

**Прямая обратная связь после исправления бага статуса Grok (§21)**:
«Тексты идеально» — реальная генерация с text-card даёт точный,
читаемый текст на экране, ровно то, на что рассчитывал весь план
этого раздела.

**Честно про атрибуцию — не разделено точно, какая часть чего дала:**
это подтверждение пришло СРАЗУ после трёх независимых изменений —
(а) исправление §19 (дословность в инструкции промпта), (б) сам
механизм text-card (§20.2–20.9, если WASM-фикс §20-производственных-
находок реально сработал — не подтверждено отдельно), (в)
исправление URL опроса статуса Grok (§21), из-за которого раньше
генерации могли просто не долетать до готового результата вовсе.
Какая доля успеха от какого именно изменения — не разделено этим
подтверждением, оно точечное, не A/B-сравнение. Но САМ ФАКТ, что
результат — «идеально», означает: главная гипотеза (компоновка текста
в кадре — в любой форме, через text-card или через усиленный словесный
промпт) на практике работает, а не осталась только планом.

**Что это меняет:** весь план §20.2–§20.9 (приоритет слотов,
хэш-инвалидация, множественные карточки по ролям) перестаёт быть
«планом на случай, если гипотеза подтвердится» — гипотеза
подтвердилась, план можно считать рабочим, а не только теоретически
готовым. Оставшаяся отдельная работа — понять, действительно ли
конкретно WASM-фикс (§20, находка о `hb.wasm`) заработал, или текст
идеальный благодаря (а)/(в) без участия text-card вовсе — см.
предложение проверить в §20-текст-ниже, не сделано в рамках этого
единственного подтверждения.

### 20.2 Сколько карточек — «столько, сколько нужно», не одна обобщённая

**Решено (по прямому запросу).** Ролик может нуждаться в НЕСКОЛЬКИХ
разных текстовых моментах — не только один `Text overlay` на всё
восьмисекундное видео. Практические примеры из уже виденных промптов
этого ТЗ: открывающий крючок-слоган, отдельная цена/промокод в
середине, финальный CTA-текст в конце. Раньше (§8.5 п.1, Этап 3) речь
шла об ОДНОМ поле `onScreenText` — с этим решением поле становится
МАССИВОМ текстовых моментов, каждый — кандидат на свою text-card.

**Модель данных (`common/reference-plan.ts` и типы промпта):**

```typescript
interface OnScreenTextMoment {
  /** Сам текст, ≤100 символов (§8.5 п.3) — короче для карточек,
   * которые реально должны читаться, а не быть частью общего фона. */
  text: string;
  /** Когда появляется — для монтажа в промпте и порядка приоритета
   * при нехватке слотов (§20.4, решение 1). */
  role: 'hook' | 'callout' | 'cta';
}
```

`extractLiteralTexts()` (оживление Этапа 3, §8.5 п.1 — тот же приватный
метод `prompt.service.ts`, тот же дешёвый вызов, что уже решён для
диалога) возвращает `OnScreenTextMoment[]`, не одну строку. Пустой
массив — если ролик не нуждается в тексте на экране вовсе (не каждый
УГС-ролик его использует).

### 20.3 Технический рендер — настоящий шрифт, не догадка модели

**Не AI-генерация изображения.** Просить image-модель (Gemini
Image/Grok Image Generation) нарисовать картинку С ТЕКСТОМ — та же
болезнь на новом месте: image-модели тоже коверкают текст, пусть в
среднем немного надёжнее video-моделей на одном статичном кадре. Нужен
настоящий рендеринг шрифта.

**Библиотека — `satori`** (открытый проект Vercel, тот же, что уже
используется в экосистеме Next.js для og-изображений). Превращает
JSX/HTML-подобную разметку в SVG чистым JS, без нативных биндингов —
на serverless-функциях Vercel это значительно безопаснее
`node-canvas`/`sharp`+Cairo, у которых есть известная история проблем
со сборкой именно в таком окружении.

**Конвейер:** `satori(jsx, {width, height, fonts}) → SVG` →
растеризация в PNG (`@resvg/resvg-js`, тот же экосистемный выбор, что
и `satori`) → заливка в тот же Blob, что уже хранит референс-фото
пользователя (`sessions/{id}/text-card-{n}.png`).

**Шрифт — Noto Sans.** Проверено (не предположено): официальная
страница Google Fonts перечисляет украинский язык среди
поддерживаемых, шрифт покрывает блоки Cyrillic, Cyrillic Supplement и
Cyrillic Extended-A — именно там живут специфично украинские глифы
(Ґ/ґ, Є/є, І/і, Ї/ї). Один статический `.ttf`-файл (Regular + Bold),
бандлится в проект как ассет — та же логика, что уже применена к
любому другому статическому ресурсу этого backend.

**Стиль карточки:**
- Фон — сплошной цвет или градиент из `brandManifest`, если он несёт
  цветовую палитру бренда; иначе — нейтральный высококонтрастный
  дефолт (тёмный фон, белый текст — читается на любом видео-фоне,
  на который его будет «смотреть» модель как референс).
  **[Скорректировано в §20.12]** У `BrandManifestSnapshot` на деле нет
  поля цвета — эта часть плана не реализована, карточка всегда
  использует нейтральный дефолт.
- Размер — тот же аспект, что и целевое видео (`9:16`/`16:9`/`1:1`,
  `common/reframe.ts` уже умеет считать целевой аспект) — референс,
  который выглядит как кадр ролика, а не как случайная картинка,
  вероятнее будет понят как «стиль текста для этого кадра», а не
  просто украшение фона.
- Роль (`hook`/`callout`/`cta`) — не влияет на дизайн карточки, только
  на приоритет слота (§20.4).

### 20.4 Открытые вопросы — закрыты (максимальный профит)

**1. Text-card считается в общий `REFERENCE_IMAGE_CAP`/7-слотов Grok
или отдельно?**

**Решено: считается ВНУТРИ общего лимита, с приоритетом персонажей.**
Превышение лимита — подтверждённая (§2 ТЗ) причина 400-ошибки у Veo;
рисковать этим ради текста — терять весь ролик ради одного элемента.
Порядок приоритета при нехватке слотов (персонажи всегда первые — они
то, ради чего обычно и снимается UGC-ролик):

```
1. Персонажи бренда (сколько есть, до вычета из общего капа)
2. Текстовая карточка роли 'cta'   (самый конверсионный момент ролика)
3. Текстовая карточка роли 'hook'
4. Текстовая карточка роли 'callout'
```

Слоты, которые не поместились, НЕ отбрасываются молча — текст остаётся
в промпте как обычный `Text overlay: "..."` (словесное описание, риск
искажения как раньше), а экран кастинга явно показывает бейдж
«текст будет описан словами, не референсом — не хватило места среди
N референсов персонажей» рядом с этим конкретным текстовым моментом.

Практическое следствие §20.2 (Grok — 7 слотов, дефолт с этого же
захода) — при обычных 1-3 персонажах бренда все три роли текста почти
всегда помещаются без вытеснения; у Veo (3 слота) это скорее
исключение, чем правило — ещё один довод в пользу Grok по умолчанию,
не только тот, что уже был (§20 повод).

**2. Автоматически или переключатель пользователю?**

**Решено: автоматически, без переключателя.** Рендер через `satori` —
не AI-вызов, а чистое вычисление (шрифт + разметка → SVG → PNG) — тот
же порядок цены, что уже стоит у любой другой операции с ffmpeg в этом
проекте, на два-три порядка дешевле любого вызова Gemini/Grok/GPT.
Прятать бесплатное (по сути) улучшение качества за переключателем —
терять профит ради несуществующей экономии. Единственное условие
показа — `extractLiteralTexts()` вернула непустой массив; ролики без
текста на экране не порождают карточек вовсе, никакого лишнего шага
для них.

**3. Когда генерировать относительно шага утверждения?**

**Решено (ваша формулировка — «утвердить вместе с персонажами на том
же шаге»): генерировать ДО показа экрана кастинга, показывать рядом с
персонажами.** `extractLiteralTexts()` — тот же дешёвый вызов, что и
рендер персонажей уже требует данные анализа; вызывается в ту же
асинхронную фазу подготовки экрана кастинга (`CharacterCasting.tsx`,
уже существующий компонент), а не отдельным шагом до или после него.
Пользователь видит карточки текста РЯДОМ с карточками персонажей, с
той же возможностью регенерации по клику, что уже есть у персонажей —
не новый паттерн интерфейса, переиспользование существующего.

**4. Регенерация при правке промпта.**

**Решено: автоматическое обнаружение расхождения, не молчаливое
устаревание.** Каждая text-card хранит хэш текста, с которым она была
сгенерирована (`sessions/{id}/text-card-{n}.meta.json` рядом с самой
картинкой, или поле на сессии — конкретное место хранения решить при
реализации). При открытии экрана генерации (после правки промпта)
сверяется текущий `Text overlay`/`extractLiteralTexts()`-текст с
хэшем — при расхождении карточка помечается «текст изменился,
обновите референс» с кнопкой перегенерации, тем же UI-паттерном, что
уже применён к другим «устаревшим до подтверждения» состояниям в этом
проекте (например, `reframePending` у видео).

**5. Шрифт под кириллицу.**

**Решено: Noto Sans** — см. §20.3, проверено по официальной
документации Google Fonts, не предположено.

### 20.5 Асимметрия провайдеров — таблица для UI и кода

| | Veo | Grok |
|---|---|---|
| Потолок референсов | 3 (`REFERENCE_IMAGE_CAP`) | 7 |
| 1 персонаж + 3 роли текста | частично — 2 из 3 карточек (4 позиции на 3 слота, худшая по приоритету роль уходит в словесный `Text overlay`) | помещается всё |
| 3 персонажа + 3 роли текста | НЕТ места ни для одной карточки — все 3 слота заняты персонажами | помещается всё (6 из 7) |

Формализовано в §20.4 п.1 (порядок приоритета) — таблица здесь для
UI-текста бейджа «не хватило места», чтобы формулировка объясняла
ПОЧЕМУ, а не просто показывала факт.

### 20.6 Что нужно от `prompt.service.ts` — интеграция с §19

§19 уже усилил инструкцию `Text overlay: [...]` в ОСНОВНОМ промпте —
это НЕ отменяется этим разделом, а становится ЗАПАСНЫМ ПУТЁМ ДЛЯ
КАЖДОЙ ОТДЕЛЬНОЙ РОЛИ: если text-card для конкретной роли (hook/
callout/cta) не поместилась в слоты (§20.4 п.1) или гипотеза §20.1 не
подтвердится вовсе, ИМЕННО ЭТА роль получает усиленную словесную
формулировку §19, а не весь ролик откатывается разом.

**Найдено при аудите этого же раздела: единственное поле `Text
overlay: [...]` в формате промпта (§19) рассчитано на ОДИН текстовый
момент — с §20.2 их может быть до трёх (hook/callout/cta) в разных
точках ролика.** Формат промпта нужно расширить до множественного
числа, тем же приёмом, что уже применён к персонажам — не общая
ссылка в одном месте, а цитирование КАЖДОЙ text-card ВНУТРИ описания
того самого действия/сцены, к которой она относится (`Subject +
action`), а не в отдельном едином поле:

- Есть card для роли → внутри соответствующего по времени места
  сцены: «match reference image N exactly for the on-screen text, do
  not alter it» — не дублировать словесное описание текста рядом со
  ссылкой на картинку, где текст уже виден.
- Нет card для роли (не поместилась или гипотеза не подтвердилась) →
  для этого конкретного момента остаётся словесная формулировка §19
  на своём месте в сцене.

Практически это меняет саму форму `Format as: "..."` из §19/исходного
промпта — из одного поля `Text overlay: [...]` она становится частью
описания каждой сцены-беата, где текст должен появиться, ближе к
тому, как уже описаны сцены персонажей построчно. Конкретная
перестройка формата — задача реализации, не решена здесь до последней
запятой; только принцип «по одному упоминанию на роль, на своём
месте в сцене», не одно общее поле на весь ролик.

### 20.7 Не решено этим заходом — честно

- Сам ручной тест гипотезы §20.1 — не проведён (нужен реальный API-
  вызов, недоступный в этой среде).
- Хранение `OnScreenTextMoment[]`/хэшей регенерации — конкретная схема
  (поле сессии vs отдельная таблица vs файл рядом в Blob) не выбрана,
  только принцип «обнаружить расхождение, не молчать».
- Стоимость `@resvg/resvg-js` на serverless (холодный старт с нативным
  Rust-биндингом внутри) — `resvg` использует нативный модуль, в
  отличие от чистого JS `satori` — стоит проверить время холодного
  старта на реальном Vercel-деплое перед тем, как полагаться на путь
  «генерируется на каждой сессии».

### 20.8 Реализовано — сквозная цепочка, найдены и исправлены две реальные ошибки в процессе

**Реализовано полностью, end-to-end:**
- `common/text-card-render.ts` — рендер через `satori`+`@resvg/resvg-js`, API обеих библиотек сверено с официальной документацией (не догадка).
- `PromptService.extractLiteralTexts()` — оживление Этапа 3, отдельный дешёвый вызов `GEMINI_MODEL` после основного промпта.
- `TextCardService` — оркестрация рендера/заливки в Blob, идемпотентная по хэшу.
- `POST /sessions/:sessionId/text-cards/ensure` — публичный эндпоинт.
- Интеграция в `reference-plan.ts` — приоритет слотов (персонажи > cta > hook > callout), с тестами.
- `referenceMappingText()`/`grokReferencePromptText()` — цитирование text-card требует копировать текст посимвольно.
- Frontend — показ карточек на экране `prompt-generation`, рядом с `PromptEditor`.

**Найдено и исправлено при повторных проходах аудита собственной реализации (не найдено сразу):**

1. **Критическая ошибка последовательности.** Первая версия показывала text-card на экране кастинга персонажей (`analysis-complete`) — ДО генерации промпта. `extractLiteralTexts()` извлекает моменты ИЗ уже готового текста промпта, которого на этом шаге ещё физически не существует — вся интеграция была бы функционально мертва (`ensureTextCards()` всегда возвращал бы пустой массив). Перенесено на экран `prompt-generation`, где `prompt` уже реально существует.

2. **Хэш устаревания не учитывал аспект/цвет.** `textHash()` изначально хэшировал только `role:text` — если пользователь МЕНЯЛ формат ролика ПОСЛЕ рендера карточки (аспект есть в мастере, `AspectRatioPicker.tsx`), хэш совпадал бы, и карточка НЕПРАВИЛЬНЫХ пропорций тихо продолжала бы использоваться как референс для нового формата. Добавлены `aspectRatio`/`brandColor` в хэш. **[`brandColor` впоследствии убран целиком — §20.12, найден как вектор злоупотребления.]**

3. Найдены (при первой реализации) и исправлены на месте: дубликат типа `GenerationPrompt` в `frontend/src/services/api.ts` (тот же класс проблемы, что уже раз вызвал провал сборки с `GeneratedVideo`, §16.4g) — добавлено поле `onScreenTextMoments` сразу, не по факту сбоя; повторение класса ошибки TS2448 (использование переменной до объявления в той же области видимости) — тот же баг, что уже раз ловился в этом файле раньше, пойман в этот раз до сборки, не после.

**Не изменилось: главная гипотеза §20.1 всё ещё не проверена реальным вызовом.** Вся эта реализация технически готова и синтаксически проверена (баланс скобок, отсутствие TS1xxx/TS2448 на изменённых файлах — типовые ошибки TS2xxx в этой песочнице оказались шумом от отсутствующих `@types/react`, не реальными проблемами), но её ценность полностью зависит от одной ещё не проведённой ручной проверки.

### 20.9 Третий проход аудита собственной реализации — ещё три находки

1. **Гонка при записи `generationPrompt`.** `updateSession()` сливает
   верхнеуровневые ключи атомарно в Postgres, но ЗНАЧЕНИЕ одного ключа
   (`generationPrompt` целиком) заменяется, не сливается по вложенным
   полям (см. её же доккомментарий, этап 47). `TextCardService`
   читал сессию в начале, рендерил карточки несколько секунд, потом
   писал СТАРЫЙ снимок `generationPrompt` — если пользователь успевал
   отредактировать промпт за это время, его правка терялась бы.
   Исправлено: сессия перечитывается непосредственно перед записью.

2. **`updatePrompt()` никогда не обновлял `onScreenTextMoments`.**
   Правка текста промпта не отражалась в извлечённых текстовых
   моментах — хэш в `TextCardService` физически не мог обнаружить
   расхождение, потому что нечему было отличаться. Добавлен повторный
   вызов `extractLiteralTexts()` внутри `updatePrompt()`.

3. **Эта же правка сразу породила третью находку**: если повторное
   извлечение ПРОВАЛИТСЯ (транзиентная ошибка) во время правки —
   раньше метод вернул бы `[]`, что стёрло бы уже успешно
   отрендеренные text-card с прошлого извлечения ради временного сбоя
   сети. Изменена сигнатура `extractLiteralTexts()` — `null` при сбое,
   `[]` только при genuинно пустом результате; `updatePrompt()`
   сохраняет прежние моменты при `null`.

**Побочно найдено и исправлено**: тесты `updatePrompt` (`prompt.service.spec.ts`)
не мокали `genai` вовсе — до правки №2 это было безопасно (модель не
вызывалась), после нее эти тесты сделали бы настоящий сетевой запрос
на фейковый ключ при каждом прогоне. Добавлен мок с намеренным отказом.

Итог трёх проходов аудита одной фичи: 1 критическая ошибка
последовательности (§20.8), 2 находки по хэшу/гонке (§20.8, §20.9-1),
1 находка по неполной инвалидации (§20.9-2), 1 находка, порождённая
исправлением предыдущей (§20.9-3), 1 находка в тестах как следствие.
Ни одна не была видна с первого взгляда на код — каждая нашлась
только при целенаправленном втором/третьем проходе.

### 20.10 Найдена и исправлена устаревшая версия зависимости

При первом добавлении `satori` в `package.json` версия `^0.10.13` была
указана без проверки — при аудите выяснилось (npmjs.com, проверено
напрямую): актуальная версия — **0.33.4** (опубликована 10 дней
назад на момент проверки), `^0.10.13` из-за caret-диапазона (0.x.y —
только патчи по семверу) залочил бы старую, менее зрелую версию.
`@resvg/resvg-js` (`^2.6.2`) — проверена, совпадает с реальной
последней версией, без изменений.

Само использование API (`satori(element, options)` с объектной формой
`{type, props: {style, children}}`, `fonts: [{name, data, weight,
style}]`) сверялось с документацией npmjs.com — она отражает ТЕКУЩУЮ
(0.33.4) версию, не версию 0.10.x — так что раскод, написанный ранее
в этом ТЗ, должен остаться совместимым после исправления номера
версии; отдельно это не перепроверялось (нет возможности установить
пакет в этой среде).

### 20.11 Найдена и исправлена непоследовательность в отчёте расходов

`extractLiteralTexts()` изначально писала расход под операцией
`'prompt'`, слитно с основной сборкой промпта — при повторном аудите
выяснилось, что это противоречит уже принятому в этом же ТЗ решению:
`grok-reference-rewrite` (§15.3) была выделена отдельной операцией по
причине «узкий, дешёвый шаг ПОСЛЕ уже готового текста, не сама сборка
промпта» — та же причина слово в слово применима к
`extractLiteralTexts()` (тоже отдельный вызов ПОСЛЕ готового промпта),
просто не была применена с первого раза. Добавлена операция
`'text-extraction'` в `AiOperation` (`common/ai-pricing.ts`), оба
вызова теперь видны в отчёте расходов раздельно. Добавлен тест.

### 20.12 Найден и закрыт вектор злоупотребления — `brandColor` убран целиком

При очередном проходе аудита проверялась защита от злоупотребления
новым эндпоинтом. Обнаружено: `brandColor` был ПРОИЗВОЛЬНЫМ клиентским
параметром (валидировался только как hex-цвет), хотя §20.3
предполагал брать его из `BrandManifestSnapshot` — который, как
выяснилось, **не хранит цвет вовсе** (поле не реализовано в схеме).
Раз `brandColor` входил в хэш устаревания карточки (§20.9), клиент мог
перебирать произвольные hex-значения, и КАЖДЫЙ раз проходил бы мимо
идемпотентности — новый рендер + новая заливка в Blob на каждый вызов,
бесплатно для клиента (endpoint session-bearer, без отдельной
проверки бюджета — та же модель доверия, что и у остальных
session-bearer эндпоинтов этого проекта, `CastingController` и т.д.,
но там нет параметра, который бы так прямо управлял стоимостью).

Решено: убрать `brandColor` целиком, а не заводить под него поле в
схеме бренда — вводить новое поле данных ради чисто косметического
дефолта фона одной картинки того не стоит. Карточка всегда использует
нейтральный `DEFAULT_BG` (`text-card-render.ts`) — контрастный тёмный
фон, читаемый поверх любого видео-фона одинаково хорошо, вне
зависимости от бренда.

Затронуто: `ensure-text-cards-request.dto.ts` (поле убрано из DTO),
`text-card.controller.ts`/`text-card.service.ts`/`text-card-render.ts`
(параметр убран по всей цепочке), `frontend/src/services/api.ts`
(заодно исправлен устаревший комментарий, всё ещё указывавший на
экран кастинга персонажей — интеграция была перенесена на экран
генерации ещё в §20.8, но комментарий не обновился вместе с кодом).

## 21. Реальный сбой Grok — подтверждена и закрыта неопределённость §10.5

Ровно та неопределённость, что была явно помечена «ПРОВЕРИТЬ перед
первым реальным вызовом» (см. доккомментарий `grok-video.service.ts`),
подтвердилась на практике: опрос статуса генерации падал с HTTP 404
«No handler found on route» — первая догадка о пути
(`GET /v1/videos/generations/{request_id}`, по аналогии с POST) была
неверна.

**Найдена официальная документация REST API**
(`docs.x.ai/developers/rest-api-reference/inference/videos`, с полным
примером запроса и ответа — не по аналогии с другим эндпоинтом):
правильный путь — `GET /v1/videos/{request_id}`, БЕЗ сегмента
`/generations/` (тот есть только у POST-эндпоинта создания). Та же
страница попутно подтвердила ДВЕ другие догадки из того же класса как
верные: `"status": "done"` (не `"completed"`) и форма `video.url` —
обе оказались правильными с первого раза, никакого дополнительного
кода не понадобилось.

Исправлено, задокументировано в самом файле (три пункта
неопределённости, два закрыты явной пометкой). Добавлен тест
(`grok-video.service.spec.ts`, отсутствовал вовсе до этого) — фиксирует
подтверждённый путь и форму ответа, включая тест с буквальным 404 из
реального сбоя.
