# Аудит реализации ИИ-скетча — 17.09.2026

Предмет: код фичи по `doc/AI-SKETCH-SPEC.md` (v3), написанный 17.09.2026 — модуль `backend/src/modules/image-sketch`, резолвер `common/active-image.ts`, промпты `common/sketch-prompts.ts`, правки в плане референсов, генерации, снимках, публичных страницах, партиях, Hedra, и фронтенд `frontend/src/features/sketch`.

Метод: чтение кода по каждому пути, который читает изображение слота, плюс сверка с ТЗ. Каждая находка ниже подтверждена в коде (файл:строка), а не предположена. Живых вызовов модели не было — поведение самой Gemini не проверялось.

## Критично

### A-1. Персонаж бренда: в ролик уходит оригинал, а не скетч

- `modules/casting/casting.service.ts:73-75,145-166` — замена `kind:'brand'` хранит `photoUrl` из снимка и ПРОВЕРЯЕТ его по списку `brandPhotos`, собранному из `snapshot.characters[].photoUrl` (всегда оригинал).
- `common/reference-plan.ts:210` — персонажи читаются только через `activeCastImage(r)`, то есть через `r.sketch`, которого у brand-замены нет.
- `modules/generation/snapshot-voice-sync.service.ts` синхронизирует снимок бренда, но не сам кастинг.

Сценарий: применить скетч персонажу бренда → выбрать этого персонажа в сессии («Бренд») → сгенерировать. В Veo/Grok уходит оригинальное фото человека — ровно то, ради чего фича делалась. После «Удалить оригинал» тот же путь даёт 404 и генерация падает.

**Исправлено.** `activeCastImage(r, brandCharacters?)` для `kind:'brand'` резолвит активное изображение ЧЕРЕЗ снимок бренда (`brandCharacterFor` — по `sourceCharacterId`, с откатом на URL для старых замен); `reference-plan.ts` подаёт туда `session.brandManifestSnapshot?.characters`. `normaliseCasting` принимает и URL скетча, хранит канонический URL оригинала и проставляет `brandCharacterId` из снимка, чтобы связь пережила смену картинки. `propagateToCasting` (см. A-12) дополнительно проставляет скетч прямо в замену.

### A-2. Ответ 429 теряет `quota` и `upgrade` — пользователь видит неверный лимит

- `modules/image-sketch/image-sketch.service.ts:193-203` бросает `HttpException({message, quota, upgrade}, 429)`.
- `common/filters/http-exception.filter.ts:100-106` оставляет из объекта только `message`, остальное отбрасывает.
- `frontend/src/services/sketch-api.ts:135-151` ищет `quota`/`upgrade` → всегда `null` → `SketchSheet.tsx:292` показывает суточный текст даже при исчерпанном месячном лимите, апсейл-кнопка не появляется никогда.

**Исправлено.** У фильтра появился явный белый список полей (`PASSTHROUGH_KEYS`: `quota`, `upgrade`, `reason`, `retryAfterMs`), они уходят в `error.details` конверта — не «всё подряд», чтобы наружу ничего лишнего не утекло. `sketch-api.ts` читает тело в трёх видах сразу (корень, `data`, `error.details`) одной функцией `errorBody`.

## Высокая

### A-3. Применение скетча не меняет уже опубликованные страницы шеринга

`image-sketch.service.ts:385-399` (`apply`) не зовёт `propagateSketch` — это делает только `deleteOriginal:449`. Публичная страница копирует фото при публикации (`shared-video.service.ts:326-340`), значит после применения скетча она бессрочно показывает оригинал. ТЗ §4 п.11 требует обратного.

**Исправлено.** `apply` зовёт `propagateSketch` сразу после записи в слот. Сбой пропагации логируется, но само применение не роняет: подмена в слоте уже произошла, а пропагация идемпотентна и догонит на следующем действии.

### A-4. «Удалить оригинал» у товара сессии удаляет общий файл товара проекта

`snapshot.ts:122-133` кладёт в `productImagePathname` путь `projects/{pid}/items/{iid}/photo.*`, а `sketch-targets.ts:548-556` удаляет `slot.originalPathname` без разбора. Сценарий: сессия создана из товара → «Удалить оригинал» в сессии → фото товара в проекте и во всех других сессиях/страницах пропадает. ТЗ §4 п.10 говорит удалять здесь только ссылку.

**Исправлено.** У слота появился признак `ownsOriginalFile`: у слотов сессии он вычисляется из пути (`sessions/{id}/…` — свой, `projects/…` — общий), у brand-замены персонажа он `false` по определению. `deleteOriginalBlob` возвращает `boolean` и общий файл не трогает; ответ маршрута несёт `fileDeleted`, чтобы интерфейсу было что сказать.

### A-5. Уборка удаляет файлы скетчей, на которые ещё ссылаются сессии

Ссылка на скетч денормализована в JSON сессии (`url`+`pathname`). `apply`/`revert` переводят прежний скетч в `superseded`, а `runCleanupTick:501-534` через 30 дней удаляет его файл, не проверяя, ссылается ли кто-то. Сценарий: скетч товара разъехался по 5 сессиям → применили новый → через месяц у старых сессий битая ссылка.

Там же: `image-sketch.service.ts:523-528` переводит кандидатов в `expired` по `id` без условия `status:'candidate'` — кандидат, применённый посреди тика, получает `expired` и обнулённый путь, хотя слот уже на него ссылается.

**Исправлено.** Перед удалением файла `isSketchReferenced` проверяет строки Prisma (`activeSketchId` у товара, персонажа и сцены бренда) и JSON сессий сырым запросом (мягко удалённая сессия тоже считается ссылкой — весь грейс-период её можно вернуть). Оба `updateMany` уборки получили условие по статусу. Сырые запросы прогнаны на локальном PostgreSQL 16.

### A-6. Персонаж и сцена бренда не умеют «по фото»

`sketch-targets.ts:334-339` — `originalPathname: null` у ассетов бренда, а `image-sketch.service.ts:213-217` на `from-image` без пути отвечает 400. Фронтенд по умолчанию выбирает «по фото», когда фото есть → гарантированная ошибка. Путь выводится из `photoUrl` (`pathnameFromUrl`), так что это чистый недосмотр.

**Исправлено.** `loadBrandAsset` выводит `originalPathname` из `photoUrl` тем же `pathnameFromUrl`.

### A-7. Мастер: применение скетча на шаге генерации ломает кнопку «Сгенерировать»

`ImageUpload` (`GenerationWizard.tsx:612`) и `ReferenceSlotsPanel` (`:854`) живут на шаге `video-generation`, то есть ПОСЛЕ одобрения промпта, а `apply`/`revert` одобрение снимают (`image-sketch.service.ts` → `resetPromptApproval`). Дальше `generation.service.ts:492` отвечает «Prompt must be approved». Экран промпт не перечитывает и не предлагает одобрить заново.

**Исправлено — снятием самого сброса.** `resetPromptApproval` удалён. Обоснование в коде: `referenceMappingText` в одобряемый ТЕКСТ не входит, он дописывается к запросу Veo/Grok во время рендера из свежего плана; пользователь одобряет сценарий, а не список картинок. Ровно так же ведёт себя выбор слотов (`ReferenceSlotsPanel`) — он стоит на том же шаге и одобрение никогда не снимал.

### A-8. Интерфейс показывает оригинал там, где генерация уже берёт скетч

`activeRowPhotoUrl` применён только в `project.service.ts:813` (товары проекта). Выдача бренда (`toCharacterView`), кастинга и сцен сессии по-прежнему отдаёт `photoUrl` оригинала, а бейдж «ИИ-скетч» живёт только в состоянии текущей сессии (`SketchSlotActions.tsx:41`, без начальной загрузки). После перезагрузки: на экране оригинал и никаких кнопок «Вернуть/Удалить оригинал», а в ролик уходит скетч.

**Исправлено.** `toCharacterView` отдаёт активное изображение и четыре поля состояния (`photoVariant`, `originalPhotoUrl`, `originalDeleted`, `activeSketchId`); те же поля добавлены товару проекта, кандидату референса (`originalThumbnailUrl`) и замене персонажа (`sketch`, `originalDeleted` уже были в JSON). `SketchSlotActions` берёт начальное состояние из props и следует за перезагрузкой выдачи — без отдельного запроса на карточку. Все пять точек встраивания подключены, включая `ImageUpload` в мастере (через новые поля `useWorkflow`).

## Средняя

### A-9. Ручной выбор слотов может вернуть скетч в первый кадр

`common/reference-plan.ts:384-386`: при явном выборе (`referenceSelection`) правило §5.6 не применяется. Пустой список слотов → `legacyFirstFrame = true` → скетч уходит как `image`/`imageUrl` (`generation.service.ts:626-640`, `:921-930`), и ролик начинается с рисунка.

**Исправлено.** Пустой ручной выбор при скетче товара принудительно занимает слот референса (единственный случай, когда ручной выбор не уважается — и он же единственный, где иначе нарушается §5.6). Плюс второй замок: `legacyFirstFrame` не может стать `true`, пока активное изображение товара — скетч.

### A-10. Квоту можно обойти параллельными запросами; превью и скетч считаются раздельно

Вид работы `'sketch'` добавлен в `WORK_KINDS`, но `claimWork` не вызывается: между `quota()` и вызовом модели окно, в которое проходят все параллельные запросы. Отдельно: превью персонажа считается по операции `character-preview`, скетч — по `ai-sketch`, обе против одних и тех же лимитов — по факту вдвое больше, чем задумано в §8.2.

**Исправлено.** Введена БРОНЬ: строка `status:'pending'` создаётся ДО вызова модели, и квота считается как расход плюс живые чужие брони, которые старше нашей (`quotaWithReservations`). Перерасход стал невозможен по построению; протухшие брони (процесс умер посреди вызова) уборка переводит в `failed`. Слот сессии дополнительно берётся под `claimWork('sketch')` — тот самый вид работы, который был заведён и не использовался. Лимит объединён: `IMAGE_OPERATIONS = ['ai-sketch', 'character-preview']` в `common/image-generation-quota.ts`, `countToday`/`countSince` принимают список операций, обе стороны считают по нему.

### A-11. Правка снимка бренда теряет скетч

`project-session.service.ts:328-337` (`applySnapshotEdit`) пересобирает `characters` из четырёх полей, без `sketch`/`originalDeleted`. До следующего `POST /generate` (который синхронизирует) активным снова становится оригинал; дочерние сессии экспорта, партий и A/B синхронизацию не проходят вовсе.

**Исправлено.** Скетч и признак удалённого оригинала переносятся из прежней записи по `sourceCharacterId`. Заодно: если форма вернула URL скетча как `photoUrl` (она показывает активный вариант), канонический URL оригинала сохраняется — иначе «Вернуть оригинал» вело бы в никуда.

### A-12. Пропагация неполна

`sketch-targets.ts:481-486` смотрит только 200 последних неудалённых сессий владельца — в более старых остаётся оригинал. `propagateToSessionsOfItem:456-475` не ставит `originalDeleted`, поэтому в таких сессиях остаётся кнопка «Вернуть оригинал» на удалённый файл. Замены `kind:'brand'` (A-1) не покрываются вовсе.

**Исправлено.** Обход идёт страницами по ВСЕМ живым сессиям владельца (курсор по `id`, страница 200), `originalDeleted` передаётся через все ветки пропагации, и добавлена `propagateToCasting` — brand-замены в кастинге получают скетч и недостающий `brandCharacterId`. `syncSnapshotSketches` тоже подтягивает `originalDeleted` всегда (правило «свой скетч сессии сильнее бренда» сохранено).

### A-13. Повторно применить скетч из истории нельзя, а 409 вводит в заблуждение

`apply` принимает только `status:'candidate'`, поэтому «вернуть прежний скетч» из ленты невозможно. Любой 409 фронтенд трактует как «фото изменилось» (`sketch-api.ts` `isSketchStale`) и предлагает платную перегенерацию. `apply` после `delete-original` зовёт `readOriginal` по удалённому пути и даёт 500 вместо 409.

**Исправлено.** `apply` принимает и `superseded` (пока у записи цел файл) — это «вернуть прежний скетч» без повторной оплаты. Сверка по `sourceHash` пропускается, когда оригинал удалён (сверять не с чем — 500 больше нет). У 409 появилась машиночитаемая причина `SKETCH_CONFLICT` (`source-changed` \| `already-applied` \| `sketch-gone`), фронтенд показывает три разных текста вместо одного. Откат при сбое записи возвращает ИМЕННО прежний статус (снят до захвата), а не всегда `candidate`.

### A-14. Новая загрузка фото товара не сбрасывает скетч

`modules/product/product.service.ts:199-205` пишет новый `productImagePathname`, но `sketch` остаётся активным — новое фото молча игнорируется генерацией. ТЗ §3.3 требует отвязки.

**Исправлено** во всех трёх местах, где меняется фото: товар сессии (`product.service.ts`), товар проекта (`product-analog.service.ts` → `persist`), ассет бренда (`confirmAssetPhoto`). Сам скетч остаётся в истории и применяется повторно одним нажатием (см. A-13).

### A-15. Мелочи фронтенда

- Минимальная длина описания: фронтенд пускал 1 символ, DTO требует 3 (`dto/sketch.dto.ts:83`) → непереведённая ошибка валидации. **Исправлено:** `SKETCH_DESCRIPTION_MIN/MAX` в `sketch-model.ts`, подсказка в форме до нажатия, новый ключ словаря в пяти языках, проверка в `scripts/sketch-model.test.ts`.
- После платного отказа модели (422) счётчик квоты не обновлялся; ветка «отказ приходит 200 с пустым url» (`SketchSheet.tsx:152-163`) мертва. **Исправлено:** отказ перечитывает квоту (`getSketchQuota`, который до этого нигде не использовался), мёртвая ветка убрана.
- Меню бейджа (`SketchBadge.tsx:75`, ширина 224 px) вылезало за экран в двухколоночной сетке сцен на 360 px; не было закрытия по клику вне и по Esc; при удалённом оригинале меню пустое. **Исправлено:** ширина ограничена вьюпортом, добавлены закрытие по клику вне/Esc и скрытие самой кнопки меню, когда пунктов в нём не осталось.
- `originalUrl` для товара проекта брался из `item.photoUrl`, который после перезагрузки уже скетч → в сравнении «до/после» обе половины одинаковы. **Исправлено:** у `SketchSlotActions` разведены `originalUrl` и `activeUrl`, все точки встраивания подают исходное фото.

## Проверено и верно (в первом проходе аудита)

- **Владение** по всем шести типам слотов: сессия — по `session.userId`, ассеты бренда — по `brandManifestId` + владельцу манифеста, товар — по владельцу проекта и `deletedAt: null`; чужое и несуществующее одинаково дают 404.
- **Пути файлов** нигде не приходят от клиента: и оригинал, и скетч берутся из слота; DTO путей не содержат.
- **Резолвер** покрывает: план референсов (персонажи, сцены сессии, сцены бренда, товар), ветку референсов Veo и `fetchReference`, `resolveReferenceUrl` Grok, продолжение цепочки, партии по каталогу, Hedra, `keepOwnCopy`, выдачу товаров проекта. Экспорт, повтор из админки и A/B идут через `generateVideo` → тот же план. Проверка «ссылка наша» (`isOwnBlobUrl`) сохранена.
- **Применение** захватывается атомарно (`candidate → applied` одним `updateMany`), при сбое записи статус откатывается, прежний скетч уходит в `superseded`.
- **Учёт расхода**: 502 не пишет `ai_usage`, 422 пишет, `userId` передаётся всегда.
- **Схема ↔ миграция ↔ код**: имена полей совпадают (включая `modelName @map("model")`), индексы и `@unique` на месте, миграция проверена на локальном PostgreSQL 16, `LIVE_KEYS` не тронуты.
- **Промпты**: обезличивание лица навязывается сервером для фото людей, запреты есть в каждой ветке, описание подставляется как данные.
- **Контракт фронтенда с DTO** (тела, query, значения enum) и словари пяти языков — совпадают; `tsc` и eslint по изменённым файлам чисты.
