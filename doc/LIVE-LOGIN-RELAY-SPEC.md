# `live-login-relay/` — детализированное ТЗ отдельного сервиса

## 0. Статус и происхождение документа

Прямая цитата запроса, с которого начат этот документ:

> Отдельный live sessions сервис делаем в отдельном каталоге, Напиши
> детализацию ТЗ

`doc/CLIENT-SITE-TUTORIAL-SPEC.md` §7.4 уже спроектировал АРХИТЕКТУРУ
этого сервиса (зачем он нужен, протокол CDP-скринкаста, жизненный цикл
сессии, хостинг на Dokploy) — этот документ её **детализирует до уровня
«можно открывать `live-login-relay/` и писать код»**: структура
каталога, точные HTTP/WS-контракты, `package.json`, `Dockerfile`,
`docker-compose.yml`, границы безопасности, тестовый план. §7.4
остаётся источником АРХИТЕКТУРНЫХ решений и на него здесь есть прямые
ссылки; этот документ ничего в них не меняет, кроме двух явно
помеченных ниже мест, где детализация вскрыла неточность в исходном
тексте (§6 и §9 этого документа — обе поправки внесены и в сам
`CLIENT-SITE-TUTORIAL-SPEC.md`).

`live-login-relay/` — пятый деплоймый каталог монорепо, РЯДОМ с
`backend/`/`frontend/`/`admin/`/`landing/`, не внутри одного из них:
свой `package.json`, свой `Dockerfile`, свой `docker-compose.yml`, ни
Prisma, ни доступа к остальному монорепо при сборке (важно для §6
ниже). Монорепо НЕ использует npm workspaces (в корне нет
`package.json` вообще — проверено: `backend/`, `frontend/`, `admin/`,
`landing/` уже сегодня полностью независимы друг от друга по
зависимостям и сборке), так что пятый такой же независимый каталог —
не новый паттерн, а точное повторение уже существующего.

## 1. Идея в одном абзаце

Маленький, постоянно живущий (не serverless) Node-процесс без NestJS и
без Prisma — намеренно минимальная поверхность, потому что у него ровно
одна обязанность: на время одной live-сессии входа держать открытым один
экземпляр headless Chromium, транслировать его экран пользователю по
WebSocket (CDP `Page.startScreencast`) и принимать от него клики/ввод
обратно в реальную страницу (CDP `Input.dispatch*`) — сам протокол уже
спроектирован в §7.4.3 основного ТЗ. Знает про Telegram/Prisma/проекты
ровно ноль — общается с нашим backend только по одному общему секрету
(`X-Relay-Secret`, §7.4.4 п.2 основного ТЗ) и никогда не вызывается
напрямую из ТМА/браузера пользователя, КРОМЕ самого WebSocket-потока
(§7.4.3: «Оба конца соединены... НАПРЯМУЮ, не проксируется через наш
NestJS/Vercel»).

## 3. Стек и `package.json`

Не NestJS (нет DI-контейнера ради четырёх маршрутов), не Express (та же
причина — четыре HTTP-маршрута и один WS-апгрейд размечаются вручную
через `node:http`+`url.pathname`, фреймворк добавил бы зависимость ради
удобства, которое здесь не нужно). Единственная реальная внешняя
зависимость сверх `puppeteer-core` — `ws` (де-факто стандартная
WebSocket-библиотека для Node, `Page.startScreencast`/`Input.dispatch*`
всё равно идут через `puppeteer-core`'s CDP-сессию, не через `ws`
напрямую).

```json
{

  "private": true,
  "license": "UNLICENSED",
  "engines": { "node": "24.x" },
  "scripts": {
    "build": "tsc -p tsconfig.json",
```

**`puppeteer-core` версия `^23.0.0` — та же, что `backend/package.json`
(строка 52 файла), НАМЕРЕННО.** Оба процесса говорят по одному и тому же
CDP-диалекту с Chromium одного и того же семейства (Chrome 127, тот же
довод, что уже зафиксирован в `headless-chromium.ts:23-26` про
совместимость протокола) — при обновлении `puppeteer-core` в одном месте
это ЖИВОЙ сигнал проверить и второе, а не независимая версия сама по
себе; при реализации стоит завести это как пункт в чек-лист ревью
зависимостей (не блокер этого документа, просто явная заметка «эти два
package.json нужно обновлять синхронно»).

**Отклонение от этого раздела, принятое при реализации пилота (этап
102 плана):** вместо `"type": "module"` (ESM) пакет собран как
CommonJS (`tsconfig.json`: `"module": "commonjs"`, без `"type":
"module"` в `package.json` выше). Причина — не архитектурная, а чисто
инструментальная: `ts-jest` в связке с ESM на момент реализации требует
заметно более хрупкой настройки (нативные `--experimental-vm-modules`,
проблемы с моками), тогда как CommonJS работает "из коробки" с тем же
`jest.config.js`, что и у `backend/` — а `live-login-relay/` сознательно
скопировал ESLint/Jest/Prettier-тулчейн `backend/` один в один (см.
`devDependencies` выше), так что CommonJS ещё и держит оба пакета в
одной конвенции вместо двух разных. `tsx watch` для `dev`-режима
работает одинаково в обоих вариантах, так что на самом dev-опыте это
никак не сказывается. Ничего в протоколе/API/Dockerfile от этого не
меняется — просто `tsconfig.json` пакета фиксирует `"module":
"commonjs"` вместо ESM-таргета, и импорты в `src/`/`test/` — обычный
CommonJS-стиль (`import ... from './session'`, без расширения `.js` на
конце пути, как требовал бы ESM).

## 4. Переменные окружения

| Переменная | Обязательна | Дефолт | Смысл |
|---|---|---|---|
| `PORT` | нет | `8088` | HTTP+WS порт внутри контейнера |
| `PUPPETEER_EXECUTABLE_PATH` | да | — | Путь к системному Chromium (см. §6, §11) — без неё процесс падает при старте (fail-fast, не при первом запросе) |
| `LIVE_LOGIN_RELAY_SECRET` | да | — | Общий секрет с backend (`X-Relay-Secret`) — без неё процесс падает при старте: **нет секрета — нет старта**, не «нет секрета — открытый доступ» (тот же fail-closed принцип, что `cron-secret.ts`, только без dev-исключения — см. §10.1, почему здесь оно не нужно) |
| `MAX_CONCURRENT_SESSIONS` | нет | `10` | Общий потолок одновременных сессий на весь процесс (§7.4.8 основного ТЗ — «общий ограниченный ресурс на всех пользователей одновременно») |
| `SESSION_WALL_TIMEOUT_MS` | нет | `180000` (3 мин) | Жёсткий потолок жизни сессии (§7.4.4 п.5 основного ТЗ) |
| `SESSION_IDLE_TIMEOUT_MS` | нет | `60000` (60 с) | Автозакрытие без единого события ввода (§7.4.4 п.5) |
| `RESULT_CACHE_MS` | нет | `60000` | Сколько после закрытия сессии `GET /sessions/:id/result` ещё отдаёт закэшированный результат повторно, не `404` (§7.2 — идемпотентность на случай повтора backend'ом при сетевом сбое) |
| `WS_AUTH_TIMEOUT_MS` | нет | `5000` | Сколько ждать `{type:"auth"}` после апгрейда WS, прежде чем закрыть соединение (§8.1) |
| `LOG_LEVEL` | нет | `info` | `debug`/`info`/`warn`/`error` |
| `NODE_ENV` | нет | `production` | Только влияет на подробность логов (полный стек ошибки в `debug`) — НЕ открывает dev-bypass, у реле такого понятия нет |

Backend со своей стороны уже документирует парную пару
`LIVE_LOGIN_RELAY_URL`/`LIVE_LOGIN_RELAY_SECRET` как опциональную
интеграцию (§7.4.9 основного ТЗ) — значение `LIVE_LOGIN_RELAY_SECRET`
ОБЯЗАНО совпадать буквально между двумя процессами, это один и тот же
секрет, заданный дважды в двух разных местах развёртывания (Vercel env
для backend, переменные сервиса в Dokploy для реле) — как и
`CHANNEL_TOKEN_KEY`/`ADMIN_LOGIN_BOT_TOKEN` и другие межпроцессные
секреты этого же проекта.

## 5. Модель сессии и её жизненный цикл

### 5.1 Состояния

```
created → streaming → finalizing → closed(cached) → gone
                 ↘ (wall/idle timeout) → closed(cached) → gone
```

- **`created`** — `POST /sessions` принят, браузер запускается
  (`launch-browser.ts`, §6), CDP-сессия открывается, `page.goto(startUrl)`
  выполняется. Пока WS не подключился и не прошёл `{type:"auth"}`
  (§8.1) — скринкаст не запущен (нет смысла слать кадры в никуда).
- **`streaming`** — WS подключён и аутентифицирован, `Page.
  startScreencast` активен, `lastActivityAt` обновляется на каждое
  `mouse`/`key`-сообщение от клиента (НЕ на `ping`/`resize` — см. §8.2,
  почему именно так).
- **`finalizing`** — `GET /sessions/:id/result` принят: снимается
  cookie jar со всего контекста (§7.4.5 основного ТЗ), браузер
  закрывается, WS закрывается кодом `4000` (`{type:"closed",
  reason:"finalized"}` перед закрытием — фронтенду есть на что
  среагировать, если он ещё слушает).
- **`closed(cached)`** — результат (`{cookies, finalUrl}` либо ошибка)
  хранится в памяти ещё `RESULT_CACHE_MS` — повторный `GET .../result`
  в этом окне отдаёт ТОТ ЖЕ результат, не `404` (см. §7.2).
- **`gone`** — запись удаляется из `Map` (по таймеру или по
  `DELETE /sessions/:id`, §7.3) — дальше `404` на любой запрос по
  этому `sessionId`.

Переход `streaming → finalizing` может случиться и без WS вообще
(пользователь так и не подключился/потерял связь, но backend всё равно
дождался таймаута и явно позвал `/result`) — эндпоинт не требует, чтобы
WS был жив в момент вызова, только чтобы сессия существовала.

### 5.2 `session-manager.ts` — модель ресурса

Один `Session` = один выделенный `puppeteer-core` `Browser` (НЕ общий
браузер на несколько сессий с несколькими вкладками — полная изоляция
между параллельными пользователями, включая cookie jar, проще и
безопаснее, чем делить один браузер через несколько `BrowserContext`).
Это принципиально ДРУГАЯ модель ресурса, чем у backend'а (§5.1
основного ТЗ — «один запрос = один свежий браузер, закрытый в конце
того же вызова»): здесь один браузер живёт МИНУТЫ, ограничен не по
запросам, а по `MAX_CONCURRENT_SESSIONS` штук одновременно. `POST
/sessions`, пришедший сверх потолка, получает `503` немедленно, без
постановки в очередь (очередь на «подождать своей капчи» — плохой UX,
дешевле явно сообщить «попробуйте через минуту»).

## 6. Запуск браузера в реле — поправка к §7.4.2 основного ТЗ

**Уточнение, вскрытое именно этой детализацией.** §7.4.2 основного ТЗ
говорит: «`live-login-relay` переиспользует ЭТУ ЖЕ функцию
(`resolveHeadlessBrowserLaunchPlan()`) как есть, импортируя `common/`».
Буквально это невыполнимо: `live-login-relay/` — отдельный деплоймый
пакет со СВОИМ Docker build context (§7.4.9 основного ТЗ сам же это
устанавливает — «у сервиса нет ни Prisma, ни остальных сервисов
монорепо»), а Docker `COPY` не может взять файл за пределами build
context (`live-login-relay/`) без того, чтобы держать build context на
весь монорепо целиком — что как раз отменяет то самое намеренное
разделение, ради которого заводился отдельный каталог.

**Исправлено (и внесено также в `CLIENT-SITE-TUTORIAL-SPEC.md` §7.4.2):**
реле НЕ импортирует файл backend'а — у него своя, значительно меньшая
копия РОВНО той функциональности, которая ему реально нужна (только
Docker-ветка, без `@sparticuz/chromium-min`/serverless-ветки, которая
реле вообще не касается):

```ts
// live-login-relay/src/launch-browser.ts
import puppeteer, { type Browser } from 'puppeteer-core';

// Скопировано построчно из backend/src/common/headless-chromium.ts:31-41
// (DOCKER_CHROMIUM_ARGS) — тот же набор флагов для системного Chromium в
// Docker, НЕ импорт: см. §6 doc/LIVE-LOGIN-RELAY-SPEC.md, почему
// буквальный импорт через границу двух отдельно деплоймых пакетов
// технически невозможен. Если этот список поменяется в backend'е,
// поменять и здесь — комментарий-маячок с точным путём оставлен
// специально, чтобы grep находил обе копии.
const DOCKER_CHROMIUM_ARGS = [
  '--no-sandbox',
  '--disable-setuid-sandbox',
  '--disable-dev-shm-usage',
  '--disable-gpu',
  '--disable-extensions',
  '--disable-background-networking',
  '--disable-background-timer-throttling',
  '--disable-renderer-backgrounding',
  '--js-flags=--max-old-space-size=256',
];

export async function launchRelayBrowser(): Promise<Browser> {
  // config.ts уже проверил это при старте процесса (§4) — повторная
  // проверка здесь дешёвая и защищает от будущего вызова в обход
  // config.ts (например, из теста).
  const executablePath = process.env.PUPPETEER_EXECUTABLE_PATH?.trim();
  if (!executablePath) {
    throw new Error(
      'PUPPETEER_EXECUTABLE_PATH не задан — см. Dockerfile (§11), путь должен быть выставлен ENV в образе',
    );
  }
  return puppeteer.launch({
    executablePath,
    headless: true,
    args: DOCKER_CHROMIUM_ARGS,
  });
}
```

Заодно у реле нет смысла в кэширующем резолвере (`resolveHeadlessBrowserLaunchPlan()`'s
`launchPlanPromise`, §2 основного ТЗ) — та мемоизация существует ИМЕННО
из-за serverless-модели («не платить за скачивание архива повторно на
каждый вызов тёплого инстанса»); здесь `PUPPETEER_EXECUTABLE_PATH`
статичен с момента старта контейнера, никакой загрузки/распаковки на
каждый запуск браузера нет — `launchRelayBrowser()` просто вызывается
заново на каждую `POST /sessions` (§5.2), без слоя кэша вообще.

## 7. HTTP API

Все запросы (кроме `GET /health`) — заголовок `X-Relay-Secret: <секрет>`,
проверяется `auth.ts` (§10.1) до разбора тела. Тело запроса ограничено
`16 КБ` (`MAX_BODY_BYTES`) — `413`, если больше; у этого API нет
легитимных тел крупнее нескольких сотен байт, лимит — дешёвая защита от
тривиального злоупотребления, не рабочий сценарий.

```
POST   /sessions
       Тело: { startUrl: string; allowedOrigin: string }
       Проверяет, что new URL(startUrl).origin === new
       URL(allowedOrigin).origin (дешёвая защита от опечатки/бага
       вызывающего кода — backend и так уже провёл настоящую
       SSRF-проверку до этого вызова, §8.2 основного ТЗ, реле её не
       повторяет, только сверяет СВОИ два поля друг с другом). Если
       MAX_CONCURRENT_SESSIONS уже достигнут — 503 «реле перегружено,
       попробуйте через минуту». Иначе: launchRelayBrowser() (§6) →
       page.goto(startUrl) → создать Session{state:'created'} с новым
       sessionId (crypto.randomUUID()) и streamToken
       (crypto.randomBytes(32).toString('base64url'), хранится в памяти
       ТОЛЬКО как sha256-хэш — см. §10.2).
       201 { sessionId: string; streamToken: string; wsPath: string }
       (wsPath = `/sessions/{sessionId}/stream` — backend склеивает
       полный wss:// URL сам, реле не знает свой собственный публичный
       хост)
       400 — startUrl/allowedOrigin не URL или origin не совпал
       401 — неверный/отсутствующий X-Relay-Secret
       503 — MAX_CONCURRENT_SESSIONS достигнут
       502 — launchRelayBrowser()/goto(startUrl) упал (текст ошибки —
       как есть, backend прокидывает его пользователю по цепочке до
       понятного сообщения на фронтенде)

GET    /sessions/:id/result
       Снимает cookie jar со ВСЕГО контекста (все домены, с которыми
       сессия взаимодействовала — §7.4.5 основного ТЗ, находка того же
       аудита про SSO-куки), закрывает браузер, переводит сессию в
       finalizing → closed(cached). Идемпотентен в окне
       RESULT_CACHE_MS (§5.1, §7.2 ниже) — повторный вызов в этом окне
       НЕ запускает снятие кук ещё раз, отдаёт тот же закэшированный
       результат.
       200 { cookies: CdpCookie[]; finalUrl: string }
       404 — sessionId не существует и не в кэше (либо никогда не
       существовал, либо gone — кэш истёк)
       409 — сессия ещё в состоянии created (браузер только запускается,
       WS даже не успел подключиться) — вызывающий код (backend) не
       должен звать этот эндпоинт раньше, чем пользователь реально
       нажал «Готово, я вошёл» на фронтенде, так что это скорее
       защитный код на баг вызывающего, чем ожидаемый путь

DELETE /sessions/:id
       Best-effort ранняя отмена (§7.3 ниже) — не обязательна для
       корректности (таймауты §5.1 — тот же результат чуть позже), но
       освобождает MAX_CONCURRENT_SESSIONS раньше под нагрузкой.
       204 — закрыто (или уже было закрыто/не существовало —
       идемпотентно в широком смысле, без различения кодом ответа)

GET    /health
       Без авторизации (отдаёт только счётчик, не содержимое сессий —
       намеренно не секрет). Для healthcheck Dokploy/docker-compose
       (§12), тот же принцип, что уже `pg_isready` у `db`-сервиса в
       docker-compose.dev.yml корня монорепо.
       200 { ok: true; activeSessions: number; maxSessions: number }
```

### 7.1 `CdpCookie`

```ts
interface CdpCookie {
  name: string;
  value: string;
  domain: string;
  path: string;
  secure: boolean;
  httpOnly: boolean;
  sameSite?: 'Strict' | 'Lax' | 'None';
  expires: number; // unix seconds, -1 = session cookie
}
```

Ровно то, что отдаёт CDP `Network.getAllCookies` (не `page.cookies()`
без аргументов — §7.4.5 основного ТЗ уже объяснил разницу и почему
важен весь контекст, не только текущая страница).

### 7.2 Почему `/result` обязан быть идемпотентным

Если backend позвал `/result`, реле успело снять куки/закрыть браузер и
ответить `200`, но сам HTTP-ответ потерялся в сети (обрыв, таймаут) —
backend по стандартному правилу «не знаю, дошло ли» обязан повторить
запрос. Без кэша повтор упёрся бы в `404` (сессия уже `gone` или как
минимум `closed`) — реальные, только что собранные куки данного пользователя
потерялись бы НЕВОЗВРАТНО (повторный live-вход — это снова минута
живого времени человека, а не бесплатная операция). `RESULT_CACHE_MS`
— дешёвая страховка именно от этого класса сбоя, не от чего-то более
экзотического.

### 7.3 Когда backend реально зовёт `DELETE /sessions/:id`

Не обязательный вызов на общем пути. Полезен в двух конкретных
случаях: (а) пользователь закрыл/свернул экран визарда с активной
live-сессией, не дождавшись «Готово, я вошёл» — backend, заметив это
(например, по явному `beforeunload`-сигналу с фронтенда, если он
реализован, или просто не реализуется вовсе для MVP — таймаут §5.1 и
так справится); (б) пользователь нажал «Отмена» на экране live-входа —
прямой, синхронный повод закрыть сессию немедленно, а не платить за
неё ещё вплоть до `SESSION_IDLE_TIMEOUT_MS`. Ни то, ни другое не влияет
на корректность (таймауты — самодостаточный бэкстоп), только на то, как
быстро освобождается место под `MAX_CONCURRENT_SESSIONS` — оптимизация
ресурса под нагрузкой, не часть основного счастливого пути.

## 8. WebSocket-протокол

`wss://{RELAY_HOST}/sessions/{sessionId}/stream` — `sessionId` в пути
(нужен для маршрутизации к нужному `Session`, сам по себе не секрет).
**Токен НЕ в query-строке** — сознательное отличие от, казалось бы,
более простого `?token=...`: query-строки WebSocket-рукопожатия обычным
образом оседают в логах прокси/CDN на пути между браузером пользователя
и реле (тот же класс риска, что утечка токена через `Referer`), а
`streamToken` живёт ровно на длину одной сессии — риск невелик, но
устраняется бесплатно другим способом (см. ниже), так что нет причины
его принимать.

### 8.1 Хендшейк

1. Клиент открывает WS на `/sessions/{sessionId}/stream` без токена в
   URL. Сервер принимает апгрейд, только если `sessionId` существует и
   его состояние — `created` или `streaming` (иначе — закрыть сразу
   кодом `4004` «unknown or closed session», ещё до полноценного
   апгрейда, если возможно, иначе сразу после).
2. Первое сообщение от клиента ОБЯЗАНО быть `{type:"auth", token:
   streamToken}` — сервер сравнивает `sha256(presented)` с сохранённым
   хэшем через `timingSafeEqual` (§10.2). Не пришло за
   `WS_AUTH_TIMEOUT_MS` (по умолчанию 5с) или не совпало — закрыть
   кодом `4001` «unauthorized».
3. Если у сессии уже ЕСТЬ активное аутентифицированное WS-соединение —
   новое аутентифицированное соединение вытесняет старое (закрыть
   старое кодом `4009` «superseded by new connection») — два
   одновременных «пульта управления» одной и той же живой страницей
   технически возможны, но бессмысленны и создают путаницу «кто сейчас
   реально жмёт кнопки»; при MVP-объёме (один пользователь на своём
   телефоне) практическая причина — случайно открытая вторая вкладка,
   не злонамеренный сценарий.
4. Успешный auth → `Page.startScreencast` стартует, состояние сессии
   → `streaming`.

### 8.2 Сообщения сервер → клиент

```ts
type ServerMessage =
  | { type: 'frame'; data: string /* base64 JPEG */; metadata: {
      offsetTop: number; pageScaleFactor: number;
      deviceWidth: number; deviceHeight: number;
      scrollOffsetX: number; scrollOffsetY: number;
    }; frameAckId: number /* см. ниже */ }
  | { type: 'navigated'; url: string }
  | { type: 'error'; message: string }
  | { type: 'closed'; reason: 'wall-timeout' | 'idle-timeout'
      | 'finalized' | 'cancelled' | 'server-shutdown' };
```

`frame` — прямое отражение CDP-события `Page.screencastFrame`; `data`/
`metadata` копируются как есть из события, `frameAckId` — тот же
`sessionId`-параметр, что CDP просит вернуть через
`Page.screencastFrameAck({sessionId})`, чтобы Chromium прислал
следующий кадр (без ack поток кадров у CDP-скринкаста останавливается —
это ЧАСТЬ протокола, не опция; `ws-handler.ts` шлёт ack сразу после
каждого полученного `Page.screencastFrame`, не дожидаясь, пока клиент
его отрисует — задержка отрисовки на телефоне пользователя не должна
душить сам поток).

`navigated` — на каждую навигацию ГЛАВНОГО фрейма (`page.on(
'framenavigated')`, отфильтрованное `frame === page.mainFrame()`) —
чистая ТРАНСПРОЗРАЧНОСТЬ для UI (фронтенд может показать текущий домен
рядом с картинкой), см. §9 ниже про то, почему это не механизм
принуждения.

### 8.3 Сообщения клиент → сервер

```ts
type ClientMessage =
  | { type: 'auth'; token: string }
  | { type: 'mouse'; event: 'mousePressed' | 'mouseReleased' | 'mouseMoved' | 'mouseWheel';
      x: number; y: number; button?: 'left' | 'right' | 'middle';
      deltaX?: number; deltaY?: number }
  | { type: 'key'; event: 'keyDown' | 'keyUp' | 'char';
      key: string; code: string; text?: string }
  | { type: 'resize'; width: number; height: number }
  | { type: 'ping' };
```

`mouse`/`key` — ретранслируются буквально в CDP `Input.
dispatchMouseEvent`/`Input.dispatchKeyEvent` (§7.4.3 основного ТЗ уже
объяснил, почему именно CDP-уровень, а не `page.mouse`/`page.keyboard`
высокого уровня) — И ТОЛЬКО ОНИ обновляют `session.lastActivityAt`
(идл-таймаут §5.1 меряет активность ЧЕЛОВЕКА, а не наличие открытого
соединения). `resize` — `Emulation.setDeviceMetricsOverride`, нужен для
верной трансляции координат клика при повороте экрана/другом размере
`<canvas>` (риск, честно отмеченный в §7.4.3 основного ТЗ) — НЕ считается
активностью для идл-таймаута (сам по себе это событие браузера
пользователя, не доказательство, что человек продолжает СМОТРЕТЬ на
экран и вводить капчу). `ping` — чистый keepalive транспортного уровня
(некоторые мобильные сети/прокси рвут «тихие» WS-соединения без
трафика) — специально НЕ считается активностью по той же причине, что и
`resize`: вкладка, забытая открытой на экране логина, обязана
истечь по `SESSION_IDLE_TIMEOUT_MS`, даже если её WS technically жив и
шлёт пинги сам по себе.

## 9. Доменная «прозрачность» вместо блокировки — поправка к §7.4.4 п.4 основного ТЗ

**Противоречие, вскрытое этой детализацией.** §7.4.4 п.4 основного ТЗ
одновременно утверждает «реле отклоняет... любую навигацию, уводящую
`page.url()` за пределы `allowedOrigin`» И тут же — «доменный замок в
live-сессии не блокирует переход целиком» (оговорка про SSO). Это две
несовместимые формулировки одного и того же механизма, оставшиеся
несогласованными с первой версии §7.4.

**Разбор при детализации.** Активно ПРЕПЯТСТВОВАТЬ навигации через CDP
не тривиально (нет чистого «наложить вето на уже начавшуюся навигацию»
— `Fetch.enable`-перехват на уровне сети возможен, но тогда нужен
поддерживаемый список легитимных сторонних доменов для КАЖДОГО
возможного провайдера SSO/3-D Secure/платёжного шлюза — задача без
чёткой границы, тот самый компромисс, которого раздел и пытался
избежать оговоркой про SSO). А застревать в детекте-и-откате (заметить
постфактум, что `page.url()` вне `allowedOrigin`, и звать
`page.goBack()`) — не блокировка, а Best-effort реакция С задержкой в
один кадр, которая ничего не мешает пользователю УСПЕТЬ увидеть/
провзаимодействовать с этой страницей за то время, пока реле «думает»
— то есть не даёт вообще никакой реальной защиты сверх того, что уже
даёт финальная проверка.

**Решение (внесено также в `CLIENT-SITE-TUTORIAL-SPEC.md` §7.4.4 п.4):**
реле НЕ пытается блокировать/откатывать навигацию во время live-сессии
вообще — единственный enforcement-пункт остаётся ровно там, где он и
был правильно специфицирован с самого начала, в §7.4.5 основного ТЗ:
`finalUrl` (URL, на котором пользователь нажал «Готово, я вошёл»)
проверяется на принадлежность `draft.baseUrl` НА СТОРОНЕ BACKEND при
завершении сессии — если пользователь остался на чужом домене (не
довёл SSO до возврата на сайт заказчика), это явная ошибка «похоже, вход
не завершён», а не тихий успех. Сама возможность зайти куда угодно ВО
ВРЕМЯ сессии — не дыра, а прямое следствие того, что за рулём в этот
момент живой, зрячий человек (WS-соединение прямое, видео идёт в
реальном времени, §7.4.3) — то самое обстоятельство, ради которого
live-сессия вообще существует (§7.4.0: «дать человеку разово
вмешаться в точке, которую автомат в принципе пройти не может»). Роль
реле здесь — чистая ТРАНСПОРТНАЯ прозрачность: `{type:"navigated",
url}` (§8.2) даёт фронтенду возможность показать текущий домен рядом с
картинкой, чтобы человек САМ заметил, если что-то пошло не так — не
принуждение программным способом.

## 10. Безопасность

### 10.1 `X-Relay-Secret` — без dev-исключения

`auth.ts` — тот же fail-closed + `timingSafeEqual` приём, что
`cron-secret.ts` (`backend/src/modules/cron/cron-secret.ts:54-89`), НО
**без** dev-исключения этого файла (`isDevAuthAllowed`, срабатывающее
при `ALLOW_DEV_AUTH=true` и `NODE_ENV!=='production'`): у `cron-
secret.ts` исключение существует, чтобы локальный dev-стенд мог дёргать
крон-маршруты curl'ом без секрета вообще. У реле такого сценария нет —
единственный легитимный вызывающий (backend) ВСЕГДА знает секрет
(читает его из своих же переменных окружения), а локальная разработка
самого визарда (§11 основного ТЗ) не требует поднимать реле вообще —
live-вход просто недоступен на dev-стенде (тот же принцип мягкой
деградации, что уже описан для отсутствующего `LIVE_LOGIN_RELAY_URL` в
§7.4.9 основного ТЗ, — кнопка на фронтенде прячется). Значит секрет
обязателен ВСЕГДА, включая локальный запуск самого реле — `config.ts`
падает при старте без него, а не «работает без него локально».

```ts
// live-login-relay/src/auth.ts
import { timingSafeEqual } from 'node:crypto';

export function assertRelaySecret(headerValue: string | undefined): void {
  const secret = process.env.LIVE_LOGIN_RELAY_SECRET; // config.ts уже
  // гарантировал непустоту при старте процесса — здесь не перепроверяется
  if (!headerValue || !safeEqual(headerValue.trim(), secret!)) {
    throw new UnauthorizedError('неверный или отсутствующий X-Relay-Secret');
  }
}

function safeEqual(a: string, b: string): boolean {
  const bufA = Buffer.from(a, 'utf8');
  const bufB = Buffer.from(b, 'utf8');
  if (bufA.length !== bufB.length) {
    timingSafeEqual(bufB, bufB);
    return false;
  }
  return timingSafeEqual(bufA, bufB);
}
```

(`safeEqual` — буквально та же функция, что `cron-secret.ts:81-89`/
`fixture-token.ts:61-69` — третья копия одной десятистрочной идиомы в
проекте; не обобщается в общий модуль по той же причине, по которой
`fixture-token.ts`'s доккомментарий уже объясняет, почему он не переиспользует
`cron-secret.ts` — а здесь ещё и физически другой пакет, обобщать
буквально некуда без нарушения границы §6.)

### 10.2 `streamToken` — не хранится в открытом виде

В отличие от `LIVE_LOGIN_RELAY_SECRET` (статичный, ОДИН на весь
процесс, живёт в переменной окружения) `streamToken` — одноразовый,
генерируется НА КАЖДУЮ сессию (`crypto.randomBytes(32).toString(
'base64url')`, 256 бит энтропии). В памяти `Session` хранится не сам
токен, а `sha256(token)` — сравнение предъявленного при WS-хендшейке
токена идёт по хэшу через `timingSafeEqual`, тем же приёмом, что §10.1.
Утечка дампа памяти процесса (маловероятный, но дешёвый в защите
случай) не отдаёт токен напрямую — та же дисциплина «не хранить секрет
плоским текстом», что уже применена в проекте для куда более
долгоживущих секретов (`token-crypto.ts`), просто здесь применена
хэшем, а не обратимым шифрованием, — токен одноразовый и короткоживущий,
расшифровывать его обратно никогда не требуется.

### 10.3 Размер тела запроса

`MAX_BODY_BYTES = 16 * 1024` на входящий HTTP-запрос (§7) — читается
вручную через `for await (const chunk of req)` с накопительным
счётчиком байт, обрыв соединения и `413`, если превышен, до того, как
тело разобрано как JSON. Мотивация — не производительность (запросов к
этому API физически мало), а дешёвая защита от тривиального
злоупотребления телом произвольного размера на процесс без Nest'овских
встроенных лимитов body-parser'а.

### 10.4 Некорневой пользователь — не блокер MVP

`DOCKER_CHROMIUM_ARGS` уже включает `--no-sandbox` (унаследовано из
`headless-chromium.ts` — необходимо для запуска Chromium от root внутри
контейнера без дополнительной настройки ядра). Полноценная защита —
непривилегированный пользователь в образе (`USER pptruser`-подобный
приём) и включённый sandbox — заметно усложняет `Dockerfile` (нужны
`setuid`-биты на конкретные бинарники Chromium). Осознанно отложено как
первое расширение объёма ПОСЛЕ MVP, тем же принципом «не блокер
запуска», что уже применён к нескольким пунктам основного ТЗ (например
§8.1 — расширение доменного замка до eTLD+1): контейнер реле и так
изолирован на уровне Docker от остального хоста, а обрабатывает он
ЧУЖОЙ веб-контент под присмотром живого человека, не произвольный
недоверенный код с диска.

## 11. `Dockerfile`

```dockerfile
FROM node:24-bookworm-slim AS base

# Chromium + минимальные системные библиотеки, которые ему нужны
# (шрифты — иначе часть страниц с кастомными шрифтами рендерится с
# «коробками» вместо текста, что мешает человеку читать капчу/форму
# входа). dumb-init — PID 1 с корректной пробросом сигналов: без него
# SIGTERM от Dokploy при остановке/передеплое контейнера не долетает
# до дочерних процессов Chromium штатно, и graceful shutdown (§13) не
# успевает отработать.
RUN apt-get update && apt-get install -y --no-install-recommends \
    chromium \
    fonts-liberation \
    ca-certificates \
    dumb-init \
  && rm -rf /var/lib/apt/lists/*

# Путь подтверждается на этапе первой сборки образа (`docker run --rm
# <образ> which chromium`) — если у конкретной версии Debian-пакета он
# отличается, меняется ТОЛЬКО эта строка: весь остальной код реле не
# завязан на конкретный путь, только на переменную окружения
# (см. §6 — тот же принцип, что уже применён в backend'е).
ENV PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium

WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY tsconfig.json ./
COPY src ./src
RUN npm install --include=dev && npm run build && npm prune --omit=dev

EXPOSE 8088
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]
```

(Двухфазная установка зависимостей — сначала `--omit=dev` для рантайма,
потом временно докатить dev-зависимости для сборки TS и `prune` их
обратно — держит финальный слой образа меньше, не тащит `typescript`/
`jest` в прод-контейнер; не критично для маленького сервиса, но дёшево
сделать правильно сразу.)

```yaml
      - PORT=8088
      - LIVE_LOGIN_RELAY_SECRET=${LIVE_LOGIN_RELAY_SECRET}
      - MAX_CONCURRENT_SESSIONS=${MAX_CONCURRENT_SESSIONS:-10}
      - SESSION_WALL_TIMEOUT_MS=${SESSION_WALL_TIMEOUT_MS:-180000}
      - SESSION_IDLE_TIMEOUT_MS=${SESSION_IDLE_TIMEOUT_MS:-60000}
      - LOG_LEVEL=${LOG_LEVEL:-info}
    ports:
      - '8088:8088'
    healthcheck:
      test: ['CMD', 'node', '-e', "fetch('http://localhost:8088/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 15s
      timeout: 5s
      retries: 3
    restart: unless-stopped
    # Chromium под --no-sandbox (§10.4) обходится дефолтным shm — но при
    # заметном числе одновременных сессий стоит проверить на практике,
    # не упирается ли рендеринг в маленький /dev/shm контейнера
    # (типовая проблема headless Chromium в Docker); при необходимости —
    # `shm_size: '512mb'` здесь же, не блокер первой поставки.
```

`PUPPETEER_EXECUTABLE_PATH` НЕ передаётся через `environment:` здесь —
он уже зашит `ENV`-строкой в сам образ (§11), а не варьируется между
средами (в отличие от `LIVE_LOGIN_RELAY_SECRET`, который обязан быть
СВОИМ секретом, не хардкоженным в Dockerfile).

Практический шаг деплоя (детализирует §7.4.9 основного ТЗ, не
переопределяет): импорт `live-login-relay/docker-compose.yml` через UI
Dokploy как есть → задать `LIVE_LOGIN_RELAY_SECRET` (тот же, что и в
Vercel-переменных backend'а) в переменных окружения сервиса на стороне
Dokploy → Dokploy сам подхватывает `healthcheck` для индикации
состояния сервиса в своём UI.

## 13. Грейсфул-шатдаун и наблюдаемость

`main.ts` подписывается на `SIGTERM` (Dokploy/Docker шлёт его при
остановке или передеплое) — при получении: (1) перестаёт принимать
новые `POST /sessions` (`503` с явным «сервис перезапускается»), (2)
для каждой активной сессии — шлёт по WS `{type:"closed",
reason:"server-shutdown"}`, закрывает браузер, (3) ждёт завершения всех
закрытий не дольше `10с`, затем выходит. Без этого шага передеплой
реле (обычное дело — Dokploy обновляет образ) обрывал бы живые
live-сессии пользователей без единого объяснения на экране, вместо
понятного «сессия закрыта, начните заново».

Логирование — структурированный JSON-лог в stdout (`{ts, level,
sessionId?, msg}`), без внешней системы сбора: Dokploy показывает логи
контейнера в своём UI напрямую, заводить отдельный стек агрегации логов
ради одного маленького сервиса — явный оверинжиниринг для объёма этой
фичи. Полезные точки логирования: создание/закрытие сессии (с
причиной), достижение `MAX_CONCURRENT_SESSIONS`, ошибки запуска
браузера — то, что реально понадобится при разборе инцидента «у
пользователя live-вход не сработал».

## 14. Тестовый план

Без реального Chromium (быстрые unit-тесты, `jest`, по образцу
`cron-secret.spec.ts`/`fixture-token.spec.ts` этого же монорепо):
- `auth.spec.ts` — `assertRelaySecret` отклоняет пустой/неверный/
  отсутствующий секрет, принимает верный, сравнение не короткоживущее
  по длине (та же таблица случаев, что уже покрывает
  `cron-secret.spec.ts`).
- `stream-token.spec.ts` — генерация даёт уникальные значения нужной
  энтропии, проверка хэша принимает верный токен и отклоняет любой
  другой (включая токен ДРУГОЙ существующей сессии — важный кейс:
  токен сессии A не должен подходить к сессии B).
- `session-manager.spec.ts` — на `jest.useFakeTimers()`: создание до
  потолка `MAX_CONCURRENT_SESSIONS` и `503` сверх него; переход в
  `closed` по истечении `SESSION_WALL_TIMEOUT_MS`/
  `SESSION_IDLE_TIMEOUT_MS` (мок «нет активности»/«активность
  обновлялась»); `GET /result` внутри и за пределами `RESULT_CACHE_MS`
  после закрытия. Браузер/CDP здесь мокается целиком (интерфейс
  `launchRelayBrowser()` — единственная точка, которую нужно
  подменить) — тестируется именно оркестрация состояний, не CDP.

С реальным Chromium (ручное/интеграционное тестирование на этапе
реализации, честно НЕ автоматизируется этим документом — тот же
принцип, что уже применён в §7.4.3 основного ТЗ к тестированию на
реальных телефонах): полный цикл `POST /sessions` → WS-подключение →
проводка кликов по настоящей форме логина с капчей → `GET .../result` →
проверка, что куки реально валидны при повторном заходе тем же cookie
jar. Это НЕ покрывается CI по той же причине, по которой сам живой
вход не автоматизируется в принципе (§7.4.0 основного ТЗ) — требует
человека и реального стороннего сайта.
