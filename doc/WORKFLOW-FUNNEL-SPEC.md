## 1. Контекст

В системе действительно ровно три места, где сущность (сессия/строка
партии/вариант A-B) последовательно проходит через именованные статусы
от создания до готового ролика — это и есть три «воркфлоу» из запроса.
Сегодня админка показывает по ним только ТЕКУЩИЙ срез («сколько сейчас
сессий в каждом статусе», вкладка «Телеметрия»), а не движение во
времени («сколько дошло до статуса X за последний час/сутки/неделю»).
Это разные вещи — первое видно сразу в БД, второе требует истории
переходов, которой сегодня нигде не пишется (см. §2.3).

## 2. Что уже есть (перепроверено чтением кода)

### 2.1. Три реальных воркфлоу и их модели статусов

**Воркфлоу 1 — сессия (основной мастер генерации ролика).**
`backend/src/common/types/session.types.ts:22-32`, `enum SessionStatus`:

```
CREATED → VIDEO_UPLOADED → ANALYZING → ANALYSIS_COMPLETE →
PRODUCT_INFO_ADDED → PROMPT_GENERATED → GENERATING_VIDEO → VIDEO_COMPLETE
```

плюс терминальная ветка `ERROR`, достижимая с нескольких промежуточных
шагов (например, `modules/analysis/analysis.service.ts:280`,
`modules/generation/generation.service.ts:786`). Хранится в
`Session.status` (`backend/prisma/schema.prisma:47-101`) — обычная
строковая колонка, не Prisma-enum (сознательно, см. код на месте: тип
`SessionStatus` живёт в TypeScript, а не в схеме БД).

**Воркфлоу 2 — пакетная генерация по каталогу.**
`schema.prisma:1492-1497`, `enum CatalogBatchItemStatus`: `PENDING →
GENERATING → DONE`, с `FAILED` как терминальной веткой из `GENERATING`
(ретраится с бэкоффом, пока не станет окончательным — §44.3 SPEC).
Модель `CatalogBatchItem` (`schema.prisma:1512-1548`) — одна строка на
товар партии, привязана к `CatalogBatchRun` (`schema.prisma:1461-1490`,
`userId` обязателен, NOT NULL — партии доступны только залогиненным
Premium-пользователям).

**Воркфлоу 3 — A/B-варианты.** `schema.prisma:1590-1595`, `enum
AbTestVariantStatus` — те же четыре значения, тот же смысл. Модель
`AbTestVariant` (`schema.prisma:1602-1638`), привязана к `AbTestRun`
(`schema.prisma:1561-1589`, `userId` тоже обязателен).

Замечание из доккомментария модели (`schema.prisma:1506-1511`,
дословно): статус `CatalogBatchItem`/`AbTestVariant` НЕ различает
«сессия создана» / «промпт одобрен» / «Veo-job стартовал» — это
внутренние подшаги одного тика воркера, `GENERATING` покрывает их все.
Настоящий мелкий прогресс рендера живёт в дочерней `Session`
(`session.data.generatedVideo.status`) и экран прогресса партии/A-B
читает его оттуда напрямую (`catalog-batch.service.ts:295-320`,
симметрично `ab-test.service.ts:245-265`). **Значит воронки 2 и 3 —
по конструкции трёхступенчатые (`PENDING → GENERATING → DONE`, плюс
ветка `FAILED`), а не такие же подробные, как воронка 1** — это не
пробел этого ТЗ, а сознательная граница детализации, принятая ещё на
этапах 65/66.

### 2.2. Сегодняшняя «Телеметрия» — снимок, а не воронка

`AdminPanelService.getTelemetry()` (`admin-panel.service.ts:176-218`):
`this.prisma.session.groupBy({by: ['status'], _count: {_all: true}})` —
считает, сколько строк СЕЙЧАС стоит в каждом статусе, плюс
`createdLast24h`/`createdLast7d` (фиксированные скользящие окна, не
селектор). Это моментальный срез базы, а не «сколько дошло до стадии X
за период»: сессия, дошедшая до `VIDEO_COMPLETE` вчера, в этом запросе
просто станет строкой `VIDEO_COMPLETE`, неотличимой от сессии,
завершившейся минуту назад — прошлое движение не восстановить.
`CatalogBatchItem`/`AbTestVariant` в «Телеметрии» вообще не участвуют.

### 2.3. Ключевая проблема: ни одна из трёх моделей не хранит историю переходов

`Session` (`schema.prisma:47-101`), `CatalogBatchItem`
(`schema.prisma:1512-1548`), `AbTestVariant` (`schema.prisma:1602-1638`)
— у каждой ровно один столбец `status`, перезаписываемый на каждом
переходе, и `createdAt`/`updatedAt`/`lastActivityAt` — метки САМОЙ
СУЩНОСТИ, не конкретного перехода. Спросить «сколько сессий стали
`ANALYSIS_COMPLETE` за последний час» сегодняшняя схема физически не
может — после перезаписи `status` прежнее значение и момент перехода в
него нигде не остаются. Это тот же класс ограничения, что уже
встречался в проекте (`CronRunLog` пишет ПОЛНУЮ историю прогонов крона
именно потому, что «текущий статус» не годится для истории) — здесь
нужна та же идея: не заменять `status`, а ДОБАВИТЬ отдельный
append-only журнал переходов.

## 3. Архитектурное решение — новая таблица событий, добавочно к существующим статусам

### 3.1. Модель `WorkflowStageEvent`

```prisma
enum WorkflowKind {
  SESSION
  CATALOG_BATCH_ITEM
  AB_TEST_VARIANT
}

/// Событие «сущность воркфлоу перешла в статус X» — append-only,
/// никогда не обновляется и не удаляется. Существующие статусные
/// колонки (Session.status, CatalogBatchItem.status,
/// AbTestVariant.status) остаются источником ТЕКУЩЕГО состояния, как
/// сегодня; эта таблица — единственный источник ИСТОРИИ переходов
/// (doc/WORKFLOW-FUNNEL-SPEC.md).
model WorkflowStageEvent {
  id         String       @id @default(cuid())
  workflow   WorkflowKind
  entityId   String
  /// Статус ДО этого перехода. NULL только для самого первого события
  /// сущности (создание — переход «из ниоткуда»). Решение §7.2: нужен
  /// для разбивки терминальных ошибок по тому, с какой стадии сорвалась
  /// сущность, но пишется на КАЖДОМ событии, не только на ошибках — это
  /// не отдельный код для особого случая, а один и тот же путь записи.
  fromStage  String?
  /// Статус, В КОТОРЫЙ перешли — по нему считается основная воронка (§3.3).
  stage      String
  occurredAt DateTime     @default(now())

  /// Обслуживает основной запрос воронки: сколько РАЗНЫХ entityId
  /// получили событие (workflow, stage) внутри окна [from, to).
  @@index([workflow, stage, occurredAt])
  /// Обслуживает разбивку ошибок по источнику (§3.2/§5): тот же фильтр
  /// по workflow+stage+occurredAt, но группировка по fromStage вместо
  /// подсчёта entityId — отдельный индекс, потому что ведущая колонка
  /// после stage здесь другая (fromStage, не occurredAt конкретно для
  /// COUNT).
  @@index([workflow, stage, fromStage])
  @@map("workflow_stage_events")
}
```

`stage`/`fromStage: String`, не Prisma-enum — по той же причине, что и
`Session.status` уже сегодня `String`: у трёх воркфлоу три разных
словаря стадий (9 значений у сессии, 4 у каждой из двух остальных),
единый enum на объединение был бы неудобнее строки без реальной пользы
(значения и так проверяются на уровне TypeScript, откуда их пишут).

Осознанно **без** колонки `userId` на самом событии — денормализация
"на будущее" усложнила бы запись (три разных источника userId у трёх
воркфлоу, см. §4) без выигрыша: он и так дёшево достаётся JOIN'ом к
родителю в момент чтения (запрос воронки не бьёт по этой таблице
часто — им пользуется только вкладка «Воронка» в админке).

### 3.2. Точки записи — одна для сессии, симметричные для партии/A-B

Каждое событие теперь пишет ДВЕ вещи: `fromStage` (откуда) и `stage`
(куда) — не только ради основной воронки (§3.3, там нужен только
`stage`), но и ради разбивки ошибок по источнику (§7.2). Один и тот же
код записи обслуживает оба назначения — нет отдельной ветки «на всякий
случай, если это ошибка».

**Сессия — создание.** `SessionService.createSession()`
(`common/session.service.ts:172-...`) пишет самую первую строку сразу
со `status: SessionStatus.CREATED` через `prisma.session.create()` —
ОТДЕЛЬНЫЙ путь записи, не `updateSession()` (см. ниже). После
`create()` добавляется `logWorkflowStage(prisma, 'SESSION', row.id,
null, 'created')` — `fromStage: null`, потому что это самый первый
переход сущности, «ниоткуда».

**Сессия — все последующие переходы.** Все 13 мест в коде, которые
сегодня меняют `Session.status` дальше по жизни сессии
(`modules/video/video.service.ts:110,139`,
`modules/analysis/analysis.service.ts:240,280,386,541`,
`modules/product/product.service.ts:53`,
`modules/prompt/prompt.service.ts:379,689` (строка 379 —
`generatePrompt()`, строка 689 — `seedPrompt()`: заполняет промпт с
нуля в свежесозданной дочерней сессии для партий/A-B/экспорта, где
`GENERATING_VIDEO`/`ERROR` физически невозможны — см. уточнение в
§3.3),
`modules/generation/generation.service.ts:543,727,786`,
`modules/library/library.service.ts:527` — тринадцатое место найдено
при аудите этого документа: применение уже готового разбора из
библиотеки (`LibraryService.applyToSession()`/`applyEntryToSessionFree()`,
обе вызывают приватный `applyEntryToSession()`) ставит сессию сразу в
`ANALYSIS_COMPLETE`, минуя `analysis.service.ts` целиком, и в
первой версии этого ТЗ было пропущено), делают это ОДИНАКОВО —
вызовом `SessionService.updateSession(id, {status: ...,
...остальнойПатч})`. Метод `updateSessionStatus`
(`common/session.service.ts:414-419`) существует как тонкая обёртка,
но реально в проде не используется — переходы идут через общий
`updateSession`. Это значит: **единственная точка правки — сам
`updateSession`** (`common/session.service.ts:225-271`), а не 13
вызывающих мест — точный список нужен только для полноты этого
документа, реализация от него не зависит (правится один метод, а не
каждое вызывающее место).

Сегодня `updateSession` — один атомарный `UPDATE ... RETURNING *`
(строки 260-268) без предварительного чтения старого статуса. Чтобы
писать событие только при РЕАЛЬНОЙ смене статуса (не на каждый вызов
`updateSession`, большинство которых статус не трогают вовсе) и заодно
знать, ОТКУДА произошёл переход (§7.2), запрос меняется на CTE,
возвращающую и новую, и старую строку одним round-trip'ом:

```sql
WITH old AS (SELECT status FROM sessions WHERE id = ${sessionId})
UPDATE "sessions"
SET "data" = "data" || ${json}::jsonb,
    "generationStatus" = ...,
    "status" = COALESCE(${status}, "status"),
    "lastActivityAt" = NOW()
FROM old
WHERE "sessions"."id" = ${sessionId}
RETURNING "sessions".*, old.status AS "previousStatus"
```

После запроса: `if (status !== null && row.previousStatus !== row.status)
{ await logWorkflowStage(prisma, 'SESSION', sessionId,
row.previousStatus, row.status); }` — `fromStage: row.previousStatus`
покрывает и обычный шаг вперёд (например `'analyzing'` →
`'analysis_complete'`), и уход в `'error'` (тогда `fromStage` — та самая
стадия, с которой сорвалась сессия, ответ на §7.2), и возврат назад
(§3.3 — `prompt.service.ts:689` может проставить `'prompt_generated'`
поверх `'generating_video'`/`'error'`; `fromStage` в этом случае честно
покажет источник возврата). Запись — вне транзакции с самим UPDATE (это
вспомогательная аналитика, не критичная для согласованности бизнес-
данных, тот же уровень строгости, что у CronRunLog).

**Пакетная генерация — создание.** `CatalogBatchService.create()`
(`catalog-batch.service.ts`, `$transaction` с `createMany` строк
`CatalogBatchItem`) — на каждую созданную строку
`logWorkflowStage(prisma, 'CATALOG_BATCH_ITEM', item.id, null,
'PENDING')`, тем же принципом «первое событие, `fromStage: null`», что
у сессии.

**Пакетная генерация — дальнейшие переходы.** При аудите этого раздела
(перечитан код воркера заново, 2026-09-11) обнаружено, что предыдущая
версия неверно описывала источник терминального `FAILED` — исправлено
ниже. Реально пишущих статус мест **пять**, не четыре:

1. **Claim → `GENERATING`** (`catalog-batch-worker.service.ts:408-411`,
   внутри `processOne()`). Строка отобрана заранее по `{status:
   'PENDING'} OR {status: 'FAILED', nextAttemptAt <= now()}`
   (`catalog-batch-worker.service.ts:184-192`), но сам `findMany` не
   выбирает колонку `status` (`select` на строках 193-199 её не
   содержит) — значит `fromStage` здесь НЕ «уже известен вызывающему
   коду» без правки, как утверждала предыдущая версия: `select` нужно
   дополнить `status: true`, чтобы строка донесла до `processOne()`, из
   какой именно ветки `OR` она пришла (`'PENDING'` или `'FAILED'`).
2. **Завершение `DONE`/`FAILED` в `advanceGenerating()`**
   (`catalog-batch-worker.service.ts:293-306`) — единственное место, где
   `fromStage` действительно всегда `'GENERATING'`: сам запрос строкой
   выше (`catalog-batch-worker.service.ts:262`) отбирает только
   `{status: 'GENERATING'}`.
3. **Терминальный/бэкофф `FAILED` в `recordFailure()`**
   (`catalog-batch-worker.service.ts:445-460`) — **исправление:** это
   НЕ всегда `fromStage: 'GENERATING'`, как ошибочно утверждала
   предыдущая версия документа. `recordFailure()` вызывается из
   `catch`-блока `runBatchLocked()` (строка 225), когда `processOne()`
   бросает исключение, — а `processOne()` запускается ровно на тех же
   `PENDING`/`FAILED`-строках из п. 1, ДО того, как строка вообще
   становится `GENERATING` (сам переход в `GENERATING` — последняя
   строка `processOne()`, после неё исключений уже не бывает). Значит
   `fromStage` здесь — `'PENDING'` (первая попытка не удалась ещё до
   старта Veo, например GPT-5 отклонил промпт) или `'FAILED'` (повторная
   попытка после бэкоффа снова не удалась) — та же нехватка колонки
   `status` в `select`, что и в п. 1.
4. **Оппортунистическая синхронизация при чтении статуса**
   (`catalog-batch.service.ts:304-322`) — здесь исходное описание верно:
   `fromStage` действительно всегда `'GENERATING'`, код проверяет
   `status === 'GENERATING'` строкой выше (`catalog-batch.service.ts:304`).
5. **Ручной точечный повтор** (`CatalogBatchService.retry()`,
   `catalog-batch.service.ts:432-441`, добавлен на этапе 74 как часть
   Д-1.3 пятого аудита, уже ПОСЛЕ первой версии этого ТЗ — отсюда и
   пропуск) — оператор нажимает «Повторить» на провалившейся строке, код
   делает `updateMany({status: 'FAILED', ...} → {status: 'PENDING',
   ...})` по фильтру `status: 'FAILED'` строкой выше
   (`catalog-batch.service.ts:392`), значит `fromStage` здесь всегда
   `'FAILED'`. Без события здесь ручной повтор был бы невидим для
   воронки — строка тихо вернулась бы в `PENDING`, и следующий проход
   крона выглядел бы как «просто ещё один товар начал обработку», без
   следа причины.

Во всех пяти местах после соответствующего `catalogBatchItem.update(...)`
добавляется `logWorkflowStage(prisma, 'CATALOG_BATCH_ITEM', item.id,
fromStage, item.status)`. Для пп. 2/4/5 `fromStage` — фиксированная
константа, известная из контекста без дополнительного чтения; для пп.
1/3 нужна одна правка `select` (добавить `status: true`), после чего
`fromStage` берётся из уже загруженной строки, а не из отдельного
запроса, как ошибочно предполагала предыдущая версия этого раздела.

**A/B-варианты.** Создание — отдельно (`ab-test.service.ts`, `create()`,
`fromStage: null`), тем же принципом, что у партии. Дальнейшие
переходы — та же структура ролей, что у партии, но **четыре** места, не
пять (см. асимметрию ниже), с той же поправкой к терминальному `FAILED`
(п. 3 выше): claim → `GENERATING` (`ab-test-worker.service.ts:372-375`,
тот же пробел в `select`, что и у партии), завершение `DONE`/`FAILED` в
`advanceGenerating()` (`ab-test-worker.service.ts:269-282`, `fromStage`
всегда `'GENERATING'`), терминальный/бэкофф `FAILED` в `recordFailure()`
(`ab-test-worker.service.ts:405-414` — **не** всегда `'GENERATING'`, та
же причина, что у партии) и оппортунистическая синхронизация
(`ab-test.service.ts:247-265`, `getStatus()`, `fromStage` всегда
`'GENERATING'`). Предыдущая версия документа здесь же ошибочно указывала
пятое число `ab-test-worker.service.ts:168-170` как ещё одно место
записи статуса — это строки `where`-фильтра выборки `PENDING`/`FAILED`
(та же роль, что `184-192` у партии, см. п. 1 выше), а не запись
статуса; исправлено. **Асимметрия с партией:** у A/B-вариантов НЕТ
метода, аналогичного `CatalogBatchService.retry()` (проверено —
`ab-test.service.ts` не содержит операции ручного повтора одного
варианта) — для A/B-воронки пятое место (п. 5 у партии) в списке точек
записи отсутствует, это не пробел документа, а отражение реальной
асимметрии в самом продукте.

Чтобы не повторять один и тот же шаблон записи много раз, предлагается
общий хелпер `common/workflow-stage-events.ts`:
`logWorkflowStage(prisma, workflow, entityId, fromStage, stage):
Promise<void>` (проглатывает собственные ошибки записи логом, не
бросает — сбой аналитики не должен ронять генерацию ролика).

### 3.3. Определение «стадия + окно»

Число на стадии X за окно W = **количество РАЗНЫХ сущностей, у которых
есть хотя бы одно событие `(workflow, stage=X, occurredAt ∈ [from(W),
now))`.** Не когортный анализ («судьба тех, кто стартовал W назад») —
событийный счётчик («что произошло за W»). Практическое следствие:
сессия, стартовавшая 50 минут назад и завершившаяся 5 минут назад,
войдёт в окно «Час» на КАЖДОЙ стадии, через которую она прошла за этот
час, но НЕ войдёт в него на стадии `CREATED`, если сама сессия была
создана раньше часа назад, а лишь сейчас, скажем, перегенерировала
промпт. Это ожидаемое и стандартное поведение событийной воронки (та же
логика, что у Amplitude/Mixpanel) — часть сущностей на любой момент
времени «ещё в пути» и не обязана попадать в одно и то же окно на всех
стадиях сразу.

Переходы возможны и НАЗАД (например, пользователь запрашивает
перегенерацию промпта после неудачного рендера через
`POST /sessions/:id/prompt` — `generatePrompt()`, `prompt.service.ts:379`,
снова проставляет `PROMPT_GENERATED` поверх `GENERATING_VIDEO`/`ERROR`;
это НЕ `seedPrompt()`, строка 689 того же файла, — тот метод вызывается
только на свежесозданной дочерней сессии партии/A-B/экспорта, у которой
`GENERATING_VIDEO`/`ERROR` физически ещё не могло быть, см. guard
`!promptApproved && !videoStarted` в `processOne()`).
Воронка считает каждый такой повторный вход как отдельное событие —
сущность может увеличить счётчик уже пройденной стадии второй раз,
если реально вернулась туда в течение того же окна. Это не баг подсчёта,
а точное отражение происходящего; в интерфейсе стоит явно не обещать
строгое убывание чисел слева направо (см. §6.3).

### 3.4. Важное ограничение — у воронки нет прошлого

Таблица `WorkflowStageEvent` начинает копиться только с момента, когда
код, пишущий в неё, попадёт на прод и накатится миграция. **Ни одного
события до этого момента восстановить нельзя** — существующие
`Session`/`CatalogBatchItem`/`AbTestVariant` хранят только текущий
статус, без даты перехода в него, поэтому исторический бэкафилл в
принципе невозможен (не «не сделан», а физически неоткуда взять данные).
Первые минуты/часы после деплоя воронка будет пустой или почти пустой —
наполняется только новыми переходами. Это стандартное свойство любой
новой таблицы событий (то же самое верно для `CronRunLog`, введённой на
этапе 69, — прим.: «Внеплановый фикс №8» в
`PRODUCT-PROJECT-IMPLEMENTATION-PLAN.md`, на который ранее ошибочно
ссылался этот документ, на самом деле описывает другую проблему —
непрокатанные на проде миграции, — а не архитектурный компромисс
«у новой истории нет прошлого»; корректной ссылки-прецедента на этот
тезис в документах проекта не нашлось, поэтому он остаётся
самостоятельным утверждением).

## 4. Единица измерения — ролики и уникальные пользователи

На каждой стадии диаграммы — два числа: **роликов** (= число сущностей
воркфлоу, строка §3.3) и **уникальных пользователей** — там, где
понятие пользователя вообще применимо:

- **Сессия.** `Session.userId` — НЕ обязателен (`schema.prisma:70`,
  `userId String?`): подавляющее большинство сессий анонимны (заходят
  не из Telegram, см. `TelegramIdentityMiddleware`). «Уникальных
  пользователей» на этой воронке — количество РАЗНЫХ `userId` СРЕДИ тех
  сущностей, у которых он вообще есть; это ВСЕГДА ≤ числа роликов, часто
  сильно меньше, и это ожидаемо, не ошибка подсчёта.
- **Пакетная генерация/A-B.** `CatalogBatchRun.userId`/
  `AbTestRun.userId` оба обязательны (Premium-функции, доступны только
  залогиненным) — здесь «уникальных пользователей» осмысленнее и почти
  всегда близко к числу роликов (один пользователь редко ведёт много
  партий одновременно).

Технически: `WorkflowStageEvent` не хранит `userId` (§3.1) — запрос
воронки для каждой из трёх воронок делает свой JOIN к владельцу:
`sessions.userId` напрямую для воркфлоу 1;
`catalog_batch_items → catalog_batch_runs.userId` для воркфлоу 2;
`ab_test_variants → ab_test_runs.userId` для воркфлоу 3. Три разных
запроса, не один обобщённый — тот же почерк, что у остальных экранов
`AdminPanelService` (каждый эндпоинт — свой конкретный запрос, без
общей абстракции ради трёх похожих, но не идентичных случаев).

## 5. Backend API

Новый метод `AdminPanelService.getWorkflowFunnel(window)` и маршрут в
существующем `AdminPanelController` (тот же `assertOperator`-гейт, что
у всех остальных семнадцати маршрутов, `admin-panel.controller.ts` —
исправлено при аудите этого документа: было указано пятнадцать,
пересчитано заново — `grep -c` по декораторам `@Get`/`@Post`/`@Patch`/
`@Delete` в файле даёт семнадцать; число не влияет на реализацию — гейт
всё равно один и тот же `assertOperator()` первой строкой):

```
GET /admin/workflow-funnel?window=hour|day|week|month
```

Окна — скользящие от текущего момента (та же семантика, что уже
использует `createdLast24h`/`createdLast7d` в `getTelemetry()`, не
календарные): `hour` = последние 60 минут, `day` = 24 часа, `week` = 7
суток, `month` = 30 суток.

```ts
export interface WorkflowFunnelStage {
  key: string;          // 'created' | 'video_uploaded' | ... | 'PENDING' | 'GENERATING' | 'DONE'
  label: string;        // человекочитаемая подпись для UI
  count: number;        // роликов, см. §3.3
  uniqueUsers: number | null;   // null там, где понятие не применимо (не нужно для этих трёх воркфлоу — везде применимо, но поле нужно на случай будущего воркфлоу без владельца)
}

/// Решение §7.2: терминальная ошибка разбита по стадии, с которой
/// сорвалась сущность (`fromStage` события, §3.1/§3.2) — не общим
/// числом.
export interface WorkflowFunnelFailureBreakdown {
  fromStage: string;      // 'analyzing', 'generating_video', ... | 'PENDING', 'GENERATING', 'FAILED' (см. §3.2, п. 3 — retry после бэкоффа тоже мог провалиться)
  fromLabel: string;      // человекочитаемая подпись той же стадии, что и в WorkflowFunnelStage.label
  count: number;
  uniqueUsers: number;
}

export interface WorkflowFunnelBlock {
  workflow: 'session' | 'catalog_batch' | 'ab_test';
  label: string;               // «Сессия», «Пакетная генерация», «A/B-варианты»
  stages: WorkflowFunnelStage[];    // основной путь, БЕЗ терминальной ошибки
  failures: WorkflowFunnelFailureBreakdown[];   // отсортировано по count desc, см. §6.3
  totalFailed: number;                          // сумма count по failures — для заголовка боковой секции
}

export interface WorkflowFunnelResult {
  window: 'hour' | 'day' | 'week' | 'month';
  from: string;   // ISO, для отображения диапазона в UI
  to: string;
  blocks: WorkflowFunnelBlock[];   // ровно 3, в порядке §2.1
}
```

## 6. UI

### 6.1. Расположение

Новая вкладка **«Воронка»** в группе «Система» шапки админки (рядом с
«Кроны»/«Телеметрия»/«Настройки» — та же группа, что уже свёрнута в
выпадающее меню, добавление четвёртого пункта ничего не усложняет).
Не расширение существующей `/telemetry` — разный визуальный жанр
(диаграмма этапов, а не таблица текущих статусов и не сетка `stat-tile`).

### 6.2. Селектор периода

Один `<select>` наверху страницы (тот же паттерн, что фильтр статуса на
«Сессиях», `sessions/page.tsx:53-67`, и переключатель на «Настройках»,
`settings/page.tsx`), общий для всех трёх блоков сразу — не отдельный
селектор на каждый воркфлоу:

```
Последний час / Последние сутки / Последняя неделя / Последний месяц
```

### 6.3. Блок-схема каждого воркфлоу

Три карточки (`className="card"`, как везде в админке), каждая:
заголовок воркфлоу, затем горизонтальный ряд «коробок»-стадий,
соединённых стрелкой (`→`), в каждой коробке — подпись стадии, крупное
число роликов, под ним мелкой приглушённой строкой — уникальных
пользователей. Терминальная ошибка (`ERROR`/`FAILED`) — боковая секция
сигнального цвета (`var(--signal-critical)`, как везде в проекте), не в
общем горизонтальном ряду, а под ним/сбоку: заголовок с общим числом
(`totalFailed`) и под ним короткий список `failures` — «с <fromLabel>:
N роликов (M пользователей)» на каждую строку, отсортированный по
убыванию (решение §7.2 — разбивка по источнику, не общий счётчик; у
партии/A-B список — до трёх строк: `GENERATING` (рендер Veo реально
провалился), `PENDING` (первая попытка сорвалась раньше старта Veo —
например, GPT-5 отклонил промпт) и `FAILED` (повторная попытка после
бэкоффа снова не удалась) — исправлено при аудите этого документа,
§3.2; у сессии список длиннее, до семи строк по числу промежуточных
стадий, с которых достижим `ERROR`).

Ряд стадий у сессии (8 значений) на телефоне не влезет в ширину экрана
— оборачивается в `overflow-x: auto`, тот же приём, что уже применён к
широким таблицам (`.table-scroll` в `globals.css`). Партия/A-B (3
стадии + ошибка) в этом не нуждаются.

Никакой новой библиотеки диаграмм — простые flex-блоки на CSS, тот же
уровень сложности, что у `.stat-grid`/`.stat-tile` на «Телеметрии»/
«Расходах»: проект последовательно избегает визуальных зависимостей
там, где хватает вёрстки.

### 6.4. Что осознанно не входит в эту версию

Проценты конверсии между соседними стадиями (например «68% дошли до
генерации») — решение §7.4: не входит в этот этап. Каждое число на
диаграмме — независимый событийный счётчик за окно (§3.3), а не
когорта, поэтому «процент от предыдущей стадии» был бы статистически
некорректен (числитель и знаменатель — не одно и то же множество
сущностей). Честная конверсия — отдельная, более дорогая задача
(когортный расчёт «сколько из тех, кто стартовал в интервале, дошли до
конца», требует привязки события не к моменту перехода, а к моменту
старта конкретной сущности) — остаётся будущим расширением, не частью
этого ТЗ.

## 7. Решения владельца продукта

Ниже — пять пунктов, которые в предыдущей версии этого документа были
открытыми вопросами; все закрыты явным ответом владельца продукта
(«Закрой 5 вопросов, таблицу заводить»). Формулировки §3-§6 выше уже
приведены в соответствие с этими решениями — здесь фиксируется САМО
решение и его прямое следствие для документа.

7.1. **Заводить новую таблицу событий — решено: да.** Без
`WorkflowStageEvent` пришлось бы приближать момент перехода через
`createdAt`/`updatedAt` сущности — грубо и неотличимо по стадиям (см.
§2.3), то есть не решало бы исходную задачу «поэтапно». Следствие:
модель `WorkflowStageEvent` (§3.1) и все точки записи (§3.2) — часть
этого ТЗ в обязательном порядке, не альтернатива.

7.2. **Терминальная ошибка — с разбивкой по стадии, с которой
сорвалась сущность.** Решено в пользу разбивки (точнее и полезнее для
диагностики, чем один общий счётчик), а не в пользу более простого
варианта. Следствие: модель получает колонку `fromStage` (§3.1),
записывается на КАЖДОМ событии, не только на ошибках (§3.2 — один код
записи, не два); API отдаёт `failures:
WorkflowFunnelFailureBreakdown[]` вместо одного числа (§5); UI — список
причин по убыванию, а не одна коробка (§6.3).

7.3. **Метрика уникальных пользователей — показывать наравне с числом
роликов, на всех трёх воронках.** Решено в пользу обоих чисел (§4) —
формулировка запроса («пользователей/роликов» через слэш) допускала и
вариант «только одно из двух», но два числа информативнее при
сопоставимой цене реализации (JOIN к владельцу по первичному ключу).
Изменений в разделах выше не требуется — §4/§5 уже описывают эту
версию.

7.4. **Проценты конверсии между стадиями — не входят в этот этап.**
Решено отложить: это отдельная, более дорогая задача (когортный
расчёт, а не событийный счётчик — см. §6.4), которая требует другой
модели данных (привязки события к моменту СТАРТА сущности, а не только
момента перехода). Возвращаться к этому вопросу — только отдельным
следующим ТЗ, если станет нужно.

7.5. **Место в шапке — вкладка «Воронка» в группе «Система», не
отдельная ссылка верхнего уровня.** Решено оставить внутри выпадающего
меню (§6.1) — это периодический аналитический экран, а не операционный
инструмент, которым пользуются ежеминутно (как «Сессии»); при
необходимости вынести наверх позже — это правка одной строки в
`AdminNav.tsx` (§8, п. 10), не архитектурное решение.

## 9. Тесты (ориентировочно, уточняется в Plan Mode перед реализацией)

- `common/session.service.spec.ts` — `createSession`: пишет событие
  `fromStage: null, stage: 'created'`. `updateSession`: событие пишется
  только при реальной смене статуса, не пишется при патче без `status`
  и при повторной записи ТОГО ЖЕ статуса; `fromStage` в событии
  корректно равен `previousStatus`, включая случай ухода в `'error'` и
  случай возврата назад по пайплайну (§3.3); отдельный тест на вызов из
  `LibraryService.applyToSession()`/`applyEntryToSessionFree()` не
  нужен — раз событие пишется
  внутри `updateSession()`, а не в вызывающем коде, этот путь уже
  покрыт теми же тестами (§3.2, п. про `library.service.ts:527`).
- `catalog-batch-worker.service.spec.ts`/`ab-test-worker.service.spec.ts` —
  события пишутся на каждом из переходов (создание с `fromStage:
  null`/claim/DONE/FAILED-от-рендера/оппортунистическая синхронизация,
  плюс у партии — ручной `retry()`) с верным `fromStage` на каждом;

  равен `'PENDING'`, когда строка провалилась на первой попытке (до
