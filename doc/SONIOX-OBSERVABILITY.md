# Soniox: глобальная статистика и голосовая приёмка

## Доступ и охват

Операторская админка: `/soniox`. API генератора: `GET /api/admin/soniox`, защищён операторской сессией. Второй источник — `GET /internal/admin/assist/soniox`, защищён существующим внутренним секретом и идентификатором оператора. Клиентская роль не получает глобальные данные.

Два источника объединяются без сокрытия частичного отказа. Периоды — скользящие 24 часа и 7 дней; роли — посетитель/клиент, оператор платформы, администратор клиента, cron, system, QA. Контекст берётся из защищённого маршрута и разрешённых сервером сущностей. Анонимные посетители не считаются уникальными пользователями. Для записи без request-контекста применяется фоновая роль; разметку фоновых интеграций следует проверять при добавлении новых клиентов Soniox.

Журнал фиксирует начало, завершение, статус, безопасную категорию причины, источник, известные идентификаторы, язык, confidence, слова/секунды/символы и задержку. Аудио, текст и сырой ответ ошибки не сохраняются. При отказе журнала провайдерный вызов продолжается, предупреждение уходит в технический лог.

## Что показывает экран

Количество попыток, долю ошибок, распознанные слова и минуты, символы синтеза, задержки avg/p95, confidence и число результатов ниже 0,6. Почасовая динамика включает часы без событий. Группы разделены по продукту, роли, источнику, операции и статусу. Фильтры применяются к группам и последним событиям; текущая активность и почасовая динамика подписаны как глобальные. Последние события ограничены 100 на источник, активные — 100 на источник.

«В работе» — незавершённые записи моложе 5 минут. Более старые — «Нет завершения», это не доказательство таймаута провайдера. Обновление раз в 15 секунд только при видимой вкладке. Наличие ключа не является проверкой доступности Soniox. Успешный STT означает наличие текста, а не успешное исполнение команды.

Финансовые данные за неделю читаются отдельно из существующих `ai_usage`/`sites.site_ai_usage`: суммы и непроценённые записи. Это другой набор фактов, он не складывается с оперативными попытками и не фильтруется ролями. Ошибки до установки журнала не восстанавливаются; первая запись явно показана. Удаление старше 30 дней происходит порциями максимум 5000 при действующих retention/sweep вызовах, не является гарантией мгновенного удаления всего накопленного объёма.

## Выкладка

1. Применить миграцию `20261010200000_soniox_observability` отдельно в `backend` (public) и `sites-backend` (sites) штатным процессом deploy. У sites использовать `SITES_DIRECT_URL` с `?schema=sites`; таблицу не выдавать роли публичного виджета.
2. Выложить sites-backend, backend, затем admin; для голосовых исправлений также frontend. Существующее соединение admin → backend → sites используется без новых публичных credentials.
3. Проверить операторский доступ и отказ клиентскому; выполнить короткие STT/TTS из TMA, виджета и клиентской админки; проверить источник, роль и объёмы. Проверить cleanup cron и отсутствие текста/аудио в журнале.
4. Проверить частичный отказ второго источника, пустую историю и текущие события. Полная неделя детальной истории появится спустя неделю сбора.

Миграции проверены локально на PostgreSQL WASM (PGlite): создание таблиц, реальные SQL track/report/prune, day/week, p95, активность, interrupted, независимость финансового источника при отсутствии журнала. Обе миграции и dashboard выложены 10.10.2026; production STT/TTS проверены на собственном sandbox. Детальная история начинается с установки журнала.

## Автоматическая голосовая приёмка

`backend`: `npm run eval:voice-control` делает dry run. Для настоящего провайдерного запуска: `npm run eval:voice-control -- --apply --max-usd=1 --out=<папка>`. Требуются действующие Soniox/Gemini ключи; защищённый placeholder `[SENSITIVE]` отвергается. Набор включает ru/uk команды, clean/noisy варианты и тишину; бюджет не выше 2 USD. Клиентские сессии не изменяются. При наличии DATABASE_URL QA-события пишутся в журнал.

Отдельно `frontend`: `npm run test:voice-runtime` проверяет реальный hook с моделируемым устройством. Локальный TTS/VAD тест не доказывает правильность Soniox: clean ru/uk и тишина прошли, после исправления локальный Silero VAD проходит 64 синтетических сценария, включая постоянный шум и короткие команды. WebSocket streaming и реальное поведение микрофона в Telegram остаются отдельной приёмкой.


## Дополнение аудита 11.10.2026

TMA подтверждает карточку только по целой фразе закрытого списка, даже если модель вернула confirm/consent с уверенностью 1. Неизвестные и отрицательные транскрипции не превращаются в согласие. Provider error body и произвольный exception message Soniox не возвращаются в результат STT/TTS генератора и не идут в его логи; остаются безопасные причины/HTTP-коды. Отсутствие речи отдельно от сбоя, таймаут TTS отдельно от HTTP-отказа, язык синтеза сохраняется в журнале. Защищённые маршруты кабинета assist относятся к администраторам клиента; публичный виджет — к клиентам/посетителям.

Семантический synthetic eval: 17 команд × clean/noisy = 34 + тишина, включая отдельное uk «Ні». Само наличие кейса не означает успешный живой прогон.

Ежедневный sandbox QA дополнен двумя настоящими roundtrip ru/uk: ответ ИИ → TTS → STT → chat с voiceTicket, порог WER 20%, максимум 1000 символов на синтез, один запуск без платных retries. Проверка включена только вне PR, использует публичный ключ собственного сайта и его бюджет; Soniox/Gemini secrets в CI не нужны. API trace отключён, артефакт содержит только метрики. Кэш TTS допускается: это доступность цепочки, а не измерение нового синтеза. Не заменяет полный 30-фразовый WER eval с порогом 15%, короткие команды, семантику действий и реальные устройства.

Подсказки Soniox не запрещают другие языки; strictLanguage — отдельное ограничение, в свободной многоязычной диктовке не включается глобально. [Документация подсказок](https://soniox.com/docs/stt/concepts/language-hints), [ограничений](https://soniox.com/docs/stt/concepts/language-restrictions).

Измерение длительности MP3 сайтов использует общий чистый parser (sync-sites-shared). Если формат не распознан, parser возвращает null; это не утверждение нулевой длины. Ошибка каталога теперь сохраняет безопасную причину в телеметрии, даже когда публичный метод по совместимости возвращает пустой массив. Стоимость в dashboard отображается до шести десятичных знаков.

Полный synthetic public STT прогон uk 11.10.2026: 30/30, 165 слов, 8 правок, WER 4,85% при пороге 15%. macOS Lesya, один синтетический голос; не приёмка коротких команд/устройств. Rate limit сработал на первом быстром прогоне, оставшиеся записи выполнены с паузами; 429 не является ошибкой текста Soniox.

### Защитный бюджет при неопределённом результате TTS

После таймаута, сетевой ошибки, пустого ответа провайдера или HTTP 5xx оценка синтеза сохраняется в суточном защитном лимите сайта и платформы. Это консервативная оценка риска, а не подтверждённое списание Soniox: финансовый журнал успешного использования не получает выдуманную запись. Локальные отказы до вызова и явные HTTP-отказы 400/401/402/403/404/413/415/422/429 освобождают резерв. Правило одинаково для виджета и прослушивания образца в кабинете. При ошибке записи успешного использования резерв также не превращается в нулевой расход.

### Плотность платных ежедневных проверок

Production-проверка после PR #12 дважды дошла до успешных TTS/STT и упала на финальном AI chat (502 UPSTREAM, серверный журнал: ApiError модели). Изолированный украинский сценарий затем прошёл. Это признак зависимости от нагрузки/времени запуска, но конкретный HTTP-код провайдера журнал не сохранил, поэтому причина 429 не считается доказанной.

Для живого ежедневного QA используется один воркер и 65 секунд между голосовыми сценариями; автоматические платные retries остаются выключенными. Неуспешный REST вызов сохраняет только этап, HTTP-статус, безопасный код и requestId — без ответа провайдера, текста, токенов или аудио. Метрики различают язык UI и реально распознанный язык; политика языка сайта определяет текст ответа. Эти сценарии не доказывают качество всех языков или выполнение голосовых команд.


### Полнота семантической приёмки

Стенд требует точный набор изменяемых полей, а не наличие одного правильного поля среди лишних. Для смешанного «Отправитель Тарас, одержувач Марина» обязательны оба поля. В summary.json записываются expectedChecks, completedChecks и complete; остановленный прогон не является завершённой приёмкой. Необработанные ошибки записываются как upstream_failed без текста исключения.

На 11.10.2026 автоматическая проверка парсера/стенда: 274 теста, 9 наборов. Полный платный семантический прогон не выполнен: защищённые Soniox/Gemini ключи недоступны локальному стенду. Работа production API не означает доступность этих ключей для локального eval. Физические устройства и исполнение действий остаются отдельной приёмкой.
