# Soniox: глобальная статистика и голосовая приёмка

## Доступ и охват

Операторская админка: `/soniox`. API генератора: `GET /api/admin/soniox`, защищён операторской сессией. Второй источник — `GET /internal/admin/assist/soniox`, защищён существующим внутренним секретом и идентификатором оператора. Клиентская роль не получает глобальные данные.

Два источника объединяются без сокрытия частичного отказа. Периоды — скользящие 24 часа и 7 дней; роли — посетитель/клиент, оператор платформы, администратор клиента, cron, system, QA. Контекст берётся из защищённого маршрута и разрешённых сервером сущностей. Анонимные посетители не считаются уникальными пользователями. Для записи без request-контекста применяется фоновая роль; разметку фоновых интеграций следует проверять при добавлении новых клиентов Soniox.

Журнал фиксирует начало, завершение, статус, безопасную категорию причины, источник, известные идентификаторы, язык, confidence, слова/секунды/символы и задержку. Аудио, текст и сырой ответ ошибки не сохраняются. При отказе журнала провайдерный вызов продолжается, предупреждение уходит в технический лог.

## Что показывает экран

Количество попыток, долю ошибок, распознанные слова и минуты, символы синтеза, задержки avg/p95, confidence и число результатов ниже 0,6. Почасовая динамика включает часы без событий. Группы разделены по продукту, роли, источнику, операции и статусу. Фильтры применяются к группам и последним событиям; текущая активность и почасовая динамика подписаны как глобальные. Последние события ограничены 100 на источник, активные — 100 на источник.

«В работе» — незавершённые записи моложе 5 минут. Более старые — «Нет завершения», это не доказательство таймаута провайдера. Обновление раз в 15 секунд только при видимой вкладке. Наличие ключа не является проверкой доступности Soniox. Успешный STT означает наличие текста, а не успешное исполнение команды.

Финансовые данные за неделю читаются отдельно из существующих `ai_usage`/`sites.site_ai_usage`: суммы и непроценённые записи. Это другой набор фактов, он не складывается с оперативными попытками и не фильтруется ролями. Ошибки до установки журнала не восстанавливаются; первая запись явно показана. Удаление старше 30 дней происходит порциями максимум 5000 при действующих retention/sweep вызовах, не является гарантией мгновенного удаления всего накопленного объёма.

## Выкладка

1. Применить миграцию `20261010200000_soniox_observability` отдельно в `backend` (public) и `sites-backend` (sites) штатным процессом deploy. У sites использовать `SITES_DIRECT_URL` с `?schema=sites`; таблицу не выдавать роли публичного виджета.
2. Выложить sites-backend, backend, затем admin; для голосовых исправлений также frontend. Существующее соединение admin → backend → sites используется без новых публичных credentials.
3. Проверить операторский доступ и отказ клиентскому; выполнить короткие STT/TTS из TMA, виджета и клиентской админки; проверить источник, роль и объёмы. Проверить cleanup cron и отсутствие текста/аудио в журнале.
4. Проверить частичный отказ второго источника, пустую историю и текущие события. Полная неделя детальной истории появится спустя неделю сбора.

Миграции проверены локально на PostgreSQL WASM (PGlite): создание таблиц, реальные SQL track/report/prune, day/week, p95, активность, interrupted, независимость финансового источника при отсутствии журнала. Production в рамках этой работы не изменялся.

## Автоматическая голосовая приёмка

`backend`: `npm run eval:voice-control` делает dry run. Для настоящего провайдерного запуска: `npm run eval:voice-control -- --apply --max-usd=1 --out=<папка>`. Требуются действующие Soniox/Gemini ключи; защищённый placeholder `[SENSITIVE]` отвергается. Набор включает ru/uk команды, clean/noisy варианты и тишину; бюджет не выше 2 USD. Клиентские сессии не изменяются. При наличии DATABASE_URL QA-события пишутся в журнал.

Отдельно `frontend`: `npm run test:voice-runtime` проверяет реальный hook с моделируемым устройством. Локальный TTS/VAD тест не доказывает правильность Soniox: clean ru/uk и тишина прошли, постоянный pink noise SNR10 выявил проблему завершения фразы. WebSocket streaming и реальное поведение микрофона в Telegram остаются отдельной приёмкой.
