# Аудит: Google Indexing API / `BroadcastEvent` для живого аукциона — пересмотр решения §7.7/§8 (v1.2)

**Дата:** 2026-09-21
**Область:** решение продукта, готовится к внесению в
`docs-tz/TZ-Virtualnaya-Studiya-i-AI-Vedushaya.md` §7.8 (Этап 6)
**Повод:** прямой запрос владельца продукта — вернуть Google Indexing API
в объём ТЗ, «очень мощный фактор раскрутки проекта».

Версия 1.2 этого ТЗ (§7.7, §8) сознательно вынесла индексацию через
Google Indexing API за объём с обоснованием: «там лот — физический товар
с SEO-ценностью широкой аудитории, здесь лот — эксклюзивное видео одного
1-го криэйтора, ценность индексации неочевидна». Это решение теперь
пересматривается по прямому запросу. Ниже — детальный разбор, ЧТО эта
технология реально делает (по текущей документации Google, проверено
web-поиском 2026 года, не по памяти из обучающих данных — политика вокруг
этого API менялась в 2024–2026), почему в НАШЕМ случае она действительно
применима без нарушений (в отличие от типичного злоупотребления этим API
на рынке), и какие реалистичные ожидания стоит от неё иметь — чтобы
решение «внести в ТЗ» не превратилось в «внести и разочароваться».

## 1. Что это на самом деле — две разные вещи под одним названием

**(а) Сам Indexing API** — это узкий технический «толчок»: сообщить
Google «прямо сейчас перекраулить вот этот URL» (`URL_UPDATED`) или «этот
URL исчез» (`URL_DELETED`). Официальная документация Google прямым
текстом: *«It requests crawling, not indexing: Google still decides
whether the page enters the index»* — API не гарантирует ни попадание в
индекс, ни ранжирование, только СНИМАЕТ задержку между публикацией и
моментом, когда Googlebot вообще узнаёт, что страница изменилась.

Официально API поддерживается только для двух типов страниц: с разметкой
`JobPosting` либо `BroadcastEvent` (вложенной в `VideoObject`) —
подтверждено документацией Google Search Central, актуальной на 2026 год.
Для обычных страниц (блог, каталог, лендинги) официальный путь — sitemap +
внутренняя перелинковка, не этот API.

**(б) Разметка `BroadcastEvent` внутри `VideoObject`** — это отдельная,
самостоятельно ценная вещь: JSON-LD-разметка, которая делает страницу
ПРЕТЕНДЕНТОМ на красный значок **«LIVE»** прямо в выдаче Google Search.
Это подтверждённая, актуальная (не устаревшая) функция — официальная
страница Google Search Central по видео-разметке прямо перечисляет:
*«LIVE badge: Get a LIVE badge added to your video by marking your video
with BroadcastEvent. The LIVE badge can be applied to any public video
that is live-streamed for any length of time»* — и приводит примеры:
спортивные трансляции, награждения, стримы влогеров, игровые стримы.

**Как это связано с Indexing API.** Сама же документация Google
формулирует связку явно: *«Make sure you follow the LIVE badge guidelines
and use the Indexing API to make sure Google crawls your page at the
right time»*. То есть Indexing API здесь — не общий SEO-ускоритель «на
всякий случай», а КОНКРЕТНО НЕОБХОДИМЫЙ механизм для ЭТОЙ разметки: если
Google перекраулит страницу эфира через час ПОСЛЕ его окончания, он
увидит «мёртвый» `isLiveBroadcast: true` с уже неактуальным контентом —
хуже, чем вообще не индексировать. Дёргать Indexing API в момент старта и
конца эфира — единственный документированный способ гарантировать, что
пометка «LIVE» показывается ровно тогда, когда трансляция реально идёт.

**Важная оговорка, которую подчёркивает сама документация Google и
независимые источники:** *«Important caveat: adding schema makes your
page eligible for rich results — it doesn't guarantee Google will display
them»*. Значок LIVE — это ВОЗМОЖНОСТЬ, не гарантия. Экспериментов,
подтверждающих conversion-эффект именно для BroadcastEvent (а не рич-
сниппетов вообще), в открытых источниках не нашлось — цифра «рич-
результаты дают 58% CTR против 41%» (Milestone Research, 2023), которую
часто цитируют в этом контексте, — это ОБЩАЯ статистика по рич-
результатам разных типов, не измерение конкретно LIVE-бейджа, и тем более
не для нашей ниши (эксклюзивное UGC-видео одного исполнителя). Приводить
её как обещание конкретного прироста было бы нечестно.

## 2. Почему это НЕ типичное «злоупотребление» API — важное отличие от рынка

Рынок вокруг Indexing API в 2024–2026 годах прошёл путь, о котором стоит
знать прежде чем включать его в ТЗ: многие SEO-инструменты и плагины
(включая популярные WordPress-плагины) годами дёргали этот API для ЛЮБЫХ
страниц — блогов, каталогов, новостей — хотя официально он поддерживает
только `JobPosting`/`BroadcastEvent`. API технически не отклоняет такие
вызовы на лету, поэтому «серая» практика долго казалась рабочей. Но:

- С сентября 2024 года подтверждение заявки на повышение квоты ОДНОВРЕМЕННО
  служит официальным «одобрением» на использование API в проде — сама
  документация Google теперь сопровождается «довольно агрессивным
  предупреждением про спам» на странице Get Started (2024 год также был
  годом крупных чисток спама в Google Jobs).
- Практикующие описывают реальные последствия при обнаружении
  злоупотребления не по назначению: облачный проект теряет возможность
  публиковать уведомления, а иногда **весь домен уходит на ручную
  проверку**, из-за чего новый контент перестаёт индексироваться вообще;
  восстановление может занять месяцы и требует обращения в поддержку
  Google с объяснением исправленных действий.

**Наш случай — противоположность этой практике.** Страница живого
аукциона В ДЕЙСТВИТЕЛЬНОСТИ является прямой трансляцией: реальное видео,
реальные метки начала/конца (`liveStreamStartedAt`/`liveStreamEndedAt`,
уже есть в схеме с Этапа 5), реально ограниченное по времени окно. Это
честно, буквально попадает в официально разрешённый тип `BroadcastEvent`
— не натяжка и не серая зона, а ровно тот сценарий, для которого API и
существует. Риск блокировки домена, который actuально пугает рынок, к
нам не относится, если (и только если) мы не начнём переиспользовать тот
же сервис-аккаунт/проект для «пингования» обычных, не-live страниц —
это стоит явно закрепить как правило эксплуатации (см. §4 ниже).

## 3. Операционная зависимость, которую нельзя пропустить: одобрение квоты

Дефолтная квота Indexing API — 200 `publish`-запросов в сутки и 180
read-only запросов в минуту на проект (актуально, страница документации
Google обновлена 2026-07-16). Но с изменением политики 2024 года это
теперь **тестовая** квота: чтобы API реально работал в проде (а не просто
отвечал `200 OK`, ничего не делая), нужно подать заявку на увеличение
квоты через Google Cloud Console — и именно её одобрение служит
фактическим «включением» API для домена. Источники 2026 года прямо
предупреждают: без прохождения этого шага вызовы могут возвращать успешный
HTTP-ответ, но не приводить к реальному краулингу.

**Практическое следствие для плана внедрения:** подача этой заявки —
самостоятельный пункт плана, который стоит сделать МАКСИМАЛЬНО РАНО и
параллельно с разработкой, а не после неё — срок рассмотрения стороной
Google не контролируется командой и не гарантирован. Технически готовый,
но неодобренный интеграционный код будет молча бесполезен до одобрения.

**Оценка реального объёма нагрузки на квоту.** Жёсткий лимит «не более 5
ACTIVE-лотов одновременно на весь сайт» (§22.1, уже реализован в
`promoteNextQueued()`) означает, что даже при пессимистичной оценке
«3 вызова API на один живой сеанс» (старт, конец, одно промежуточное
обновление при существенном продлении антиснайпером) весь сайт
физически не может сгенерировать больше примерно ~15 вызовов в сутки при
полной загрузке витрины — на два порядка меньше даже тестовой квоты в
200. Риск здесь не в объёме, а исключительно в задержке одобрения со
стороны Google.

## 4. Соответствие требованиям LIVE-бейджа

Google требует не использовать «вульгарные или потенциально оскорбительные
формулировки» в разметке. Название и описание лота — свободный текст,
который вводит исполнитель при подаче заявки. Хорошая новость: этот текст
и так проходит через существующую модерацию оператора (`adminApprove`/
`adminReject` до перехода в `QUEUED`/`ACTIVE`, §22) — отдельного нового
шага модерации заводить не требуется, но стоит явно включить пункт «не
подходит по тону/лексике для показа в Google с LIVE-бейджем» в
чек-лист/памятку оператора при модерации (без изменений кода).

## 5. Калиброванная оценка эффекта — честно, без хайпа

**Что это реально может дать:**
- Соответствующий политике, практически бесплатный (инфраструктура
  Этапа 5 уже полностью готова — см. §6 ниже) способ получить визуально
  выделяющийся значок в выдаче Google именно в момент, когда лот
  действительно в эфире — то есть попадание рекламного сообщения ровно
  в момент максимальной ценности («торги идут прямо сейчас»).
- Устранение задержки краулинга — Google узнаёт о начале/конце эфира
  сразу, а не когда доберётся сам.
- Даёт основание для честной формулировки «наши трансляции показываются
  в Google с живым статусом» в собственных промо-материалах площадки —
  само по себе маркетинговый актив, не только техническая деталь.

**Чего это НЕ даёт само по себе:**
- Не гарантирует показ бейджа (решение всегда за Google) и не гарантирует
  попадание в индекс вообще — это прямо прописано в документации Google.
- Не создаёт спрос — только точнее обслуживает уже существующий органический
  поисковый трафик по теме конкретного лота/исполнителя/площадки. Для
  нишевого товара (эксклюзивное видео ОДНОГО исполнителя) абсолютный объём
  такого спроса по определению мал по сравнению с флагманскими примерами
  самого Google (спорт, награждения, стримы популярных блогеров) —
  ожидание «мощного фактора раскрутки» стоит калибровать соразмерно
  реальному масштабу площадки, а не по аналогии с YouTube-стримами
  миллионников.
- Не заменяет уже существующие (и, вероятно, более весомые для роста
  молодой площадки) каналы: Telegram-рассылку (`MarketingBroadcastService`),
  собственный блог/новости (Этап 57-58), и — по прецеденту самого
  SilverFinance — сценарии для TikTok-промо через Grok (`generatePromoScript`
  в их `liveStream.ts`) как отдельный, более прямой канал привлечения,
  которым в этом ТЗ мы вообще не занимались.

**Итоговая формулировка для ТЗ (вместо «мощный фактор раскрутки»):**
низкозатратный, соответствующий политике Google бонус поверх уже
существующей инфраструктуры Этапа 5 — стоит делать ИМЕННО ПОТОМУ, что
теперь это практически бесплатно (схема готова, хуки готовы), а не
потому, что он сам по себе обеспечит заметный рост. Реальный источник
роста площадки — это по-прежнему прямые каналы привлечения (соцсети,
рассылки, качество самого продукта), а не скорость индексации.

## 6. Почему это дешевле сделать СЕЙЧАС, чем когда решение исключало эту фичу

На момент версии 1.2 этого ТЗ полей `liveStreamActive`/
`liveStreamStartedAt`/`liveStreamEndedAt` на `AuctionListing` ещё не
существовало — их пришлось бы добавлять специально ради этой фичи (как в
своё время сделала SilverFinance, у которой эти поля заведены именно
под задачу индексации). После реализации Этапа 5 эти поля уже есть и уже
поддерживаются жизненным циклом эфира (`LiveAuctionOrchestratorService.
activateLiveStream()`/`collapseInactiveStreams()`, `AuctionService.
closeListing()`/`closeExpiredListings()`) — вся работа сводится к
добавлению best-effort side-effect'ов в уже существующие точки, без
новой миграции и без новой доменной логики. Именно поэтому пересмотр
решения сейчас обходится дешевле, чем обошёлся бы до Этапа 5.

## 7. Источники (проверено веб-поиском, не по памяти)

- Google Search Central, «Video (VideoObject, Clip, BroadcastEvent)
  structured data» — официальное описание LIVE-бейджа и требования к
  разметке.
- Google Search Central, «Requesting Approval and Quota» (Indexing API
  v3) — квота 200 publish/сутки, 180 read-only/мин, обновлено 2026-07-16.
- Независимый разбор изменения политики 2024 года (одобрение через
  заявку на увеличение квоты, тестовая природа дефолтной квоты) и
  практический разбор рисков злоупотребления API не по назначению
  (блокировка домена, сроки восстановления) — рыночные источники 2026
  года, независимые от Google, использованы для калибровки рисков, не
  как официальная позиция Google.
