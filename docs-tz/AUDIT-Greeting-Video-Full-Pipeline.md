## Находка 1 (ВЫСОКАЯ): экспорт tier B (перерендер в другой формат) недостижим для GREETING_VIDEO — ✅ ИСПРАВЛЕНО

`ExportService.startRerender` (`backend/src/modules/export/export.service.ts:295`,
`POST /sessions/:id/export/rerender` — второй платный рендер в
принципиально ином соотношении сторон, не просто кроп) **всегда** вызывает
общий `GenerationService.generateVideo()`, а не `GreetingVideoService`,
который был написан отдельно именно для того, чтобы не тащить
GREETING_VIDEO через инфраструктуру, для этого не спроектированную (см.
находку №3 первого аудита).

`GenerationService`'s `startGeneration` (`generation.service.ts:501-506`)
безусловно требует изображение товара:

```ts
const productImage = activeProductImage(session.productInformation);
if (!productImage?.pathname) {
  throw new BadRequestException(
    'Product image must be uploaded before generating video',
  );
}
```

У GREETING_VIDEO-сессии `productInformation` не существует вообще (сессия
создаётся из `GreetingBrief`, не из `ProductItem`). **Любой вызов
`POST /sessions/:id/export/rerender` на GREETING_VIDEO-сессии гарантированно
падает 400** с сообщением про товарное фото — которое не имеет смысла и
вводит пользователя в заблуждение (у ролика-поздравления никогда не было
и не будет «товарного фото»).

Экспорт tier A (`POST /sessions/:id/export` — дешёвый кроп уже
отрендеренного файла в другое соотношение той же «семьи», ffmpeg, без
повторной генерации) этой проблемы не имеет и работает корректно — баг
касается только смены соотношения сторон, требующей нового рендера
(например, 9:16 → 16:9 для короткого ролика).

**Что нужно решить:** `ExportService.startRerender` должен для
GREETING_VIDEO-сессий (определяется по `session.greetingBriefSnapshot` или
`Project.type`) вызывать `GreetingVideoService`-эквивалент перерендера, а
не `GenerationService.generateVideo()`. Сегодня такого метода в
`GreetingVideoService` нет — его нужно спроектировать отдельно (он должен
уметь принять целевой aspect ratio, не 9:16 по умолчанию), либо, как
временная мера меньшего риска, явно отключить tier B для GREETING_VIDEO на
уровне контроллера/сервиса с понятным сообщением («перерендер в другое
соотношение сторон для роликов-поздравлений пока недоступен»), пока не
будет принято архитектурное решение. Молчаливо оставлять как есть —
значит держать кнопку в интерфейсе (если/когда `ExportPanel` предложит
tier B для 9:16-ролика), которая гарантированно не работает.

**Что сделано:** выбран второй, явно помеченный в аудите как менее
рискованный вариант — полноценный GREETING_VIDEO-совместимый перерендер
не строился (это отдельная архитектурная задача, требующая
компилируемого окружения для проверки, которого у нас нет), вместо
этого `ExportService.startRerender` (`export.service.ts`) теперь
проверяет `session.greetingBriefSnapshot` сразу после загрузки сессии,
до всех проверок по aspect-ratio-семье, и явно отказывает
`BadRequestException` с понятным сообщением («перерендер в другое
соотношение сторон … пока не поддерживается — используйте дешёвый
экспорт (POST /export)»), вместо прежнего непонятного 400 про
отсутствующее товарное фото. Экспорт tier A (кроп) для GREETING_VIDEO
как работал, так и работает без изменений.

## Находка 2 (СРЕДНЯЯ): у GREETING_VIDEO нет модерации текста промпта — ✅ ИСПРАВЛЕНО

`GreetingPromptService.generateGreetingPrompt` жёстко проставляет
`moderationStatus: ModerationStatus.APPROVED` (`greeting-prompt.service.ts:131`,
plus добавленный в прошлом сегменте `approvedAt: now`) **без единого вызова
проверки контента**. Для сравнения, `PromptService`'s аналог для SINGLE/LINE
(`prompt.service.ts`'s `moderateContent`, вызывается на каждый
сгенерированный промпт) размечает попадающий под ключевые слова текст как
`FLAGGED`/`PENDING`, требуя от пользователя явного `approvePrompt()` —
то есть хотя бы фиксирует факт «пользователь осознанно одобрил
подозрительный текст» (переход в `BYPASSED`, а не тихое `APPROVED`).

У GREETING_VIDEO пользовательский текст (`personalMessage`, до 2000
символов, `customOccasionText`, до 200 символов — оба только `.trim()`,
без проверки содержимого, см. `update-greeting-brief.dto.ts`) и
сгенерированный Gemini черновик `speech` уходят прямо в текст сцены и
дальше в промпт для Grok **без единой проверки на ключевые слова**. Строка
`speech.replace(/"/g, "'")` (`greeting-prompt.service.ts:232`) экранирует
только двойные кавычки для безопасности самой JSON-строки промпта — это не
модерация контента, это защита синтаксиса.

Практическое следствие: пользователь может вписать в `personalMessage`
текст, нарушающий политику использования, и он гарантированно уйдёт в
рендер видео с пометкой «одобрено» с первого же вызова — ни флага, ни
записи, которую впоследствии мог бы увидеть оператор (в самой кодовой
базе не нашлось ни одного места, которое читало бы `FLAGGED`-промпты у
GREETING_VIDEO — искать там нечего, потому что этот статус для этого
типа проекта никогда не выставляется).

**Что нужно решить:** прогонять тот же (или упрощённый) вызов
`moderateContent`/ключевых слов, что использует `PromptService`, над
`personalMessage`/`customOccasionText`/сгенерированным `speech` до записи
`moderationStatus: APPROVED`.

**Что сделано:** дублировать ключевые слова/паттерны не пришлось —
`PromptService` уже был доступен через DI, поэтому в нём добавлена
публичная обёртка `moderateText(text)` над существующим `private
moderateContent`, единственная причина её существования — дать
`GreetingPromptService` доступ к тому же самому конвейеру проверки, что
уже использует SINGLE/LINE, без копирования логики. `GreetingPromptModule`
теперь импортирует `PromptModule`, `GreetingPromptService` получает
`PromptService` через конструктор (поле названо `promptService`, чтобы
не путать с локальной переменной `prompt: GenerationPrompt` в том же
методе) и вызывает `this.promptService.moderateText(sceneDescription)` —
именно на финальном тексте сцены, том самом, что уходит в Grok, а не
только на сыром `personalMessage`. Результат разбит на два случая:
чистый текст получает `moderationStatus: APPROVED` и `approvedAt` сразу
же (у GREETING_VIDEO нет отдельного экрана одобрения промпта, как у
SINGLE/LINE — значит, «одобрено» проставляется автоматически, как и
раньше); текст с флагами получает `moderationStatus: FLAGGED` и
`moderationFlags`, но **не** получает `approvedAt`. Поскольку у этого
типа проекта нет экрана «одобрить несмотря на флаг» (аналога
`approvePrompt()`'s FLAGGED → BYPASSED), просто выставить флаг было бы
недостаточно — пользователь получил бы одобренный по факту, но
формально флаженный промпт, из которого молча срендерилось бы видео.
Поэтому в `GreetingVideoService.startVideo()` добавлена отдельная
проверка: если `session.generationPrompt.moderationStatus ===
ModerationStatus.FLAGGED`, генерация видео отклоняется
`BadRequestException` с сообщением, перечисляющим причины флага и
просьбой отредактировать текст поздравления/повод на шаге брифа и
собрать сценарий заново.

## Находка 3 (СРЕДНЯЯ): доккомментарий про `planWork()` не соответствует действительности — язык озвучки для GREETING_VIDEO всегда `null` — ✅ ИСПРАВЛЕНО

Доккомментарии в `greeting-prompt.service.ts:16-19` и
`greeting-video.service.ts:20-22` утверждают: «`postprod.service.ts`'s
`planWork()` читает исключительно `session.generationPrompt`/
`session.brandManifestSnapshot` — никогда `Project.type` и никогда
`session.productInformation`». Построчная проверка ВСЕГО тела
`planWork()` (`postprod.service.ts:1036-1083`) показала, что это
утверждение неверно — есть ровно одно место, где `productInformation`
всё-таки читается:

```ts
language: session?.productInformation
  ? resolveVoiceoverLanguage(session.productInformation).language
  : null,
```

(`postprod.service.ts:1079-1081`). Поскольку у GREETING_VIDEO-сессии
`session.productInformation` всегда `undefined`, `work.language`
**всегда `null`** для этого типа проекта — и что важнее, `null`, а не тот
осмысленный дефолт, который сама функция `resolveVoiceoverLanguage` уже
умеет возвращать для отсутствующего товара:

```ts
// common/voiceover.ts:133
return { language: 'en', languageName: 'English', source: 'default' };
```

Тернарий в `planWork()` НЕ вызывает `resolveVoiceoverLanguage` вовсе,
когда `productInformation` отсутствует, — то есть намеренно обходит
собственный дефолт этой функции. `null` дальше уходит в TTS-синтез
(`postprod.service.ts:1132-1138`); для ElevenLabs это означает
отсутствующий `language_code` в запросе, что скорее всего приводит к
автоопределению языка по тексту (вероятно, работает случайно правильно
для большинства случаев), но это неверифицированное, недокументированное
отличие поведения для типа проекта, чьи собственные doc-комментарии прямо
утверждают, что этот код-путь его не касается вовсе.

Обнаружить это раньше было сложно именно потому, что находка №4
первого аудита («`planWork()` уже полностью тип-агностична») была
подтверждена лишь ОДНИМ конкретным полем на тот момент, а не построчным
чтением всего метода — второй аудит (аудит-2, фронтенд) унаследовал это
утверждение как данность и процитировал его повторно, не перепроверяя.

**Что нужно решить:** либо явно передавать в `planWork()`/`buildWork()`
предпочтительный язык озвучки из `GreetingBriefSnapshot` (у него есть
`countryCode` проекта, из которого уже сегодня выводится страна/валюта —
тот же сигнал, что `resolveVoiceoverLanguage`'s `languageCode`-ветка
использует для товаров), либо хотя бы убрать асимметрию и передавать
`resolveVoiceoverLanguage(undefined).language` (то есть `'en'`) вместо
голого `null`, когда `productInformation` отсутствует — это как минимум
согласует поведение с тем, что сама функция считает разумным дефолтом.

**Что сделано:** выбран более точный вариант, чем голый `'en'`-дефолт —
`postprod.service.ts` уже импортирует `resolveVoiceoverLanguage` из
`common/voiceover.ts`, а этот модуль отдельно экспортирует
`detectLanguage(text)` — тот самый эвристический детектор языка по
скрипту/ключевым словам, который `resolveVoiceoverLanguage` сама
использует как один из шагов своей цепочки приоритетов, и который не
привязан к `ProductInformation`. `planWork()`'s поле `language` теперь:
при наличии `productInformation` — прежнее поведение без изменений
(`resolveVoiceoverLanguage(...).language`); при его отсутствии (всегда
верно для GREETING_VIDEO) — `detectLanguage(speech) ?? 'en'`, то есть
язык определяется по фактическому тексту озвучки сессии (переменная
`speech` уже вычислена ранее в том же методе), а не по постоянному
`null`. Это точнее, чем просто прописать дефолт `'en'` для всех
GREETING_VIDEO-сессий: ролик-поздравление на русском теперь получит
`language: 'ru'`, а не английский код по умолчанию.

## Находка 4 (НИЗКАЯ): у оператора нет возможности увидеть содержимое брифа GREETING_VIDEO в админке — ✅ ИСПРАВЛЕНО

`AdminPanelService` (`admin-panel.service.ts`) нигде не читает
`session.greetingBriefSnapshot` или `session.greetingReferenceImages` —
единственное поле, которое он вытягивает для отображения «товара» в
списке/детали сессии, это `productInformation.productName`
(`admin-panel.service.ts:743`), которое у GREETING_VIDEO всегда
отсутствует. Практически это означает: оператор, открывший
GREETING_VIDEO-сессию в админке, видит пустое место там, где у SINGLE/LINE
было бы название товара — ни повода, ни имени получателя, ни тона, ни
текста поздравления не видно нигде в интерфейсе оператора.

В сочетании с находкой №2 (нет модерации) это означает, что сегодня у
администратора **нет вообще никакого способа** просмотреть, что на самом
деле сгенерировано в GREETING_VIDEO-ролике, не открывая сам файл видео
вручную по прямой ссылке.

**Что нужно решить:** добавить в admin-panel хотя бы текстовое
отображение брифа (повод/получатель/тон/текст поздравления) для сессий,
у которых есть `greetingBriefSnapshot`, — по аналогии с тем, как уже
отображается `productInformation` для SINGLE/LINE.

**Что сделано (с уточнением серьёзности):** при повторной проверке
перед исправлением выяснилось, что формулировка «нет вообще никакого
способа» была преувеличением — `AdminPanelService.getSession(id)` уже
возвращает `{ ...toSummary(row), data: sessionData(row) }`, то есть
ПОЛНЫЙ сырой JSON сессии, а `admin/src/app/sessions/[id]/page.tsx` уже
дампил его целиком через `<pre>{JSON.stringify(session.data, null,
2)}</pre>`. То есть `greetingBriefSnapshot` был технически виден и
раньше — находка была не о видимости данных, а о её оформлении: найти
повод/получателя/текст поздравления среди сотен строк неразобранного
JSON неудобно и легко пропустить, особенно флаг модерации. Поэтому
исправление — не новый API-эндпоинт, а добавление в тот же файл
(`admin/src/app/sessions/[id]/page.tsx`) двух заметных карточек над
существующим сырым JSON-дампом: (1) карточка с предупреждением, когда
`generationPrompt.moderationStatus === 'flagged'` (см. находку №2),
показывающая причины флага; (2) карточка «Бриф ролика-поздравления» —
повод (с человекочитаемой меткой из словаря `OCCASION_LABEL`,
переиспользующего те же названия поводов, что уже в мастере
фронтенда), получатель/отправитель, тон (`TONE_LABEL`), текст
поздравления и список загруженных референс-изображений с подписями.
Обе карточки — чисто защитное чтение (`data: unknown`, нет общего
пакета типов бэкенд/админка), рендерятся только когда соответствующее
поле реально присутствует в `session.data`.

## Проверено и подтверждено корректным (без изменений)

- **Тарифные ограничения брифа** (`greeting-config.ts`'s
  `resolveGreetingConfig`) — и создание проекта, и `PATCH
  /projects/:id/greeting-brief` независимо заново читают тариф
  пользователя и заново прогоняют через `resolveGreetingConfig`,
  которая бросает `ForbiddenException` при попытке получить
  `hedra`/1080p не по тарифу. Обхода через прямой PATCH нет — DTO не
  вызывает доверия к сырому значению без повторной проверки сервисом.
- **Снапшот сессии** (`createFromGreetingBrief`/`greetingBriefSnapshotFrom`)
  — копирует все поля, которые объявляет `GreetingBriefSnapshot`;
  `greetingBriefSnapshot`/`greetingReferenceImages` оба корректно в
  `DATA_KEYS`, не теряются при обновлении сессии.
- **Обход тарифного гейта у референс-изображений** — подтверждён
  безопасным: `assertSlotAccess` короткозамыкается на `if (slot.feature)`,
  `feature: null` у `session-greeting-reference` гарантирует, что
  `plans.assertUser` не вызывается вовсе (а не вызывается с `null` и
  падает непредсказуемо).
- **Биллинг** — оба вызова `aiUsage.record` (`greeting-prompt` и
  `generation:grok-imagine-video-1.5:{resolution}`) сверены с таблицей
  цен построчно: ключи совпадают для всех трёх разрешений и для модели
  Gemini по умолчанию — нет риска молчаливого нулевого списания из-за
  несовпадения строкового ключа.
- **Понижение разрешения при референсах** — `effectiveGrokResolution`
  вычисляется дважды (один раз в `GreetingVideoService` для биллинга,
  один раз внутри `GrokVideoService.startGeneration` для реального
  тела запроса), но с одинаковыми входными данными — билл и
  фактически отправленное разрешение гарантированно совпадают.
  Отмечено как хрупкое место (двойной расчёт одной и той же величины
  в двух местах) на будущее, не как баг сегодня.
- **Замки/гонки** — `'prompt'` и `'generate'` — разные ключи в
  `WORK_KINDS`, не конфликтуют; `startVideo` требует существующий
  `generationPrompt`, поэтому параллельный вызов `greeting-video` до
  `greeting-prompt` просто получает понятный 400, не гонку данных.
- **Таймауты/ошибки рендера** — `renderExpired`/`markFailed` у
  `GreetingVideoService` используют те же поля (`initiatedAt`,
  `xaiBatchId`) на общем типе `GeneratedVideo` — идентичное поведение
  с SINGLE/LINE.
- **Уборка сессий / TTL** — колонка `generationStatus`, по которой
  cron решает, оставлять ли платный ролик, выводится универсально из
  `generatedVideo.status` в одном и том же атомарном `UPDATE`, без
  всякой зависимости от `productInformation`/типа проекта. Готовый
  GREETING_VIDEO-ролик защищён от преждевременной уборки так же, как
  и у SINGLE/LINE.
- **Проверки владения** — `GreetingReferenceController`/
  `GreetingPromptController`/`GreetingVideoController` не объявляют
  собственных guard'ов, но покрыты глобальным `SessionOwnerGuard`
  (`app.module.ts`, `APP_GUARD`), который проверяет `:sessionId` из
  параметров маршрута на каждом запросе — тот же механизм, что уже
  защищает `ScenesController`/`ReferenceSlotsController`. Утечки
  чужой сессии по `sessionId` не найдено. `GreetingBriefController`/
  `ProjectSessionController` (маршруты по `:projectId`) используют
  явный `WHERE userId = ...` — тоже без пробелов.
- **Публикация** (`PublicationService.snapshotFromSession`) — все
  товарные поля читаются через `?.`, `PublicationRequest.productItemId`/
  `.projectId` в Prisma-схеме реально nullable (`onDelete: SetNull`),
  админский экран публикаций не обращается ни к `productName`, ни к
  `productItemId` напрямую — рендерится без крашей и на
  GREETING_VIDEO-заявках.

## Заключение

Пайплайн GREETING_VIDEO в целом построен последовательно и без
архитектурных перекосов — большинство инвариантов, о которых
заявляли doc-комментарии кода (тип-агностичность постпродакшена,
безопасность обхода тарифного гейта у референсов, единообразие
биллинга и уборки сессий), подтвердились при построчной проверке.
Но ровно там, где GREETING_VIDEO соприкасается с кодом, изначально
писавшимся только для SINGLE/LINE и предполагающим наличие товара
(`GenerationService.generateVideo` в экспорте tier B, языковая ветка
в `planWork()`, отображение товара в админке), обнаружились реальные
несоответствия — три из четырёх находок этого аудита ровно такого
рода.

**Все 4 находки исправлены в одном проходе** (по запросу «Давай
исправим все в одном проходе»): №1 — tier B явно и понятно отключён
для GREETING_VIDEO вместо непонятного 400; №2 — реальная модерация
текста сценария подключена (переиспользован конвейер SINGLE/LINE через
новый `PromptService.moderateText()`), плюс жёсткий гейт на генерацию
видео при `FLAGGED`-статусе, раз у этого типа проекта нет экрана
ручного одобрения; №3 — язык озвучки для GREETING_VIDEO больше не
`null`, а определяется по фактическому тексту сценария через уже
существующий `detectLanguage`; №4 — админка получила читаемые карточки
брифа и предупреждения о модерации поверх уже существовавшего (но
неудобного) сырого JSON-дампа.

Ограничение, отмеченное во всех предыдущих аудитах этого проекта,
остаётся в силе и здесь: `npm install` в этой песочнице падает с 403,
поэтому ни один из четырёх фиксов не прогонялся через компилятор/тесты
— проверка сделана построчным чтением, вручную сверенными сигнатурами
типов и скриптовой проверкой баланса скобок по каждому изменённому
файлу. Рекомендация — прогнать `tsc`/юнит-тесты на этих файлах перед
деплоем в окружении, где `npm install` работает.
