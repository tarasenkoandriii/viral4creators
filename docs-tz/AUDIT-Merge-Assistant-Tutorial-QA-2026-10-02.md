# Аудит и проект слияния: встроенный помощник, обучалка CLIENT_SITE, QA — 02.10.2026

**Что это.** Сравнительный аудит встроенного ИИ-помощника генератора
(консультант лендинга, гид мастера TMA) и обучалки по сайту заказчика
(`CLIENT_SITE`, реле живого входа) по чек-листу платформы ИИ-помощника
(Э0–Э3, `sites-backend/`), плюс проект этапа **«Э-С: слияние»**.

**Как проверялось.** Чтение кода и документации, без запуска тестов
(машина общая). Секреты, `.env`, `.pem` не читались. Ссылки вида
`файл:строка` — на состояние рабочего дерева 02.10.2026. Код не правился.

**Поправка к вводной.** Учётные данные клиентских сайтов хранятся **не на
реле**. Реле (`live-login-relay/`) держит только живой браузер и снятые
куки в памяти процесса: сессия ≤ 3 мин, результат ≤ 60 с после закрытия
(`RESULT_CACHE_MS`, `live-login-relay/src/config.ts`). Пароли тестовых
входов (`credentialsEnc`) и cookie jar (`cookiesEnc`) лежат в **основной
БД генератора**, таблица `ClientSiteTutorialDraft`
(`backend/prisma/schema.prisma:3701–3742`). Они зашифрованы AES-256-GCM
ключом `SITE_TUTORIAL_TOKEN_KEY` из env бэкенда
(`backend/src/modules/client-site-tutorial/draft-credentials.ts`). Главный
риск реле другой: это **SSRF с картинкой**, а не утечка базы паролей.

## 3. Проект слияния — этап «Э-С: слияние»

### 3.0. Принципы

1. **Один бэкенд клиентских сайтов (В-2).** Всё, что знает о чужих сайтах
   (реестр, владение, обход, креды входа, карты интерфейса), принадлежит
   `sites-backend`. Генератор (`backend/`) держит только своё: проекты,
   ролики, деньги пользователя генератора.
2. **Изоляция генератора.** У генератора нет DSN к `site_*` и нет ключей
   кредов. Он ходит во внутренний API с секретом, как QA-ТЗ §1.5 уже
   предписывает для `CLIENT_SITE`.
3. **Чужой JS — только в изолированном браузере-воркере** с
   egress-фильтром (QA-ТЗ §4.2). Ни в функции бэкенда, ни рядом с Dokploy.
4. **Порядок — от риска.** Сначала закрыть К-1…К-4 (дни), потом переезд
   помощника (недели; выгода — меньше кода, риск низкий).

#### Целевая модель данных (всё в `sites-backend`)

```
SiteAccount ── SiteHost (verified, 90 дн.)
   │              ├─ site_pages / site_crawl_runs      (общий кэш обхода: помощник + QA; обучалка читает)
   │              ├─ site_ui_maps   НОВОЕ              (карта элементов по host+path из раундов обучалки;
   │              │                                     читают: подсветка Э6 / голос Э6-бис / редактор Э6-тер / Flow-QA)
   │              └─ site_credentials НОВОЕ            (креды входа и сессия; см. ниже)
   └─ SiteAccountMember (telegramId, productRoles + НОВОЕ tutorial: owner|none)
Генератор: Project(CLIENT_SITE) ── siteHostId (ссылка, без FK между БД) ── TutorialVideoAsset
```

Кэш `site_pages` привязан к кабинету (`accountId`, `siteId`, `hostId` —
`schema.prisma:375–379`). «Общий» значит общий между продуктами **одного
кабинета**, не между кабинетами. Это правильно, так и оставить.

Текст страниц, который обучалка или QA захотят отдать модели (подписи,
сценарий озвучки), идёт **только** через `assist-knowledge-core` (карантин
`injection.ts`, ворота версии). Сырой DOM в промпт не попадает.

#### Модель хранения учётных данных входа (`site_credentials`)

| Требование | Решение |
|---|---|
| Шифрование | Конвертное: свой DEK на запись (AES-256-GCM), AAD = `credId:accountId:hostId:version`; DEK зашифрован KEK с идентификатором версии (`kid`) из отдельного секрета `SITE_CREDENTIALS_KEK_v{n}`; позже — KMS. Формат `v1.<kid>.<iv>.<tag>.<ct>` |
| Ротация | Новый `kid` + перешифровка DEK кроном (сами данные не трогаются); старый KEK удаляется после 100% перешифровки |
| Доступ только системной роли | Отдельная роль БД `site_secrets` (не `assist_public`, не роль кабинета). Расшифровка — только в браузерном воркере через «аренду»: воркер предъявляет id прогона, sites-backend проверяет, что прогон авторизован, хост подтверждён и не заморожен, и отдаёт открытый текст один раз по каналу с HMAC/mTLS. Генератор, операторы и админка видят только метаданные (`есть / нет`, когда использовались) |
| Привязка к подтверждённому хосту | Запись ссылается на `SiteHost`; `assertHostVerified(hostId, 'tutorial-login' \| 'qa-login')` на каждой аренде; отзыв или истечение владения замораживает креды сразу (льготы 72 ч нет — это не виджет) |
| Срок жизни | Пароли: 30 дней с последнего использования, максимум 90 (как подтверждение); куки сессии: по их `expires`, но не больше 7 дней; только куки регистрируемого домена хоста |
| Удаление по запросу | Кнопка «Забыть данные входа» в TMA генератора и QA + API; удаление записи и DEK (crypto-shred); каскад при удалении хоста или кабинета; опция «одноразово — стереть после сборки» |
| Аудит доступа | Каждая аренда, создание, удаление и неудачная попытка — в `AuditLog` с цепочкой `prevHash` (QA-ТЗ §5.6): кто, какой прогон, назначение, результат |
| Реле | Хранит только живую сессию; результат (куки) сразу уходит в `site_credentials` через тот же канал, не в генератор |

#### Два режима обучалки (уточнение владельца 02.10.2026)

Обучалка законно работает и по **чужому сайту со своим аккаунтом
клиента** (ролик-инструкция по SaaS, которым клиент пользуется). Поэтому
К-4 закрывается не обязательным подтверждением владения для всех, а двумя
режимами: **A «свой сайт»** — хост подтверждён в `sites-backend`, учётки из
реестра ниже, общие с QA; **B «чужой сайт со своим аккаунтом»** —
подтверждение прав на аккаунт и согласия с условиями сайта, пароль не
храним (только сессия ≤ 7 дней в личном хранилище пользователя, не в
реестре сайта и не для QA), лимиты логинов/доменов/попыток, запрещённые
категории (банки, платёжки, госпорталы, веб-почта…), opt-out, журнал.
Подробно — `docs-tz/SECURITY-PROPOSALS-2026-10-02.md` §2.

#### Тестовые учётные записи сайта (режим A) — одни на обучалку и QA (уточнение владельца 02.10.2026)

Креды входа нужны и обучалке, и QA, и сайты у них **одни и те же**. На
одном сайте заказчик заводит **несколько тестовых пользователей**, чтобы
показать и проверить разные роли и пакеты (гость, покупатель, «Pro»,
менеджер, администратор). Поэтому хранилище — не «один пароль на черновик
обучалки» и не отдельный `ScanCredential` QA, а **реестр тестовых
учётных записей сайта** в `sites-backend`, общий для обоих продуктов (и
обоих их инстансов — `tutorial.*` в генераторе и QA-TMA):

| Сущность | Поля и правила |
|---|---|
| `site_test_accounts` — тестовый пользователь сайта | `siteId`, `accountId` (кабинет), `label` («Покупатель Pro»), `role` (свободный текст + подсказки: guest / customer / manager / admin), `plan` (пакет/тариф на сайте заказчика), `loginMethod` (`password` \| `session` — только сессия через живой вход \| `sso`), `hostIds[]` — на каких **подтверждённых** хостах этого сайта он действует (`shop.` и `admin.` одного сайта, один SSO), `products[]` — кому разрешено (`tutorial`, `qa`; позже `assist-admin` для голосовых тестов «Админки»), `status` (active / frozen / expired), `createdBy`, `confirmedTestAccountAt` (владелец подтвердил: это тестовый аккаунт, не реальный клиент), `lastUsedAt`, `expiresAt` |
| `site_credentials` — секреты учётки | 1:N к учётке: пароль (конверт по модели выше), сессия-куки с `expires` ≤ 7 дней и только домены регистрируемого домена её хостов; TOTP не храним; версии ключа |
| Аренда | `lease(testAccountId, runId, purpose='tutorial-login'\|'qa-login', hostId)`: хост ∈ `hostIds` и подтверждён для назначения, продукт ∈ `products`, учётка active, прогон авторизован; иначе отказ с причиной; каждое — в `AuditLog` |
| Где видно | Один список «Тестовые пользователи сайта» в кабинете сайта: QA-TMA и TMA генератора (через внутренний API Ш1) показывают его же — завёл в одном продукте, видно в другом; секреты не показываются никому, только «есть / когда использовался» |
| Удаление | «Забыть» — crypto-shred секретов учётки; каскад при удалении хоста/сайта/кабинета; заморозка при отзыве владения любым из её хостов; неиспользуемая 90 дней — `expired` |

Что это даёт продуктам: **обучалка** снимает один сценарий под разными
ролями/пакетами (вариант ролика «для администратора», «для тарифа Pro»);
**QA** получает матрицу ролей — проверка разграничения доступа (страница
роли A недоступна роли B, IDOR по идентификаторам между тестовыми
пользователями), а не только «зона за логином» одним аккаунтом.
Ограничения QA-ТЗ §3.6 остаются: 1–2 попытки входа, без перебора, active
по `env:prod` — с доп. подтверждением, креды не попадают в логи и
артефакты. Решение аудита QA об асимметричном шифровании (бэкенд
шифрует открытым ключом воркера) переносится на `site_credentials`
целиком: расшифровать может только браузерный воркер (Ш3); до Ш3 —
временно расшифровка в `sites-backend` по аренде.
