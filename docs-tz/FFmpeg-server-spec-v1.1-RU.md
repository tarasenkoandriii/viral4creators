# Собственный FFmpeg API для Viral4Creators — анализ и техническое задание

Дата: 21.10.2026. Редакция 1.1 после аудита. Статус: исправленный проект ТЗ; реализация, нагрузочные испытания и развёртывание не выполнялись.

## 1. Решение

Сделать внутренний FFmpeg API, совместимый с используемым платформой протоколом Very Good FFmpeg. Первый этап — на существующем VPS с одной изолированной задачей одновременно. Перенос на отдельный VPS — по измеренной нагрузке либо при нарушении качества голосового relay. Не создавать отдельный микросервис для каждой операции, Kubernetes, Redis-кластер или новую административную систему.

«Полная калька» означает совместимость всех реально используемых платформой запросов, результатов и цепочек команд. Это не обещание повторить чужие GPU, оборудование, dashboard, тарифную систему, SDK и SLA. Для замены нашего клиента обязательны API и операционная вкладка в существующей админке; внешний dashboard провайдера копировать не требуется. Полную совместимость с внешним API для сторонних пользователей не включать в первый релиз; неизвестные поля отклонять явно, а не молча игнорировать.

Основной выигрыш: контролируемая версия FFmpeg и фильтров, настоящая идемпотентность, понятные лимиты, приватные материалы и отсутствие отдельного счёта за каждую обработку. Экономия не доказана без объёма операций и реального счёта провайдера: небольшой поток может быть дешевле на внешнем API.

## 2. Что подтверждено

### 2.1. Текущая интеграция

Источник: `backend/src/modules/postprod/ffmpeg-api.service.ts`.

- База по умолчанию `https://verygoodffmpeg.com/api`, настраивается `FFMPEG_API_BASE_URL`.
- Авторизация `Authorization: Bearer …`, ключ `FFMPEG_API_KEY`.
- `POST /ffmpeg`: поля `input_files`, `output_files`, `ffmpeg_commands`.
- Клиент отправляет `Idempotency-Key`, SHA-256 от сериализованного тела запроса. Реальная дедупликация у нынешнего провайдера кодом не подтверждена.
- `GET /jobs/{id}`: клиент разворачивает `data`, читает `status`, `output_files`, `error_message`.
- В коде используются placeholders `{{имя}}`, строки с ведущим `ffmpeg`, несколько команд и результатов. Публичная документация провайдера также показывает относительные пути `inputs/...`, `outputs/...` и команды без ведущего бинарника.
- Story-Tales задаёт `retrySubmit: false`, тайм-аут отправки 25 с; неизвестный исход не должен приводить к новой обработке.
- Часть остальных клиентов допускает повтор POST при сетевых ошибках/429/5xx. Поэтому атомарная серверная дедупликация обязательна до подключения платформы.

Потребители: postprod (основная обработка и форматы), actors (субтитры), publishing/audio-track (аудиомикс), portfolio (водяные знаки), Story-Tales, tutorial-runner, tutorial-video-versions, shared-video (постер), client-site-tutorial. Поиск только переменной `this.ffmpeg` неполон: инвентаризировать также инъекции и другие имена клиента.

## 3. Границы продукта

### Входит в первый релиз

1. Скачивание входов по HTTPS и текстовых SRT/ASS-файлов.
2. Последовательное выполнение массива команд в одной задаче с промежуточными файлами.
3. Обрезка, crop/scale/pad, fps/SAR, форматы, склейка, freeze/loop/still, скорость видео, аудиодорожки.
4. Субтитры libass и используемые шрифты с кириллицей, украинским и латиницей; drawtext/водяные знаки.
5. AAC/MP3/WAV, libx264, JPEG/PNG, WebM/VP9 — точный перечень сверить с командами репозитория; необязательные кодеки не устанавливать без потребителя.
6. Фильтры Story: loudnorm, sidechaincompress, amix с normalize=0, aresample, apad, atrim, setpts/asetpts, concat, overlay, setsar, fps.
7. Очередь, идемпотентность, статусы, приватная выдача файлов, очистка, отмена, журнал и метрики.
8. Проверка результата через ffprobe; SHA-256 каждого файла и версии инструментария.

Не входят: синтез речи, STT, LLM, lip-sync, генерация персонажей, изменение Nova, новая редакция принятого Tutorial, автопубликации, публичный сервис произвольных команд, GPU и распределённые воркеры. Обработка не исправляет плохую исходную мимику или липсинк сама по себе.

## 4. Архитектура без лишних компонентов

Новая папка монорепозитория `ffmpeg-server/`: TypeScript/Node поддерживаемой LTS, HTTP API и фоновый диспетчер. Один управляющий процесс, SQLite в WAL на постоянном локальном volume; миграции схемы, busy timeout и атомарные транзакции. Redis не нужен при одном узле. При будущем разделении нескольких управляющих узлов пересмотреть БД отдельно.

Поток:

1. Backend отправляет команду → API валидирует авторизацию, синтаксис и лимиты.
2. Транзакция записывает job и idempotency key → немедленный ответ, без ожидания скачивания.
3. Диспетчер атомарно забирает job → безопасный downloader сохраняет inputs.
4. Изолированный executor без сети выполняет FFmpeg и ffprobe.
5. Сервис проверяет результаты и публикует ссылки только после готовности всех обязательных файлов.
6. Backend опрашивает прежний job id и импортирует результат существующим способом.
7. После TTL сервис удаляет временные данные, сохраняя минимальную историю и tombstone идемпотентности.

Управляющий процесс не запускать от root. Он не должен получать Docker socket хоста: Docker API даёт чрезмерные полномочия. Для изоляции использовать rootless Docker/Podman под отдельным системным пользователем с проверенными cgroup v2 либо заранее ограниченный executor через systemd. На реализации выбрать один реально поддерживаемый механизм, не поддерживать оба ради универсальности. Невозможность enforce CPU/RAM/PID/network/mount-ограничения — блок подключения production.

Traefik завершает TLS. URL-кандидат `ffmpeg.viral4creators.app`; до настройки подтвердить DNS и владение. Порт executor, SQLite и файловый volume наружу не публиковать.

## 5. Контракт API v1

### 5.1. Авторизация

Сервис предназначен для server-to-server. Ключ минимум 32 случайных байта, только secret store, отдельный от relay. Сохранять хеш/идентификатор ключа, обеспечить ротацию с коротким периодом двух активных ключей. Ни ключи, ни signed input URLs не выводить в журнал. Job принадлежит стабильному client_id, а не конкретному ключу: ротация ключа этого клиента сохраняет доступ к его прежним задачам. Внутренний ops-доступ отдельный. Клиент не может передать произвольный client_id в теле для получения чужого доступа.

### 5.2. Создание задачи

`POST /api/ffmpeg`

```json
{
  "input_files": {"base": "https://storage.example/video.mp4"},
  "output_files": ["poster.jpg"],
  "ffmpeg_commands": ["ffmpeg -i {{base}} -frames:v 1 {{poster.jpg}}"]
}
```

Ответ HTTP 202:

```json
{"data":{"id":"job_uuid","status":"queued","error_message":""}}
```

Обязателен `Idempotency-Key` для нашего backend. На синтаксически некорректный запрос — 400 до создания задачи. 401 — ключ, 403 — запрещённый источник/профиль, 409 — ключ с другим телом, 413 — размер JSON, 422 — неподдерживаемая команда, 429 — очередь/квота с Retry-After, 503 — временная недоступность до приёма задачи. Для уже существующего ключа сначала вернуть прежнюю задачу, даже если очередь заполнена, приём приостановлен или входная ссылка уже истекла; повторно проверять только аутентификацию, размер запроса и совпадение hash. Квоты и readiness применяются к созданию новой задачи, не к поиску принятой.

Успешная фиксация должна означать: job переживёт рестарт. После фиксации не отвечать «не принято» из-за ошибки запуска dispatcher; сохранить тот же job и вернуть/восстановить его по ключу.

### 5.3. Опрос

`GET /api/jobs/{id}` → HTTP 200:

```json
{"data":{"id":"job_uuid","status":"succeeded","output_files":{"poster.jpg":"https://ffmpeg.example/api/files/job_uuid/poster.jpg?token=REDACTED"},"error_message":"","progress":100}}
```

Публичные статусы: queued, processing, succeeded, failed, canceled. Клиент уже распознаёт succeeded/failed/canceled; внутренние downloading/running/validating/publishing можно отдавать как processing и отдельную `stage`. Ошибка имеет стабильный `error_code` и безопасное сообщение. Progress приблизительный: время из FFmpeg, не обещание линейной готовности; для неизвестной длительности — null.

Метаданные additive: created_at, started_at, finished_at, expires_at, outputs_metadata (bytes, sha256, mime, duration, streams), ffmpeg_version, image_digest. Метаданные не подменяют существующую независимую проверку и приёмку на backend.

404 — чужой/неизвестный id без утечки существования. Для известной задачи с удалёнными файлами GET возвращает HTTP 200, `status: failed`, `error_code: OUTPUT_EXPIRED` либо `OUTPUT_PURGED`, пустой output_files и `execution_status: succeeded`, если исполнение ранее завершилось успешно. Исходный факт выполнения и журнал не переписывать. Так существующий клиент получает terminal-ошибку, а не бесконечно ловит HTTP 410 и оставляет задачу pending. Сам файловый URL после TTL отвечает 410. Повтор POST прежнего ключа возвращает тот же id, без нового рендера. Адаптер backend обязан сохранять безопасный error_code в ошибке операции; это проверяется сквозным тестом.

### 5.4. Вспомогательные endpoints

- `POST /api/jobs/{id}/cancel`: идемпотентная отмена; гонка с завершением разрешается CAS, готовая задача не превращается в canceled.
- `GET /api/health`: минимальная liveness без внутренних данных.
- `GET /api/ready`: доступен SQLite, executor, достаточно диска, применены миграции и пройден capability self-test; отказ → 503.
- `GET /api/capabilities`: авторизованный список версии, кодеков, фильтров, профиля лимитов.
- `GET /api/jobs/by-key/{key}`: авторизованная сверка потерянного ответа по idempotency key, без создания задачи; ключ не писать в access logs. 404 означает отсутствие записи в сохранной БД, а не разрешение автоматически отправить задачу к другому провайдеру.
- `DELETE /api/jobs/{id}/artifacts`: отзыв результатов, прекращение выдачи новых ссылок, остановка активной задачи и удаление её файлов; повтор безопасен. Ответ 202 при незавершённой остановке, 200 только после подтверждённого удаления. Tombstone и аудит сохраняются.
- `POST /api/control/pause`, `/drain`, `/resume`: только ops-клиент, атомарное состояние на диске; pause останавливает выдачу новых задач worker, drain также запрещает новые submit и даёт активной завершиться. Read/status/cancel/purge продолжают работать. При старте после потери БД — только paused/recovery.
- `/metrics`: только внутренний ops-доступ.

Webhook, загрузка локальных файлов и GPU не требуются текущему клиенту. Если заявляется расширенная совместимость с внешним API, их делать отдельным этапом по документированному контракту, включая подписи webhook и повторы, а не имитацией success.

## 6. Команды и безопасность исполнения

Не выполнять строки через shell, `sh -c`, `exec(command)` или подстановку окружения. Токенизировать shell-подобные кавычки без исполнения, удалить только допустимый ведущий `ffmpeg`, запустить фиксированный бинарник через argv. Недопустимый/неоднозначный синтаксис → 422. Фильтры с кавычками, двоеточиями и обратными слешами сохранять: примитивный split по пробелу непригоден.

Поддержать `{{input-key}}`, `{{output-name}}`, `inputs/name`, `outputs/name`. Имена input/output не пересекаются. Подстановка только в разобранных аргументах с контролем контекста, включая разрешённые локальные пути внутри subtitles/фильтров. Не применять свободный replace URL или пользовательских имён в исполняемую строку. Все пути сопоставляются с manifest конкретной задачи.

Все outputs и промежуточные файлы внутри workspace задачи. Запрет absolute paths, `..`, NUL, symlink/hardlink escape, устройств и специальных файлов. Команды в цепочке могут читать объявленные результаты предыдущей команды. Незаявленные финальные результаты не выдавать. Разрешить безопасные генерируемые сервисом файлы concat/list только через явную модель, если инвентаризация найдёт такой потребитель.

FFmpeg читает только локальные inputs и промежуточные файлы. Executor без сети: недопустимы URL в -i, movie/amovie, вложенные плейлисты с удалёнными адресами. Ограничить protocols и filesystem mounts. Не считать protocol_whitelist единственной защитой: фильтры и демультиплексоры также могут читать файлы. Разрешённые фильтры и опции сформировать из реального корпуса команд; при несовместимости не ослаблять sandbox молча.

Исполнитель: non-root, read-only root FS, отдельный рабочий mount, no-new-privileges, без capabilities, без host mounts, без Docker socket и секретов; ограничение CPU/RAM/PIDs, размера файлов, stderr и wall clock. Патчить образ FFmpeg; версия и build flags фиксируются digest. Не давать API принимать исполняемые файлы или произвольные системные программы.

## 7. Downloader и приватные материалы

- Только HTTPS, без userinfo; лимит redirect 3. URL проверять при каждом redirect.
- Allowlist доменов реальных input-хранилищ и backend маршрутов. Не ограничивать весь Vercel общей маской без проверки нужных хостов.
- DNS rebinding: проверять все A/AAAA, отклонять loopback/private/link-local/metadata/reserved диапазоны, подключаться к проверенному адресу с правильным TLS hostname; повторять на каждом новом соединении.
- Тело читать потоково; лимит по реальным байтам, независимо от Content-Length. Проверять тайм-ауты, тип файла и ffprobe. Скачивание не должно блокировать API.
- Input URLs с токенами и команды с текстом/путями — приватные данные. Полный request payload хранить зашифрованно (AEAD с key_id и отдельным ключом вне БД/backup), не в SQLite plaintext и не в stderr. Независимый fingerprint хранить как HMAC от канонического тела, чтобы удаление payload не разрушало сверку повторов; ключ HMAC хранить отдельно с версией и политикой ротации. После скачивания удалить URL там, где восстановление не требует его; не писать query в access logs.
- Выходные файлы приватные. Скачивание по короткоживущему bearer URL (30 минут), HTTPS, без directory listing; token хранить хешированным и привязанным к job/file/expiry. Выдача проверяет актуальный статус отзыва на каждом новом запросе; подпись URL без проверки revocation недостаточна. Поддержать GET/HEAD и ограниченный Range для повторного скачивания, без продления TTL. Повторный авторизованный status может перевыпустить ссылку, пока существует результат. Cache-Control: private, no-store; Content-Type и безопасный Content-Disposition заданы сервером, X-Content-Type-Options: nosniff.
- TTL самого файла 24 часа от завершения — не от последнего GET. После импорта backend остаётся владельцем своей копии; сервер не удаляет Blob/готовые сборки платформы.
- При отзыве согласия: отмена известной задачи и удаление её временных input/output по внутреннему авторизованному запросу; backend хранит связь product operation → provider/job и посылает purge с устойчивым повтором до подтверждения. После отзыва прекратить новые скачивания; уже переданные байты отозвать невозможно. Backend повторно проверяет согласие перед фиксацией импорта: результат не публикуется в продукт. TTL — запасная очистка, не замена отзыва.

## 8. Очередь, идемпотентность и восстановление

SQLite: jobs, idempotency_keys, artifacts, attempts, минимальный журнал событий. Уникальность `(client_id, idempotency_key)`. В одной транзакции проверять канонический hash тела и создавать job; параллельные одинаковые POST получают тот же id. JSON canonicalization сортирует ключи объектов, но сохраняет порядок commands/outputs; числовые/строковые типы не смешивает. Внутренний fingerprint — HMAC-SHA-256 от канонического тела (не сам клиентский ключ). Один ключ с другим телом — 409.

Не дедуплицировать разные ключи только по командам: одинаковый URL может со временем вести на другие байты. Текущий клиент включает signed URLs в hash; после их обновления ключ изменится. Поэтому backend обязан сохранять связь operation → job/idempotency key до сетевого запроса, и при неопределённом исходе сверять прежний ключ. Серверная дедупликация не заменяет продуктовый замок.

Клиентский Idempotency-Key ограничить 128 печатными ASCII-символами; первая версия клиента использует стабильный UUID/хеш операции. Ключи/tombstones хранить 90 дней и не короче разрешённого окна повторов; после очистки тяжёлых файлов повтор ключа возвращает тот же завершённый/expired job, не новый рендер. Backend не делает транспортных повторов старше 90 дней; операция требует ручной сверки. Новый осознанный рендер требует новой версии операции. За пределами документированного срока гарантии дедупликации нет.

Один worker, atomic claim, lease и heartbeat. После рестарта: queued продолжаются только при сохранных БД/ключах и доступных входах; running сначала сверяются с изолированным executor по job/attempt id. Не запускать второй процесс, если прежний жив. Если executor исчез, попытка помечается interrupted; не более одной повторной локальной попытки только после доказанного завершения старого процесса и при сохранных входах. Новых TTS/STT/внешних задач эта попытка не создаёт. OOM, invalid-command, output-too-large автоматически не повторять.

Публикация результата атомарная: сначала временные файлы + проверка всех outputs, затем rename/фиксация manifest. GET не должен выдавать частичные outputs при failed. При cancel/timeout убить всю process group, подтвердить отсутствие дочерних процессов, только затем освобождать слот и очищать workspace.

## 9. Стартовые лимиты и размер сервера

Это проектные ограничения пилота, не измеренная производительность:

- 1 активная задача на весь pipeline (download → execute → publish), не более 20 ожидающих на сервер и 10 на клиент. Очередь не скачивает inputs заранее. Повтор того же ключа не занимает новое место. Справедливость между клиентами — round-robin при наличии нескольких клиентов; внутри клиента FIFO.
- API/dispatcher до 256 MiB RAM; executor до 3 GiB, 2 CPU, 128 PIDs; threads, filter_threads и filter_complex_threads не выше 2; прогон проверить с фактическими аргументами. FFmpeg-процессы из массива команд выполняются последовательно. Весь FFmpeg-контур должен иметь общий лимит, чтобы дочерние процессы не умножали ресурс.
- На существующем VPS не выделять оставшиеся CPU целиком; relay и Dokploy должны иметь запас. Убедиться, что лимиты реально применены на целевой системе.
- JSON ≤512 KiB, до 20 inputs, 10 commands, 10 outputs; суммарный текст команд ≤128 KiB.
- До 512 MiB на input, до 1 GiB суммарных скачиваний; до 512 MiB суммарных outputs; workspace ≤4 GiB с учётом intermediates.
- Профиль пилота: до 1920×1080, 60 fps, входная длительность до 10 минут; отдельная проверка на decompression bombs, размеры изображений ≤24 MP. Лимиты ширины/высоты проверять с учётом поворота и SAR.
- Время очереди ≤20 минут от приёма; весь активный pipeline ≤15 минут от claim, в том числе скачивание/ffprobe/все команды/публикация. На файл скачать не дольше 120 с, connect ≤10 с, отсутствие прогресса ≤15 с. Общий pipeline deadline имеет приоритет над суммой отдельных тайм-аутов. Пока срок входного токена не известен, нельзя обещать, что очередь 20 минут совместима с ним: перед canary сверить все реальные TTL (у Story input около 30 минут), предусмотреть запас минимум 5 минут на скачивание; при нехватке запаса отклонять новую задачу или уменьшать профиль очереди, а не обновлять подписанный URL за пользователя. При истёкших входных ссылках — явная ошибка, без нового TTS.
- При свободном диске <15 GiB не принимать новые задачи; workspaces вместе ≤15 GiB, outputs вместе ≤10 GiB. Для одной активной задачи резервировать workspace заранее, а загрузку и запись считать потоково. На filesystem поддержать проверяемую жёсткую project quota/ограниченный отдельный volume; если доступен только мониторинг свободного места, shared-VPS production не разрешать. Ограничить I/O через cgroups, проверить поддержку в runtime. Дополнительный read-only volume для fonts допустим; другие host mounts запрещены. Лимит применяется до/во время записи, уборка не должна затрагивать relay и Dokploy.
- История задач 90 дней без исходных URL и медиа; логи 14 дней с ограниченным общим объёмом. Окончательные значения утвердить после оценки приватности и эксплуатации.

Если корпус наших команд требует больше — создать обоснованный профиль, а не глобально снять лимит.

Отдельный сервер: стартовая рекомендация 4 выделенных/предсказуемых vCPU, 8 GiB RAM, 80–160 GiB SSD, без GPU; concurrency сначала 1. Это размер для теста, а не обещание throughput. Переход оправдан, если relay ухудшается, очередь систематически превышает 2 минуты при целевом потоке, нужны большие файлы/длительности или нагрузка требует concurrency>1. Высокая нагрузка/steal CPU на shared vCPU — дополнительный аргумент за выделенные CPU. Покупка VPS и тариф не входят в это ТЗ без отдельного решения владельца.

## 10. Качество, синхрон и Story-Tales

- Один зафиксированный образ FFmpeg с libx264/libass и шрифтами, обязательный capability smoke при build и ready.
- Проверять duration всех потоков, разрешение, fps, codecs, sample rate, наличие нужных streams, bytes, SHA-256; ошибки не превращать в succeeded.
- Существующие продуктовые правила не переносить глобально в сервис. Например, Story требует 1280×720, длительность с допуском около 0.15 с и MP4 ≤3 MiB; остальные продукты могут иметь другие ограничения.
- По расчёту 3 MiB на 110 с дают около 229 kbit/s суммарно до контейнерных накладных расходов; AAC 128 kbit/s оставляет около 101 kbit/s на видео. Поэтому прохождение размера на простом локальном тесте не гарантирует качество сложных сцен. Собственный сервер сам этот конфликт не устраняет.
- Не снижать качество и не повышать лимит Story скрытно. На сложном fixture отдельно решить: явный bitrate budget/двухпроходное кодирование, приемлемый профиль сцены либо самостоятельное изменение транспорта/хранения и продуктового лимита. При невозможности — понятный отказ.
- A/V-проверка технических длительностей не доказывает lip-sync. Тестовый клип со вспышкой и звуковым импульсом проверяет сохранение синхрона сборки; мимика и речь исходника требуют отдельной приёмки.
- Принятый Tutorial, эталон, Nova и все ранее одобренные хеши неизменны. Использовать синтетические fixtures и отдельные тестовые записи; не рендерить принятый ролик «для сравнения».

## 11. Переход без потери старых задач

Простая смена `FFMPEG_API_BASE_URL` недостаточна: job ids внешнего сервиса останутся в БД, а status начнёт искать их на нашем VPS.

В `FfmpegApiService` добавить provider routing: `hosted` и `selfhosted`, раздельные адреса/ключи. Старые id без префикса всегда направлять к hosted; новые selfhosted выдавать как `selfhosted:<uuid>` (проверить длины всех колонок и сериализаторов). Для новых внешних job можно сохранить прежний формат. Важнее: выбранный provider, provider_job_id и client_operation_id фиксируются до/при submit и не меняются при редактировании настроек. Восстановление по ключу направляется к провайдеру, выбранному при первой отправке. Маршрутизация status не зависит от текущего default provider. Контракт бизнес-сервисов submit/status сохраняется.

При нехватке длины поля вместо префикса — персистентная provider map с миграцией. В реализации выбрать один вариант после инвентаризации, не смешивать эвристики. Конфигурация API base URL не должна содержаться в пользовательском job id.

Порядок:

1. Инвентаризация, fixtures, локальный сервис, тесты; никаких production переключений.
2. VPS canary только синтетика, проверить влияние на relay и очистку.
3. На новой тестовой операции Story/Tutorial подтвердить полный импорт; без TTS/LLM/генераций.
4. Включить selfhosted для ограниченного списка новых внутренних операций.
5. После приёмки перевести новые операции; старые продолжают опрашивать hosted до terminal/expiry.
6. Rollback меняет default только для будущих задач. Уже принятые selfhosted задачи обслуживаются нашим сервером до завершения.

Запрещён автоматический fallback submit к hosted после timeout: собственная задача могла уже начаться. Допустим только доказанный отказ до приёма, с явной политикой расходов; в первом релизе fallback ручной. Секрет hosted не удалять до завершения старых задач. API base/ключи меняются через secret store и деплой, не через произвольные URL в админке.

## 12. Учёт затрат и наблюдаемость

Сейчас `model: ffmpeg-api` учитывается как условный внешний вызов; собственный CPU не должен продолжать списываться как реальный счёт этого провайдера. Добавить provider к usage/логам без изменения пользовательской оплаты. Разделить техническую себестоимость и продуктовый кредит/резерв; не обнулять автоматически весь резерв Story, который также покрывает речь и QA.

Для selfhosted писать wall seconds, CPU seconds, peak RAM, input/output bytes, queue delay, attempt count, exit code, image digest, job/operation ids. Денежную оценку VPS помечать как расчётную, не как invoice. API-ключи, токены, речь, содержимое субтитров и полный command с приватным текстом в общий журнал не писать.

Метрики: длина/возраст очереди, p50/p95 времени по профилю, успех/ошибки по кодам, OOM/timeouts, диск, очистка, занятые slots, crash recovery; отдельно качество relay до и во время нагрузки. Алерты: ready=false, диск ниже порога, orphan executor, очередь без прогресса, повторные OOM, ошибки cleanup.

Экономика: внешний расход сравнивать с реальным billable GB, не числом вызовов. На публичной странице провайдера опубликованы уровни $0.50/GB до 10 GB, $0.10/GB от 10 до 100 GB, $0.08/GB выше; точное применение ступеней и определение GB сверить по кабинету/счёту. Эти цены не доказывают, что отдельный VPS окупится при малой нагрузке. Формула решения: внешний счёт + внешнее хранение/трафик против добавочного VPS + трафик + хранение/backup + сопровождение + риска влияния на relay. Исторических объёмов и счёта в этом проходе нет; сумму экономии и срок окупаемости не заявлять.

## 13. Тесты и критерии приёмки

### Контракт и идемпотентность

- Реальный существующий `FfmpegApiService` работает с новым сервером: submit, status, ошибка, output import.
- Корпус всех генераторов команд репозитория, включая postprod, субтитры и несколько форматов, проходит parser/manifest без ручного изменения строк.
- 50 параллельных POST с одним ключом дают один job и один executor; разрыв ответа после commit затем повтор — тот же job; другой payload — 409.
- Повтор после TTL медиа не создаёт новый рендер. Restart не создаёт второй живой executor.
- Старый hosted id и новый selfhosted id опрашиваются правильно при переключении и rollback.

### Функциональная матрица

- Постер, crop/reframe 9:16/1:1/16:9, watermark, SRT/ASS с кириллицей/UK/EN, audio mix/fit.
- Цепочка минимум из двух команд с промежуточным файлом; несколько outputs; отказ второй команды не публикует первый как полный успех.
- Story 110 с: intro, основная часть, подарок, outro, картинка рассказчика, loudnorm, ducking, effects. Отдельно простой и сложный движущийся видеоряд.
- Видео со звуковыми импульсами/визуальными маркерами: измерить сдвиг после склейки, разрывы на стыках, длительности потоков. Технический допуск не хуже существующих продуктовых проверок; lip-sync не объявлять проверенным этим тестом.
- Проверять decoded frames/audio и метаданные; побайтовое совпадение с чужим энкодером не требовать. Отдельно хешируется конкретный полученный output для приёмки.

### Защита и сбои

- SSRF: IPv4/IPv6, redirects, rebinding, metadata, вложенные playlists; протокольный и filesystem escape; shell injection и symlink.
- Превышение каждого лимита, decompression bomb, заполнение диска, истёкшая ссылка, обрыв загрузки, отсутствующий фильтр, OOM, timeout, cancel во время публикации.
- Смерть API/worker на downloading/running/publishing, рестарт VPS, восстановление очереди, удаление orphan workspaces без чужих файлов.
- Приватный output недоступен без capability, чужому клиенту и после expiry; query-токен отсутствует в access logs.

### Нагрузка и эксплуатация

- Минимум 20 синтетических задач разных профилей подряд, без внешних AI-вызовов; все результаты и попытки учтены.
- Замерить wall/CPU/RAM/диск и relay baseline; под нагрузкой нет рестартов/OOM relay и роста p95 relay более чем на согласованный порог (предлагается 20% при достаточной выборке). При отсутствии достаточного трафика использовать бесплатный локальный тест relay, а не делать вывод по отсутствию ошибок.
- 24 часа canary и проверка cleanup; тест восстановления SQLite из консистентного online backup и проверки idempotency mapping; копирование только основного .db в WAL-режиме не считать backup. Backup каждые 15 минут, retention 7 дней, RPO ≤15 минут и целевой RTO ≤2 часа (проектные цели, проверить drill). После restore job-creation заблокирован до сверки с executor и продуктовой БД: потерянные последние ключи не должны вызвать повтор задач. Невосстановимые операции помечаются UNKNOWN и требуют ручной сверки; гарантию exactly-once при потере БД не заявлять. Ключи шифрования/HMAC восстанавливать отдельно, с ограниченным доступом. Медиа краткоживущие и в backup не попадают.
- CI затронутых проектов зелёный. Не деплоить неизменённые проекты. Операторская инструкция позволяет pause/drain/cancel/rollback без SSH-правки БД.

## 13.1. Обязательная вкладка в существующей админке «FFmpeg»

Это часть первого релиза, а не отложенный внешний dashboard. Страница `/ffmpeg` в существующем Next.js admin, файл `admin/src/app/ffmpeg/page.tsx`, один пункт «FFmpeg: обработка» в существующем каталоге `admin/src/lib/nav.ts` в группе эксплуатации/системы. Не создавать второй кабинет или прямой браузерный доступ к VPS. Навигационный тест проверяет единственность ссылки. Ссылка из очереди внимания ведёт на отфильтрованную страницу/задачу.

### Данные и экран

1. **Сводка:** выбранный провайдер новых задач, canary allowlist, режим приёма/worker, ready с конкретной причиной отказа, активные/ожидающие/ошибочные задачи, возраст старейшей задачи, свободный диск/квоты, CPU/RAM executor, версия образа. У каждого значения timestamp; устаревшие данные явно обозначены. Недоступный VPS не показывать как пустую очередь или «всё нормально».
2. **Задачи:** пагинация по курсору, 25 на страницу; фильтры провайдер, состояние, продукт, период, client operation id, job id. Столбцы: операция/продукт, статус/этап, очередь/исполнение, попытки, размер, код ошибки, время. По умолчанию последние 24 часа; запросы индексированы, без full scan на каждый refresh. Нет поиска по содержимому речи/субтитров.
3. **Карточка:** timeline состояний, id операции и провайдера, входные/выходные имена без секретных URL, технические метаданные/SHA-256, resource peaks, версия FFmpeg, ограниченный очищенный stderr (до 64 KiB). Отдельно показывать «выполнено, но файлы истекли/отозваны». Ссылки в существующие Story/Tutorial/сессии; не менять приёмку материалов.
4. **Лимиты и обслуживание:** текущие effective limits и их версия, очередь/диск, история изменений и режима drain. Секреты и произвольные команды не редактируются через этот экран. Нельзя менять hostname API/доступ к filesystem/образ контейнера из формы.
5. **Результаты:** preview/download только по явному действию и разрешению на продукт; без автоматического воспроизведения. Кнопка выдаёт короткую ссылку через backend, не раскрывает VPS key и исходные input URLs. Не встраивать недоверенный SVG/HTML; фото/видео отдавать с безопасным MIME. При необходимости отдельного media-read права отказ не блокирует просмотр метаданных.

Автообновление только видимой вкладки раз в 10 с с backoff при ошибке; отмена запросов при уходе. Никакого создания задач при GET, refresh или повторном открытии. Состояние фильтров в URL; клавиатурная навигация, читаемые ошибки/индикаторы и подтверждение результата действия обязательны.

### Доступ и серверная интеграция

Использовать текущую admin-session авторизацию (`backend/src/modules/admin-auth/admin-session.guard.ts`) и общую модель защиты мутаций. Не заявлять существование гранулярного RBAC, если его нет: при реализации добавить проверяемые серверные permissions `ffmpeg.read`, `ffmpeg.operate`, `ffmpeg.configure`, `ffmpeg.media.read` либо до появления RBAC разрешить их только владельцу/существующему superadmin. По умолчанию запрет; QA viewer не получает FFmpeg-доступ автоматически. Скрытая кнопка не считается проверкой прав.

Браузер → существующий backend `/api/admin/ffmpeg/...` → FFmpeg API. Ключ VPS остаётся backend secret. Защита CSRF/Origin для cookie-мутаций в соответствии с текущим admin auth; GET никогда не изменяет очередь. Тайм-аут запроса к VPS ≤5 с, мутации возвращают состояние/идентификатор операции, затем UI опрашивает результат. Интеграция не держит HTTP-запрос до завершения рендера.

Backend endpoints: GET `overview`, `jobs`, `jobs/:id`, `limits`; POST `pause`, `drain`, `resume`, `jobs/:id/cancel`, `jobs/:id/purge`, `jobs/:id/reconcile`, `limits` с expected revision, `routing` с canary allowlist и expected revision; POST `jobs/:id/download-link` для короткой ссылки. Реальные маршруты согласовать с существующим префиксом контроллеров, не дублировать `/api`. Мутации защищены operation id/idempotency key и CAS по версии. Старое состояние → 409 и обновление экрана.

### Разрешённые действия оператора

- **Сверить:** read-only status/by-key; не рендерит, не вызывает hosted submit, не сбрасывает UNKNOWN в queued. Истечение ссылок не повод создавать задачу.
- **Приостановить / продолжить worker**, **drain**: подтверждение с описанием влияния на активную и очередь; права operate. Resume невозможен при нехватке ресурсов/непройденной readiness.
- **Отменить:** только выбранную queued/active задачу, с подтверждением и причиной; отмена не обещает возврат денег и не удаляет продуктовую принятую версию.
- **Удалить временные файлы:** перечислить затрагиваемые outputs, показать необратимость и получить явное подтверждение; отозвать ссылки немедленно, завершение удаления отобразить отдельно. Не касаться Blob продукта, принятого Tutorial и эталонов.
- **Изменить лимиты/маршрутизацию:** только configure, в пределах верхних границ конфигурации деплоя; показать старое/новое и область действия. Рост concurrency выше 1 на общем VPS UI не разрешает. Изменения касаются новых задач; провайдер и профиль уже принятых неизменны. Перевод canary → default требует отдельного подтверждения владельца после критериев приёмки.
- **Повторный рендер:** в первом релизе кнопки нет. После терминальной ошибки оператор возвращается к исходной операции продукта; только её существующий поток может создать новую версию с новым ключом и собственной проверкой расходов/согласия. Не делать удобный обход через FFmpeg dashboard.

Для мутации хранить actor id, действие, job/operation id, причину, old/new revision, время, результат и correlation id. Событие запроса записать до отправки, исход подтвердить после сверки; при сетевом обрыве UI показывает «результат неизвестен, сверяем», а не повторяет действие с новым ключом. Журнал append-only для приложения, retention 90 дней; токены/команды/личные тексты исключены. Право просмотра журнала — read, изменение лимитов — configure.

### Приёмка вкладки

Обязательные E2E: owner/read-only/нет сессии; прямой вызов каждой мутации без права; CSRF/чужой origin; повтор клика/timeout/refresh не дублируют действие; cancel ↔ succeeded гонка; purge отзывает выданную ссылку; pause/drain переживают рестарт; stale revision даёт 409; VPS offline показывает stale/error; фильтры/пагинация; секреты отсутствуют в DOM/network ответах/логах. Проверить ограничения media-read, ссылки на исходную операцию и сохранность принятых сборок. CI admin/backend/ffmpeg-server включается только при изменениях соответствующих проектов.

## 14. Этапы и результат поставки

Этап A: корпус команд, зафиксированная матрица совместимости, проверка лицензий сборки/шрифтов, parser и контрактные тесты.

Этап B: API + SQLite + downloader + изолированный executor + приватные outputs + очистка; локальные интеграционные тесты без платных вызовов. Реализовать вкладку `/ffmpeg`, backend-proxy, права, операторский аудит и тесты раздела 13.1; без неё этап не завершён.

Этап C: развёртывание canary на существующем VPS, ресурсные лимиты, capability smoke, нагрузка и проверка relay; production default остаётся hosted.

Этап D: provider routing и раздельный учёт, внутренний тестовый импорт, ограниченный переход, проверка rollback; готовые версии не изменяются.

Этап E: после измерений — решение оставить общий VPS или вынести тот же образ и данные на отдельный сервер. Не строить распределённую очередь заранее.

Оценка для одного разработчика: 8–14 рабочих дней при отсутствии несовместимых фильтров и инфраструктурных блоков включая вкладку админки и fault-injection, плюс окно наблюдения. После этапа A уточнить оценку по корпусу команд и доступности sandbox на VPS. Это предварительная инженерная оценка, не обязательство по сроку. Контрактное ядро и миграция существующих операций важнее внешнего dashboard.

Поставка: исходники, Dockerfile с digest/версиями, конфигурация Dokploy/Compose с лимитами, env.example без секретов, миграции SQLite, tests/fixtures, инструкция backup/restore/drain/rollback, матрица совместимости, результаты замеров и обновлённый TODO. Лицензии FFmpeg/включённых GPL-компонентов и шрифтов приложить к образу, проверить обязательства выбранного способа распространения отдельно.

## 15. Условия завершения

Сервис считается заменой текущего FFmpeg-контура только при готовой вкладке админки по разделу 13.1 и после прохождения всей матрицы реально используемых команд, восстановления после сбоев, доказанной идемпотентности, приватности outputs и production canary. ## 16. Изменения после аудита ТЗ (редакция 1.1)

1. Устранён конфликт HTTP 410 с текущим polling: истечение outputs стало terminal-результатом совместимого status, без повторного рендера.
2. Разделены идентичность клиента и ключ авторизации; ротация ключей не теряет доступ к старым задачам.
3. Повтор принятого ключа проверяется раньше квот/readiness; добавлена сверка потерянного ответа по ключу.
4. Добавлены точные stop/drain/purge-контракты, отзыв ссылок и повторная проверка согласия перед импортом.
5. Шифрование распространено на payload с приватными командами, определён HMAC для сверки после удаления payload.
6. Уточнены общий deadline, TTL signed inputs, отсутствие предварительного скачивания очереди, filesystem quota и I/O-изоляция.
7. Указаны WAL-safe backup, RPO/RTO и запрет новых задач после restore до сверки; exactly-once при потере БД не обещается.
8. В первый релиз включена обязательная вкладка админки с правами, действиями, журналом и E2E. Оценка расширена до 8–14 рабочих дней плюс наблюдение.

Это аудит документа и контрактов по коду, не результат проверки ещё не написанного сервера. Обязательные условия, требующие замеров на VPS, остаются критериями реализации.
