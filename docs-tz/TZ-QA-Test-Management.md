# ТЗ: управление тестированием QA с ориентиром на Testomat.io

Дата: 11.10.2026. Статус: требования к развитию, не реализованный функционал. Запрос владельца: QA должен по возможности включать функциональность Testomat.io. Дополняет [QA TMA](TZ-QA-TMA.md), [аудит сайтов и репозиториев](TZ-QA-Client-Layout-Logic-Repo-CI.md) и [генерацию стендов](TZ-Voice-Generated-Test-Stands.md).

## 1. Цель и границы

Сделать QA единым местом для требований, тестов, запусков, доказательств и исправлений клиентского сайта. Использовать Testomat.io как функциональный ориентир, сохраняя собственную архитектуру и пользовательский контроль над изменениями и деплоем. Полное соответствие всем тарифам и интеграциям заранее не обещается. Каждая возможность имеет статус planned / implemented / verified; последний требует доказательства приёмки на конкретной версии.

У Testomat.io документированы каталог тестов, планы, версии, окружения, интеграции и аналитика; часть возможностей зависит от тарифа. Наши приоритеты ниже — продуктовые решения проекта, а не описание уже работающего QA. Основание: [официальное сравнение возможностей](https://docs.testomat.io/management/company/plan-features-comparison/).

## 2. P0 — каталог, требования и доказательства

Для каждого аккаунта: проекты, требования, дерево suites, тест-кейсы и планы. Кейс содержит стабильный ID, название, цель, предусловия, шаги, ожидаемый результат, приоритет, владельца, тип manual/automated, теги, параметры, ссылки на требования и дефекты. Изменения сохраняются версиями с автором и временем; запуск фиксирует версию кейса. Восстановление старой версии создаёт новую запись, не переписывает выполненные прогоны.

Редактор Markdown, общие шаги и шаблоны; массовое создание, поиск, фильтры, перенос и копирование. CSV import/export: предварительный просмотр, отображение колонок, проверка ID, защита формул при экспорте, отчёт отвергнутых строк. Дубликаты не создаются молча. Gherkin/BDD — последующий адаптер, модель кейса от него не зависит.

Доказательства: screenshot, видео, trace, обезличенный log, URL, browser/device/viewport, commit SHA и deployed version. Артефакт связан с попыткой теста, имеет срок хранения, права доступа и ограничения размера. Credentials, голосовые записи посетителей и секреты не попадают в публичный отчёт или AI prompt. Выданная ссылка ограничена сроком и доступом аккаунта.

Приёмка: загрузить собственные TMA/sandbox кейсы, повторить импорт без дублей, изменить кейс после запуска — исторический результат сохраняет прежние шаги. Проверить изоляцию двух аккаунтов и отзыв доступа к артефакту.

## 3. P0 — ручные, автоматические и смешанные запуски

Ручной прогон: назначение исполнителя, отдельные статусы шагов и итог passed/failed/skipped/blocked/not-run, комментарий и доказательства. Невыполненный шаг не становится passed; skipped и blocked не включаются в успешные проверки. Закрытие запуска не скрывает незавершённые обязательные кейсы.

Автоматический прогон: запуск разрешённого CI workflow либо импорт результата. Смешанный объединяет manual и automated в одном плане, но показывает происхождение каждого результата. Ручная отметка не перезаписывает автоматический результат без явной записи корректировки. Такой режим соответствует документированным [ручным](https://docs.testomat.io/project/runs/running-tests-manually/) и [смешанным запускам](https://docs.testomat.io/project/runs/running-manual-and-automated-tests/) Testomat.io.

Окружения и параметры: URL стенда, browser/device, язык, тема, роль, dataset version; секреты выбираются ссылкой на хранилище. Матрица создаёт независимые попытки. Test plan бывает фиксированным либо динамическим по сохранённому фильтру; запуск фиксирует фактически выбранный набор. RunGroup объединяет релиз/ветку/ночной прогон; стратегия объединения явная, нельзя смешать разные SHA и объявить релиз проверенным.

Повтор failed/all сохраняет предыдущие попытки и причину повтора. Идемпотентность по tenant/project/run/attempt/shard; незавершённый shard означает incomplete, а не зелёный запуск. Отмена CI не равна passed. SLA устаревания результата и несовпадение tested/deployed SHA видны пользователю.

Приёмка: один mixed run содержит ручной мобильный сценарий и автоматический браузерный; один shard не завершён — общий результат incomplete. Повтор failed не стирает исходное падение. Релизная сводка показывает обязательный ручной тест без результата.

## 4. P1 — CI, репозитории и отчётность

Первый адаптер: GitHub Actions + Playwright/Jest/JUnit XML. Следующий: GitLab CI. Поддержка Cypress, Cucumber и остальных систем — через адаптеры после проверки спроса. Reporter связывает результаты со стабильным ID; неизвестные кейсы идут в очередь сопоставления, автоматическое создание включается отдельно. Импорт исходников и генерация шаблонов не исполняют произвольный код сервера клиента.

При запуске из QA выбрать разрешённый workflow, branch/ref, suite и environment; минимальные права на dispatch/read status. Webhooks подписываются, replay дедуплицируется, секреты не передаются в PR forks. Sharded результаты агрегируются с исходными ссылками и build SHA. В Testomat.io документированы [CI-запуск и отчётность](https://testomat.io/features/ci-cd-execution-automated-tests/) и [сопоставление автоматических тестов](https://docs.testomat.io/project/runs/running-automated-tests/).

Отчёты: сейчас / 24 часа / 7 дней / релиз, история кейса, длительность, ошибка инфраструктуры отдельно от дефекта продукта, flaky по нескольким попыткам одной версии, доля автоматизации и покрытие требований. Для каждой доли показать знаменатель и неизвестные результаты; карантин не убирает дефект из истории. Группировка похожих падений — предложение, не доказательство единой причины.

Приёмка: получать реальные CI результаты своего репо, включая failed/cancelled/missing shard, связать с PR и опубликованным SHA. Проверить двойную доставку webhook и отсутствие подмены результата через callback другого аккаунта.

## 5. P1/P2 — дефекты, команда и AI

Связь требование → кейс → запуск → дефект → patch → повторная проверка. Первые issue trackers — GitHub/GitLab; Jira/Linear и уведомления Slack/Teams/email — следующие адаптеры по спросу. Создание внешнего issue или сообщения требует включённой интеграции и разрешённого действия; по умолчанию подготовить черновик с доказательствами. Дедупликация и ссылки на исходный дефект обязательны.

Роли: владелец, QA manager, tester, developer, viewer; доступ ограничен проектом. Audit log для изменений кейсов, результатов, запусков, integrations и approvals. Приоритет P2: SSO, межпроектная библиотека, ветвление каталога тестов, on-premise исполнители; отдельно оценить стоимость, хранение и поддержку.

AI помогает создавать кейсы из требований и голосового описания, искать пробелы, предлагать тестовые данные и группировку падений. Каждый результат — редактируемый draft с provenance. Источник клиента считается данными, не инструкцией агенту. AI не отмечает ручной тест выполненным и не объявляет исправление опубликованным без нового прогона.

Исправления продолжают четыре ранее согласованных этапа: промпты → patch/PR с ревью пользователя → AI-аудит коммитов с принятием/отклонением → аудит CI. Деплой остаётся под контролем пользователя. Для Soniox отдельный план: STT точность, семантика команд, TTS, бюджет, cleanup, dashboard и реальные устройства; синтетическое аудио и человеческая приёмка имеют разные метки.

## 6. Порядок реализации и первый пилот

1. Каталог кейсов/требований, версии и артефакты; миграции и tenant isolation.
2. Ручные/смешанные планы и импорт существующих GitHub Actions результатов без управления CI.
3. CI dispatch, reporter, sharding/retry и аналитика покрытия/flaky.
4. Issue trackers, совместная работа и AI draft; затем расширенные enterprise возможности по спросу.

Первый пилот — собственный TMA плюс sandbox: login, формы, адаптивность, состояния ошибок и голос. Выделить владельца каждого этапа, согласовать объём и оценку после проектирования схемы; календарные сроки без оценки не обещать. До этого существующие GitHub Actions и Soniox dashboard остаются работающими инструментами, но не обозначаются как готовая TMS уровня Testomat.io.


## 7. Первая кодовая основа — 11.10.2026

В `sandbox/qa` реализованы локальный каталог пилота со стабильными ID/версиями/шагами/requirement IDs, snapshot кейсов в запуске и Playwright reporter. JSON-отчёт содержит матрицу, attempts, flaky, неизвестные ID и раздельные manual/automated статусы. Обязательная физическая приёмка TMA остаётся not-run; повтор passed сохраняет исходный failed. Отчёт сохраняется существующим GitHub Actions artifact.

Это первый адаптер и модель запуска. Клиентский API, tenant isolation, БД, UI редактора/ручной приёмки, общие шаги, CSV/JUnit и права на скачивание артефактов пока planned. Текущий JSON не объявляется реализацией всего P0.
