# ТЗ: создание стендов и mock API с кликабельным UI по голосу

Дата: 10.10.2026. Статус на 14.10.2026: шаблонный MVP реализован в коде; полная голосовая генерация запланирована. Связано с `TZ-QA-Client-Layout-Logic-Repo-CI.md`, `TZ-QA-TMA.md` и голосовым управлением Soniox.

## 1. Цель и исходный пример

Пользователь голосом или текстом описывает небольшой сайт/кабинет/API. Система превращает описание в проверяемый контракт, создаёт изолированный стенд с кликабельным UI и mock API, проверяет его и предлагает исправления. Стенд подходит для экспериментов, обучения AI helper и регрессионного QA.

Владелец указал пример уже сделанного стенда для OnlyFans. В текущем checkout исходники с этим названием не обнаружены. ТЗ использует этот пример как требуемый формат результата; фактические компоненты и совместимость переиспользуемого стенда ещё нужно проверить. Не предполагается доступ к реальному API OnlyFans или использование реальных данных клиентов.

## 2. Использование в проекте

Tutorial получает воспроизводимый сайт для обучения входу, заполнению форм, навигации и обработке отказов; набор действий не зависит от внешнего сайта. QA получает изолированную репродукцию дефектов, эталонные состояния интерфейса и контрольные ответы API. AI helper проверяется на новых экранах, намерениях и ролях до подключения к клиентскому сайту. Собственный TMA — первый пациент: стенд воспроизводит проблемные экраны и состояния, но не считается доказательством исправления production без проверки настоящего TMA.

Коммерческий вариант: заказчик создаёт демонстрационный кабинет/интеграцию до разработки, экспортирует согласованный контракт и принимает сценарии. Генерацию стенда и дальнейший аудит можно учитывать раздельно в лимитах и биллинге. Это гипотеза продукта, не прогноз выручки.

## 3. Путь пользователя

1. «Создай кабинет с логином, списком заказов и фильтром; редактор и администратор; API с пагинацией; иногда сервер отвечает 429».
2. Soniox распознаёт речь; UI показывает транскрипт и оценку уверенности. Низкая уверенность или противоречие → уточнение. Можно редактировать описание текстом.
3. Планировщик предлагает короткую спецификацию: экраны, сущности, поля, роли, запросы, сценарии и ограничения. Неуказанные детали помечаются предположениями; неоднозначности влияющие на доступ/данные не принимаются молча.
4. Пользователь подтверждает создание. Система показывает preview URL, используемую версию, mock-режим, тестовые роли и состояние генерации.
5. Пользователь кликает или говорит «добавь поле телефона», «покажи ошибку сети», «проверь мобильную версию». Система предлагает изменение и ожидает подтверждения перед применением.
6. Аудит выдаёт замечания с доказательствами; после исправления запускаются затронутые проверки и регрессии. Доступны откат, сброс данных, экспорт и удаление стенда.

Голос — альтернативный способ ввода, не условие использования. Не пересоздавать стенд после каждого partial transcript. Повторная команда с тем же id не создаёт второй платный стенд.

## 4. Каноническая спецификация

Версионированный документ включает standId, владельца/tenant, язык, исходное описание, подтверждённые требования и предположения, сущности и поля, ограничения, связи, синтетические fixtures, API-контракт, роли, экраны, переходы и сценарии ошибок. Каждый экран и endpoint получает стабильный id для аудита и диффов.

Для endpoint обязательны method/path, schema запроса и ответа, статусы, роль, изменение состояния, пагинация/фильтры, сценарий задержки/отказа. Для формы — поля, подписи, validation, submit, loading/error/success, правила повторного клика. Действия интерфейса привязаны к endpoint или явно локальному действию. Нельзя выдавать статический макет за рабочий API.

OpenAPI и UI строятся из одного контракта. Mock не доказывает соответствие реальному стороннему сервису; imported OpenAPI хранит источник и версию. Несовместимые изменения контракта отмечаются до применения.

## 5. Архитектура и границы выполнения

Soniox → распознанный текст → структурированный план → валидатор контракта → подтверждение → генерация из проверенных шаблонов → mock engine и UI → проверки → preview. LLM не получает production credentials и не выполняет произвольные команды.

Первый этап использует существующий sandbox и шаблоны: статический UI, изолированный mock engine, JSON state и предсказуемые HTTP-ответы. Engine может работать в браузере для простого preview, но тогда явно обозначается, что API доступен только внутри preview. Для внешних HTTP-клиентов необходим серверный адаптер с тем же контрактом и разрешёнными методами.

Отдельный VPS не является обязательным условием проектирования/MVP. Серверное выполнение больших стендов допускается только после аудита ресурсов и выбора изолированного worker/container. При shared worker — отдельное хранилище и ограничения CPU/RAM/времени/размера на tenant. Не запускать LLM-код в процессе основного API.

## 6. Mock и состояние

Детерминированный seed, синтетические имена/контакты, фиксируемые часы и сценарии; reset возвращает baseline. Поддержать GET/list/detail, POST/create, PATCH/update и DELETE с воспроизводимыми эффектами. Ошибки: validation, 401/403, 404, 409, 429, 500, timeout, slow response, empty result, offline и повторная отправка.

Роли/login моделируются демонстрационными учётками и server-side проверкой mock API; скрытая кнопка не считается контролем доступа. Реальные логины/пароли запрещены по умолчанию. Tokens отделены от production и ограничены стендом. Reset/replay, создание и изменение сохраняются в журнале без секретов.

## 7. UI

Рабочие ссылки, кнопки, формы и состояния; подтверждение опасного удаления; отображение loading/error/empty/success. Адаптивность минимум 360/390/768/1440 px, длинные тексты, разные языки, светлая/тёмная тема где поддерживается шаблоном, клавиатура и читаемые labels. Полезные элементы: выбор роли и сценария, список запросов с безопасными payload, просмотр ответа, reset, версия, переключение ошибки/задержки.

Постоянная метка «Тестовый стенд / синтетические данные». Внутренние пути, stack trace и технические инструкции не показывать обычному пользователю. Никакие платежи, сообщения людям или реальные внешние записи не выполняются без отдельного подключения и явного действия пользователя.

## 8. Автоматический аудит

После создания и каждого patch:

- API: схема запросов/ответов, все объявленные статусы, role checks, CRUD, pagination/filter/sort, идемпотентность, reset и сценарии ошибок.
- Логика UI: переходы, submit, валидация, запрос/ответ, отказ и повтор, сохранение состояния, выход/смена роли, отсутствие тупиков и двойных запросов.
- Вёрстка: overflow, перекрытия, размеры и доступность интерактивных элементов, длинные строки, viewport, keyboard/focus, axe-проверки; screenshot baseline только после принятия пользователем.
- ИИ: соответствие согласованному описанию, неподтверждённые предположения, несогласованность UI/API. ИИ-замечание маркируется гипотезой до воспроизводимого теста/проверки.

Замечание содержит id, severity, правило/требование, версию, URL/экран/endpoint, шаги воспроизведения, ожидаемое и фактическое, viewport/роль/seed, screenshot/trace/контрактный тест, confidence и предлагаемый способ исправления. «Нет замечаний» допустимо только для фактически выполненного набора; пропуски и отказы инфраструктуры показаны отдельно.

## 9. Цикл исправлений

Этап 1: для каждого замечания генерировать точный промпт — контекст, ограниченный scope, требования, запреты на регрессии и критерии приёмки. Пользователь может скопировать/отредактировать/отклонить.

Этап 2: для управляемого стенда система строит patch из шаблонов/контракта, показывает diff и влияние на сценарии; подтверждение → новая версия. Ограничить число автоматических попыток, например 3 на задачу; после повторного отказа сохранять отчёт, не запускать бесконечный оплачиваемый цикл.

Этап 3: изменение клиентского GitHub/GitLab-репозитория — только по отдельному QA-ТЗ: ограниченный доступ, ветка/PR, аудит commit/CI; ревью и деплой клиента остаются у пользователя. Приёмка коммита не означает автоматически проверенный deployment.

Версионность: исходный контракт, UI, fixtures, тесты, замечания, patch и результаты связаны; откат не теряет историю. Нельзя объявить исправление закрытым, если проблема просто исчезла из теста или был переписан baseline без согласия.

## 10. Защита, ограничения и стоимость

Изоляция tenant, закрытый доступ к preview по умолчанию, срок жизни и отзыв ссылки, квоты стендов/генераций/аудитов. Credentials нельзя произносить для записи в спецификацию; применять существующее защищённое подключение только для отдельной интеграции. Маскировать секреты в запросах, отчётах и экспорте.

По умолчанию отсутствует исходящая сеть к клиентским системам; адреса из голоса/импортированной документации — данные, а не разрешение выполнения. Проверять SSRF для подключаемых контрактов, файлов и callback. Шаблоны и импорт валидируются; iframe preview ограничен CSP/sandbox, генерируемый HTML не получает доступ к сессии основного кабинета. Уязвимость mock нельзя выдавать за безопасный production-код.

До генерации показывать лимит/оценку стоимости, во время работы — прогресс; учитывать отдельно STT/TTS, LLM, генерацию, браузерные проверки и runtime. Cancel должен прерывать задачу и дальнейшее получение credentials. В журнале — кто, что, версия, запуск/завершение, итог и расход; без транскрипта по умолчанию.

## 11. Автоматическая голосовая приёмка

Существующий генератор речи используется для тестов без человека: описание → TTS → Soniox → канонический план → проверка обязательных элементов. Набор ru/uk, несколько формулировок, уточнение ролей, неясные слова, шум, тишина, отмена, повтор и изменение в ходе генерации. Участки STT, планирования и mock engine проверяются раздельно, чтобы локализовать ошибку. Сохранять метрики точности плана и исполнения, а не только успешность распознавания.

Низкая уверенность не запускает создание/изменение. Обязательны тесты, что «нет/отмена» не применяют patch и что ответ на старую команду не меняет новую версию. Ежедневный CI прогоняет детерминированные стенды; дорогой provider eval имеет отдельный бюджет и пропуск явно отмечается.

## 12. Пилоты и этапы

М1: редактор описания и контракт, подтверждение, вопросы, dry-run и экспорт. М2: один шаблон creator-кабинета и рабочий mock, seeded reset, preview, ограничение доступа. М3: API/browser/layout аудит, промпты, patch, регрессии и откат. М4: интеграция Tutorial/QA/AI helper, ежедневный CI, multi-template, импорт OpenAPI и пользовательский репозиторий по существующему ТЗ.

Пилот TMA: воспроизвести проблемные формы/карточки/длинные строки, проверить мобильные размеры и реальные состояния API, затем проверить исправление в настоящем TMA. Пилот creator-кабинета по образцу OnlyFans: демонстрационный login, список записей, фильтр/пагинация, редактирование, две роли, 403/429/timeout и reset. Название и API-контракт стороннего сервиса не считаются подтверждёнными без источников/артефактов.

## 13. Критерии завершения MVP

Новый пользователь без кода создаёт стенд из голосового описания и может выполнить все согласованные сценарии кликами. UI и ответы API соответствуют одной принятой версии. API реально выполняет заявленные изменения состояния. Неясный запрос приводит к уточнению; повтор не создаёт дубликат.

Аудит обнаруживает специально внесённые дефекты формы, доступа и переполнения; промпт/patch содержит воспроизводимый критерий. После принятия исправления исходная проверка и регрессии проходят; отклонение сохраняет версию. Reset и replay воспроизводят результаты. Экспорт содержит контракт, исходники, fixtures, проверки и инструкции без секретов.

Ни один тест не обращается к реальной пользовательской системе по умолчанию. Чужой tenant не читает/не изменяет стенд. Cancel останавливает новые операции. Отчёт различает пройдено/не пройдено/не запускалось; пользователь видит лимиты и стоимость.


## 14. Размещение в продукте и анонс (14.10.2026)

Клиентская точка входа — **QA → «Стенды»**, рядом с каталогом кейсов и прогонами. Маршрут кабинета: `#/sites/:siteId/qa-stands`; на 14.10 реализованы шаблонный пилот (§15) и ограниченный генератор с Soniox (§16). Инструкция: [QA-STANDS.md](../doc/QA-STANDS.md). Не создавать отдельные генераторы для QA, Tutorial и AI helper: все три используют один стенд, его контракт, версию и доказательства проверок.

В списке показывать название, связанный клиентский сайт, версию, состояние создания, результат последней проверки и срок хранения. Карточка стенда содержит описание/голосовой ввод, подтверждение контракта, preview UI, API/OpenAPI, синтетические данные и роли, режимы ошибок/задержек, reset/replay, аудит, историю изменений и экспорт. В Tutorial стенд выбирается как учебное окружение; в AI helper — как окружение проверки действий. Результат на mock не заменяет проверку реального сайта.

Глобальная админка получает **«Mock-стенды»**: очередь и активные задания, ошибки, расход и лимиты по аккаунтам, ресурсы worker, сроки хранения, остановка и удаление с журналом действий. Reddit Research/Content Studio остаётся отдельным модулем; его fake AI — инструмент тестирования, а не генератор клиентских стендов.

### Когда анонсировать доступность

Для анонса полной готовности, без beta-ограничений, требуется выполнение критериев §13 и сквозная приёмка: новый стенд создаётся из описания, UI и API работают по одной версии контракта, роли и аккаунты изолированы, reset воспроизводим, аудит обнаруживает контрольные дефекты, исправления проходят повторную проверку, экспорт доступен. В релизном сообщении перечислить поддержанные шаблоны и ограничения; при частичном покрытии обозначать пилот/beta, а не общую готовность.


## 15. Шаблонный пилот MVP (14.10.2026)

Маршрут QA → «Стенды»: `#/sites/:siteId/qa-stands`. Описание, название и строка «Поля: Название, Статус» задают контракт фиксированного шаблона records. Перед созданием требуется подтверждение. Остальные пожелания сохраняются в описании, но не объявляются реализованными. Платный LLM и исполнение пользовательского кода не используются.

Реализованы Postgres account/site scope, идемпотентное создание по requestId, демонстрационные viewer/editor/admin, список/поиск, создание/удаление, 403/422/429/500/empty, reset, экспорт JSON-контракта и семь проверок engine без изменения сохранённых данных. Ограничения: 100 записей, восемь полей, 500 символов на значение. Стенды загружаются по 50; доступно удаление.

API кабинета `/qa/sites/:siteId/stands`: GET список, POST plan, POST создание, GET/:id, DELETE/:id, POST/:id/check и POST/:id/reset. REST: GET/POST `/:id/mock/records`, DELETE `/:id/mock/records/:recordId`, с настоящими HTTP-статусами. POST `/:id/mock` возвращает envelope `{status,data,revision}` для отображения смоделированных ошибок. Все маршруты требуют авторизации кабинета; демо-роль не повышает продуктовые права. Viewer кабинета читает, QA admin/owner меняет данные. Публичного preview/API нет.

Миграция `20261022090000_qa_stands` и deployment backend/assist обязательны до production-приёмки. Выбор роли моделирует вход, а не проверяет настоящий пароль. Этот пункт описывает базовый v1-шаблон; генерация UI, голос и OpenAPI добавлены в §16. Пока нет PATCH, latency/replay, истории аудита и интеграций Tutorial/AI helper. Полная приёмка §13 остаётся открытой; этот релиз — ограниченный шаблонный пилот. Проверки engine не заменяют браузерный аудит вёрстки.


## 16. Генеративный контракт и Soniox (14.10.2026)

Дополнительно к старому шаблону records доступна генерация Gemini из свободного описания. Результат — декларативный контракт v2: до 5 сущностей × 8 полей (text/number/email/select), до 10 экранов (list/form/dashboard), существующие ссылки переходов и явные допущения. React строит интерфейс из этого контракта; сервер валидирует типы, обязательность, enum, роль и entityId. Неизвестные ссылки/типы и дубликаты отвергаются. Произвольный HTML/JS/внешние запросы не исполняются; неподдержанные требования должны быть указаны в допущениях. Это генерация в рамках поддержанной схемы, а не реализация любой бизнес-логики.

В UI пользователь просматривает контракт и допущения, затем подтверждает создание; распознавание/генерация сами не создают стенд. Старые records/v1 остаются совместимыми. Для generated/v2 mock REST GET/DELETE принимает `?entity=:entityId`; POST — `{entityId,role,values}`. Записи разных сущностей разделены; сброс возвращает пустое синтетическое состояние. Сохраняются экспорт контракта и удаление.

POST `/qa/sites/:siteId/stands/generate` — ИИ-план; POST `…/voice` — base64-аудио. Голос: MediaRecorder до 60 секунд либо файл до 1 МБ, RU/UK/EN hints. Сервер определяет формат по заголовку файла, ограничивает JSON только на этом пути, очищает decoded buffer в finally, использует существующий Soniox-клиент с удалением временных артефактов. Текст редактируется перед генерацией; низкая уверенность требует визуальной проверки. Микрофон освобождается на stop/error/unmount. Реальный микрофон разных устройств требует отдельной аппаратной приёмки.

Вызовы требуют QA admin/owner и сайта своего аккаунта. Бюджет обучения резервируется до провайдера и корректируется по факту; оплаченные невалидные ответы/тишина учитываются. Новые операции qa-stand-plan/qa-stand-stt имеют продукт QA. Soniox events сохраняют account/site/actor и источник маршрута; ни аудио, ни описание не помещаются в журнал расходов. Дефолт TTS Nova не меняется.

Планировщик не делает скрытых повторных платных запросов; неверный контракт или отказ провайдера оставляет описание пользователю. Проверки engine подтверждают модель данных/API; визуальный браузерный аудит и сложные сценарии CI/клиентского репозитория остаются отдельными этапами.

### Экспорт действующего API (2026-10-14)

В обоих видах стендов добавлена кнопка «Скачать OpenAPI». Файл OpenAPI 3.0.3 описывает REST GET/POST/DELETE, обязательный выбор сущности для генеративного стенда, поиск, сценарии ошибок, демонстрационные роли и ответы. Значения полей передаются строками в массиве `values` в порядке `x-stand-fields`; типы и обязательность полей указаны в этом расширении. При импорте нужно указать адрес backend и настроить действующую авторизацию кабинета с доступом к аккаунту/сайту. Экспорт не предоставляет публичный доступ и не содержит токены или сохранённые записи. Исходники, независимый preview URL и полная генерация бизнес-логики остаются будущими этапами.

### Чтение для участников QA (2026-10-14)

Интерфейс чтения использует `GET /qa/sites/:siteId/stands/:id/mock` с `entity`, `q`, `scenario`. Ответ — envelope `status/data/revision`, поэтому смоделированные ошибки показываются в UI без потери ответа. Маршрут требует QA_READ, выполняет только GET с демонстрационной ролью viewer и не меняет revision. Настоящий REST `GET .../mock/records` сохраняет действующие HTTP статусы. POST envelope и операции записи/удаления/сброса требуют QA_WRITE; демонстрационная роль не повышает права аккаунта.


## Расширение от 15.10.2026: TikTok mock и форма создания приложения

Следующий доменный пресет после Reddit, на общем workflow engine. Детали Developer Portal/API перед реализацией сверить с официальной документацией; ниже целевые тестовые сценарии, не обещание полного совпадения с текущим TikTok.

1. **Форма создания приложения:** название, описание, иконка-placeholder, website, privacy/terms URL, redirect URI, платформы, products/scopes, тестовые пользователи. Не собирать настоящие client_secret, пароли и cookies; URL сохранять без серверного открытия.
2. **Валидация:** обязательные поля, неверные URL, дубли redirect URI, неподдержанный scope, конфликт версии, отказ сохранения. Все юридические страницы и галочки — имитация, не принятие настоящих соглашений.
3. **Workflow приложения:** draft → ready_for_review → in_review → approved/rejected, причина отказа, исправление, новая ревизия, сброс согласования после правок. Доступность видеоопераций зависит от статуса приложения и scopes.
4. **Фиктивные credentials:** явная маркировка MOCK для client_key/client_secret; сценарии выдачи, ротации, отзыва и истечения. OAuth consent/redirect — локальная имитация, без передачи настоящих ключей.
5. **Видео:** метаданные файла и заглушка загрузки, uploading/processing/failed/ready, подпись и настройки, согласование, очередь, scheduled/simulated_published. Настоящих публикаций и сетевых запросов к TikTok нет.
6. **Отрицательные ветки:** 401/403/429/500, таймаут, отмена, повтор действия, stale revision, отозванный scope, отклонённое приложение. При отказе данные не меняются.
7. **Приёмка:** браузерная форма + REST + engine проверки + сохранение/перезагрузка; кейсы Developer Portal и публикационного workflow. Для файлов, асинхронных задач и OAuth-экранов сначала расширить общий контракт и тесты.

Статус: roadmap, TikTok-пресет пока не реализован. Reddit-пресет не считается реализацией TikTok.
