# Реализация: Виртуальная студия, Этапы 1–3

Источник: `docs-tz/TZ-Virtualnaya-Studiya-i-AI-Vedushaya.md` §2–§6 (версия
1.2). По прямому решению владельца задачи Этапы 1–3 (референс-кадр +
видео-фрагмент → голосовой фрагмент → ИИ-анализ) реализованы **в один
проход**, ради экономии времени и бюджета. Этап 5 (привязка студии к
живому аукциону, оркестрация подсказок озвучки, SSE-эфир) **не входит**
в этот проход — самая рискованная и дорогая часть ТЗ, зависящая от уже
обкатанных Этапов 1–2.

Референс: пользователь предоставил рабочий проект SilverFinance
(архив, распакован при подготовке) — оттуда взяты форма вызовов Grok
image/video и ElevenLabs TTS, но код не скопирован буквально: viral4creators
— NestJS/Prisma, SilverFinance — Next.js, паттерны переведены, а не
перенесены.

## Что сделано

### Схема (Prisma), миграция

- `backend/prisma/schema.prisma`: `VirtualStudio`, `VirtualStudioVariant`,
  `VirtualStudioFragment` + энумы `VirtualStudioFragmentKind`,
  `VirtualStudioStatus` — по точной форме §2 ТЗ, плюс `BrandManifest.
  virtualStudioFragments` (обратная связь, без неё `prisma validate`
  отказал бы схему).
- **Найдено при реализации, не было в ТЗ**: у `VirtualStudioFragment` нет
  места для id асинхронной задачи провайдера (Grok `request_id`, Hedra
  `job_id`) — ни версия ТЗ, ни референс SilverFinance (там статус
  опрашивается по колонке самой студии/аукциона, не по отдельной таблице
  фрагментов) этого не предусматривают. Добавлено поле `providerJobId
  String?` — без него поллинг статуса видео-фрагмента был бы физически
  невозможен. Тот же приём, что `AvatarVideo.providerJobId` у пилота
  аватара.
- Миграция `20261204090000_virtual_studio/migration.sql` написана вручную
  (сеть до `binaries.prisma.sh` недоступна в песочнице разработки) — по
  образцу `20261130090100_greeting_briefs`.

### Backend — новый модуль `backend/src/modules/virtual-studio/`

- `grok-image.service.ts` — единственный действительно новый клиент:
  `POST /v1/images/generations` xAI (референс-кадр). Форма ответа не
  подтверждена реальным вызовом — читается защитно, тем же приёмом, что
  `HedraClientService`/`GrokVideoService` уже применяют для своих
  неподтверждённых полей. Требует проверки одним тестовым вызовом до
  прода.
- `virtual-studio.service.ts` — оркестрация: студии, варианты
  референс-кадра (Grok image + автовыбор первого варианта), видео-
  фрагменты (Grok — переиспользует существующий `GrokVideoService`;
  Hedra — переиспользует существующий `HedraClientService` напрямую, без
  `sessionId`, без единой правки в `actors/`, по правке §10.5.3 самого
  ТЗ), голосовые фрагменты (переиспользует `TtsProviderResolverService`
  целиком, без нового кода), ИИ-анализ (по образцу
  `AuctionAiAssessmentService`, не `VideoAuditService` — та же причина:
  произвольный внешний URL, не сессия, не пользовательский тариф).
- `virtual-studio.controller.ts` — `admin/virtual-studio`, точно по
  таблице эндпоинтов §5 ТЗ, `AdminSessionGuard` + `assertOperator` на
  каждом методе, `RateLimit` на трёх дорогих вызовах (вариант, видео,
  анализ) — тот же лимит, что у `actors.controller.ts` (5/15с).
- `virtual-studio.module.ts` — по образцу `actors.module.ts`.
- Флаг Hedra (`VIRTUAL_STUDIO_HEDRA_ENABLED`, §3.5) — через уже
  существующий `PlatformSettingsService`, не отдельная таблица; два
  простых эндпоинта прямо на контроллере студии (не заведён отдельный
  сервис по образцу `AdminVoiceoverSettingsService` — оверкилл ради
  одного булева значения).
- `common/ai-pricing.ts` — новая модель `grok-imagine-image`
  ($0.02/img, `docs.x.ai/developers/pricing`, сверено 2026-09-21 в самом
  ТЗ) и четыре новые операции (`virtual-studio-image/video/voice/
  analysis`) — отдельные строки в отчёте расходов, не смешанные с
  `avatar-generation`/`voiceover`/`auction-assessment`, которые
  переиспользуют тот же провайдерский код, но для другой фичи.
- `config/configuration.ts` — `config.grok.imageModel`
  (`GROK_IMAGE_MODEL`, по умолчанию `grok-imagine-image`).
- `app.module.ts` — `VirtualStudioModule` зарегистрирован.

### Admin-фронтенд

- `admin/src/app/virtual-studio/page.tsx` — список студий, детали
  выбранной (варианты референс-кадра с выбором/удалением, три формы
  создания фрагментов, список фрагментов с поллингом статуса видео каждые
  4с, тот же интервал, что у `/actors`).
- `admin/src/app/settings/page.tsx` — карточка «Hedra для видео-
  фрагментов студии» (чекбокс, по умолчанию выключен).
- `admin/src/components/AdminNav.tsx` — пункт «Виртуальная студия» в
  группе «Генерация».
- `admin/src/lib/types.ts`, `admin/src/lib/endpoints.ts` — типы и
  функции запросов ко всем эндпоинтам §5.

## Осознанные упрощения (не в ТЗ буквально, добавлены при реализации)

1. **Hedra видео-фрагмент требует существующий VOICE-фрагмент**
   (`voiceFragmentId` в теле запроса), а не текст реплики заново. §4.2 ТЗ
   говорит «синтезировать аудио под лип-синк ДО вызова Hedra» — реализовано
   так, чтобы это была ТА ЖЕ реплика, что оператор уже наговорил и
   прослушал через «Озвучить» (§3.3), а не второй, потенциально
   рассинхронизированный синтез той же фразы отдельным вызовом.
2. **Разрешение видео не хранится отдельной колонкой** на фрагменте (её
   не заводит и сама схема §2) — расход по факту готовности логируется с
   разрешением по умолчанию (720p), даже если оператор явно запросил
   другое. Приемлемое приближение для admin-only инструмента с низким
   объёмом вызовов; при желании точного учёта — колонка `resolution`
   легко добавляется отдельной аддитивной миграцией.

## Ограничение среды разработки (диск/сеть)

`npm install` в этой песочнице не проходит (`prisma generate` в
`postinstall` не может достать бинарники) — полный `tsc`/`prisma
validate`/`prisma migrate` в рамках этой сессии не запускались.
Верификация — точечная (`tsc --noEmit` на каждый новый/изменённый файл
глобально установленным компилятором, с фильтрацией ожидаемого шума
«не могу найти типы без node_modules») плюс ручной построчный обзор всех
имён полей Prisma против только что написанной схемы. Реальные ошибки
типов (в первую очередь — соответствие `VirtualStudioService`
сгенерированному Prisma Client, который появится только после `prisma
generate` на реальном стенде) этим способом не ловятся полностью —
первый `npm run build`/`tsc` на настоящем CI обязателен перед мержем.
