# Аудит двух ТЗ по GREETING_VIDEO и план этапов

Версия 1.0 · 2026-09-22 · Предмет аудита:
`TZ-Greeting-Video-Landing.md` (версия 1.1) и
`TZ-Greeting-Video-Upgrade-40-Features.md` (версия 1.1).

Метод: каждое утверждение обеих ТЗ о существующем коде проверено
чтением этого кода. Там, где утверждение не подтвердилось, ниже стоит
точная ссылка `файл:строка` и цитата — не «кажется, неверно». Рыночная
часть обеих ТЗ (разделы 2А–2Д компаньона) **не** перепроверялась: у
этого аудита нет доступа к тем же поисковым данным, и объявлять её
верной или неверной было бы таким же необоснованным утверждением, какие
он ищет. Она принята как есть и на решения ниже не влияет — все
находки чисто инженерные.

Решения владельца продукта, зафиксированные до составления плана:

| Вопрос | Решение |
|---|---|
| `greeting.viral4creators.app` | тот же проект `landing/`, поддомен через host-rewrite в middleware |
| Hedra (раздел 4 компаньона) | решение отложено — план строится так, чтобы оно НЕ блокировало лендинг |
| Монетизация (фичи 27–33) | вне этого прохода: `PLANS_BILLING_ENABLED` остаётся выключенным |
| Групповой режим (фичи 10–18) | отложен, спланирован отдельным этапом |

## 1. Находки — по убыванию последствий

### 1.1 Блокер. Поздравление сегодня нельзя опубликовать публичной страницей вообще

`backend/src/modules/shared-video/shared-video.service.ts:123`:

```ts
const product = session.productInformation;
if (!product?.productName) {
  throw new BadRequestException(
    'No product information in this session — add the product first',
  );
}
```

У сессии GREETING_VIDEO `productInformation` нет по определению — это
другой тип проекта, без товара. Значит `SharedVideoService.create()`
отвергает любое поздравление, и публичной страницы `/video/[id]` у
поздравления не существует ни одной.

Компаньон-ТЗ, раздел 1, строка таблицы «Публикация ролика»
утверждает: «Работает (переиспользует `PublicationService`,
`productName`-поля везде опциональны)». Это **наполовину верно и
наполовину нет**, и разошлись как раз две разные службы:

- `PublicationService` (очередь на YouTube/TikTok) — действительно
  работает: `publication.service.ts:118` использует `product?.productName`
  через опциональную цепочку;
- `SharedVideoService` (публичная страница ролика и вся петля шеринга) —
  не работает, см. цитату выше.

Последствия шире, чем одна строка таблицы. От публичной страницы
зависят: витрина лендинга (раздел 5 ТЗ лендинга), фича №29
(реферальная петля на странице просмотра), фича №20 («магическая
ссылка» — надстройка над `landing/video/[id]`), фича №21 (QR на
страницу ролика). Четыре фичи из 40 и вся витрина стоят на службе,
которая для этого типа проекта возвращает 400.

Смежное, из той же проверки: `SharedVideoPage.productName` объявлен
`String` без `?` (`backend/prisma/schema.prisma`, модель
`SharedVideoPage`) — то есть NOT NULL на уровне БД, и одной правкой
сервиса дело не обойдётся, нужна миграция. А страница
`landing/src/app/video/[id]/page.tsx` рендерит товарную рамку
безусловно: `productName` уходит в `description` метаданных (строка 57),
в `og`-описание (110), в `alt` картинки (151), в блок названия (155) и
в блок цены (162–163). Для поздравления это либо пустая строка в
`<title>`-описании, либо имя получателя в роли «названия товара» —
оба варианта в выдаче Google выглядят одинаково плохо.

### 1.2 Фича №31 — не «S, инфраструктура уже есть», и она на критическом пути лендинга

Компаньон-ТЗ оценивает её как S и пишет «технически почти бесплатно
(`PublicationService` уже работает на GREETING_VIDEO без изменений), не
хватает: (а) поля `Project.type`/`occasion` в выдаче, (б) операторской
курации».

Фактический состав работ, по чтению кода:

1. Миграция `SharedVideoPage`: `productName` → nullable, новые колонки
   `projectType`, `occasion`, `featured`. Поля именно на этой таблице, а
   не join к проекту — снимок на момент публикации, это принцип самой
   модели (её доккомментарий про «страница обязана пережить TTL-уборку
   сессии»).
2. Ветка в `snapshotFromSession` для поздравлений: заголовок из брифа,
   а не из товара (находка 1.1).
3. Публичного **списочного** эндпоинта не существует вовсе. Есть только
   `GET /shared-video/:id` — одна страница по id
   (`landing/src/lib/shared-video-api.ts`, доккомментарий прямо это
   называет). Витрине нужен новый список с фильтрами
   `projectType` / `occasion` / `featured`, с пагинацией и кешем.
4. `PublicSharedVideoPage` на стороне лендинга — новые поля.
5. Страница `/video/[id]` — вариант для поздравления без товарной рамки
   (находка 1.1).
6. Чек-бокс курации в админке. Компаньон-ТЗ сам выносит его в раздел 7
   «не входит в 40» — то есть лендинг зависит от работы, которая
   формально не входит в список, который он же и реализует.

Честная оценка — **M**, и это первая задача всего плана, потому что без
неё раздел 5 ТЗ лендинга не может быть выполнен, а раздел 8 («витрина
показывает реальные ролики либо не рендерится вовсе») превращается в
«не рендерится никогда».

### 1.3 `Faq` нельзя переиспользовать как есть, и у переиспользования есть неочевидная цена

ТЗ лендинга, раздел 4 пункт 7: «FAQ — компонент `Faq`,
переиспользуется, свой набор вопросов». Компонент своего набора не
принимает:

```tsx
export function Faq() {
  const { dict } = useDictionary();
  ...
  {dict.faq.items.map((item, index) => {
```
(`landing/src/components/Faq.tsx`)

Он жёстко читает `dict.faq` из контекста локали. Добавить проп `items` —
работа на десять минут, но есть вторая, менее заметная сторона. В том же
файле:

```tsx
data-faq-index={index}
```

Это адрес, по которому ИИ-консультант прокручивает страницу, когда
бэкенд присылает `action {kind:'faq', faqIndex}`
(`backend/src/modules/assistant/actions.ts` валидирует диапазон против
главного словаря). Второй FAQ на другой странице с теми же
`data-faq-index` даст консультанту два разных ответа под одним номером.
Значит либо у виджета на странице поздравлений должен быть свой набор
действий, либо `AssistantWidget` на ней не должен присылать `faq`-
действия вовсе. Решать это надо до публикации страницы, а не после
первой жалобы «ассистент показывает не тот вопрос».

### 1.4 `HowItWorks` переиспользуется, но притащит иконки товарного пайплайна

Компонент действительно принимает набор шагов пропом
(`steps: StepsDict`, `variant`, `hrefBase` —
`landing/src/components/HowItWorks.tsx`), так что раздел 4 пункт 4 ТЗ
лендинга в этой части верен. Но внутри:

```tsx
function StepIcon({ n, size }: { n: number; size: number }) {
  return <IllustrationIcon name={`how-step-${n}`} size={size} />;
}
```

Имя файла иконки выводится из **порядкового номера шага**, а не из
содержания. Четыре шага поздравления (бриф → референсы → сценарий →
видео) получат `how-step-1…4` — иконки, нарисованные под «загрузите
товар», «выберите референс», «ИИ разбирает ролик», «проверьте
релевантность». Нужен либо проп с префиксом имени иконки, либо свой
набор `greet-step-1…4.svg`. Вторая правка того же компонента:
`hrefBase` ведёт на `/how-it-works`, у поздравлений такой полной
страницы нет — на ней ссылки должны быть якорями внутри страницы (`''`,
тот же режим, что уже используется на самой `/how-it-works`).

### 1.5 Лендинг не может импортировать словари фронтенда

Раздел 4 пункт 3 ТЗ лендинга: подписи поводов «переиспользуется, не
дублируется заново для лендинга — импорт из общего словарного файла».

Первая версия этого аудита утверждала, что причина — корневая
директория сборки на Vercel. Проверка в панели (`viral-landing` →
Build and Deployment) это **не подтвердила**: Root Directory = `landing`,
но «Include files outside the root directory in the Build Step» включено,
то есть файл из `frontend/` физически в сборку попадёт. Утверждение было
неверным и заменено на две настоящие причины.

**Первая — механизм словарей.** `landing/src/lib/get-dictionary.ts`
статически импортирует ровно пять своих файлов, строит из русского тип
`Dictionary` и держит `Record<Locale, typeof ru>`. Чужой словарь другой
формы в эту схему не встраивается без переписывания механизма, а
переписывать его ради подписей поводов — несоразмерно.

**Вторая, менее очевидная и более опасная.** В том же разделе панели
включено «Skip deployments when there are no changes to the root
directory or its dependencies». Правка, затронувшая только
`frontend/src/dictionaries/*.json`, лендинг переразвернуть не обязана —
и тогда визард показывает новую подпись повода, а лендинг продолжает
отдавать старую, пока кто-нибудь не тронет `landing/`. Молчаливое
расхождение двух витрин одного и того же списка — худший вид
рассинхронизации: его никто не замечает, пока не пожалуется
пользователь.

Это, впрочем, и не нужно. Подпись повода в визарде («День рождения») и
подпись плитки на лендинге — разные тексты по задаче: первая
функциональная, вторая продающая и нагруженная ключевыми словами. Копия
в словарях лендинга здесь не дублирование, а правильное разделение.
Единственное, что обязано совпадать буквально, — **коды** поводов
(`BIRTHDAY`, `WEDDING`…), потому что они уходят в query-параметр входа
в TMA. Их и стоит закрепить тестом на совпадение с `GREETING_OCCASIONS`.

### 1.6 ТЗ описывает маршрут, заказ — поддомен; это не одно и то же

ТЗ лендинга, раздел 2: страница живёт по адресу
`/[locale]/greetings`. Задача от владельца продукта —
`greeting.viral4creators.app`. Принято решение: тот же проект, поддомен
через rewrite по заголовку `Host` в middleware. Что из этого следует и
чего в ТЗ нет:

- `landing/src/middleware.ts` сейчас занимается только локалью и
  исключает из обработки `/legal`, `/feed`, `/video`. Появляется вторая
  ответственность — ветвление по хосту. Порядок важен: сначала хост,
  потом локаль, иначе поддомен получит `/ru/` в пути и обе логики
  начнут спорить.
- Один и тот же HTML станет доступен по двум адресам. Без `canonical`
  на поддомен это классический дубль контента — и худший из возможных
  исходов: обе страницы конкурируют друг с другом в выдаче.
- `SITE_URL` в `landing/src/lib/content.ts` — одна константа на весь
  проект, и `sitemap.ts` c `robots.ts` строят абсолютные адреса из неё.
  Поддомену нужны свои `sitemap` и `robots`, иначе он либо не
  проиндексируется, либо объявит своими чужие страницы.
- Раздел 6 ТЗ лендинга («добавить маршрут в `sitemap.ts`») в этой
  конфигурации выполняется иначе, чем там написано.

### 1.7 Блокирующих решений два, а не одно

Компаньон-ТЗ, раздел 4, называет блокером только судьбу Hedra. Второй
блокер в документе не назван, хотя он шире: `PLANS_BILLING_ENABLED`
выключен, все тарифы бесплатны. Без оплаты не существуют фичи №23, 27,
28, 30, 33 (пять из семи в группе D), и раздел 3 ТЗ лендинга сам
признаёт, что секция цен будет повторять «сейчас бесплатно», как на
главном лендинге.

Решение владельца — оплату в этом проходе не включать. Значит группа D
целиком уходит за периметр, кроме №29 (реферальная петля), которая
денег не требует вовсе, и №31 (витрина), которая к монетизации
отнесена в ТЗ по недоразумению — это маркетинговая инфраструктура.

### 1.8 Оценки сложности занижены там, где фича кончается не кодом

Оценки S/M/L в компаньон-ТЗ считают стоимость изменения кода и не
считают стоимость **контента**, которого это изменение требует.

- **№1 «расширить `GREETING_OCCASIONS` до 20+» (S).** Enum и миграция —
  действительно часы. Но повод в этом продукте не метка: от него
  зависит промпт, который Gemini превращает в сценарий. 13 новых
  поводов — это 13 промптовых веток, которые нужно написать и
  прогнать глазами, иначе «Соболезнование» сгенерирует поздравление в
  том же тоне, что «День рождения», только со словом «соболезную».
  Плюс подписи в пяти словарях фронтенда и пяти лендинга, плюс
  переверстка формы: семь вариантов выбора и двадцать — разные UI.
  Реально **M**.
- **№8 стикеры/оверлеи (S), №38 титульная карточка (S), №39 закрывающая
  подпись (S).** Все три — новый ffmpeg-слой в постпродакшене, которого
  там нет: нужны ассеты (конфетти, снежинки, сердечки), шрифты с
  кириллицей, раскладка текста под три соотношения сторон и проверка,
  что шаг не включается для SINGLE/LINE. Первая из трёх — **M**,
  остальные две после неё действительно S, потому что переиспользуют
  уже построенный слой. ТЗ в принципе 5 раздела это предвидит
  («обязана ПОВТОРНО построчно проверить `planWork()`/`buildWork()`»),
  но в оценку это не заложило. Нынешнее состояние: в
  `postprod.service.ts` ветвление по `productInformation` существует
  ровно в одном месте (строки 1080–1090, про язык) — всё остальное
  товарных допущений пока не делает, и это надо сохранить.
- **№19 отложенная доставка (S).** Поле `deliverAt` и крон-тик —
  действительно S. Но доставлять **некуда**: канала связи с получателем
  в продукте нет, он появляется только в №26. Сегодня №19 в одиночку
  означает «ролик лежит и ждёт», без адресата. Две фичи связаны
  жёстко, и порядок обратный тому, в котором они пронумерованы.
  Мелочь в той же фиче: ссылка «по аналогии с уже существующими
  `live-auction-tick`/`auction-close` (см. `cron-jobs.service.ts`)» —
  задания эти есть, но живут в `admin-cron.service.ts:91–111`.

### 1.9 №22 — приватность третьего лица, а не UX-фича

«Уведомление отправителю, когда получатель открыл ролик». ТЗ честно
помечает источник как «нет прямого продукта, общий паттерн receipt
confirmation». Но у паттерна из мессенджеров есть свойство, которого
здесь не будет: там **обе** стороны — пользователи сервиса, видят
настройку и могут её выключить. Здесь получатель ссылку не запрашивал,
аккаунта не имеет, о слежении не предупреждён и отказаться не может.

Это ровно та зона, ради которой сам ТЗ лендинга (раздел 4 пункт 7)
требует честного ответа в FAQ про хранение данных получателя: «эта
категория пользователей чувствительнее к вопросу приватности
персональных данных о ТРЕТЬЕМ лице». Документ требует честности в FAQ и
рядом проектирует фичу, о которой в этом FAQ придётся умолчать.

Минимально приемлемый вариант, если фичу делать: уведомлять фактом без
подробностей («ваше поздравление посмотрели») и не собирать ни времени,
ни числа просмотров, ни устройства — и написать об этом на самой
странице просмотра. Лучший вариант — не делать вовсе; ценность для
отправителя маленькая, цена репутационная.

### 1.10 №25 — «календарь получателя» это календарь отправителя

«Интеграция с календарём получателя — добавить в календарь сам повод на
следующий год». Доступа к календарю получателя у сервиса нет и быть не
может. Кнопка «добавить в календарь» на странице просмотра добавляет
событие тому, кто на неё нажал, — то есть **получателю его собственный**
день рождения, что бессмысленно. Полезная версия фичи — `.ics` для
**отправителя**, в его кабинете, после того как ролик готов: «напомнить
за неделю в следующем году». Это же и единственное, что делает
осмысленной фичу №33, надстроенную над №25.

### 1.11 Что в обеих ТЗ выдержало проверку

Чтобы соотношение было честным — проверено и подтвердилось:

- Отказ Hedra реальный и не замаскирован: `greeting-config.ts` бросает
  `ForbiddenException` вместо тихой подмены на grok, ровно как описано.
- Тарифная таблица (LITE 480p / STANDARD 720p / PREMIUM 1080p, hedra
  только на PREMIUM) — совпадает с `MAX_RESOLUTION` и §7.
- `avatarLipsync: false` на всех тарифах — подтверждено в
  `common/plans.ts`.
- `QrCode.tsx` в `marketplace/src/components/` существует (фича №21).
- `TelegramNotifyService` существует (фича №12).
- `jsonLdScript` существует в `landing/src/lib/json-ld.ts` (раздел 5 ТЗ
  лендинга).
- Принцип 1 раздела 3 («`GreetingBrief` остаётся отдельной таблицей») и
  принцип 4 («честный отказ вместо тихой деградации») — верны и должны
  сохраниться во всех новых фичах.
- Решение не публиковать секцию группового режима, пока фичи нет
  (раздел 4 пункт 5 ТЗ лендинга) — правильное и в плане соблюдено.

## 2. План этапов

Порядок выбран так, чтобы продуктовая работа и лендинг шли синхронно:
каждый этап заканчивается состоянием, в котором лендинг можно
публиковать без единого обещания, которого нет в проде. Сроки не
проставлены намеренно — их ставит тот, кто будет делать, а не документ.

### Этап 1 — Фундамент витрины (продукт)

Без него лендинг физически не может быть опубликован в виде, который
описывает его собственная приёмка.

1. Миграция `SharedVideoPage`: `productName` → nullable, добавить
   `projectType`, `occasion`, `featured`.
2. `SharedVideoService.snapshotFromSession` — ветка GREETING_VIDEO:
   заголовок из `GreetingBrief`, товарные поля `null`, отказ только
   если нет готового видео.
3. `/video/[id]` — вариант страницы для поздравления: без цены,
   названия товара и фото товара; свой `description`/`og`; CTA
   «сделать такой же» ведёт в визард поздравлений, а не в форк разбора
   (у поздравления нет `libraryEntryId`).
4. Новый публичный списочный эндпоинт с фильтрами `projectType`,
   `occasion`, `featured`, с пагинацией.
5. Чек-бокс «показать в витрине» в админке (раздел 7 компаньон-ТЗ).

**Готово, когда:** оператор может отметить конкретное поздравление, и
оно приходит в списочном эндпоинте, а его страница открывается без
единого товарного элемента.

### Этап 2 — Глубина, которую лендингу будет что показать (продукт)

Всё, что не требует ни Hedra, ни оплаты, ни новой инфраструктуры.

- №1 — поводы до 20+, **вместе с промптовыми ветками** под каждый
  (оценка M, не S — находка 1.8).
- №3 — серверная валидация тона для чувствительных поводов, тоны
  `SUPPORTIVE`/`RESPECTFUL`. Идёт сразу за №1: без неё «Соболезнование»
  можно сгенерировать в тоне `FUNNY`.
- №2 — корпоративные пресеты.
- №37 — честная оценка времени рендера вместо статичного текста.
- №40 — субтитры на втором языке.

**Готово, когда:** сетка поводов на лендинге может показать двадцать
плиток, и каждая ведёт в визард, который действительно умеет этот
повод, а не просто принимает его код.

### Этап 3 — Лендинг, первая публикуемая версия

Идёт строго после этапов 1–2 — обе зависимости содержательные, а не
календарные.

1. Инфраструктура поддомена: host-rewrite в `middleware.ts` (хост
   раньше локали), `canonical` на поддомен, отдельные `sitemap`/
   `robots` для него, `MARKETPLACE_URL`-подобная константа адреса.
2. Страница `[locale]/greetings/page.tsx` + раздел словаря
   `greetingsLanding` в пяти файлах, с программной проверкой совпадения
   ключей (та же, что уже применяется к словарям лендинга).
3. `GreetingOccasionGrid` — коды поводов закреплены тестом на
   совпадение с `GREETING_OCCASIONS` (находка 1.5).
4. `GreetingSampleGallery` на эндпоинте этапа 1; пустое состояние —
   секция не рендерится (раздел 5 ТЗ лендинга, соблюдается буквально).
5. `Faq` получает проп `items`; решается вопрос `data-faq-index` и
   действий ИИ-консультанта на этой странице (находка 1.3).
6. `HowItWorks` получает префикс имён иконок; рисуются `greet-step-1…4`
   (находка 1.4).
7. Перелинковка: ссылка с главного лендинга и из подвала.
8. Домен в панели Vercel.

**Готово, когда:** страница открывается на пяти локалях по поддомену,
витрина показывает реальные отмеченные ролики, и ни один текст не
обещает того, чего нет в проде.

### Этап 4 — Доставка и вручение (продукт → лендинг)

- №26 (каналы доставки) **раньше** №19 (отложенная доставка) — находка
  1.8.
- №20 — «магическая ссылка» с раскрытием, поверх страницы этапа 1.
- №21 — QR (компонент уже есть).
- №24 — повторная выдача ссылки.
- №29 — реферальная петля на странице просмотра. Единственная фича
  группы D в этом проходе: денег не требует.
- №22 — **только** в урезанном виде из находки 1.9, либо не делать.
- №25 — в переформулированном виде: `.ics` отправителю (находка 1.10).

**Лендинг:** секция «сюрприз без спойлера» и честный ответ в FAQ
«можно ли создать ролик, если получатель не знает» — появляются здесь,
не раньше.

### Этап 5 — Качество генерации (продукт)

- №6 — референс-кадр до видео (закрывает находку №2 первого аудита).
- №36 — автовыбор сеттинга, продолжение №6.
- №34 — клонирование голоса отправителя (инфраструктура `user-voices`
  уже в проде).
- №35 — модерационный гейт на знаменитостей.
- №4 — музыкальные темы.
- №7 — мультисценовый ролик.
- №8 → №38 → №39 в этом порядке: первая строит ffmpeg-слой, две другие
  его переиспользуют (находка 1.8).

**Лендинг:** секция возможностей наполняется тем, что реально
отличает продукт; витрина к этому моменту показывает ролики
заметно лучшего качества — её и стоит переснять.

### Этап 6 — Групповой режим (отложен решением владельца)

Фичи №10–18 целиком, плюс модерационная очередь для клипов участников
(раздел 7 компаньон-ТЗ). Планируется отдельным заходом; секция-тизер на
лендинге не публикуется до его завершения.

### Ветка H — Hedra (решение отложено)

Вынесена из линейного порядка намеренно: фичи №5, №9, №13, №27 зависят
от решения, которого пока нет, и ни один этап выше на них не
опирается. Когда решение будет:

- **Вариант A** — вывод пилота в прод + квоты + лимиты стоимости +
  мониторинг, и только после этого №5 (голосовые пресеты) и №9.
- **Вариант B** — убрать выбор hedra из тарифной таблицы, оставив
  `ForbiddenException` только как защиту от прямых вызовов API;
  PREMIUM переписывается в словарях как «1080p + библиотека».

Пока решения нет, действует то, что в проде сейчас: PREMIUM формально
предлагает выбор, которым нельзя воспользоваться. Лендинг об этом
выборе не упоминает вовсе — это и есть страховка от обещания, которого
продукт не держит.

### Ветка M — Монетизация (вне прохода)

Фичи №23, 27, 28, 30, 33 — после включения `PLANS_BILLING_ENABLED`, с
правкой оферты и публичным эндпоинтом цен, который нужен ОБОИМ
лендингам (главному и поздравлений) — иначе два места с ценами
придётся править руками одновременно, о чём главный лендинг уже
предупреждает комментарием в секции `plans`.

## 3. Приёмка страницы (дополнение к разделу 8 ТЗ лендинга)

К пяти пунктам оригинальной приёмки добавляются те, что следуют из
находок выше:

- Поддомен отдаёт страницу, главный домен отдаёт её же по `/greetings`,
  и `canonical` обеих указывает на поддомен.
- `robots`/`sitemap` поддомена перечисляют только его страницы.
- Коды поводов на лендинге совпадают с `GREETING_OCCASIONS` — проверено
  тестом, а не глазами.
- Страница `/video/[id]` поздравления не содержит ни одного товарного
  элемента и корректна в `og`-превью.
- ИИ-консультант на странице поздравлений не присылает `faq`-действий
  с индексами главного словаря.
